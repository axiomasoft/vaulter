# 02-extensions

Дата: 2026-09-29. Ответ Perplexity; поисковые утверждения не равны проверке первоисточника. Проверенные выводы и ограничения см. в основных документах папки.

## Запрос

Нужно исследование для Laravel document-management package: разделение node kind / MIME format / structured document schema / editor / exporter. Найди конкретные реализации Nextcloud FileInfo и capabilities, Spatie laravel-medialibrary custom media model+collections, Laravel Scout EngineManager extend, Tiptap extension schema. Нужны 6–8 ПРЯМЫХ первичных ссылок на исходники/официальные docs и для каждой: что реально реализовано, переносимый принцип, ограничения, тест для Vaulter. Особенно lifecycle registries (boot, config cache, collisions, long-lived workers), unknown type preservation, schema version upgrades. Не предлагай весь framework заново. Только обычные абзацы и нумерованные списки, НЕ таблицы: таблицы теряются при выгрузке. 700–1000 слов, русский.

## Ответ

Для Vaulter стоит разделить четыре независимые оси: node kind отвечает за поведение узла в дереве; MIME — за байтовый формат/обнаружение типа; structured schema — за семантическую структуру содержимого и её версию; editor и exporter — за инструменты чтения и представления, а не за идентичность документа. Ниже — конкретные реализации и переносимые проверки; прямые ссылки ведут на официальную документацию или исходники.
- Nextcloud: FileInfo и capabilities. Публичный в исходниках Nextcloud — интерфейс метаданных файловой системы, а не редакторский формат. Его смысл — дать потребителю общие сведения об объекте независимо от того, где и как файл хранится. Отдельно официальная документация Capabilities API описывает endpoint GET /ocs/v1.php/cloud/capabilities: сервер и приложения сообщают клиенту доступные возможности. Это публичная capability discovery, а не реестр файловых типов. Переносимый принцип: общие метаданные узла не смешивать с «способен ли этот клиент/сервер редактировать или экспортировать данный формат». Ваulter-тест: два узла разных kind могут иметь один MIME; одинаковый kind — разные MIME; capability editor не должна менять классификацию node. Ограничение: FileInfo не является полноценной схемой документа и не задаёт правила обновления содержимого. Ссылка ведёт на публичный интерфейс в ветке master, поэтому при фиксации совместимости Vaulter следует привязать аудит к конкретному тегу Nextcloud.
- Spatie Media Library: custom media model. Официальная инструкция по собственной модели прямо предлагает расширить базовую Media-модель и настроить пакет на использование пользовательского класса. Это точка расширения для доменных методов и связей; она не превращает модель в общий классификатор node kind, MIME и document schema. Коллекции задаются отдельно на владельце: описывает registerMediaCollections() и получение зарегистрированных коллекций. Переносимый принцип: пользовательскую модель и named collections использовать для добавочных свойств и группировки, сохраняя неизменёнными базовые метаданные файла. Vaulter-тест: custom model корректно сохраняет/загружает дополнительные поля; коллекция с ограничением типа отклоняет недопустимый файл; отсутствие коллекции не приводит к потере исходного MIME. Ограничение: коллекция — категория/политика вложения, не универсальный тип узла; MIME-проверка не доказывает, что содержимое соответствует MIME или schema. Для кастомной модели также следует проверить миграции и сериализацию при обновлении пакета.
- Laravel Scout: подключение движка. В Scout есть явный менеджер движков; исходник показывает паттерн Laravel Manager: драйверы создаются через фабрики и расширяются регистрацией имени и callback. Это полезный пример реестра адаптеров, но не готовая архитектура для node kinds. Ветка ссылки — 10.x; при реализации Vaulter проверьте API конкретной поддерживаемой версии Scout. Переносимый принцип: для exporter/editor backend можно иметь именованный driver registry с явной фабрикой, не привязывая к нему доменную запись документа. Ваulter-тесты lifecycle: регистрация до первого разрешения; повторная регистрация того же ключа с предсказуемым поведением (ошибка или явное замещение); неизвестный driver даёт диагностируемую ошибку; несколько разрешений возвращают ожидаемый объект. Отдельно тестировать config:cache и долгоживущий worker: реестр не должен накапливать состояние между запросами или зависеть от повторного выполнения provider boot. Сам паттерн менеджера не решает эти гарантии автоматически.
- Tiptap: schema и расширения. Официальная документация Tiptap по расширению показывает, что extension может менять schema: например, ограничить content, определить attributes, HTML parse/render и расширять существующие атрибуты через this.parent?.(). Документация подчёркивает строгость схемы; имя extension также присутствует в JSON-документе. Значит, schema — часть сохранённого контракта, а не просто настройка UI. Переносимый принцип: хранить structured content с явным идентификатором schema и версией отдельно от editor name/version; редактор — один из клиентов схемы. Ваulter-тест: неизвестный node/attribute round-trip сохраняется либо сохраняется как opaque payload, а не молча удаляется; старый документ проходит последовательные миграции; экспорт без редактора возможен из канонических данных. Ограничение: Tiptap может удалить неописанные schema элементы при разборе/нормализации, поэтому редактор не должен быть единственным хранилищем оригинала, если важна сохранность неизвестных типов.
- Практическое правило для неизвестных типов и миграций. Не делайте MIME единственным источником истины: сохраняйте исходную строку MIME и исходный payload даже при неизвестном значении. Неизвестный node kind должен быть либо допустимым opaque node, либо явно помеченным unsupported — но не автоматически переклассифицированным. Для schema upgrades задайте чистые переходы N → N+1, храните текущую версию на документе и тестируйте повторный запуск миграции как идемпотентный. Для registries используйте уникальные namespace/key, детерминированный порядок загрузки и явную политику collision; проверяйте boot, cache и worker lifecycle отдельно от unit-тестов фабрик.
Ссылки выше дают пять первичных точек для исследования: публичный файловый контракт и discovery возможностей Nextcloud, две точки расширения Media Library, менеджер Scout и schema/extension модель Tiptap. Их общий урок — расширяемость полезна, но ни один из этих механизмов сам по себе не обеспечивает Vaulter сохранение неизвестных типов, устойчивую версионизацию схемы или безопасный lifecycle registry.
