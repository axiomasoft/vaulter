# 05-cas-concurrency

## Запрос

Нужны первичные источники и реальные OSS patterns для CAS + SQL document platform. 7–9 ссылок: restic repository design/prune/locks, OCI distribution garbage collection, PostgreSQL explicit locking/transaction isolation/unique nulls, AWS S3 conditional writes/consistency, Flysystem streams. Развить ULID/UUID identifiers without integer casts; CAS dedup domain versus physical disk/encryption domain; quota active head bytes versus retained versions/physical bytes, atomic conditional quota update, version allocation concurrent updates; storage bytes cannot rollback with SQL; GC grace period plus recheck liveness and writer coordination; backup restore DB+objects. У каждого паттерна ограничения: offline registry GC не копировать для online DMS; strong consistency S3 не distributed transaction. В конце 5 конкретных failure-injection scenarios. Только абзацы/списки без таблиц, русский, 900 слов.

## Ответ

## Рекомендуемая модель

Стройте document platform как две связанные, но не транзакционно общие системы: SQL — источник истины для документов, версий, ссылок и квот; CAS-хранилище — для неизменяемых blob-объектов. Сначала надёжно записывайте объект, затем фиксируйте SQL-ссылки; сбои между этими этапами должны оставлять обнаруживаемые сироты, а не видимые документы без данных.
Идентификаторы документов и версий храните как ULID/UUID в строковых или бинарных колонках, но не как целые числа: в Laravel явно настройте тип ключа модели и отключите auto-increment ($incrementing = false, $keyType = 'string'). Не допускайте неявного (int) преобразования в маршрутах, DTO, связях и миграциях. Для внешнего API можно выдавать ULID, а внутренние FK — хранить в выбранном представлении последовательно во всей схеме.

## CAS, версии и квоты

- Разделите логический dedup и физическое хранение. Логический CAS-ключ может быть хешем содержимого в пределах tenant/security domain; физический объект — ключом от хеша уже зашифрованного payload в пределах конкретного storage/encryption domain. Нельзя дедуплицировать между арендаторами или ключами шифрования только потому, что совпал plaintext-хеш: это может раскрыть факт наличия данных, нарушить изоляцию и создать несовместимость при ротации ключей. Restic иллюстрирует content-addressed неизменяемые объекты, записываемые один раз, с отдельными индексами и snapshot-ссылками.
- Разведите квоты. active_head_bytes — сумма размеров документов, на которые сейчас указывает актуальная версия; retained_version_bytes — размер удерживаемых исторических версий; physical_bytes — реально занятые байты в storage domain, включая шифрование, временные объекты и сироты. Это разные метрики: общий blob может иметь несколько логических ссылок, поэтому нельзя уменьшать физический счётчик при удалении одной версии.
- Обновляйте квоту атомарно в SQL. В одной транзакции заблокируйте строку quota (SELECT … FOR UPDATE) либо примените условный UPDATE … WHERE used + :delta <= limit и проверьте число изменённых строк. Не делайте «прочитал остаток — потом записал» в отдельных запросах. PostgreSQL описывает явные блокировки и уровни изоляции; уникальные ограничения должны закрывать гонки как последний рубеж.
- Выделяйте номер версии конкурентно. Блокируйте строку документа на время вычисления next_version, либо используйте уникальность (document_id, version_number) и повтор операции после конфликта. Для «текущей версии» лучше хранить явный head pointer с optimistic concurrency/version token. Не полагайтесь на MAX(version_number)+1 без блокировки. Если ключ уникальности содержит nullable-поля, учтите, что PostgreSQL по умолчанию считает NULL отличающимися; для требования «не более одной NULL-записи» используйте UNIQUE NULLS NOT DISTINCT или эквивалентный частичный индекс.
- Учтите границу SQL и storage. Откат SQL-транзакции не удалит уже загруженный объект, а удаление объекта нельзя откатить SQL rollback’ом. Типовой протокол: stream upload во временный ключ → проверка длины/хеша → publish неизменяемого CAS-объекта условной записью → SQL-транзакция создаёт версию, ссылку и outbox-событие. Повторяемые операции должны быть идемпотентны; фоновый reconciler разбирает зависшие uploads и сироты.
- Потоковая обработка — не удобство, а ограничение памяти. Flysystem readStream/writeStream передают ресурсы, позволяя не буферизовать крупный файл целиком; отдельно обрабатывайте исключения чтения/записи и закрывайте ресурсы.

## GC, блокировки и восстановление

Restic — полезный паттерн для неизменяемых объектов, ссылок и эксклюзивной координации prune: удаление сначала исключает объект из индекса/набора ссылок, а физическая очистка выполняется отдельно. Для собственного CAS добавьте grace period: помечайте кандидатов, ждите больше максимального времени upload/SQL commit, затем повторно проверяйте liveness непосредственно перед удалением. Согласуйте GC с писателями через lease/lock или поколения: писатель публикует объект и SQL-ссылку, GC не удаляет объект, который мог появиться между mark и sweep.
OCI Distribution показывает важное ограничение: его документированный GC — mark-and-sweep и требует read-only режима либо остановки registry, иначе новый upload может быть ошибочно удалён. Это хороший offline/maintenance pattern, но его нельзя просто копировать как «online GC для DMS»: у DMS другая модель конкурентных транзакций и новых ссылок. Нужны координация писателей, grace period и повторная проверка ссылок; без них безопаснее приостановить записи.
Для S3 используйте условную запись If-None-Match: * при публикации content-addressed ключа: существующий объект не будет молча перезаписан; конфликт 412 означает, что надо проверить уже имеющийся объект и его целостность. S3 обеспечивает strong read-after-write и согласованность LIST после успешных операций, но это не distributed transaction с PostgreSQL: успешный PUT не означает, что SQL commit тоже состоялся, и наоборот.
Бэкап и восстановление должны охватывать SQL и объекты. Зафиксируйте согласованный checkpoint/maintenance window либо журнал/границу времени, чтобы восстановленная БД не ссылалась на отсутствующие blobs; после восстановления проверьте ссылки, хеши и сироты. Практический критерий готовности — регулярно делать тестовый restore в отдельное окружение, а не только проверять успешность backup job.

## Failure injection

- Завершить процесс после upload CAS, но до SQL commit: объект должен стать обнаруживаемой сиротой и позже удалиться GC, не повредив другие ссылки.
- Убить процесс после SQL commit версии, но до подтверждения клиенту: повтор запроса с тем же idempotency key не создаёт вторую версию и повторно не списывает квоту.
- Два параллельных обновления одного документа: проверить уникальность номера версии, корректность head pointer и отсутствие двойного превышения квоты.
- Запустить GC между публикацией blob и созданием SQL-ссылки, затем замедлить писателя дольше обычного: GC не должен удалить живой объект благодаря grace period и повторной проверке.
- Восстановить SQL из одного момента времени, а object storage — из другого: система должна выявить missing blobs и лишние объекты, не выдавая неполные документы как исправные.
