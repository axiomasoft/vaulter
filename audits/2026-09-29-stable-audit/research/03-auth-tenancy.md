# 03-auth-tenancy

Дата: 2026-09-29. Ответ Perplexity; поисковые утверждения не равны проверке первоисточника. Проверенные выводы и ограничения см. в основных документах папки.

## Запрос

Исследуй security boundary для embeddable Laravel DMS, HTTP + PHP API + jobs + CLI. Первичные источники: Laravel Gates/Policies authorize and scoped bindings/Octane; Spatie laravel-multitenancy queue context reset; stancl tenancy single database scoped models limitations; Nextcloud permissions. Нужны 6–8 конкретных ссылок и практические выводы: actor identity != audit actorId, immutable context, same process tenant A then B, tenant unresolved fail-closed, system maintenance GC across tenants, route auth vs object authorization, revoke of shares during queued work. Не утверждай, что отсутствие Sanctum автоматически уязвимость; обсуди Eloquent как нормальный публичный API Laravel. Для каждого механизма ограничения и один проверочный сценарий. Только абзацы/списки, НЕ таблицы, русский, 800 слов.

## Ответ

## Короткий вывод

Для embeddable DMS границу безопасности нужно строить не вокруг HTTP-маршрутов, а вокруг операций с объектом: кто действует, в каком tenant-контексте, над каким объектом и с каким актуальным разрешением. Laravel предоставляет механизмы аутентификации, binding и авторизации, но сам по себе не превращает Eloquent-модели или tenant-scopes в полный слой изоляции данных.

## Механизмы и проверки

- Actor identity и audit actorId — разные понятия. В запросах, jobs и CLI передавайте явный неизменяемый контекст выполнения: tenant, тип и ID инициатора, цель, correlation/idempotency key. actorId в аудите — запись о том, кто инициировал действие; это не доказательство текущей личности и не источник полномочий. Для фоновой системной операции актор может быть system, а инициатор — отдельным полем. Laravel Policies/Gates принимают user и модель как входы проверки, но формат аудита и неизменяемость контекста — ваше приложение, не гарантия framework. Предел: scoped binding Laravel ограничен lifecycle запроса/job и не делает произвольные глобальные переменные, singleton-ы или статическое состояние безопасными.Проверка: выполнить в одном worker последовательно job от пользователя A и job от B; у второй проверки и audit-записи не должны остаться actor/tenant-поля первой.
- Контекст tenant должен быть явным и fail-closed. HTTP должен разрешать tenant из доверенного источника, а затем проверять членство пользователя; нельзя принимать tenant ID из body как достаточное основание. Для очереди сериализуйте стабильный tenant ID и заново устанавливайте контекст при исполнении. Spatie Multitenancy делает jobs tenant-aware, умеет восстанавливать прежний контекст после выполнения и завершает ошибкой tenant-aware job, если tenant уже не найден. Предел: пакет управляет tenant context, но не подтверждает право конкретного актёра на документ и не заменяет ваши правила для нестандартных entrypoint-ов.Проверка: обработать A, затем B в одном процессе; после удаления tenant до исполнения job она должна завершиться ошибкой, а не продолжить работу с предыдущим или landlord-контекстом.
- Single-database scopes — защита от случайных ошибок, не универсальная граница. Документация stancl указывает, что BelongsToTenant сужает primary-модели, а для некоторых secondary-моделей нужен отдельный trait; более глубокие связи не покрыты автоматически. Эти traits влияют на выборки, но не обеспечивают проверку доступности уже известного экземпляра. Предел: прямой Comment::all(), raw SQL, query builder, relation без scoped parent или найденная по ID модель могут обойти ожидаемую цепочку.Проверка: создать документ A и дочернюю версию B; попытаться получить их напрямую по ID и прямой коллекционной выборкой из контекста A — результат не должен раскрывать B.
- Глобальная maintenance/GC — отдельный системный режим. Команда, обходящая tenants, должна сначала перечислить tenants из доверенного реестра, для каждого явно установить контекст, ограничить выборку tenant-ом и гарантированно сбросить контекст после итерации. Не превращайте «нет текущего tenant» в неявный режим «все tenant-ы». Spatie документирует tenant-aware Artisan-команды и отдельное поведение jobs без tenant; конкретный безопасный цикл GC — ответственность приложения. Предел: framework не доказывает, что все запросы maintenance-кода tenant-scoped.Проверка: запустить GC по двум tenants с уникальными маркерами; каждый проход удаляет только просроченные записи своего tenant, а ошибка в A не оставляет контекст A для B.
- Route authentication не равна object authorization. Middleware auth устанавливает идентичность, но не право читать или изменять конкретный файл. Используйте Policy на объектной операции (view, download, update, delete, share); scoped route binding помогает связать дочерний объект с родителем, но не заменяет Policy. Laravel прямо разделяет Gates/Policies и документирует scoped bindings. Предел: binding не проверяет ACL/share/роль сам по себе; endpoint, job и CLI могут получить модель не через route binding.Проверка: аутентифицированный пользователь A подставляет ID документа B в download, update и вложенный route; каждый путь должен отказать независимо от успешного логина.
- Публичный Eloquent API не означает публичный HTTP API. Eloquent — штатный ORM и query builder Laravel; возможность вызвать Document::find() или Document::query() не является уязвимостью сама по себе. Риск возникает, если приложение раскрывает эти операции через endpoint/SDK без tenant-фильтрации и policy-проверок. Отсутствие Sanctum также не является автоматически уязвимостью: Laravel предлагает его как способ API-token-аутентификации, но корректный механизм зависит от интеграции — например, host-приложение может передавать аутентифицированного пользователя через другой guard. Проверяйте фактическую аутентификацию, границы доверия и авторизацию, а не наличие конкретного пакета.
- Отзыв share во время queued work требует повторной проверки. Nextcloud представляет share как изменяемые права и поддерживает удаление share через API. Для DMS это означает: job, поставленный в очередь до отзыва, не должен считать разрешение вечным; перед фактической выдачей содержимого или внешним side effect проверяйте актуальное состояние share/ACL. Предел: повторная проверка не отменит уже завершённую отправку/выгрузку; для долгих операций нужны определённая семантика отзыва и контроль точек выдачи.Проверка: поставить export job в очередь, отозвать share до обработки, затем подтвердить, что job отказывает и не публикует файл.
