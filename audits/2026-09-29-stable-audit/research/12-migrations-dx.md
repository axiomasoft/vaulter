# 12-migrations-dx

Дата: 2026-09-29. Ответ Perplexity; рекомендации требуют сопоставления с кодом и принятыми контрактами Vaulter.

## Запрос

Для PHP Laravel package public API stabilization нужны практики изменения ID/schema/config без бессмысленного переписывания. Найди 5–7 первичных ссылок: Laravel package migration publishing/loading and config merge caveats, Spatie package-tools migrations/config, Composer package naming versus source URL, Laravel upgrade testing/Testbench, PHP named argument parameter renaming BC, executable documentation examples (PHPUnit/Pest or real package tests). Контекст Vaulter: ULID/UUID7 storage IDs passed into int-only CAS; physical keys snull/tnull may already exist and blobs shared with edges; adding new scope strings breaks GC key parser. Исследуй безопасный repair design: inventory/dry-run, immutable bytes verified hash, mapping old refs to new scope, shared blob copied not moved/deleted, transactional repoint, old object retention, retry/idempotence, unknown historical tenant cannot invent. Отличай подтверждённые source practices от собственных предложений. НЕ обещай автоматическую миграцию без данных и backup. Только prose/list, русский 700 слов.

## Ответ

Для стабилизации Laravel-пакета лучше разделить публичные контракты и внутреннее хранилище: расширяйте API совместимо, а repair данных делайте отдельной проверяемой операцией с явным планом и сохранением исходных объектов. Для Vaulter описанные ниже шаги — предложение по дизайну, не подтверждённая автоматическая миграция: без инвентаризации, реальных данных и backup её обещать нельзя.

## Подтверждённые практики и ссылки

- Laravel: migrations и config. Laravel документирует загрузку ресурсов пакета через service provider, публикацию config и миграций; publishesMigrations при публикации обновляет timestamp файла миграции. Важная оговорка: mergeConfigFrom объединяет только верхний уровень, поэтому новые вложенные настройки не появятся автоматически в частично опубликованном config. Новые ключи лучше проверять на конфигурациях старых приложений и явно описывать обновление config.
- Spatie package-tools. hasConfigFile() регистрирует и делает config публикуемым; миграции можно объявлять через hasMigration(s) или обнаруживать, а runsMigrations() позволяет запускать их без публикации. Это удобный механизм регистрации, но не отмена проверки совместимости и поведения опубликованных файлов.
- Composer: имя не равно URL репозитория. Composer описывает пакет через name, версию и источник загрузки (source и/или dist); источник указывает, откуда брать код. Следовательно, имя пакета — идентификатор зависимости, а не обещание, что оно совпадает с URL исходного репозитория.
- Тестирование пакета. Laravel рекомендует Orchestra Testbench, если пакет нужно тестировать как установленный в обычное Laravel-приложение; его документация описывает тестовую Laravel-среду для команд, миграций и интеграционных сценариев. Pest показывает примеры тестов как исполняемых файлов в каталоге tests. Практический вывод: ключевые примеры API и upgrade-сценарии стоит проверять тестами, а не только поддерживать как текст документации.
- PHP named arguments. RFC PHP подтверждает, что вызов может ссылаться на аргумент по имени, а переименование параметра способно сломать такой вызов. Поэтому имена параметров публичных методов — часть совместимого API для клиентов, использующих named arguments; переименование следует считать потенциальным BC-break и тестировать именованные вызовы.

## Предлагаемый repair для Vaulter

- Инвентаризация без изменений. Отдельная команда inventory/dry-run собирает старые refs, физические ключи, связи с edges и метаданные tenant/scope. Выводит план, число затронутых записей, конфликты и причины пропуска; по умолчанию ничего не пишет.
- Не угадывать происхождение. Если исторический tenant/scope нельзя восстановить из авторитетных данных, пометить запись как unknown и остановить её автоматическое преобразование. Нельзя подставлять «default tenant» или выводить tenant из неоднозначного ключа.
- Сохранить данные, а не перетаскивать их. Для каждого источника вычислить hash, скопировать байты в целевой ключ, перечитать и сверить hash. Поскольку snull/tnull уже могут существовать, сначала проверять целевой объект: при совпадении hash — считать копию готовой; при несовпадении — конфликт, не перезаписывать молча. Старый объект и любые потенциально общие blobs не перемещать и не удалять.
- Развести идентификаторы. ULID/UUID7 — storage/reference IDs, а CAS получает только поддерживаемый им тип. Не приводить UUID к int и не считать такое преобразование безопасным. Предложить явное сопоставление «старый ref → новый scope/key/ref»; проверять коллизии до записи.
- Защитить транзакционное переключение. После проверенной копии — в DB-транзакции с блокировкой/optimistic guard обновить только refs, чьё исходное значение всё ещё совпадает с планом. Внешнее хранилище обычно не участвует в DB-транзакции, поэтому сбой после копирования оставляет безвредную копию; повторный запуск должен сверить hash и продолжить, а не дублировать или удалять.
- Удерживать старые объекты. Не запускать GC старых ключей как часть repair. Сначала выпустить версию, чей GC parser понимает старые и новые форматы, затем провести отдельный аудит ссылок и срок удержания; неизвестные форматы трактовать как «не удалять».

## Защита публичного API

Не переименовывать публичные параметры, config keys и scope-строки «заодно с рефакторингом». Для новых вариантов предпочтительны новые методы/адаптеры либо период совместимости с явной диагностикой; конфигурацию проверять на старом опубликованном файле, включая вложенные массивы. Для GC сначала обеспечить чтение старых форматов и тесты на неизвестный scope: неизвестный ключ должен сохраняться, а не приводить к ошибочному удалению. Тесты пакета должны включать старые и новые refs, общий blob с несколькими edges, занятые target keys, конфликт hash, повторный запуск, прерванное выполнение и неизвестный tenant. Это рекомендации по Vaulter-дизайну, а не обещание, что текущая схема данных уже позволяет восстановить все связи.
