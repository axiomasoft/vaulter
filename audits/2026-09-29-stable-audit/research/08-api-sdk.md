## Ответ

## Вывод

Для Laravel DMS разумно зафиксировать контракт в OpenAPI 3.1, генерировать из него REST-клиент для Vue, а обратную совместимость проверять отдельно от SemVer PHP-пакета. /v1 — вариант политики API, а не обязательное требование HTTP или OpenAPI; важнее заранее определить, как сервер и развёрнутые клиенты переживают изменения контракта.

## Контракт и версионирование

OpenAPI описывает интерфейс HTTP API и пригоден как источник документации и генерации клиентов. Но версия самого формата OpenAPI — например, 3.1.1 — не равна версии описываемого API: спецификация прямо различает эти значения.
Варианты политики URL или заголовка имеют разные свойства. /api/v1 заметен в маршрутах и логах и позволяет параллельно поддерживать старую и новую поверхность API; заголовок вроде Accept: application/json; version=1 отделяет версию представления от URL, но менее очевиден при ручной отладке и требует аккуратной обработки прокси и кэшей. Paperless-ngx использует заголовок Accept с параметром version, а при отсутствии версии отдаёт v1; это пример конкретного решения, не стандарт, которому обязан следовать DMS. Документация обещает старым версиям поддержку минимум год после выхода новой, но оставляет возможность её прекратить позднее.
Практичная политика для собственного продукта: публичный префикс /api/v1 только если вы планируете поддерживать несколько несовместимых API-контрактов одновременно; иначе можно начать с /api и вводить версию при реальной необходимости. Зафиксируйте срок поддержки, процесс deprecation и критерии breaking change независимо от формата адреса. SemVer Laravel-пакета относится к совместимости кода пакета и его зависимостей; он не гарантирует, что уже развёрнутый Vue-клиент совместим с новым сервером. Это требует контрактных проверок и явной политики API.
Acceptance scenario: старая сборка Vue продолжает читать и изменять документы после совместимого серверного релиза; breaking change либо сохраняет старый контракт в течение объявленного окна, либо приводит к заранее документированному отказу, а не к неожиданной поломке.

## Конкурентные изменения

RFC 9110 определяет If-Match как условие, проверяемое сервером до выполнения метода; при несовпадении клиент может обнаружить, что редактируемая версия ресурса устарела. Для DMS это естественный механизм optimistic concurrency: сервер выдаёт ETag документа, клиент посылает его в If-Match при сохранении.
Преимущество: потерянное обновление не затирает тихо чужие правки. Ограничение: ETag должен соответствовать выбранному представлению, а интерфейс должен уметь разрешить конфликт.Acceptance scenario: два пользователя открывают один документ; после сохранения первым второй получает 412 Precondition Failed и видит предложение перезагрузить или сверить изменения.
Для лент и списков Laravel cursorPaginate строит запросы по значениям сортировки, что полезно для больших наборов данных. Но Laravel требует стабильного порядка: колонка или комбинация колонок должны быть уникальны, NULL для колонок сортировки не поддержан; произвольное переключение на курсор не устраняет неоднозначность порядка.
В DMS сортировку, например, по дате следует дополнить уникальным id как tie-breaker. Для nullable-поля надо определить явное правило, например отдельный признак nullability и нормализованный sort key, либо запретить такую сортировку в cursor-режиме. Текстовая сортировка зависит от collation: смена локали или правил сравнения может изменить порядок и сделать старый курсор некорректным. Курсор не гарантирует снимок набора: при параллельных изменениях сортируемых полей запись может переместиться между страницами.Acceptance scenario: при равных датах элементы не пропускаются и не дублируются; API документирует поведение при изменении сортировки и отклоняет или сбрасывает курсор, созданный при другой схеме сортировки/collation.

## Ошибки и повторы

RFC 9457 задаёт стандартную структуру machine-readable ошибок. Для DMS стоит возвращать application/problem+json, HTTP-статус и стабильный машинный код в расширении, например code: "document_locked"; текст detail предназначен для человека и не должен быть API-кодом, на который ветвится Vue.
Преимущество: клиент может отображать понятные сообщения по коду, а сервер менять формулировки и локализацию. Ограничение: типы ошибок и их расширения всё равно надо поддерживать как часть контракта.Acceptance scenario: для document_locked фронтенд показывает действие разблокировки; неизвестный code отображается как общее сообщение, не вызывает падение приложения.
Идемпотентность нужна прежде всего для повторов POST после таймаута, когда клиент не знает, успел ли сервер выполнить операцию. Stripe сохраняет результат первого запроса по ключу, сравнивает параметры повторов и может повторно вернуть сохранённый ответ, включая ошибки; ключи могут быть удалены после 24 часов. Это полезный пример семантики, но не универсальное правило для всех API.
В DMS ключ операции следует ограничивать пространством tenant и actor, связывать с отпечатком запроса и хранить результат дольше возможного окна повторов. Повтор с тем же ключом, но иным содержимым должен давать конфликт, а не выполнять новую операцию. При загрузке файла нельзя полагаться только на повтор multipart-запроса: определите, создаёт ли повтор новую запись, и поддержите resumable/chunk upload либо безопасное повторное завершение одной операции.Acceptance scenario: после потери ответа Vue повторяет загрузку с тем же ключом и получает ту же операцию/документ; тот же ключ с другими байтами отклоняется.

## Генерация и UI

openapi-typescript генерирует статические TypeScript-типы из OpenAPI; проект отдельно подчёркивает, что генерация типов не обеспечивает runtime-валидацию. oasdiff сравнивает версии OpenAPI и помогает выявлять breaking changes в CI. Эти инструменты дополняют друг друга, но ни один не доказывает, что Laravel реально отвечает согласно описанию.
Acceptance scenario: CI генерирует типы из актуальной спецификации, проверяет diff относительно принятой версии и запускает интеграционные тесты против реального Laravel API. На границе сети клиент валидирует критичные данные либо безопасно обрабатывает неожиданный ответ.
Для расширяемых типов документов не делайте UI зависимым от исчерпывающего enum: сервер может добавить тип раньше обновления фронтенда. Предусмотрите fallback-компонент с общими полями и безопасными действиями, а неизвестный тип показывайте как «неподдерживаемый формат» без попытки интерпретировать специфичные метаданные. Это снижает риск несовместимости при rollout, но требует теста на неизвестное значение.Acceptance scenario: API возвращает новый document_type; список и карточка отображают базовые метаданные и не ломают маршрутизацию или форму.
