# Моя позиция: развивать контракты, удерживать сложность

Это предложения Codex для обсуждения с Opus. Обоснование по коду — [E1–E10](01-evidence.md), внешняя практика — [карта S01–S30](03-source-map.md). Здесь намеренно нет порядка коммитов, сроков и окончательного набора классов.

## 1. Операция — подходящее место для общей гарантии

Я предпочитаю application service с явным, неизменяемым контекстом: actor, логическое storage, tenant при включённом режиме, основание system operation и correlation ID. HTTP, facade и jobs должны доходить до одного решения о доступе и одной upload policy. `actingAs()` может быть удобным способом создать **новый bound object**; изменять tenant/user в singleton manager нельзя.

Контекст — не сертификат доверия сам по себе: host может сконструировать PHP-объект. Его ценность — сделать зависимости явными и не дать пакету случайно пропустить принятую политику. Нужна повторная проверка актуальных прав в момент значимого действия; результат прежнего `authorize` нельзя бессрочно переносить в очередь.

Не навязывать Sanctum и отдельный tenancy framework. Предусмотреть простую интеграцию обычного Laravel-приложения, adapter к host tenancy и явно ограниченный maintenance-путь. При включённом строгом tenant-режиме отсутствие контекста должно давать отказ, а не все tenants. Менять host-owned tenancy следует отдельным решением с учётом существующего ADR и тестов. Основание: S04–S05.

**Чтение тоже операция.** Если доступ к metadata закрыт, список, search, totals и preview не должны раскрывать denied nodes. Exact SQL либо согласованная permission projection предпочтительнее фильтрации уже выданной страницы. Если выбран bounded scan кандидатов, continuation должен помнить позицию сканирования, даже когда все просмотренные элементы запрещены. У этого подхода есть цена по latency; это не готовое решение для Vaulter без измерений. Основание: E10, S30.

## 2. Объединить lifecycle загрузки, сохранить различия транспорта

Single multipart, tus, S3 multipart и PHP streams могут иметь разные adapters. Общие инварианты начинаются с доверенного staging handle: кому принадлежит, какие реальные bytes, какие policy и scope применены, можно ли завершить и открыть результат. Финализация должна повторяться безопасно после потерянного ответа.

Для `UploadSource` полезны явные factories `fromBytes/fromPath/fromStream`, но важнее их контракт: закрывает ли пакет поток, поддерживает ли non-seekable, откуда считается длина, как ограничен staging. Общая policy должна проверять фактические staged bytes. Quota reservation для длинных uploads — вариант, если реальная нагрузка требует заранее учитывать незавершённые сессии; одного этого механизма недостаточно для ограничения локального temp disk.

Quarantine стоит оформлять как доступность содержимого, если включена обязательная проверка. Запрет охватывает download, preview, export, public share и фоновых обработчиков. Timeout сканера — неизвестный результат, не `clean`. При этом встроенный антивирус/CDR для всех установок не обязан стать условием 1.0: обязательным может быть корректный inspection seam и согласованное поведение выбранной policy. Основание: E4, S02, S06–S08.

## 3. Сначала определить сохраняемые данные и смысл квоты

Развести логические head bytes, retained history bytes и physical/staging bytes. По нынешним тестам quota учитывает head bytes; сохранение этого поведения — разумная отправная точка. Ограничение и изменение счётчика должны быть одной атомарной операцией. Для concurrent revisions прежний head и delta нужно брать из согласованного состояния, а не старого переданного Eloquent instance.

CAS identity должна включать явную область дедупликации со строковым ID без потерь; disk и encryption domain требуют отдельного решения. Не стоит автоматически добавлять disk во все ключи: текущий ADR сознательно закрепляет disk-agnostic lookup. Сначала решить, разрешает ли logical scope использовать несколько физически независимых дисков и какой результат обещает повторная загрузка.

**Исправление scope может потребовать ремонта уже записанных данных.** Если разные storages сошлись в `snull`, менять префикс существующего объекта опасно: у blob несколько владельцев через version edges. Нужен inventory/dry-run, вывод новых scope из достоверных связей, проверка bytes, копирование по нужным scopes, атомарное переключение ссылок и удержание старого объекта до безопасной очистки. Потерянный исторический tenant нельзя угадывать. Если таких данных нет, это должно быть установлено проверкой, а не предположением.

GC/reconciler уже существуют. Их инварианты надо сохранить при изменении IDs; одного grace period недостаточно без координации writers и повторной проверки ссылок. Продвижение объекта и SQL rollback не образуют одну транзакцию. Основание: E1–E2, S09–S12.

## 4. Для событий выбрать уровень обещания

Нужны три независимых понятия: **command idempotency key**, **event occurrence ID**, **aggregate revision/sequence**. Повтор доставки сохраняет event ID; новая команда с прежним итоговым именем получает новый event ID. `A → B → A → B` — три изменения, даже если результат повторяется.

Если webhook является надёжным журналом интеграции, business row и outbox row фиксируются вместе. Ошибка записи outbox тогда означает отказ всей операции. Если это best-effort notification, текущая resilience-политика допустима только как явно заявленное ограничение с механизмом восстановления. Это продуктовый выбор: существующие тесты местами специально предпочитают успешную mutation при staging failure.

Доставка остаётся at-least-once. SQL relay достаточно; Kafka/Debezium не требуются ради названия паттерна. Источники S13–S15 нужны для event identity и понимания гарантий, а не как список новых инфраструктурных зависимостей.

## 5. Расширение должно переживать отсутствие редактора

Сохранить закрытый structural `NodeKind`. Для документа отдельно определить стабильный `type_key`, `schema_version`, content encoding и revision. MIME помогает маршрутизации файлов; ID редактора не должен становиться единственным идентификатором долговечного содержимого.

Минимальный document-type contract: ключ, совместимые schema versions, создание/проверка содержимого, чтение старых данных и описание возможностей. Export, collaboration и preview подключать отдельными capabilities, когда они поддерживаются. Не заставлять простой Markdown-тип реализовывать фиктивные collaborative methods ради большого интерфейса. Уже существующий `DocumentContent` — исходная точка, а не повод завести второй эквивалентный слой.

Главный proof extension: внешний пакет добавляет один новый тип без правок core; после удаления пакета документ остаётся в дереве, bytes сохраняются, недоступные действия дают понятный отказ. Unknown-type UI fallback должен существовать и в старом Vue SDK.

Registry: стабильные namespaced keys, явная duplicate/override policy, детерминированный tie-break, metadata для API без PHP objects и FQCN компонентов. Boot freeze полезен, если runtime-регистрация не нужна; он не обязателен сам по себе. Нынешний registry умеет сбрасывать cache при регистрации. Дополнительно проверить: capabilities получают полный `FileDescriptor`, а memoization учитывает только MIME/extension/capability — корректно ли это для handler, зависящего от размера или других полей? Это тест контракта расширения, пока не установленный дефект built-ins. Основание: E5, S01–S03.

Для совместных Yjs-документов binary state сохраняет CRDT-историю; JSON — отдельная проекция. Non-collaborative Markdown не обязан использовать Yjs. Старый несовместимый schema client не должен переписать новый документ. Restore при активных клиентах требует выбора: CRDT-операция восстановления либо замена состояния с fencing/room generation и контролем старых/offline updates. Последний вариант — предложение, не встроенная гарантия Hocuspocus. Основание: S16–S18.

## 6. Публичная поверхность может оставаться Laravel-native

Eloquent не делает Laravel-пакет архитектурно неправильным. Для PHP-интеграции модели и swappable subclasses могут быть самым удобным контрактом; для REST нужны стабильные resource schemas. DTO/VO оправданы там, где устраняют неоднозначность и защищают invariant: scope ID, upload source, operation context. Удалять ORM из всех интерфейсов ради воображаемого remote backend сейчас не обосновано.

Предпочитаю короткий glossary с сопоставлением существующих имён. `Storage` можно документировать как logical root; термин `Profile` для конфигурации можно обсуждать отдельно. Всеобщие переименования `for → drive`, `FileVersion → FileRevision`, `Action → без Action` не должны задерживать исправление CAS и событий. Имена параметров тоже затрагивают клиентов, использующих named arguments.

У REST прежде всего нужны описанная политика совместимости и проверяемая схема. `/v1` — возможный выбор; Paperless демонстрирует версию через header. ETag/If-Match уместен для metadata и обычного content update, но не заменяет CRDT concurrency protocol. Выбрать error envelope с машинными кодами; RFC 9457 — готовый вариант, миграция существующих клиентов всё равно нужна. Основание: S19–S22.

## 7. Границы пакетов доказываются установкой и зависимостями

Я бы пока сохранил существующий набор Composer packages. Зафиксировать владельцев schema/behavior и допустимые зависимости, затем проверить их Deptrac и изолированным consumer installation. Новый package оправдан независимой установкой, тяжёлой optional dependency или самостоятельным release lifecycle. Переименование `core` в `kernel` само по себе связанность не уменьшает.

Для config сначала определить единственный канонический ключ, precedence legacy aliases и ошибки конфликтов. Typed normalized config полезен; восемь новых config files без такого правила лишь распределят путаницу. Для docs выгоднее три реально исполняемых host recipes (core, drive, documents), чем универсальный парсер всех Markdown snippets в первой итерации.

Release evidence должно относиться к **собранному артефакту**: clean consumer без workspace autoload, provider/config/migrations, supported matrix по manifests, upgrade с предыдущего поддерживаемого артефакта, schema/API diff. Отдельно учесть vendor names, `self.version`, split tags и Testbench, подхватывающий соседние tests. Основание: S23–S27.

В эксплуатационную документацию добавить restore drill, dry-run диагностику и явные prerequisites очередей/scheduler. UI-проверка дерева клавиатурой и понятных ошибок загрузки — часть качества готового пакета. OCR, новые редакторы и отдельный search cluster не становятся обязательными только потому, что встречаются у больших DMS. Основание: S22, S28–S29.
