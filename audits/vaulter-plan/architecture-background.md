# Архив обоснований Vaulter для FlexCms, FlexCrm и Edufy

Исполнитель начинает с [поэтапной спецификации](../../plan/README.md). Для каждой задачи там указаны владелец, зависимости, вход, пример и наблюдаемый результат. [Матрица ревью](review.md) связывает требования с воспроизводимыми проверками. Здесь сохранены продуктовые решения и основания выбора на 20 ноября 2026 года, исходная ревизия Vaulter — `b230f6e27`.

## С чего начинаем

**Зафиксировано владельцем.** FlexCms получает существующий одиночный редактор. Для закрытого FlexCrm отдельно устанавливаются PHP, фронтенд и Hocuspocus для коллаборации. У таблиц и AI будут собственные закрытые репозитории. У AI будет общее ядро и два адаптера содержимого. Первый агент запускается через Laravel AI. Работа с содержимым идёт через SDK в пределах прав пользователя. Существующий код сохраняем, установка начинается с пустой БД.

| Работа | Основание | Первый результат |
| --- | --- | --- |
| Проверить базовую поставку CMS | Состав метапакета известен. У Vue есть слот редактора, у Documents — сохранение и контроль версии | В чистом потребителе со штатным Tiptap пользователь сохраняет правку и видит её после перезагрузки. Конкурентная запись из второй вкладки даёт наблюдаемый конфликт. Результат становится точкой сравнения при разнесении пакетов |
| Подготовить извлечение Sheets | Тип книги, Vue-оболочка, регистрация и тесты уже имеют конкретные пути в репозитории | Зафиксирован текущий тест сохранения снимка. Тот же тест проходит из отдельно установленного пакета, сборка базового клиента проходит без него. Это можно сделать до выбора табличного движка |
| Проверить штатную коллаборацию CRM | Реализованы все три компонента. Штатный WebSocket-провайдер в локальном прогоне потерял параметр версии, и ветвь Hub без версии допускает только чтение | Два браузера на текущих точках входа отправляют по правке, после переподключения виден общий сохранённый результат. После исправления проверяем запись обоих клиентов и сохранение после рестарта |
| Определить проверку SDK | Для агента уже известен смысл поручения, права и ожидаемый результат | На фиксированном договоре описаны целевая и соседняя правки, потеря ответа и отзыв прав. На книге задан диапазон, формула и эталон пересчёта. Измеряем объём чтения полного снимка для сравнения с адресным чтением. Этим же набором позже проверяем PHP, фоновый runtime и фронтенд |

Чистая установка CMS и работа двух вкладок уже воспроизведены. Следующие задачи — перенести существующую оболочку книги, исправить версию WebSocket-клиента и реализовать первую адресную замену на фиксированном договоре. Получены все шесть исследовательских отчётов. Для расчёта книги и адресного чтения PostgreSQL выполнены отдельные локальные прогоны. Сохранность совместной команды после сбоя и стоимость обновления проекций проверяются на следующих этапах. [Выполненные проверки](review.md) [Исследования и приложения](../../roadmap/research-prompts.md)

Долгосрочный результат — офис, в котором человек и агент работают с одним содержимым. Для машинного клиента чтение, поиск, редактирование, проверка результата, история и восстановление — штатные операции. В Univer особенно полезен цикл «найти объект → прочитать часть → изменить → пересчитать → проверить». Для сложных поручений у них есть отдельный черновик, проверка и публикация. У нас этот сценарий должен работать из фонового процесса, в том числе при закрытом браузере. Выбор модели и будущий чат остаются у продукта. [Операции агента Univer](https://docs.univer.ai/ai/content-operations) · [Проверка черновика](https://docs.univer.ai/ai/worktree)

## Как агент выполняет поручение

Например, «В разделе об оплате замени 15 дней на 30 и покажи, что изменилось». Аналог для таблиц — «в выбранных строках заполни существующую колонку отклонения формулой Факт − План и проверь результат». Это тестовые поручения для SDK. Их можно выполнить детерминированным клиентом ещё до подключения LLM.

В таблице показано целевое развитие инструментария. Точные доступные команды первой версии, их параметры и результаты заданы в [контракте SDK](../../plan/spec/agent-sdk.md).

| Шаг | Что получает агент | Что выполняет сервис |
| --- | --- | --- |
| Найти | Список доступных документов, идентификатор, тип, краткое совпадение. Список возможностей и описание выбранной команды по запросу | Ограничивает выборку областью пользователя и проекта, применяет права до выдачи названий и фрагментов |
| Осмотреть | Для текста — оглавление и идентификаторы блоков. Для книги — листы, именованные диапазоны, размеры и типы столбцов. Для повторного запуска — изменения с указанной позиции | Возвращает короткие страницы с курсором, версией и признаком усечения. При истёкшем курсоре предлагает перечитать область |
| Прочитать | Только целевой блок с соседним контекстом либо прямоугольный диапазон с выбранными полями. Для вопроса про итог — серверный агрегат, формула и статус пересчёта | Извлекает данные и считает на стороне движка. Устанавливает предел числа ячеек, байтов и времени. Большой результат выдаёт частями или ссылкой с проверкой доступа |
| Изменить | Типизированные команды, например `replaceBlockText`, `insertAfter`, `setRangeValues`, `setFormula`, `insertRows`. Можно передать связанный набор одним вызовом | Проверяет типы, актуальные права, версию и условия на прочитанные значения. Текст и формула имеют разные типы. Движок нормализует текст или пересчитывает ссылки |
| Проверить и завершить | Краткая разница, изменённые ID/диапазоны, результат контрольного чтения, статус вычислений, ID команды и подтверждённая версия | Меняет данные через штатный путь записи. Для задания с проверкой сохраняет предложение отдельно и перепроверяет условия перед применением. Режим прямого исполнения выбирает политика продукта |
| Продолжить или отменить | Статус по ID команды после разрыва, история операции, возможность отмены при выполнении условий | Отмена создаёт компенсирующую правку конкретной команды. Последующая правка другого пользователя защищена проверкой условий. Восстановление документа целиком — отдельная операция |

SDK передаёт контекст хоста, область, цель, версию, тип команды, её параметры и устойчивый `command_id`. Идентичность и полномочия сервис получает из доверенного сеанса или задания. Выбор модели и инструкции агента не расширяют эти права. При изменении намерения после конфликта возникает новая команда. При повторе прежнего намерения используется тот же идентификатор. Если подтверждение потеряно, SDK запрашивает статус. Для активной комнаты семантическую команду нужно связать с сохранённым обновлением: новый Yjs update после повторного исполнения может оказаться другой правкой. [Операции Documents](../../packages/documents/src/Operations/DocumentOperations.php) · [Запись состояния](../../packages/documents/src/Content/DocumentStateWriter.php) · [Журнал](../../packages/collaboration/src/Persistence/UpdateLog.php)

Для первого среза SDK проверяем семь операций: найти документ, прочитать фрагмент, получить описание инструмента, подготовить правку, применить её, узнать исход и проверить сохранённый результат. Их можно вызывать из PHP или через языконезависимый интерфейс. Детальные схемы команд загружаются по запросу. В прототипе достаточно `text.replace_exact@1` для однородно оформленного фрагмента и `sheet.fill_formula@1` для диапазона. Пакет правок адресован одному документу. [Исследование SDK](../../roadmap/research/answers/1.md)

В договоре SDK читает пункт 4.2 и возвращает маркер чтения, привязанный к содержанию и оформлению цели. Подготовленная замена «15 рабочих дней» на «30 рабочих дней» получает неизменяемый идентификатор предложения и контрольную сумму. При применении сервер повторно проверяет права и исходный смысловой фрагмент. Правка другого раздела допускается, замена «рабочих» на «календарных» в цели требует нового решения. Хост сохраняет ключ команды до первого запроса на запись. После потери ответа он может узнать исход по ключу. Контрольное чтение различает результат в момент фиксации и текущее состояние, которое мог изменить следующий пользователь.

В книге поручение получает явную область: фиксированный состав выбранных строк либо все актуальные строки таблицы. При фиксированном выборе команда перепроверяет выбранные устойчивые ID и изменяет только их. Для всей таблицы изменение состава завершает прежнюю команду с `scope_changed`; требуется новое чтение, предложение и ключ. При проверке итогов +20 и −20 проверяем обе формулы, ссылки, отдельные значения и версию пересчёта. Нулевой итог сам по себе допускает ошибку знака в обеих строках.

После первых двух адаптеров расширяем охват на доступные операции жизненного цикла: создание из шаблона, размещение и поиск в Drive, комментарии и ответы, именованные версии, сравнение, экспорт конкретной версии и получение результата фоновой задачи. Для каждого инструмента нужны входная схема, ограничение ответа, требуемое право, предусловие и наблюдаемый исход. Каталог инструментов фильтруется по правам и типу документа. Схемы детализируются по запросу. Голос, окно агента и будущие инструкции пользователя или проекта подключаются к тому же контракту.

## Как подключается агент потребителя

Первый исполнитель — отдельный агент на Laravel AI SDK с ключом провайдера на сервере. Он получает инструменты документов из установленного пакета. Сначала проверяем те же операции обычным PHP-вызовом и детерминированной моделью в тесте, затем прогоняем одно поручение через реальную модель в тестовом контуре. Формы запросов, результаты и коды ошибок принадлежат офисному SDK. Это позволяет использовать одинаковую запись и подтверждение из очереди, приложения и чата. [Laravel AI SDK](https://laravel.com/framework/docs/13.x/ai-sdk)

| Что приносит пакет потребителя | Как это выглядит для хоста |
| --- | --- |
| Инструменты, описания параметров и обработчики | Доверенный установленный пакет регистрирует их через Laravel service provider. Для доменного модуля Vaulter уже есть регистрация расширений. Проект получает список реально подключённых возможностей. Совпадение ключей выявляется при сборке конфигурации. [Регистрация расширений Vaulter](../../docs/adr/0039-native-packman-extensions.md) |
| Агент и его настройки | Хост указывает профиль по умолчанию, модель, ссылку на секрет, разрешённые инструменты и лимит исполнения. Позже поставщик профиля может выбирать агента и инструкции для пользователя или проекта. Хост определяет приоритет настроек. Фактический доступ ограничивается правами пользователя и политикой хоста независимо от текста инструкции |
| Другой исполнитель, в том числе AgenTools | Исполнитель получает описание доступных инструментов и вызывает тот же контракт. В локальном AgenTools уже есть ToolPort и LlmPort, а в Edufy — собственный AiCore. Первый тест совместимости — один сценарий чтения и записи через оба входа с одинаковым результатом и проверкой прав |
| Python или другой удалённый процесс | Версионированный JSON-контракт поверх авторизованного HTTP позволяет вызвать цель, команду и проверку статуса. Достаточно общего набора примеров запросов, ответов и ошибок. PHP/Node/Python можно распределить по реальным требованиям библиотек. В базовой поставке достаточно PHP и браузерного JS. Node нужен живой комнате и тому табличному движку, для которого он выбран |

Например, модуль Edufy сможет зарегистрировать агента методиста с инструкцией и инструментами чтения урока и предложения правки. Учитель с правом редактирования применит её, ученик с правом чтения получит только разрешённые операции. FlexCrm сможет подключить собственного агента и разрешить прямое исправление черновика договора. Оба продукта получают квитанцию одной формы. Разработку механизма сложения произвольных политик откладываем до второго реального профиля.

## Что увидит пользователь таблиц

Первый интерфейс — самостоятельная книга в Drive. Пользователь открывает лист, выделяет диапазон, различает исходную формулу и вычисленное значение, вставляет прямоугольник из буфера и видит подтверждение сохранения. Для первого прототипа берём **Univer Sheets**. В отчётах срез на версии 1.5.2. Сравнение ведём на общей книге по двум направлениям. [Исследование движка](../../roadmap/research/answers/3.md) · [Исследование интерфейса](../../roadmap/research/answers/5.md)

| Кандидат | Что проверяем и что повлияет на выбор |
| --- | --- |
| **Univer Sheets** | Один документ открывается в Vue и в фоновом Node-процессе. Проверяем формульную строку, вставку строк, пересчёт после холодного открытия и сохранность ресурсов плагинов. Это основной кандидат на полноценную книгу. [Интеграция в Vue](https://docs.univer.ai/guides/sheets/getting-started/integrations/vue) · [Устройство SDK](https://docs.univer.ai/overview) |

| **IronCalc** | Независимое сравнение вычислителя и обмена файлами на версии 0.9.1 из отчёта. Проверяем межлистовые ссылки и систему дат, смещение именованных диапазонов и сохранность объектов XLSX. [Проект IronCalc](https://github.com/ironcalc/IronCalc) |

React-компонент с лицензией MIT запрашивает значения через `getCellContent`, передаёт пакет правок через `onCellsEdited`, поддерживает выделение и подсветку диапазонов. С таким UI на команде остаются интеграция React в Vue, модель книги и вычислитель, история, XLSX и согласование с сервером. Имеет смысл собирать этот вариант, если продукту нужен собственный интерфейс поверх данных CRM. Для той же задачи есть RevoGrid с готовым Vue 3-компонентом. [Glide](https://grid.glideapps.com/) · [Редактирование](https://docs.grid.glideapps.com/api/dataeditor/editing) · [Выделение](https://docs.grid.glideapps.com/api/dataeditor/selection-handling) · [RevoGrid для Vue 3](https://github.com/revolist/vue3-datagrid) |

Общий браузерный тест: закрытый Vue-пакет монтирует книгу, пользователь отправляет агенту D2:D3 и вводит «проверено» в E2. После ответа видны 10 и −10, исходные формулы и сохранённое E2. Локальный undo отменяет ввод пользователя, агентская правка сохраняется. Большой paste 100×100 отменяется одним действием. На тех же данных проверяем фокус, экранный диктор, время первого ввода и память после 20 открытий. Документация Glide описывает ленивую отрисовку, измерение фактических сетевых и серверных чтений остаётся частью опыта.

Vue-адаптер лениво загружает движок при открытии книги, создаёт экземпляр для текущего документа, освобождает его при закрытии и сохраняет выделение при обычном обновлении интерфейса. Пользователь отправляет агенту ссылку на выделение с версией. После правки клиент подсвечивает затронутые ячейки и показывает актуальные формулы и результаты. Изменение приходит через штатную модель сохранения, поэтому работу агента видит и пользователь, который открыл книгу позже. Для прототипа проверяем ввод с клавиатуры, copy/paste, undo/redo, переключение листов, прокрутку разреженной книги и задержку пересчёта. Встроенный в текст диапазон проходит отдельную проверку прав, фокуса, экспорта и поведения при удалении источника. [Механизм NodeView Tiptap](https://tiptap.dev/docs/editor/extensions/custom-extensions/node-views)

## Как хранить данные для точного и дешёвого доступа

| Данные | Владелец и модель | Проверка |
| --- | --- | --- |
| Идентичность, дерево, доступ, блобы, версии | Существующие Drive, Media и Documents. Узел Vaulter остаётся общей точкой ссылки. Рабочая версия, именованная ревизия и поколение коллаборации имеют разные назначения | Ссылка на объект, вызов SDK и обычный пользовательский API разрешают один и тот же набор действий |
| Содержимое текста | Для одиночного редактора используем текущий путь JSON с проверкой ожидаемой версии. Для живой комнаты сохраняем Yjs-состояние и журнал. JSON доступен после соответствующего checkpoint. Во время отставания можно дождаться актуальной проекции либо читать через авторизованный runtime | Обычная правка в живой комнате проходит через её движок. Человек остаётся в том же поколении, а вставки агента и человека видны после перезапуска. [Сохранение Hocuspocus](https://tiptap.dev/docs/hocuspocus/guides/persistence) |
| Структурный доступ к тексту | Стабильные ID блоков в схеме редактора, PHP и hub. Для больших документов закрытый адаптер строит производный индекс разделов и блоков с ключами области, узла, версии и блока. Поиск возвращает ID и короткие совпадения. Индекс можно перестроить | После split/join, вставки копии и восстановления ID однозначны. Ответ содержит версию индекса. Устаревший фрагмент нельзя использовать как основание для записи без проверки |
| Книга | На первом срезе полный снимок выбранного движка с версией схемы и проверкой конкурентной записи. Для Univer кандидат — штатная сериализация со всеми ресурсами плагинов. Sheets владеет формулами, адресацией листов, пересчётом и при необходимости индексом диапазонов. Большие снимки или чанки выносим в Media по результатам замеров | Прототип сравнивает стоимость выборки диапазона и пересчёта при холодном и прогретом runtime. При росте переходим к загрузке листа/диапазона или чанкам, если они уменьшают фактические чтения. Содержимое книги восстанавливается из канонического формата |
| Выполнение агента | AI хранит запуск, команду, типизированный результат, автора, исходную версию, список целей и связь с подтверждением записи. Уникальность команды ограничивается её областью. Связь с записью фиксируется в одной транзакции, где это возможно, либо подтверждается и восстанавливается по устойчивому ID в журнале владельца | Сбой между commit и ответом даёт одну правку. Повтор с тем же ключом и другим содержимым отклоняется. Журнал позволяет объяснить и по возможности отменить действие |
| Поиск, изменения, фоновые задания | Проекции получают события из действующего outbox, хранят позицию обработанного события и версию источника. Индексы, результаты поиска, кэш и чтение изменений учитывают область доступа. Модель получает компактную выборку, а не учётную запись БД | Тесты проверяют задержку, повтор события, восстановление индекса, смену прав и удаление объекта. Ни название, ни сниппет закрытого документа не попадают в ответ |

Пример запроса после изменения — «верни изменённые блоки для этой команды» или «верни формулу, рассчитанное и отображаемое значения итога, актуальные как минимум на эту ревизию». В ответе различаем фиксацию команды в журнале, доступность проекции и проверенный результат расчёта. Для единственной правки в длинном договоре индекс хранит ID блока, родителя, порядок, путь заголовков и хеш. Результат поиска ведёт к чтению выбранного блока с разметкой и комментариями. Для книги сначала измеряем доступ к именованному диапазону, затем проверяем индекс по листам и разреженным участкам. Выдача 20 ячеек должна экономить и токены, и реальные чтения на сервере.

Для первого прототипа PostgreSQL сравниваем полное чтение с перестраиваемой проекцией абзацев и непустых ячеек. Строки проекции и обработанную позицию публикуем одной транзакцией при совпадении поколения и версии основы. После команды чтение принимает выданный сервером маркер документа, организации, поколения и минимальной позиции. Отставание даёт явное ожидание или чтение через авторитетный источник с проверкой прав. При восстановлении отбрасываем запоздалые события старого поколения. Версию вычисления формулы отслеживаем отдельно. При одинаковом ответе на корпусах 1× и 10× измеряем прочитанные байты, холодный и прогретый p95, цену записи и перестроения. [Отчёт по хранению](../../roadmap/research/answers/2.md)

Для коллаборативной книги сначала выбираем владельца фиксации. Если движок ведёт свой OT-журнал, его ревизия определяет успешность правки. Снимок Vaulter отмечает, до какой ревизии он доведён. Два независимых подтверждения в SQL и движке нельзя выдавать за одну атомарную запись. При отдельном хранилище движка нужны повторяемая доставка, сверка позиции и восстановление после сбоя. Для нескольких документов результат фиксируется по каждому объекту. Атомарность набора правок ограничиваем тем, что подтвердил конкретный адаптер.

Для измерения экономии запускаем одинаковые поручения по полному снимку и через SDK. На наборах малого, типичного и предельного размера снимаем долю верных результатов, входные/выходные токены, вызовы инструментов, байты ответа, прочитанные из БД/хранилища байты, длительность и p95. Отдельно измеряем поведение после конфликта и стоимость перестроения индекса. Критерий первого среза: для правки одного блока и чтения фиксированного диапазона размер ответа ограничен выбранной областью при росте документа. Бюджеты времени, токенов и памяти устанавливаем по результатам на реальных примерах. Семантический поиск подключается при измеримом выигрыше поверх поиска по структуре и тексту.
