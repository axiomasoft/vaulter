# 2. Самая важная доработка: команды редактирования для агентов

JSON — хорошее представление документа, но само по себе оно не решает проблему редактирования агентом.

Представим задачу: «В разделе условий замени срок оплаты с 15 на 30 дней».

Если агент читает весь JSON, изменяет его у себя и отправляет целиком, возникает несколько проблем: за это время человек мог изменить соседний абзац; адрес нужного блока мог сдвинуться; повтор запроса после тайм-аута может выполнить действие снова.

Нужен контракт, который выражает **намерение и условия применения**.

## 2.1. Разделить полную замену документа и обычное редактирование

В текущем `DocumentStateWriter` операция `Update` документа с заполненным `collab_protocol` увеличивает `collab_epoch`. Это корректный механизм полной замены состояния: старые участники совместного редактирования должны перестать записывать изменения в прежнее поколение. Но вызывать такой путь для каждой правки агента было бы неудачно. [DocumentStateWriter](https://github.com/axiomasoft/vaulter/blob/b230f6e27b53c92145fa81be2fdeb89ea5c8ae03/packages/documents/src/Content/DocumentStateWriter.php).

Для живого Yjs-документа у вас уже есть более подходящий механизм:

**`serverWrite` в collaboration hub.**

Он открывает прямое соединение с текущим документом, выполняет изменение в его `Y.Doc`, захватывает обновления и использует существующий журнал сохранения. В durable-режиме ожидает подтверждения сохранения. [Реализация serverWrite](https://github.com/axiomasoft/vaulter/blob/b230f6e27b53c92145fa81be2fdeb89ea5c8ae03/packages/collaboration/hub/src/persistence.js).

Я бы построил поверх него операции вида:

- заменить текст в конкретном блоке;
- вставить блок после указанного;
- изменить атрибуты выбранных блоков;
- изменить ячейки таблицы внутри документа;
- применить набор связанных изменений.

**Агент и человек должны изменять одну живую модель документа.**

Отдельная техническая тонкость: `Y.Doc.transact` группирует изменения, но не даёт SQL-подобного отката при исключении. Поэтому весь план нужно проверять до изменения живого документа, а поведение при ошибке посередине исполнения — определить явно. Одного `try/catch` вокруг транзакции недостаточно. [Yjs Docs](https://beta.yjs.dev/docs/api/transactions/?utm_source=chatgpt.com)

## 2.2. Добавить идемпотентность именно команды агента

В Vaulter уже есть хорошая идемпотентность операций и дедупликация обновлений протокола. Но это два разных уровня.

Например:

1. Агент отправил «вставить абзац».
2. Абзац сохранён.
3. Ответ потерян.
4. Агент повторяет команду.
5. Новый запуск генерирует новое CRDT-обновление.

Дедупликация старого `update_id` здесь не поможет: новый запуск может получить другой идентификатор обновления.

Нужна долговечная связь:

**`commandId → исходные условия → сохранённые обновления → результат`.**

Повтор той же команды должен возвращать уже известный результат. Для неизвестного исхода нужна операция проверки статуса. Просто записать `started`, вызвать hub, а потом записать `done` недостаточно: между этими действиями остаётся окно сбоя.

При этом существующий механизм receipt следует переиспользовать там, где он уже применим. В текущих политиках PHP-операция `documents.documents.update` и HTTP-операция `documents.documents.update_content` имеют разные режимы идемпотентности. Добавление HTTP-заголовка само по себе не превращает любой endpoint в операцию с receipt. [Политики операций](https://github.com/axiomasoft/vaulter/blob/b230f6e27b53c92145fa81be2fdeb89ea5c8ae03/packages/documents/src/Operations/DocumentsOperationPolicies.php), [контракт идемпотентности](https://github.com/axiomasoft/vaulter/blob/b230f6e27b53c92145fa81be2fdeb89ea5c8ae03/docs/concepts/idempotency.md).

Для агента я бы закрепил правила:

- неизменённый запрос после сетевой ошибки повторяется с тем же идентификатором;
- повторное чтение и новый план после конфликта создают новую команду;
- сведения об исходе хранятся достаточно долго для фоновых задач;
- после истечения срока дедупликации клиент не делает слепой повтор.

## 2.3. Ввести устойчивые адреса элементов

Агенту неудобно надёжно редактировать «третий параграф пятого раздела»: структура меняется.

Нужны:

| Документ | Устойчивая адресация |
|---|---|
| Текст | `blockId`, идентификаторы таблиц и других структурных объектов |
| Таблица | `sheetId`, именованная таблица или диапазон, условия относительно прочитанной версии |
| Презентация | `slideId`, `elementId`, идентификаторы layout и master |

В текущей стандартной TipTap-схеме я не обнаружил системного стабильного идентификатора блока. Добавлять его нужно согласованно в PHP-схему, расширения редактора и схему hub, иначе разные участники будут по-разному принимать или сохранять документ. [TipTapSchema](https://github.com/axiomasoft/vaulter/blob/b230f6e27b53c92145fa81be2fdeb89ea5c8ae03/packages/documents/src/Content/TipTap/TipTapSchema.php).

Здесь есть готовая основа — Tiptap `UniqueID`, учитывающий операции разделения, объединения, вставки и отмены. Его стоит проверить прежде, чем писать своё управление идентификаторами. [Tiptap Editor Docs](https://tiptap.dev/docs/editor/extensions/functionality/uniqueid?utm_source=chatgpt.com)

Но ID не заменяет проверку смысла изменения. Если агент увеличивает цену исходя из прочитанной себестоимости, а себестоимость уже изменилась, успешное CRDT-слияние ещё не означает правильность решения. Нужны проверки прочитанных значений или соответствующего диапазона.

## 2.4. Усилить проверку структуры документа

Текущий `TipTapContent` проверяет разрешённые узлы, поля и атрибуты. При этом в просмотренной реализации я не увидел полной проверки правил вложенности ProseMirror; например, `heading.level` проверяется как числовое значение. Это наблюдение по коду, а не воспроизведённая ошибка выполнения. [TipTapContent](https://github.com/axiomasoft/vaulter/blob/b230f6e27b53c92145fa81be2fdeb89ea5c8ae03/packages/documents/src/Content/TipTap/TipTapContent.php).

Для машинных изменений я бы добавил:

- проверку документа реальной схемой соответствующего движка;
- ограничения глубины, количества узлов и допустимых атрибутов;
- проверку структуры таблиц;
- общие проверочные примеры для PHP, браузера и hub;
- отдельную проверку результатов миграции схемы.

Для spreadsheet аналогичная проблема сейчас выражена ещё явнее: корректный JSON-объект не обязательно является корректной книгой. Плагину потребуется собственный кодек и проверка модели.

# 3. Каким должен быть интерфейс для агента

Я бы сделал небольшой общий набор инструментов, а конкретные возможности документа раскрывал через его тип.

| Инструмент | Назначение |
|---|---|
| `describe` | Тип документа, доступные возможности, схема, версия движка, разрешённые действия |
| `read` | Структура документа или выбранные блоки, диапазоны, слайды |
| `search` | Поиск с возвратом устойчивых адресов |
| `propose` | Подготовка изменения и содержательного diff |
| `apply` | Применение команды с условиями и идентификатором повторного выполнения |
| `operation_status` | Выяснение исхода после тайм-аута или разрыва соединения |
| `inspect` / `render` | Проверка результата, включая внешний вид |
| `revert` | Условная отмена конкретного изменения |

Пример **предлагаемого нового контракта**, а не существующего API:

```json
{
  "documentId": "doc_123",
  "commandId": "cmd_8f72",
  "baseToken": "token-returned-by-read",
  "commands": [
    {
      "type": "richtext.replace_text",
      "blockId": "paragraph_42",
      "expectedText": "Оплата в течение 15 дней.",
      "replacement": "Оплата в течение 30 дней."
    }
  ]
}
```

`baseToken` лучше выдавать сервером как непрозрачный маркер. Для обычного документа он может опираться на `state_version`; для живого совместного документа должен учитывать поколение и позицию в журнале либо ревизию движка. Одна версия последнего JSON-снимка может не описывать все уже сохранённые совместные изменения.

Ответ должен различать:

- команда принята;
- изменения надёжно сохранены;
- JSON-проекция догнала нужную ревизию;
- результат проверен или отрисован.

Тогда агент не сообщает «готово» на основании изменения только в памяти.

## Два уровня инструментов

Для обычных задач достаточно компактных типизированных команд. Для сложных преобразований — например, обработки нескольких тысяч строк — полезен **кодовый режим поверх API движка**.

Такой режим я бы запускал в отдельном ограниченном процессе, с доступом к конкретному авторизованному документу. Он позволяет выразить сложное действие одним небольшим скриптом и вернуть краткий отчёт вместо передачи всей книги в контекст модели.

Именно такое сочетание — структурное чтение, поиск API, выполнение и отдельное подтверждение commit — уже описано в нынешнем Univer AI SDK. В его документации специально различаются успешное выполнение кода и подтверждённое сохранение на сервере. [Univer Office SDK](https://docs.univer.ai/ai/content-operations?utm_source=chatgpt.com)

## MCP можно взять готовый

Для Laravel есть официальный `laravel/mcp`: инструменты, ресурсы, схемы и механизмы аутентификации. Я бы использовал его как транспортный слой, подобрав совместимую с проектом версию. Доменные права всё равно должны проверяться Vaulter: вход через MCP не означает разрешения на конкретный файл. [laravel.com](https://laravel.com/framework/docs/13.x/mcp?utm_source=chatgpt.com)

**Не стоит выполнять агентские действия через `Actor::system('ai')`.** В текущем коде системный actor имеет особое поведение относительно ACL. Нужен делегированный пользователь либо отдельный ограниченный субъект доступа. Для фоновых задач права следует заново разрешать по ссылке на actor. [OperationGuard](https://github.com/axiomasoft/vaulter/blob/b230f6e27b53c92145fa81be2fdeb89ea5c8ae03/packages/drive/src/Access/OperationGuard.php), [Actor](https://github.com/axiomasoft/vaulter/blob/b230f6e27b53c92145fa81be2fdeb89ea5c8ae03/packages/core/src/ValueObjects/Access/Actor.php).

## История должна объяснять действия агента

Помимо бинарных обновлений полезно хранить:

- инициатора и действовавшего от его имени агента;
- `runId`, `commandId`, correlation/causation;
- затронутые объекты;
- исходную и результирующую версии;
- краткое описание действия и связь с подтверждениями сохранения.

Полный prompt для этого не обязателен.

Отмена должна по возможности обращать **изменение конкретной команды** с проверкой последующих правок. Восстановление всей старой версии остаётся отдельной операцией: оно может затронуть работу других участников.

# 4. Что брать для Excel-подобных таблиц

## Первый кандидат — Univer

Для вашей задачи это сейчас наиболее подходящий кандидат для практической проверки: он объединяет модель книги, редактор, формулы, команды, серверное выполнение и совместную работу. Документация описывает загрузку книги агентом, чтение диапазонов, выполнение изменений и подтверждение commit. [Univer Office SDK](https://docs.univer.ai/ai/content-operations?utm_source=chatgpt.com)

Важно, что это совпадает с уже выбранным в Vaulter направлением `vaulter/univer`.

Однако выбор должен пройти два независимых испытания:

1. **Функциональность и сохранность ваших файлов.**
2. **Возможность распространения и эксплуатации в вашей модели продукта.**

### Сравнение вариантов

| Решение | Где подходит | Что останется вашей задачей |
|---|---|---|
| **Univer** | Основной кандидат для полноценного табличного плагина | Интеграция ACL, сохранения, истории, агентов; проверка лицензии и совместимости |
| **Handsontable + HyperFormula** | Управляемые бизнес-таблицы, формы, модели с расчётами | Значительная часть платформы документов и совместной работы |
| **FortuneSheet** | Вариант с MIT-лицензией и доступным исходным кодом редактора | Адаптация к Vaulter/Vue, надёжный backend совместной работы, проверка формул и обмена файлами |
| **SheetJS / ExcelJS** | Импорт, экспорт, серверная обработка файлов | Интерактивный редактор, совместная работа и вычислительный движок |
| **ONLYOFFICE Docs Developer** | Сценарии, где особенно важна работа с существующими Office-файлами | Интеграция отдельного офисного сервера с Vaulter и его моделью документов |

У Handsontable нет встроенного транспорта совместной работы и алгоритма разрешения конфликтов: это ответственность приложения. HyperFormula имеет GPLv3/коммерческое лицензирование. Поэтому связка может быть хорошей, но не даёт вам готовую совместную офисную платформу. 

FortuneSheet предоставляет операции `onOp`/`applyOp` и распространяется под MIT. Возможность передавать операции — полезный строительный блок; гарантии сохранения, восстановления и согласованной работы нужно оценивать отдельно. [GitHub](https://github.com/ruilisi/fortune-sheet?utm_source=chatgpt.com)

SheetJS CE и ExcelJS полезны для обмена файлами, но сами не вычисляют результаты формул. Их можно использовать внутри отдельных функций плагина, не возлагая на них роль полного редактора. [SheetJS Community Edition](https://docs.sheetjs.com/docs/csf/features/formulae/?utm_source=chatgpt.com)

У ONLYOFFICE Developer предусмотрен сценарий встраивания; Automation API доступен в Developer и требует отдельного платного расширения. Это другая архитектура интеграции, которую имеет смысл проверять при высоком приоритете Office-совместимости. [onlyoffice.com](https://www.onlyoffice.com/compare-editions?utm_source=chatgpt.com)

Для новой разработки Luckysheet я бы исключил: репозиторий архивирован, авторы направляют пользователей к Univer. [GitHub](https://github.com/dream-num/Luckysheet/blob/master/docs/guide/README.md?utm_source=chatgpt.com)

## Что обязательно проверить в Univer

Наличие импорта XLSX не гарантирует сохранность любой книги после цикла «открыть → изменить → экспортировать».

Проверочный набор должен включать ваши реальные:

- формулы и зависимости между листами;
- именованные диапазоны и таблицы;
- даты, числовые форматы и локали;
- диаграммы и сводные;
- условное форматирование;
- изображения;
- большие разреженные диапазоны.

В официальной матрице Univer перечислены ограничения, в том числе в отношении VBA, XLSB/ODS и автоматического обновления внешних связей между книгами. Это следует сопоставить с ожидаемыми файлами пользователей. 

Оригинал импортированного файла я бы сохранял через существующий media/CAS-механизм, а при преобразовании выдавал отчёт о неподдержанных возможностях. Экспорт должен строиться из определённой версии документа.

Для агента чтение ячейки желательно возвращать как набор отдельных значений: **формула, вычисленное значение, формат отображения, ошибка вычисления**. Иначе агент легко перепутает исходные данные с результатом расчёта.

## Лицензия — существенный архитектурный вопрос

У Univer Community — Apache 2.0; Business и Enterprise регулируются коммерческими условиями. Условия разрешают собственные приложения, включая API и агентские интерфейсы, но отдельно ограничивают самостоятельное переупаковывание и распространение SDK. [Univer](https://univer.ai/legal/license-agreement/?utm_source=chatgpt.com)

Для Vaulter это важно: если вы распространяете пакеты, которые другие разработчики встраивают в свои продукты, обычную лицензию на собственное приложение нельзя автоматически считать подходящей.

Я бы проверил два варианта:

- **OEM/redistribution-соглашение** с вендором;
- **BYOL:** ваш адаптер распространяется отдельно, а пользователь получает коммерческие компоненты и лицензию напрямую.

Аналогичную проверку стоит провести при использовании платных Tiptap-компонентов. Их Pro-лицензия отдельно рассматривает SDK, библиотеки и предоставление функциональности третьим сторонам для дальнейшего встраивания; публикация собственного адаптера с отдельно лицензируемой зависимостью предусмотрена условиями. [tiptap.dev](https://tiptap.dev/pro-license?utm_source=chatgpt.com)

# 5. Как вписать Univer в вашу БД и гарантии Vaulter

**Причин менять базовую систему хранения только ради агентов я не вижу.**

Vaulter уже разделяет тип документа, сериализованное содержимое, совместное состояние и его публикацию. Это подходящая основа для движков с разными протоколами. [Описание протоколов](https://github.com/axiomasoft/vaulter/blob/b230f6e27b53c92145fa81be2fdeb89ea5c8ae03/docs/extending/collaboration-protocols.md).

Я бы закрепил владение:

| Данные и поведение | Владелец |
|---|---|
| Дерево файлов, tenant, пользователь, права | Vaulter |
| Модель текста и текстовые изменения | TipTap/Yjs |
| Модель книги, формулы и преобразование табличных операций | Univer |
| Надёжное сохранение, связь с документом, outbox и история | Интеграционный пакет в рамках контрактов Vaulter |
| JSON для чтения, поиска и экспорта | Версионируемая проекция соответствующего движка |

**Один документ должен иметь один определённый протокол совместного изменения.** Оборачивание целого workbook JSON в Yjs само по себе не реализует корректное изменение ссылок формул при вставках строк, сортировках и структурных операциях.

## Самое опасное место — граница сохранения

В Univer есть контракт адаптера БД и готовые варианты для PostgreSQL, SQLite и PostgreSQL с объектным хранилищем. Адаптер отвечает за атомарность, проверку ожидаемой ревизии и сохранение идентификаторов отправки; для других требований предусмотрена собственная реализация. [Univer Office SDK](https://docs.univer.ai/server/collaboration/database-adapters?utm_source=chatgpt.com)

При этом обработчик события `changesetCommitted` **не равен транзакционной записи outbox Vaulter**: события доставляются внутри процесса с best-effort-гарантией, а обычные бизнес-обработчики выполняются вне транзакции collaboration. [Univer Office SDK](https://docs.univer.ai/server/collaboration/middleware-and-events?utm_source=chatgpt.com)

Поэтому вариант «Univer записал в свою БД, потом callback уведомил Vaulter» оставляет окно потери связи между двумя состояниями.

### Предлагаемая интеграция

Следующий вариант — мой проектный вывод, его нужно подтвердить прототипом:

1. Node-runtime выполняет вычисления и обработку операций.
2. Его адаптер обращается к внутреннему persistence API PHP-пакета.
3. Один атомарный метод адаптера соответствует одному короткому запросу сохранения.
4. PHP фиксирует необходимые записи протокола, связь с командой, pending-состояние и outbox в одной транзакции.
5. Подтверждение возвращается после commit.

Для общей атомарности нужно именно **одно физическое транзакционное соединение**, а не просто два сервиса с доступом к одному PostgreSQL.

При этом нельзя держать открытую PHP-транзакцию, ожидать Node, а из Node обращаться обратно в PHP за блокировками того же документа. Планирование и вызовы движка должны происходить вне длительных SQL-блокировок.

Собственный адаптер следует проверять тестовым набором контракта Univer; такой testkit опубликован в community-репозитории. [GitHub](https://github.com/dream-num/univer-collaboration-sdk-community?utm_source=chatgpt.com)

## Проекция может отставать — это нормально, если явно выражено

Сохранённое изменение и опубликованный JSON-снимок могут появляться в разное время.

Для этого нужны:

- номер подтверждённой ревизии;
- номер ревизии, вошедшей в проекцию;
- монотонное обновление проекции;
- запрет старому заданию перезаписать более новое состояние;
- отсечение старого поколения после restore;
- чтение, которое гарантированно включает результат указанной команды.

У Vaulter уже есть pending-состояния, поколения и контролируемая публикация. Их стоит расширить под новый протокол.

## Большие книги потребуют отдельного профиля хранения

В стандартной конфигурации документов лимит JSON составляет 5120 KiB. Для табличного плагина необходимо проверить реальные размеры и определить собственные ограничения. [Конфигурация](https://github.com/axiomasoft/vaulter/blob/b230f6e27b53c92145fa81be2fdeb89ea5c8ae03/packages/documents/config/vaulter-documents.php).

Я бы начинал с простого снимка, измерял размеры, стоимость пересчёта и время сохранения, а затем при необходимости вводил блоки данных и манифесты контрольных снимков.

Переход к «одна SQL-строка на каждую ячейку» не является обязательным следствием добавления Excel. Для поиска и аналитики можно иметь производные индексы, сохраняя нативную модель книги в её движке.

# 6. Как предусмотреть презентации

**Сначала я бы проверил Univer Slides в связке с выбранным spreadsheet-стеком.**

Это уже существующий продукт: документация описывает браузерный редактор, серверную обработку без UI, команды, модель презентации, collaboration и обмен файлами через Server SDK. Есть интеграция с Vue. [Univer Office SDK](https://docs.univer.ai/guides/slides?utm_source=chatgpt.com)

Потенциальная экономия здесь существенная: общие механизмы запуска runtime, авторизации, сохранения, агентского доступа и версионирования.

При выборе Univer я бы сохранял его нативную структуру презентации внутри плагина. В ней предусмотрены идентификаторы, порядок слайдов, masters, layouts, темы и ресурсы. Создание параллельной универсальной модели Vaulter добавило бы постоянную задачу синхронизации двух форматов. [Univer Office SDK](https://docs.univer.ai/guides/slides/model/slide-data?utm_source=chatgpt.com)

Для агентов нужны операции уровня:

- создать слайд из layout;
- изменить текст элемента;
- заменить изображение;
- обновить диаграмму;
- переставить слайды;
- изменить заметки докладчика;
- отрисовать выбранные слайды и проверить результат.

Здесь структурной валидации недостаточно. Нужно выявлять выход текста за границы, подмену шрифтов, перекрытия и обрезанные изображения. Поэтому серверный render и привязка проверки к конкретной ревизии — часть нормального процесса редактирования.

### Альтернативы

**PPTist** — Vue 3/TypeScript-редактор, который можно изучать как кодовую базу. Он распространяется под AGPL-3.0; интеграцию с Vaulter и условия использования нужно оценивать отдельно. [GitHub](https://github.com/pipipi-pikachu/PPTist?utm_source=chatgpt.com)

**PptxGenJS** — хороший кандидат для программной генерации и экспорта PPTX. Он распространяется под MIT; интерактивный редактор, импорт и совместную работу придётся решать другими компонентами. [GitHub](https://github.com/gitbrent/PptxGenJS?utm_source=chatgpt.com)

Для вашей цели первым выглядит наиболее экономичным общий стек Univer для таблиц и презентаций, если подтвердятся лицензирование и качество работы с файлами.

# 7. Как разделить пакеты

У вас уже принят переход к native Packman extensions. Новые возможности следует подключать через этот механизм. Вводить ещё одну систему модулей для AI не требуется. [ADR-0039](https://github.com/axiomasoft/vaulter/blob/b230f6e27b53c92145fa81be2fdeb89ea5c8ae03/docs/adr/0039-native-packman-extensions.md).

Предлагаемое распределение ответственности:

| Пакет | Ответственность |
|---|---|
| `vaulter-agents` | Выполнение команд, результаты, provenance, подготовка изменений, проверка статуса |
| `vaulter-mcp` | MCP-транспорт к разрешённым операциям |
| `vaulter-spreadsheets` | Тип книги, кодек, команды, импорт/экспорт |
| Vue-пакет spreadsheets | Подключение редактора и его интерфейса |
| `vaulter-presentations` | Тип презентации, команды, ресурсы и экспорт |
| `vaulter-univer` | Общая интеграция с runtime, OT, сохранением и версиями Univer |

Названия условные; важнее направление зависимостей:

- `core`, `drive` и `media` не зависят от LLM-провайдера;
- MCP не содержит бизнес-логику редактирования;
- команды формата принадлежат соответствующему плагину;
- слой агентов организует их выполнение;
- особенности Univer остаются в его адаптере.

Ключ `vaulter/spreadsheet` при переносе существующего задела я бы сохранил. Переход к новому формату снимка должен иметь явную миграцию.

Также следует отдельно учитывать **версию схемы Vaulter, версию формата движка и ревизию содержимого**. Они отвечают на разные вопросы.

Для связи документов полезно предусмотреть ссылки вида «документ → устойчивый объект → ревизия». Например, диаграмма в презентации может помнить исходную таблицу и диапазон. Это позволит агенту обновлять связанные материалы осмысленно и воспроизводимо.

# 9. Приоритетный план доработок

Я бы двигался по этапам с проверяемым результатом.

| Приоритет | Работа | Критерий готовности |
|---|---|---|
| **P0** | Контракт чтения и применения команд: версии, адреса, ошибки, статусы | Агент понимает структуру документа и не пишет поверх неизвестного состояния |
| **P0** | Проверка схемы и обязательные предусловия для агентского пути | Некорректный или устаревший запрос не оставляет частично изменённый документ |
| **P1** | Текстовые команды поверх `serverWrite`, связь команд с сохранёнными обновлениями | Человек и агент работают одновременно; потеря ответа не дублирует правку |
| **P1** | MCP-пакет поверх публичных операций | Внешний агент читает, изменяет и проверяет результат с текущими правами пользователя |
| **P1, параллельно** | Прототип Univer и проверка лицензирования | Подтверждены нужные функции, качество файлов и допустимая модель распространения |
| **P2** | Табличный плагин и надёжный persistence-адаптер | Формулы, структурные операции, совместная работа и восстановление проходят проверку |
| **P3** | Презентационный плагин на общей интеграции | Редактирование элементов, render и экспорт работают на контрольных презентациях |
| **По измерениям** | Блочное хранение, оптимизация проекций, расширенный поиск | Улучшения подтверждены профилем реальных документов |

### Проверки, которые действительно важны

Основной набор я бы строил вокруг отказов и конкуренции:

1. Ответ потерялся после commit — повтор команды не изменяет документ второй раз.
2. Человек вставил абзац или строку между чтением и записью агента — правка попадает в нужный объект либо возвращает понятный конфликт.
3. Доступ отозван после подготовки изменения — применение отклоняется.
4. Процесс упал между сохранением журнала и построением проекции — состояние восстанавливается.
5. Старое задание публикации завершилось после restore — новое поколение остаётся целым.
6. Отмена команды агента сохраняет последующие независимые правки человека.
7. Импорт и экспорт реальных XLSX/PPTX не скрывают потери поддерживаемых данных.
8. Агент получает номер сохранённой ревизии и может проверить именно результат своей команды.
