# Vaulter. Карта изменений монорепозитория

Пути в этом файле отсчитываются от корня Vaulter. Исходная ревизия — `b230f6e27`. В таблицах «существует» означает файл в этой ревизии, «создать» задаёт конечное место нового файла. Точки поставки здесь — публичные пакеты документов и закрытая тройка для коллаборации. Эталонные потребители — изолированные приложения для проверки артефактов. Код FlexCms, FlexCrm и Edufy для выполнения задач не нужен.

## 0.1. Получить исходный потребитель

1. В корне выполнить `bash plan/checks/flexcms/run.sh`. Это имя сохранённого исходного стенда. Внутри используется штатный сборщик ZIP по release-манифесту, чистый Composer home, npm-архив, отдельная SQLite и реальный браузер. Сохранить выведенные ревизии, lock-файлы, контрольные суммы, вывод doctor и HTTP/браузерных проверок. Путь к каталогу напечатает сам скрипт. Предусловия, включая ревизию Packman и версию PHP/Node, приведены в [рецепте установки](../base-install.md).
2. Снять состав поверхности до переноса. В выделенном приложении `axiomasoft/vaulter` подтягивает четыре доменных PHP-пакета, а базовый `@vaulter/vue` ещё экспортирует `VaulterSpreadsheet`. Возможность пройти browser smoke до удаления не доказывает отсутствие приватного кода в архиве после удаления.
3. Для нового результата использовать конкретную зафиксированную ревизию (`VAULTER_REF`), чтобы `git archive` видел проверяемые файлы. Новый эталон из задачи 1.3 получает готовые архивы. В обоих случаях повторить сборку из отдельного каталога без workspace alias.

## 1.0. Разнести содержимое и метаданные документа на чистой установке

Это отдельное изменение до 3.1/3.3. Сопоставление внешнего `resource_id` идёт через `v_nodes.id = v_documents.node_id` (UNIQUE); внутренние `document_id` ссылаются на `v_documents.id`. Все новые таблицы ниже принадлежат Documents, включая нейтральное сохранённое состояние протокола. Установка пустой БД и сохранение нового документа — базовая проверка. В owner DB нет второго источника канонического JSON.

### DB0 и 2.1. Как выбрать писателя и оградить старых клиентов

В исходном `DocumentStateWriter::write(Create)` тип с `SupportsCollaboration` заранее заполняет `collab_protocol`/формат, даже при одиночном редактировании. Ветка `Update` увеличивает `collab_epoch` при непустом protocol. Такое состояние не подходит для определения владельца записи: соседнее обычное сохранение сразу сделало бы правильный агентский read_token чужим поколением. Новое поле `v_documents.write_mode` на head обязательно, допускает `snapshot` и `journal`; начальное значение — `snapshot`. Данные о поддерживаемом формате/протоколе в sync-state описывают формат. Mode читается из текущей заблокированной строки. [Исходный writer](../../../packages/documents/src/Content/DocumentStateWriter.php) · [Целевая схема](../database/sql/documents.sql)

| До и событие | Действие под T → N → D | Что получает клиент |
| --- | --- | --- |
| snapshot, обычное сохранение изменённого JSON | Подтвердить права, тип, mode и ожидаемую позицию, сохранить payload и увеличить state_version. При неизменившемся содержимом сохранить прежнюю позицию. collab_epoch у обычного изменения остаётся прежним | Вторая вкладка со старым ETag получает 412; точечная команда после соседнего autosave может успешно перепроверить свои зависимости |
| snapshot, читатель открывает документ | Вернуть обычное чтение. Запрос сессии сам по себе у читателя не создаёт голову журнала, токен писателя или смену режима. Для родного клиента закрытого пакета обработать состояние snapshot через чтение из Documents | У reader сохраняются прежние ETag и epoch. Если mode уже journal, читатель получает существующую read-only сессию при наличии права |
| snapshot, разрешённый переход в совместный режим | Создать `Actions/Documents/ChangeDocumentWriteModeAction.php` и операцию `change_write_mode` в `DocumentsOperationPolicies`. Для перехода требуется право редактировать и разрешение политики расширения активировать совместное редактирование. Запрос потребителя на первое совместное редактирование может вызвать этот переход перед выдачей токена. Сверить mode, ожидаемые поколение/позицию, отсутствие pending/неподдерживаемой привязки, зафиксировать `snapshot→journal` и повысить epoch и state_version в одном commit. Оба конкурента видят одно новое поколение. Подписать токен и seed из подтверждённого состояния после этого commit | Прежние HTTP-писатели не используют старый snapshot. Hub восстанавливает seed по известной версии даже при сбое между переходом и первым подключением |
| journal, приходит полный PUT/старый token/закрывшийся Hub | Под блокировкой отказать обычной полной замене с доменной ошибкой 409 `document_command_required`. В 2.x PHP на append под блокировками сверяет действующие права, документ, generation, привязку и mode. В 3.5 каждый путь записи в строгую комнату дополнительно проверяет owner_id, owner_fence и срок аренды. Временная недоступность Hub и пустая комната оставляют писателем журнал | Клиент показывает ожидание или отказ. Отключённый клиент и сервер очереди не могут вернуть документ в snapshot либо заново применить старое намерение |
| journal, управляемое выключение либо restore | Выключение останавливает новый ввод, дожидается непрерывного префикса и checkpoint, под блокировками документа и головы повторно проверяет journal, поколение, head_seq = checkpoint_seq, checkpoint_version = state_version и отсутствие pending. Если после публикации появилась новая позиция, требуется новый checkpoint. Успешный переход закрывает старую голову и в той же транзакции повышает epoch и state_version. Restore берёт исторический payload/состояние, выбирает допустимый текущим владельцем режим и всегда открывает новое поколение. В старую комнату запись закрывается | Старые токены, отложенные envelope, intent, outbox и последняя попытка прежнего owner получают отказ при записи в новое поколение. Отзыв/восстановление не зависит от присутствия браузера |

Режим нельзя задавать в полном PUT содержимого либо подсказывать из JSON модели. `DocumentOperations::collaborationSession` сначала оценивает доступ и выбирает драйвер; приглашение читателю проверяется без запуска перехода. Зарегистрировать переход в публичном каталоге операций Documents; активный драйвер подтверждает совместимый seed и правила сессии. В эталонном стенде сделать тесты `tests/State/DocumentWriteModeTest.php` и `tests/Concurrency/DocumentWriteModeRaceTest.php` под Documents, а при установленном закрытом модуле — `tests/Collaboration/WriteModeAdmissionTest.php` под Collaboration. Среди обязательных исходов два конкурирующих входа в одну комнату и попытка автономного HTTP-клиента записать сохранённый JSON сразу после успешного перехода.

## 3.3 и 4.2. Один атомарный вызов владельца Documents

Контракт закрытой стороны и размещение `SingleTextOwner` зафиксированы в [карте AI](ai.md). Новые публичные файлы в `packages/documents/src/` — `Contracts/AtomicDocumentMutation.php`, `Contracts/LockedDocumentMutation.php` и `Data/Documents/DocumentMutationState.php`. В `Actions/Documents/` создать `RunAtomicDocumentMutation.php` и внутренний `LockedMutation.php`; связать контракт в существующем `Providers/BindingsRegistrar.php`. Имена и граница вызова одинаковы для одиночного текстового адаптера и команды частного Sheets. Этот порт получает уже удостоверенный `Vaulter\Drive\Operations\DriveContext`. Ссылка на scoped-объект теряет силу при выходе из callback.

```php
// AtomicDocumentMutation
/** @template TResult
 *  @param Closure(LockedDocumentMutation):TResult $operation
 *  @return TResult
 */
public function run(DriveContext $context, int|string $nodeId, Closure $operation): mixed;

// LockedDocumentMutation
public function snapshot(): DocumentMutationState;
public function replace(DocumentContent $content, int $expectedStateVersion): DocumentMutationState;
public function connection(): \Illuminate\Database\Connection; // соединение текущей транзакции
```

`DocumentMutationState` — неизменяемое значение с `nodeId`, внутренним `documentId` (`v_documents.id`, нужен адаптеру для своего FK в той же транзакции), `type`, `schemaVersion`, `generation`, `position`, `writeMode` (snapshot/journal), nullable `protocol`, `pending` (есть незакрытый pending fence) и типизированным `DocumentContent $content`. Для одиночной записи generation отображается на `collab_epoch`, position — на `state_version`. Конструктор отвергает счётчик больше 2^53−1 до выдачи маркера. На границе с клиентом PHP DTO сериализует закрытый адаптер SDK.

**Callback выполняется один или несколько раз.** `VaulterDatabase::transaction` повторяет весь callback после 40001/40P01, по умолчанию до 3 попыток (`packages/core/src/Database/VaulterDatabase.php`). Поэтому каждая попытка заново читает `snapshot()`, пишет только через `connection()` и не выполняет внешних эффектов. `run()` вызывается только на внешнем уровне транзакции. Scoped-объект закрывается при выходе из callback, в том числе по исключению.

**Образец** → `plan/examples/reference/atomic-mutation/` (порты, `RunAtomicDocumentMutation::lock`, `LockedMutation::replace`, `SingleTextOwner::decideLocked`, `OwnerRoutes`; таблица переноса в README) → `bash plan/checks/atomic-mutation/run.sh` → код 0, 30 строк `OK`, мутанты `mode_first` и `authorize_before_lock` различены.

1. Операцию зарегистрировать в `DocumentsOperationPolicies` и через `OperationRunner` открыть одну транзакцию Vaulter. Порядок фиксирован: T (`lockAggregateShared('drives')`, `DriveLifecycle::assertWritable`) → N (`TreeGuard::lock`, FOR UPDATE узла) → **решение Edit на заблокированном узле** → D (`lockForNode`). T, N и D уже даёт `DocumentWriteLock::acquire()`; проверку Edit добавить сразу после неё отдельным запросом на том же соединении, без мемоизированного решения. Действующий `DocumentOperations::writeContent` решает Edit **до** транзакции. В образце этот порядок воспроизведён мутантом `authorize_before_lock`: он записывает после зафиксированного отзыва. Предварительная проверка остаётся как ранний отказ, решающей становится проверка под блокировкой. `RevokeNodeAccessAction` блокирует строку своего узла, поэтому отзыв на самом документе строго упорядочен с записью. Отзыв на предке не берёт N документа. В READ COMMITTED проверка под N видит каждый отзыв, зафиксированный до неё, а более поздний отзыв линеаризуется после записи. Это допустимо. Отказ на любом из этих шагов (нет узла, чужой диск, корзина, не документ, нет права) выглядит одинаково: `resource_unavailable`. Повторное чтение квитанции через status проверяет View отдельно, без блокировок записи.
2. Закрытый адаптер внутри callback действует в таком порядке. (а) Найти исход по ключу или по `proposal_id`. Если исход есть, сверить fingerprint и вернуть его **без** проверки режима, поколения и схемы: квитанция остаётся у выдавшего её владельца, даже если документ уже перешёл в journal. (б) Если исхода нет, проверить срок, `writeMode` + поколение (`generation_changed`), тип + схему (`schema_changed`) и цель (`precondition_failed`). Отказ записать как durable `rejected` без `replace`. (в) Построить новое содержимое из свежего снимка и вызвать `replace` один раз. При настоящей коллаборации `replace` отказывается от одиночной записи. Поддерживаемый тип, режим, pending fence и expectedVersion проверяются у владельца. Повтор логической команды с существующей квитанцией завершается без вызова `replace`.
3. `LockedMutation::replace` использует `ContentDecoder`, `DocumentStateWriter::write`, штатную запись доменного события и те же ограничения на размер, что `UpdateDocumentContentAction`. Перенести их общее внутреннее действие в `Actions/Documents/WriteLockedDocumentContent.php`, вызываемое обоими путями. Действующий публичный HTTP autosave по-прежнему использует исходные ETag, обработку пустой/неизменённой записи и свою политику идемпотентности. Эффективное сохранение повышает версию один раз. При принятом намерении с содержимым без изменений квитанция может ссылаться на уже существующую позицию.
4. До возврата из того же callback адаптер сохраняет исход, доказательство и необходимое событие доставки на текущем подключении Vaulter. Для текста физическая таблица `v_ai_text_commands` принадлежит закрытому `ai-documents` и ставится рядом с владельцем документа; название учитывает настраиваемый префикс Vaulter. Для Sheets аналогичные таблицы принадлежат Sheets. Отказ до фиксации откатывает и контент, и запись успеха. Окончательное доменное отклонение записывается как отказ без применения изменения. Сетевой вызов, расчёт LLM или запуск Node внутри транзакции исключены. Для удалённого владельца хост отправляет одно удостоверенное намерение до входа в эту транзакцию; ответ об успехе выходит только после commit.
5. Для собственно книги v2 создать маркер `Contracts/RequiresCommandWrite.php` (marker interface) и доменную ошибку `Exceptions/DocumentCommandRequiredException.php`. В обычном `UpdateDocumentContentAction` проверять маркер типа под блокировкой перед записью, вернуть 409 `document_command_required` в error catalog/lang/HTTP. Проверка распространяется и на обычный PHP-вход полной замены, который вызывает это действие. Для специализированного writer зарегистрированный пакет вызывает порт прямо. На чистой установке профиль закрытой книги v2 регистрирует только свой тип. Эталонный снимок v1 служит входом для проверки явно поддержанного формата. Восстановление использует `RestoreDocumentRevisionAction`, увеличивает поколение и ставит задачу перестроить производные таблицы.

Для проверки атомарного отката использовать тестовую таблицу в том же подключении; исключение после вставки квитанции оставляет прежнее содержимое и отсутствие квитанции. Перенести сценарии B и C из `plan/checks/atomic-mutation/scenario.php`: отзыв держит N, писатель ждёт (барьер `pg_blocking_pids`) и получает отказ; две попытки с одним ключом, при commit и при rollback первой. Сценарий D (серверная ошибка 40001 внутри callback) переносится в `AtomicDocumentMutationTest`. Внешний PHP-процесс правит соседний абзац между prepare и commit; его правка переживает замену. Политики и интерфейс проверяют `composer php-api`, контрактные снапшоты Documents и `scripts/t sqlite -p documents`. Изменение `409` отражается в `src/Errors/{DocumentsErrorCode,DocumentsProblemDefinitions}.php`, соответствующих файлах `resources/lang/`, `resources/contracts/error-codes.json` и корневом OpenAPI. Проверить независимую одиночную установку Docs без закрытых пакетов.

Коды для публичных PHP/HTTP-операций генерируются по текущей системе пакета. Закрытый адаптер отображает доменные ошибки в коды SDK: недоступный узел → `resource_unavailable`, изменившаяся цель → `precondition_failed`, новое поколение → `generation_changed`, несовместимая схема → `schema_changed`. Для своей политики обычный HTTP PUT продолжает возвращать существующий `document_state_mismatch` при 412. [Коды и действия клиента](../agent-sdk.md)

Аренда убитого процесса не снимается: новый писатель получает следующий fence только после её срока по часам БД. ### Внутренние сообщения владельца комнаты для 3.5

Новые операции в приватном `openapi/hub.yaml` и `routes/collaboration.php` размещаются под существующим префиксом `collaboration/hub/`. Предлагаемые имена относительных POST-путей — `ownership/acquire`, `ownership/renew`, `commands/next`, `commands/settle`. Последний принимает тег `commit` либо `reject`, ID зарегистрированного намерения, поколение, fence и ожидаемый head. Для commit передаётся упорядоченный список бинарных обновлений + update ID + hash и проверяемый результат адаптера. При reject разрешён доменный код без применённых байтов. Авторитетный PHP проверяет lease, контекст намерения, реальное право и предусловия. Пустой ответ next означает отсутствие готовой работы. Если используется polling вместо push, задание после разрыва остаётся running, новый владелец повторяет подготовку на подтверждённой основе. Уже committed/rejected команда получает прежний исход после повторной авторизации.

Ответ commit содержит receipt_id, generation, base_seq, from_seq и to_seq. Hub применяет к комнате не свой буфер, а байты, прочитанные операцией `load` в интервале (applied_seq, to_seq]. Пустой список байтов фиксирует команду без обновления (`from_seq` NULL, `to_seq = base_seq`), как допускает DDL. Событие outbox несёт позицию. Доставщик может приложить байты, но комната сверяет их хеш с записью журнала той же позиции. Позиция не выше applied_seq с тем же хешем — повтор, с другим хешем — отказ. Позиция выше applied_seq+1 запускает догон по журналу. Событие другого поколения не меняет комнату. Проверка lease выполняется после проверки состояния команды: устаревший владелец получает прежний исход уже завершённой команды, а новую запись не фиксирует.
