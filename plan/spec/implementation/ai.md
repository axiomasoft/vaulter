# Закрытый репозиторий vaulter-ai

Исполнитель работает в новом закрытом репозитории. Пути ниже отсчитываются от его корня. Все перечисленные файлы будущего репозитория требуется создать в соответствующем шаге. Уже существующие примеры и схемы находятся в Vaulter. Для первого вертикального среза выполнить шаги 3.2a–3.3e и запустить один сценарий на настоящем владельце документов до подключения модели. Отдельный процесс с локальным ключом модели входит в 3.4. [Входные сообщения, результаты и коды ошибок](../agent-sdk.md) · [Машиночитаемые примеры](../../examples/office-sdk.json)

## Устанавливаемые пакеты

Слева имя каталога под `packages/`. Каждый пакет поставляет `composer.json`, собственный `src/` и свои `tests/`. В столбце provider указан класс в корне соответствующего пространства имён и файл `src/<имя класса>.php`. Манифест объявляет `autoload.psr-4` и `extra.laravel.providers`. Публичный Vaulter и FlexCms не зависят от этих пакетов.

| Каталог и Composer-имя | Namespace и provider | Прямые зависимости и регистрация |
| --- | --- | --- |
| `core`, `axiomasoft/vaulter-ai-core` | `Vaulter\Ai\Core`, `OfficeServiceProvider` | Illuminate для контейнера, конфигурации, маршрутов, очереди и своей БД; валидатор JSON Schema Draft 2020-12 (`opis/json-schema`) и собственный канонизатор RFC 8785 `Protocol/ProposalDigest` (байты сверяются с `plan/examples/reference/proposal-digest/vectors.json`). `mmccook/php-json-canonicalization-scheme` 1.0.0 из экосистемы AgenTools расходится с JCS на 5 векторах (U+2028, 10.0, 1.5e20, 2^53+1), поэтому для digest не используется. В корне создать `composer.json` для разработки с path-репозиториями `packages/*`, dev-зависимостями Pest, Orchestra Testbench и PHPStan, `composer.lock`, `phpunit.xml.dist` с каталогами тестов шести пакетов, `phpstan.neon.dist` и `tests/Support/OfficeTestCase.php` для состава тестового хоста. Привязать зависимости внутри первого согласованного комплекта к одной версии пакетов. Для Vaulter и Sheets указать минимальный выпуск, уже содержащий используемый порт. Сначала локально собрать согласованные архивы зависимостей и проверить установку из них. Отсутствующий релиз нельзя заменить совместимым на бумаге диапазоном версий. Исходный профиль Vaulter использует PHP 8.4 и Laravel 13. Исходный пример Botkit для первого исполнителя закрепляет `laravel/ai v0.6.8`. В тестовом комплекте записать именно проверенные lock/digest и платформу. [Процессы автономного стенда](processes.md)

`packages/core/resources/contracts/office-v1.schema.json` — копия утверждённой схемы для загрузки в рантайме; `tests/Fixtures/office-sdk.json` — тестовые обмены, `tests/Fixtures/provenance.json` — исходный commit Vaulter, относительный путь, SHA-256 каждого файла. При начальном переносе скопировать [схему](../schemas/office-v1.schema.json) и [примеры](../../examples/office-sdk.json) без редактирования содержимого. Изменения протокола впоследствии выпускает AI Core. Проверка синхронизации сравнивает SHA исходного комплекта. Потребитель тестирует тот же контракт из архива и своего lock. `clients/python/pyproject.toml`, `clients/python/vaulter_office/{__init__.py,client.py}`, `clients/python/tests/test_wire.py` — тонкий клиент stdlib и его тесты. Для внешней интеграции достаточно одного авторизованного POST.

## Порядок реализации и проверки

Миграции, физические поля, типы, связи, индексы, сроки хранения и окна восстановления заданы в [словаре БД AI](../database/ai.md). `CORE` обозначает соединение журнала офисных заданий. `OWNER` — соединение Vaulter владельца ресурса. В первом стенде обе роли используют одну базу. Второй прогон поднимает отдельный процесс внешнего клиента с HTTP к владельцу. Проверку согласия, необходимую непосредственно при записи, обслуживает локальная авторитетная запись у владельца. Если задания живут на другом соединении, их статус вычисляется по квитанции владельца. SQL-транзакции между владельцами не объединяются.

| Шаг | Что меняет исполнитель | Независимая проверка |
| --- | --- | --- |
| 3.2a. Форма сообщения | Создать core composer, provider, конфиг и Protocol/Data по таблице. PHP и HTTP принимают один DTO; HTTP не принимает actor, policy или approval из JSON. Клиент получает ровно один из result/error |

| 3.3a. Подготовка | Собрать Prepare/ReplaceExact/ProposalDigest. Два вхождения (включая перекрывающиеся), токен неполного постраничного чтения, смешанное форматирование или потерянный ID отклоняются до записи. Если lease истёк и CAS не прошёл, worker ничего не пишет в CORE, в том числе отказ | `ProposalDecisionRaceTest`: два конкурирующих решения P оставляют одно решение и один dispatch, Q остаётся pending. | 3.3c. Изменение у владельца | SingleTextOwner использует `AtomicDocumentMutation::run(DriveContext, $nodeId, Closure $operation): mixed` (commit #2). Порт уже держит T → N → Edit → D. В callback порядок такой: (1) исход по ключу/proposal_id → вернуть его без проверки режима; (2) срок, режим + поколение, тип + схема, цель → durable `rejected` без replace; (3) ТОЛЬКО нужная замена в свежем DocumentContent → `replace($content, snapshot()->position)` → строка `v_ai_text_commands`, evidence, outbox через `LockedDocumentMutation::connection()`. Callback может повториться после 40001/40P01, поэтому всё выводится из snapshot. Наружу результат выходит только после commit. Отказ записывается только здесь: под D после (1). Отказ, вычисленный вне callback (сбой транспорта, timeout, устаревший снимок worker'а), не сохраняется. [Образец](../../examples/reference/atomic-mutation/README.md) | `OwnerTransactionTest`: обрыв после replace до квитанции откатывает оба изменения. Обрыв после commit до отправки не создаёт второго эффекта. При независимой правке соседнего абзаца сохраняются обе правки; изменённый целевой контекст получает precondition_failed. Писатель выбирается при prepare по `DocumentMutationState.writeMode` актуальной головы владельца: `snapshot` → SingleTextOwner, `journal` → проверенный live-адаптер. Выбор запечатывается в план (`writer`) и при первом commit копируется в `v_ai_owner_routes.owner_key`. Status и повторный commit идут к этому владельцу, даже если режим документа с тех пор сменился. Только так повтор после потери ответа и последующего snapshot→journal возвращает исходную квитанцию; сценарий A и мутант `mode_first` в `plan/checks/atomic-mutation`. Наличие `collab_protocol` само по себе режим не определяет. В snapshot обычное сохранение меняет позицию, сохраняя поколение. Смену режима или restore сериализует домен под теми же блокировками. Проверить ситуацию: пользователь изменил соседний блок через autosave; ещё действующее предложение успешно применимо к сохранившейся цели. Если у ключа ещё нет исхода, а режим между prepare и commit сменился, владелец под блокировкой сверяет запечатанные режим и поколение и записывает durable `rejected/generation_changed`. Для конкурентной записи документ уже заблокирован обычным доменным путём T→N→D, после чего читается/добавляется исход собственного ключа. Все писатели этого домена используют тот же порядок. При двух повторах под одной областью сверяется fingerprint и выполняется обычная проверка чтения квитанции. При конфликте на уже изменённой цели фиксировать `rejected` как собственный долговечный исход без частичного текста. Операционный сбой оставляет известное намерение `running`; его может безопасно продолжить следующий worker. После перезапуска при неизвестном исходе первым действием служит status, повторный commit использует прежний ключ. Наружная транзакция AI не оборачивает сетевой вызов.
