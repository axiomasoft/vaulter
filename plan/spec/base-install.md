# Контракт базовой поставки документов

Пользователь открывает документ в своём диске, редактирует его, сохраняет и после перезагрузки видит сохранённую правку. Два открытых экземпляра обнаруживают конфликт. Читатель может открыть документ. Это объём редактора FlexCms для первой поставки. Доступные исходники получают клиенты FlexCms. Оплачиваемая совместная работа, книги и AI подключаются другими продуктами отдельно. Исходная версия Vaulter для проверок ниже — `b230f6e27`.

## Что ставит каждый потребитель

| Потребитель | Устанавливает | Что проверять отдельно |
| --- | --- | --- |
| FlexCms | Метапакет `axiomasoft/vaulter` с Core, Media, Drive и Documents, фронтенд `@vaulter/vue`, Vue и редактор Tiptap хоста | У пустого приложения есть подходящий guard, доступ к дистрибутивам зависимостей и права на запись для владельца. В установленных пакетах есть только общедоступная реализация. Аутентификация в приватных реестрах, WebSocket и ключ LLM для этой установки не нужны |
| Закрытый FlexCrm с коллаборацией | Тот же базовый релиз, `axiomasoft/vaulter-collaboration`, `@vaulter/vue-collaboration`, образ `vaulter-collaboration-hub` | Совместимая тройка PHP/JS/hub отдельно проходит тест совместного редактирования и восстановления. По REST-сценарию FlexCms нельзя подтвердить работу этой тройки |
| FlexCrm или Edufy с таблицами, AI | Согласованные базовые пакеты плюс выбранные закрытые пакеты из соответствующих репозиториев | Для Sheets — регистрация типа и viewer, свои миграции и повторное открытие книги. Для AI — выбранный хостом агент, ограниченные права и доступ к документу через SDK. Edufy определяет свой набор пакетов |

[Метапакет](../../packages/vaulter/composer.json) задаёт состав базы. В [манифесте поставки](../../release/packages.json) у отдельных PHP- и npm-пакетов свои каналы. Например, Filament и Webhooks присутствуют в реестре доступных пакетов, однако метапакет их не устанавливает. Клиент FlexCms получает исходники базовых пакетов через разрешённый ему канал. Если историю общего Git-репозитория предполагается открывать клиентам, сначала проверить по всем доступным им веткам и тегам, что в них не попадают исходники закрытых модулей. Способ продажи хоста не определяет видимость истории его зависимостей.

## Владение кодом и схемой

| Участок | Что сохраняем в базе | Что проверяет исполнитель |
| --- | --- | --- |
| Core, Drive, Media | Модули, ACL, узлы и диски, файлы и их существующие операции. Используем фактический permission driver хоста | Пользователь запрашивает узел через API, получает индивидуальные `abilities`. Сервер проверяет доступ и при прямой записи в документ |
| Documents | `vaulter/rich-text` по умолчанию и `vaulter/markdown`. Храним текущее состояние, `schema_version`, `state_version`, ревизии и комментарии согласно действующим контрактам. Текущие HTML/Markdown-экспортёры, если применимы к типу, продолжают работать | Таблицы документов, ревизий и комментариев создаёт сам модуль. Тест на пустой БД проверяет также зависимости от Drive и Media и корректную ссылку на текущую ревизию. Поддержку импорта/экспорта DOCX в объём этой поставки не включали |
| Общий API расширений | Реестр типов, разрешённые кодеки, точки подключения viewer и адаптера коллаборации доступны внешним пакетам | В чистой установке остаётся валидный fallback для неизвестного viewer. Встроенная таблица внутри текстового документа сохраняет своё представление `table/tableRow/tableCell/tableHeader` |
| Отдельный репозиторий Sheets | Забирает реализацию `SpreadsheetDocumentType`, компонент `VaulterSpreadsheet`, регистрацию `vaulter/univer`, специфичные тесты и примеры | Сначала проверить ту же книгу в закрытом потребителе. Затем убрать встроенный класс, экспорт, регистрацию и ссылки на эту реализацию из поставляемых базовых исходников, деклараций и bundle. Две сборки проверяются совместно. Порядок изменений приведён в [спецификации Sheets](spreadsheets.md) |

Исходная схема создаётся установленными модулями на пустой БД с настройками хоста. При изменении состава сохраняем установочные определения и необходимые ограничения. Перенос прежних пользовательских записей не требуется. Общие колонки Docs, которые задействует опциональный протокол совместной работы, рассматриваем вместе с точками подключения протоколов. Само наличие таких колонок не требует установки hub. Таблицы собственно Sheets, AI и хранилище совместной работы принадлежат установившим их модулям. На структуру конкретных таблиц опирается владелец модуля. Закрытый AI SDK использует публичный прикладной порт Documents для чтения и изменения документа от имени пользователя. [Модульная схема документов](../../packages/documents/src/Schema/DocumentsSchema.php) · [Регистрация встроенных типов и экспортёров](../../packages/documents/config/vaulter-documents.php).

## Редактор FlexCms

Хост получает `node` с `presentation` и `abilities` через `client.nodes.get(id)`, устанавливает `VaulterPlugin` и монтирует Tiptap в default slot `VaulterDocumentNode`. Слот передаёт `content`, `readonly`, `setContent`, `flush` и `conflict`. Хост загружает полученный JSON в редактор, преобразует изменения через `editor.getJSON()`, передаёт их в `setContent` и позволяет сохранить через `flush` или дождаться autosave. Для читателя Tiptap получает `editable: false`. При конфликте показываем его состояние и сохраняем локальный черновик до решения пользователя. При повторном открытии читаем состояние с сервера. [Компонент](../../packages/vue/src/components/VaulterDocumentNode.vue) · [Клиент](../../packages/vue/src/api/client.ts) · [Пример формы слота и проверки конфликтов](../../packages/vue/tests/document-node.test.ts).

В тестовом потребителе пользователь начинает со списка. Обработчик `VaulterDrive @open-node` получает выбранный узел и открывает страницу или окно с `VaulterDocumentNode` и его слотом. Если хост уже использует `VaulterViewer`, зарегистрировать на ключ `vaulter/tiptap` компонент хоста, который внутри монтирует тот же слот; dynamic component в стандартном viewer получает props и не принимает пользовательский слот через родителя. Для rich text и Markdown выбрать соответствующий `presentation.viewer.props.preset`. В приёмке 1.3 пройти оба типа из списка Drive. Локальный исходный стенд открывает конкретный документ по ID. [Событие открытия](../../packages/vue/src/components/VaulterDrive.vue) · [Стандартный viewer](../../packages/vue/src/viewers/VaulterViewer.vue)

Точный состав сериализуемых узлов, marks и атрибутов задаёт [TipTapSchema](../../packages/documents/src/Content/TipTap/TipTapSchema.php). Эталон rich text для реализации включает заголовок, абзац, ссылку с атрибутами Tiptap, нумерованный список, выделение, изображение и небольшую встроенную таблицу. Для Markdown используем допустимое подмножество. Для обоих типов в браузерном тесте нужно сравнить сериализованное дерево до сохранения и после загрузки, включая настройки расширений хоста для изображений и таблиц. Существование типа на сервере само по себе не подтверждает его полное отображение в редакторе. Панель инструментов, импорт офисных форматов и набор коммерческих расширений не входят в этот контрольный пример.

## Стенд исходной версии

Зафиксированный состав — PHP 8.4, Composer 2, Laravel 13, SQLite, Node 26 и Chromium. В тестовом хосте укажите установленный guard и middleware для маршрутов, затем проверьте `vaulter:doctor --json`. Для сравнения упаковки зафиксируйте исходный экспорт `VaulterSpreadsheet` и зависимости публичного архива.

Сценарий [run.sh](../checks/flexcms/run.sh) собирает ZIP пяти Vaulter и трёх Packman из выбранных Git-ревизий, устанавливает их в новый Laravel-хост, создаёт SQLite, проверяет API, собирает публичный Vue-пакет и запускает две вкладки браузера. Результирующие `composer.lock`, `package-lock.json`, `doctor.json`, списки зависимостей и лог HTTP-сервера лежат в отдельном временном каталоге. Путь выводится при завершении. Слушающий только loopback сервер останавливается автоматически. В `PATH` нужны Bash, Git, Python 3, curl, PHP с SQLite и Zip, Composer 2, Node 26 и npm. Во время первого прогона требуется загрузка публичных зависимостей и Chromium. Рядом нужен checkout Packman с ревизией `a5a5442`, либо путь к нему в `PACKMAN_DIR`. Сборка Vaulter использует его штатный release-манифест, для Packman готовятся локальные входные ZIP.

```bash
bash plan/checks/flexcms/run.sh
```

Для уже установленного Chrome можно указать `BROWSER_BIN=/usr/bin/google-chrome`. Скрипт создаёт чистый Composer home и npm user config, собирает архивы без выдачи приватных токенов и указывает временный SQLite-файл как единственную БД тестового приложения. Признаки успешного завершения — `CMS-REST-PASS`, `CMS-BROWSER-PASS` и код 0. [Фикстура и проверки HTTP](../checks/flexcms/host.php) · [Tiptap в слоте хоста](../checks/flexcms/editor.mjs) · [Две вкладки и читатель](../checks/flexcms/browser.mjs).

### Фикстура прав и последовательность запросов

В чистом хосте создать двух пользователей его модели. Через PHP-фасад `Vaulter::drive($owner)->asSystem('create fixture')` подготовить диск. В корне выдать `Subject::ofModel($owner)` роль `RoleRegistry::OWNER`, второму пользователю — `RoleRegistry::READER` через `access()->grant($drive->root(), new GrantInput(subject: ..., role: ...))`. Системный контекст применяется только при подготовке диска. Запросы ниже аутентифицируются как обычные пользователи. В каждом шаге — `Accept: application/json`, при записи — JSON. Базовый префикс — `/api/vaulter/v1`. Сохранять возвращённый ETag целиком, включая кавычки.

| Кто и запрос | Тело или условие | Ожидаемый ответ |
| --- | --- | --- |
| Владелец, POST `/drives/{driveId}/documents` | `{"name":"Spec","content":{"type":"doc","content":[{"type":"paragraph","content":[{"type":"text","text":"Initial"}]}]}}` | 201, `data.id` нового узла |
| Владелец, GET `/documents/{id}/content` в A и B | Оба читают один снимок | 200, `Initial`, версия 1, ETag A = ETag B |
| A, PUT на тот же URL | Объект `{"content":...}` с текстом `New` и заголовок `If-Match` из A | 200, версия 2 и новый ETag |
| B, PUT на тот же URL | Снимок с текстом `Stale`, `If-Match` из B | 412, `document_state_mismatch`. В браузере виден конфликт, пользователю доступен локальный текст |
| Читатель, GET, затем PUT на тот же URL | GET возвращает актуальный ETag. Попытка записи с этим тегом | 200, затем 403 `permission_denied` |
| Владелец, новое открытие | Загрузить узел и содержимое в новом экземпляре клиента | 200, в хранилище ровно текст `New`, версия 2 |

За существующие детали API отвечает [DocumentNodeApiTest](../../packages/documents/tests/Document/DocumentNodeApiTest.php), включая отдельный цикл ревизии, восстановления и экспорта. Сценарий чистого потребителя расширяет [consumer-smoke.sh](../../scripts/release/consumer-smoke.sh). Сценарий сохраняет commit обоих исходников, lock-файлы, digest архивов и перечень таблиц в каталоге прогона. Перед выдачей релиза те же проверки нужно связать с реально распространяемыми сборками. Для release-кандидата повторить проверку через канал, который будет доступен клиенту FlexCms. [Штатный сборщик](../../scripts/release/build-artifacts.php). Прогон по исходным ZIP отвечает на вопрос о работоспособности сегодняшнего кода.

## Приёмка итерации 1

1. Сохранены возможности прежнего редактора на корпусе rich text и Markdown. Состояние в БД и браузере совпало после повторного открытия. Владелец может сохранить, читатель видит read-only и получает отказ при прямой записи, вторая вкладка сохраняет локальный черновик при 412.
2. Чистые Composer- и npm-потребители собираются по своим lock-файлам из реально поставляемых базовых артефактов. Перечислены прямые и транзитивные зависимости, провайдеры, зарегистрированные типы, фактические таблицы пустой установки и публичные JS-экспорты. Установка и HTTP-сценарий повторены на поддерживаемой СУБД пакетного стенда.
3. Архивы базы содержат общие контракты расширения без закрытой реализации. Доступа клиента к исходникам платных дополнений нет. Страница редактора загружается и сохраняет при отсутствии hub, Sheets и AI. Запуск ни одного из этих сервисов не требуется при сборке потребителя.
4. Парная проверка «база + закрытый Sheets» подтвердила прежний табличный сценарий после переноса. В чистом базовом потребителе можно сохранить обычную текстовую таблицу Tiptap. Состояние каждого пункта подтверждено своим прогоном и независимой установкой из архивов.
