# 3. SDK и одиночный текст

[Файлы Documents и Hub](../spec/implementation/vaulter.md) · [Файлы AI](../spec/implementation/ai.md) · [Схема сообщений](../spec/schemas/office-v1.schema.json) · [Договор и обмены](../examples/office-sdk.json).

### 3.1 Адресуемые блоки

**После** — 1.0.

1. Для абзаца и заголовка rich text ввести необязательный атрибут `attrs.blockId`. Синхронизировать PHP, расширение Tiptap, Hub schema и проверки сериализации. В wire поле называется `block_id`.
2. При split первая часть сохраняет ID, вторая получает новый. При join сохраняется ID первого блока; при paste как копировании каждый вставленный блок получает новый ID. У однозначного перемещения ID сохраняется. При restore действуют ID восстановленной ревизии и новое поколение.
3. При создании и авторизованной нормализации присвоить и проверить уникальность ID в документе. Две конкурирующие нормализации проходят через CAS. GET пользователя или SDK не изменяет документ.

- **3.1-A** Повторное открытие сохраняет ID, копирование/удаление/restore дают указанные исходы. Reader не изменяет ETag и state_version. Повтор нормализации не создаёт вторую версию.
- **3.1-B** `{"type":"text","marks":[{"type":"bold"}],"text":"15"}` под блоком p42 сохраняет оформление в PHP и браузере. Markdown и исходный одиночный сценарий по-прежнему проходят.

### 3.2 Ядро SDK и чтение

**После** — 0.2, 3.1.

1. Создать в закрытом AI ядро, transport PHP/HTTP и регистрацию адаптеров. Доверенный контекст строит сервер. Установить текстовые проекции у владельца. Реализовать `office.search/read/describe`, версии, лимиты и курсоры по [контракту](../spec/agent-sdk.md).
2. По фразе «срок оплаты» обнаружить договор, p42 и p71; вернуть только запрошенные позиции. Уточнение главы, поиск и чтение проверяют ACL перед выдачей результата.
3. Проверить три границы HTTP: неизвестное имя даёт транспортный 400 invalid_request, известное имя с неподдерживаемой версией даёт ошибку v1 unsupported_version, неверный input известной операции даёт invalid_input. Воспроизвести задержку проектора, пропуск события, повтор и restore до публикации. Для чтения с `after_receipt` тестовая фикстура владельца заранее сохраняет квитанцию с известной позицией. В 3.3 повторить чтение с квитанцией настоящей записи. Сверять версии и содержимое по [протоколу хранения](../spec/storage.md).

- **3.2-A** PHP и HTTP возвращают допустимые сообщения; другой tenant, отозванный пользователь и скрытая цель не раскрывают названия, сниппета или маркера.
- **3.2-B** Одна страница соответствует одной опубликованной версии, старая сборка не появляется после restore. Проверка чтения после квитанции возвращает свежие данные или документированный статус ожидания.

### 3.3 Подготовка, запись и проверка

**После** — 3.2.

1. Реализовать `text.replace_exact@1` и четыре операции `prepare/commit/status/verify`. Хост сохраняет ключ до commit. Сравниваются точное совпадение в нужном блоке, смысловой контекст, marks/attrs, согласованный digest, поколение и текущий доступ.
2. Закрытый адаптер вызывает доменный порт Documents в БД владельца. Содержание, версия и исход команды фиксируются атомарно. Задание на другой БД восстанавливает исход по тому же ключу.
3. Исполнить `text_success`, `text_conflict`, `lost_response`, `acl_revoked` с событиями из fixture, затем повторить через Python/HTTP. Исполнитель не читает SQL.
4. **Образец** → `plan/examples/reference/atomic-mutation/` → `Vaulter\Documents\Actions\Documents\RunAtomicDocumentMutation::run` и vaulter-ai `SingleTextOwner::decideLocked`, `OwnerRoutes`, `Operations\{Commit,Status}` → `bash plan/checks/atomic-mutation/run.sh` → код 0, 30 строк `OK`. Повтор после kill и snapshot→journal возвращает прежний receipt и маркер 3/29. Мутанты `mode_first` и `authorize_before_lock` дают неверный исход.

- **3.3-A** На момент фиксации p42 содержит «30» с исходным bold; соседняя правка p71 сохранена. Изменившееся условие или атрибут ссылки конфликтует без частичной замены.
- **3.3-B** После потери ответа повтор возвращает ту же квитанцию. Другой digest под тем же ключом отклоняется. Историческая и текущая проверка после дальнейшей человеческой правки имеют корректные независимые результаты.

**Образец** → `ProposalDigest::digest()` ([PHP](../examples/reference/proposal-digest/php/ProposalDigest.php), Node, Python-эталон `verify-fixtures.py::jcs`), `ReplaceExact`/`TextVerifier` ([ProseMirror](../examples/reference/text-replace/replace-exact.mjs) ↔ [PHP](../examples/reference/text-replace/replace_exact.php)) → `bash plan/checks/sdk/run.sh` → `OK area 4`: 16 JCS-векторов и 5 digest совпадают в трёх реализациях, mmccook 1.0.0 расходится ровно на 5 задокументированных векторах, 14 случаев правки и 3 commit-after совпадают в PM и PHP, `verify` даёт at_commit passed / current failed / at_commit passed, 8 неверных ответов, допустимых по схеме, отвергнуты.

### 3.4 Исполнители Laravel AI и AgenTools

**После** — 3.3.

1. В тестовом потребителе зарегистрировать изолированный профиль Laravel AI; в отдельной комплектации добавить AgenTools. Поставщик выбирает из разрешённых инструментов и получает краткий вывод. Ключ провайдера хранится в процессе агента.
2. Выполнить один сценарий под детерминированным провайдером, повторить после сбоя worker. Внешнему исполнителю доступен HTTP-порт. Предикаты записи повторно проверяет владелец. Прогон с настоящей моделью и стоимостью вести отдельной строкой при наличии тестового ключа.

- **3.4-A** С каждого адаптера получен один доменный эффект и проверяемая квитанция. При выключенном AgenTools базовый тест Laravel AI проходит; пользовательские инструкции не расширяют разрешения.

### 3.5 Атомарная команда в живой комнате

**После** — 2.2, 3.3.

1. Реализовать регистрацию намерения, аренду комнаты с fencing token, подготовку на копии Y.Doc и принятие байтов в БД владельца до их публикации. Все писатели и доставка в комнату согласуют один порядок.
2. После потери процесса воспроизвести сохранённые байты от checkpoint до подтверждённой позиции; следующая команда ждёт непрерывного префикса. Маршрут определяется `write_mode` под блокировкой головы. Одиночная запись в обход journal запрещена даже при недоступном Hub.
3. Пройти все варианты [A42](../examples/live-write.json). Составная правка в этой фикстуре проверяет атомарность внутреннего обработчика. Публичная команда v1 по-прежнему точечно заменяет один фрагмент.

**Образец** → `hub/src/room-sequencer.js` `createRoomSequencer` по [эталону](../examples/reference/live-write/room-sequencer.mjs) → `bash plan/checks/collaboration/live-write.sh` → SIGKILL после commit A42 до apply; новый процесс применяет те же байты один раз, одна квитанция, A43 на базе 42, отказ второго действия не меняет комнату; Hocuspocus 4.3.0 обходит барьер только через DirectConnection и Redis.

- **3.5-A** После падения между SQL commit и публикацией в комнате покупатель видит одну принятую правку агента и одну соседнюю человеческую правку. Старая аренда не фиксирует изменения после смены владельца.
- **3.5-B** Каждый из 11 независимых аварийных сценариев имеет наблюдаемый исход в SQL и в новом клиенте. До прохождения всех сценариев capability live commit отключена, одиночный адаптер продолжает работать. Автономный образец (`bash plan/checks/collaboration/live-write.sh`) проходит 7 из 11 с мутантом на каждый: `stale_owner`, `different_intent_same_key`, `partial_patch_failure`, `concurrent_duplicate` (барьер `pg_blocking_pids`), `generation_restored`, `late_delivery_after_restore`, `offline_target_edit_arrives_later` (якоря Yjs в evidence, `verify(current)`). Не пройдены и остаются приёмке пакета: `precondition_changed`, `edit_revoked`, `read_revoked` (права в образце не моделируются), `projection_behind`.
