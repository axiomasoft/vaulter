# Tiptap Pro: карта относительно плана Vaulter

Дата: 2026-11-21. Эта записка сопоставляет **текущий код и принятый план Vaulter**, а также задаёт проверяемые сценарии исследования. Она не утверждает, что закрытый сервер Tiptap реализован описанным здесь способом. Фактические результаты Cloud-прогонов должны ссылаться на отдельные обезличенные артефакты стенда.

Метки: **код** — проверено в checkout; **план** — требование, которое ещё нужно реализовать/принять; **эксперимент** — вопрос к исследуемому продукту; **предложение** — наша возможная независимая реализация.

В фазах 2/3 и контракте коллаборации нет полноценного собственного контракта comments, suggestion review/tracked changes или пользовательского snapshot compare. Наличие ревизий и агентского prepare/commit не закрывает эти три области.

## Матрица black-box экспериментов

Все документы стенда создаются с отдельным префиксом запуска. Два писателя A/B и читатель R используют независимые browser contexts. Для каждого сценария фиксируются версии пакетов, начальное содержимое, действия, события provider, очищенный сетевой trace, финальный JSON/Y.Doc и повторное чтение независимым клиентом C.

| ID | Действия | Что установить | Как это использовать в Vaulter |
| --- | --- | --- | --- |
| COL-01 | A/B вставляют текст в разные блоки и в одну позицию; C открывает документ | Сходимость, поле Y.Doc, границы updates, порядок provider events | Эталон UX и схема редактора; наша приёмка 2.1-B |
| COL-02 | Отключить сеть A, менять A/B, восстановить связь | Где хранится offline ввод, что теряется при reload; разница disconnect/reconnect и reload | Политика локальной очереди и предупреждение об неподтверждённом вводе |
| COL-03 | После индикации сохранения закрыть A/B; открыть C | Что именно можно подтвердить о повторном чтении | Наблюдаемость saved; не доказательство внутренних fsync/SQL транзакций Cloud |
| AUTH-01 | Проверить scope, expiry и неправильную подпись на собственном тестовом документе | Отказ при connect, изменение live session, refresh flow; коды/причины | Наш контракт короткоживущей сессии и поведения UI |
| AUTH-02 | R пытается вводить через editor command и напрямую через provider | Server-side защита записи, отделение чтения/комментариев/review | Приёмка прав не должна ограничиваться disabled toolbar |
| AUTH-03 | Отозвать право A при открытом соединении, затем послать новый update | Есть ли немедленный/периодический recheck, что видит клиент | Сравнение с нашим отзывом; граница «до/после commit» остаётся нашей |
| COM-01 | Выделить диапазон, создать thread/reply, resolve/reopen, удалить reply | Shape объектов, команды, канал HTTP/WS/Y.Doc, события | Самостоятельный контракт comments |
| COM-02 | B вставляет до/внутри/на границе выделения; удаляет весь target | Перемещение/расширение якоря; orphan/collapsed state | Политика собственного якоря, включая `assoc` на границах |
| COM-03 | Undo/redo, split/join, copy/paste, move блока с comment | Дублируется ли thread или только decoration; сохраняется ли ссылка | Правила копирования и жизненного цикла |
| COM-04 | A/B одновременно отвечают/редактируют/resolve один thread; A offline | Конфликты, версии, tombstones, права удаления | Команды comments должны иметь явные предикаты/дедупликацию |
| VER-01 | Изменить документ, дождаться/создать снимок, назвать его, перечитать историю | Auto/manual snapshots, metadata, pagination, triggers | Надстройка timeline над имеющимися revisions |
| VER-02 | Сравнить две версии с форматированием, ссылкой, списком и таблицей | Текстовый или структурный diff; границы изменений и атрибуция | Собственный diff должен хранить rich структуру |
| VER-03 | Восстановить V1 при открытой A, которая содержит новые/offline правки | Поведение старого клиента, якорей и истории; создаётся ли новый снимок | В Vaulter restore всё равно обязан сменить generation и оградить A |
| REV-01 | Включить tracking: вставить, удалить и заменить фрагмент; изменить mark/link | Представление предложений в JSON/Y.Doc, команды/события; преобразование замены | Спецификация собственного review data model |
| REV-02 | A создаёт change, B редактирует его диапазон и accept/reject | Привязка операции к актуальному документу, конфликты reviewer | Нельзя реализовать reject простым возвратом старого JSON всего документа |
| REV-03 | Параллельные accept/reject; повтор после потери ответа; bulk accept | Идемпотентность, terminal outcome, атомарность группы | Идентичность команд и проверка серверных прав |
| REV-04 | Undo/redo, paste rich text, таблица, code block, heading split, IME | Какие операции отслеживаются и как группируются | Приёмочный корпус собственного расширения |
| MIX-01 | Thread внутри удаляемого suggestion; затем accept/reject и restore | Связь comments/review/history; исчезновение/возврат якоря | Единая политика адресов, а не три несовместимых механизма |
| SCH-01 | A открывает документ с новым node/mark; B без этого extension | Ошибка, пауза, удаление неизвестного content; эффект на A/C | Защита schema parity и capability, особенно при отключении Pro |
| CMD-01 | Серверная правка при online A/B; повтор команды после потери ответа | Какие публичные APIs действительно доступны; итог и семантика повтора | Сравнение со своим 3.5; отсутствие дубля в одном прогоне не доказывает exactly-once |

Не использовать подмену read-only токена или обращение к чужим документам для «проверки» обхода прав. AUTH-тесты выполняются над собственными ресурсами и выданными им credentials.

## Как фиксировать обмены, чтобы вывод можно было проверить

Для HTTP записывать метод, путь без секретных query, status, название операции и схему очищенного тела. Для WS — направление, время относительно действия, тип/размер сообщения и декодируемые поля; бинарные фреймы декодировать штатными установленными OSS библиотеками соответствующих версий. Результат декодирования сопоставлять с JSON редактора и состоянием Y.Doc. Не объявлять неизвестный байтовый префикс «схемой сервера» по одной записи.

Наблюдаемые запросы позволяют описать контракт, но не показывают внутренние таблицы, транзакции, lease, репликацию, retention или способ выполнения запроса на сервере. Названия routes и minified методов также не доказывают архитектуру. Для гипотезы указывать минимум альтернативное объяснение и следующий различающий эксперимент.

Сырые HAR, WS auth frames, npm configuration, bearer/JWT и ключи держать в локальной исключённой папке. В артефакт исследования попадают отредактированные fixtures и counts/hashes; секреты в JSON bodies, query, WS auth и text snippets очищаются до сохранения публикуемых свидетельств.

## Возможные независимые реализации

Это **предложения для Vaulter**, а не реконструкция proprietary реализации Tiptap.

### Синхронизация и авторизация

Оставить Tiptap OSS editor с Yjs и собственным Hocuspocus Hub, PHP — владельцем ACL/журнала/квитанций. Собственная библиотека адаптирует editor commands к этому транспорту. Закрытые клиентские пакеты Tiptap не должны становиться частью основного runtime.

У Hocuspocus официально предусмотрены hooks для authentication, загрузки и хранения; это точки интеграции, а не готовое доказательство нашей durability-модели. Наши проверки append/recheck/fence и общий порядок в строгой комнате остаются обязательными. [Официальные hooks](https://tiptap.dev/docs/hocuspocus/server/hooks).

### Comments

Ввести собственные `thread_id`, `comment_id`, автора, состояния open/resolved/deleted и командные версии. Текст сообщения и автора сохраняет сервер с ACL. Для диапазона рассмотреть пару Yjs relative positions вместе с `generation`, `blockId` и fallback-цитатой. Это проектный вариант; выбранную семантику граней, удаления и restore нужно проверить отдельно. Yjs предоставляет relative positions, преобразование в absolute position и явный `null` при недоступной цели. [Y.RelativePosition](https://docs.yjs.dev/api/relative-positions).

Расположение discussion data в отдельном Y.Map или в SQL — отдельный выбор. При SQL + Yjs anchor требуется зафиксировать поколение/позицию, на которой создан якорь, и порядок публикации; иначе thread может ссылаться на ещё не сохранённое изменение. При хранении в Y.Doc нельзя доверять клиентскому author ID и считать скрытую UI-команду защитой от произвольного update. Awareness использовать для присутствия, не для постоянных comments.

### История и сравнение

Исторический payload хранить как неизменяемую revision вместе с schema и маркером состояния. Transport checkpoint решает восстановление журнала, пользовательская revision — историю; удаление сжатого хвоста не должно уничтожать обещанную историю. Restore проходит через владельца документа и открывает новое поколение согласно текущему плану.

Для compare сначала определить минимальный продуктовый корпус и строить структурный diff по нормализованным ProseMirror nodes/marks/attrs. Стабильные `blockId` помогают сопоставлению перемещённых блоков, но не решают автоматически diff внутри текста. Атрибуция авторам требует отдельной информации; её нельзя достоверно восстановить только из финального JSON.

### Tracked changes

Начать со своего небольшого контракта insertion/deletion/replacement и accept/reject. Хранить собственную идентичность изменения, автора, затронутую область, base marker и состояние. Рендерить review слой плагином/marks/decorations редактора; не переносить minified код Pro в новый пакет.

Выбор «удалённый текст остаётся в review-документе» против «удалённый текст хранится отдельно» меняет поиск, export, anchors, копирование и сериализацию. Это должно стать явным wire/storage решением. Accept/reject проверяет текущие права, поколение и целевое изменение под блокировкой, а затем использует тот же writer и command receipt. Две параллельные ревизии не должны перетирать соседние человеческие изменения.

Сначала ограничить поддерживаемые операции проверенным корпусом. Не обещать корректность для tables, nested structures, arbitrary pasted marks и IME по одному успешному сценарию обычного текста.

### Schema и граница совместимости

При собственной реализации зарегистрировать одинаковые nodes/marks/attrs во всех писателях, преобразователях и исторических readers. Не удалять Pro extension из редактора поверх уже записанных proprietary nodes, предварительно не определив миграцию и read-only fallback.

Текущая документация Tiptap прямо различает обычное удаление неописанного schema content и режим `enableContentCheck`, который при несовместимости приостанавливает запись. В ней приведены минимальные версии для этой защиты. Это аргумент добавить SCH-01 в наш корпус; применимость проверяется на фактически зафиксированных npm-версиях стенда. [Collaboration: invalid schema handling](https://tiptap.dev/docs/editor/extensions/functionality/collaboration#content-that-doesnt-fit-the-schema).

## Порядок переноса результатов в основной план

1. Получить воспроизводимые COL/AUTH/SCH fixtures и описать фактически доступный профиль аккаунта. Недоступную entitlement-функцию помечать как непроверенную.
2. По COM/VER/REV/MIX составить отдельные минимальные контракты с точными примерами до/после, правами и исходами конкуренции.
3. Согласовать, какие из этих функций нужны первой поставке. Само наличие функции у Tiptap не делает её обязательной для Vaulter.
4. Затем добавить задачи и приёмку в основной `plan/`, сохраняя уже выбранные поколения, journal owner и идемпотентные команды. Этот документ основной план не изменяет.
5. Собственную реализацию проверять теми же внешними fixtures на независимом стенде. Совпадение интерфейса и наблюдаемого результата — цель совместимости; внутренняя схема и алгоритм могут отличаться.

На момент создания этой записки Cloud-прогоны автором записки не выполнялись. Приведённые IDs — программа испытаний, а не список пройденных тестов. JS/TS symbolic overview был недоступен в Serena (активен только PHP LSP); PHP исследован символами, конкретные участки JS/TS прочитаны после этой ошибки без изменения кода.
