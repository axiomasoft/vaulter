# Backend собственной реализации Tiptap Pro для Vaulter

Проект от 2026-11-21, сверенный с checkout `06576b393`. Первый выпуск — согласованная замена срока в одиночном договоре. Text и Sheets используют Drive, общий конверт SDK и форму квитанции. Documents хранит rich text, Collaboration ведёт журнал Yjs, Sheets владеет книгой, её вычислителем и доказательством формул. Хост определяет политику и профиль. База FlexCms сохраняет самостоятельное редактирование на Tiptap OSS и штатный REST. Этапы и команды приёмки находятся в [development-plan.md](development-plan.md) и [acceptance-matrix.md](acceptance-matrix.md).

## 2. P/Q и модель разрешений

Хост авторизует решение. Владелец ресурса авторизует запись. Worker восстанавливает исходного инициатора и проект по сохранённой записи хоста, а рецензент остаётся отдельным субъектом аудита. В первом профиле на одном PostgreSQL требуется действующее право согласования рецензента и в момент commit. Отозванное согласование блокирует исполнение, сохраняя факт уже принятого решения. Для отдельного процесса доступ к владельцу осуществляется через авторизованный порт. Если хост использует внешнюю политику, проверяемую только по сети, строгий профиль требует авторитетной версии прав в БД владельца с оговорённой границей отзыва; кэшированный allow не даёт такой гарантии. [H2/H3](../spec/host-integrations.md)

| Операция | Проверка в доверенной области |
| --- | --- |
| Search/read/describe/prepare | View; фильтры по проекту и профилю до выдачи; для подготовки пишущей команды также доступность команды и Edit. Read token фиксирует фрагмент, маркер и срок. |
| Показать текущий diff / approve/reject | View цели и способность review этого предложения; исторические фрагменты дополнительно требуют доступа к истории. Сверить digest из запроса с сохранённым. |
| Первый commit и повтор commit | Достоверное делегирование исходного инициатора, Edit на заблокированном документе, профиль/команда. Для новой записи — действующие approval, reviewer, scope, поколение, схема и предусловия. Для выдачи прежней квитанции также текущий доступ к ней. |
| Status/verify/показать run | Office status и verify требуют исходного scope/субъекта и View; для квитанции и `at_commit` требуется разрешение на исторический результат. Другой reviewer читает данные через UI хоста со своей проверкой View/review/history. Неавторизованный ответ скрывает сам факт наличия ресурса и outcome. |
| Сессия/append/restore | View для чтения, Edit для ввода; проверять актуальные права и binding при записи. Restore требует Edit, доступа к исходной revision и разрешения хоста на restore. Token scope и срок ограничивают доступ. |
| Discussions/чат/импорт/экспорт | Для discussion View + профиль comment; edit/delete собственного комментария либо модерация, resolve/reanchor по политике. Для чата — членство и текущие права на связанные ресурсы перед выдачей. Экспорт требует View + export и history для исторической версии. Применение импорта требует Edit, создание ресурса — create. |

**Prepare.** Текущий `read_token` удостоверяет p42 и границы чтения. `text.replace_exact@1` разрешает одно совпадение в одном run с однородными marks, хранит весь форматированный контекст блока и UTF-16 диапазон. Канонический digest v1 — SHA-256 JCS от `{version:1,prepare_input,plan}` с `plan` без самого digest. Неизменяемые внутренние данные связаны через `proposal_id`. Fingerprint дополнительно закрепляет область, версию команды, писателя, поколение и предусловия. Права, expiry и запечатанные данные проверяются сервером. Контекст p71 может поменяться. Смена p42 с 15 на 20, замена его marks/attrs или удаление дают `precondition_failed`. [SDK и правила сравнения](../spec/agent-sdk.md)

**Транзакция решения.** `POST /office/proposals/{id}/decision` с `{digest,decision}`. Хост разрешает доверенную область из сеанса рецензента. В короткой транзакции проверяет текущие View/review, блокирует запись P и после ожидания повторяет авторизацию перед выдачей текущего решения. После получения lock P проверить срок по `clock_timestamp()`, действующие права и пригодность поколения для нового принятия. Для нового решения выполнить условный UPDATE по `pending` под удерживаемой блокировкой. В эталоне проверка expiry в одном UPDATE без предварительного lock позволила принять просроченное P, пока транзакция ждала неизменившуюся строку. В той же транзакции для `approved` записываются один `command_id`, owner route и dispatch outbox с постоянным event_id. Для `rejected` диспетчеризации нет. Терминальный повтор с совпадающим digest обоим уполномоченным рецензентам возвращает победившее решение. Запрос со старым digest конфликтует. Q не затрагивается. При общем подключении порядок решения T→N→D→P. Отзыв review для V1.3 сериализуется по N документа, как и прямой отзыв Edit, поэтому решающая проверка видит отзыв, зафиксированный до неё. При отдельной БД решение опирается на свежую проверку хоста, а commit повторно проверяет все условия через разрешённую локальную политику владельца. Транзакция решения не вызывает Hub или модель.

Решение и применимость хранят разные факты. Restore или expiry делает P неприменимым; отклонение заменой нового текста или отзывом прав оставляет прежнее решение в аудите. Операция принятия под неподходящим поколением возвращает `generation_changed`. Если принятие уже зафиксировалось, последующий worker может получить этот же исход исполнения. Утратившему доступ субъекту diff/квитанция не выдаются. Повторная подача намерения требует нового чтения, proposal и ключа.

## 3. Фиксация, потерянный ответ и воспроизведение

**Одиночный путь.** Worker забирает dispatch с ограниченной арендой, завершает его после долговечного перехода шага и при неизвестном исходе сначала вызывает `status`. Маршрут status и повтора идёт по сохранённому `owner_key`, даже если документ уже перенесён в другой режим. Переиспользовать порт из 3.3. [Атомарная мутация](../spec/implementation/vaulter.md) · [Маршрутизация](../spec/implementation/ai.md)

1. Владелец коротко блокирует в порядке T (shared lifecycle drive) → N (узел) → D (document). Edit перепроверяется свежим запросом на том же соединении под блокировкой. Отзыв на самом узле берёт N; при отзыве на предке обязательна проверка с видимостью фиксаций до неё. Для этого профиля проверка прав линеаризует более поздний отзыв после записи. Хосты с более строгой границей обязаны сериализовать отзыв и финальную авторизацию через общий fence. Никаких сетевых проверок и вычислителей под SQL-lock.
2. После блокировки читать запись бизнес-ключа **до** проверки режима/свежести намерения. Совпавший fingerprint и сохранённый исход возвращаются при текущих правах; другой fingerprint даёт `idempotency_conflict`. Для новой попытки сверить режим, поколение, digest, политику, approval, срок и контекст цели на свежем состоянии. Snapshot-кандидат над актуальным payload сохраняет p71. Если подготовка вынесена из транзакции, сверить CAS позиции и пересобрать при соседней правке; при изменении цели завершить с `precondition_failed`.
3. В одной owner-транзакции записать payload, новую позицию, запись команды с квитанцией, evidence, событие изменения и событие исхода в outbox. Отказ по неизменяемому предусловию фиксирует terminal outcome без записи содержимого и события его изменения. При отзыве Edit скрыть ресурс и завершить шаг хоста по актуальной авторизации. Владелец может не создавать строку команды. Если инициатор всё ещё авторизован, а текущий reviewer больше не вправе согласовывать P, фиксировать `rejected/approval_required` для этого ключа, без effect. Хост требует новое предложение и решение. Таймаут/падение до commit оставляет право безопасно проверить статус и повторить исходный ключ. Истёкший ключ распознаётся по retained route/tombstone и не порождает новую запись. После удаления evidence оставить scoped fingerprint/tombstone на всё время, пока пространство ключей принимает команды; полнота квитанции и доступность доказательства имеют собственные сроки. При неизвестном исходе за пределами окна — сверка истории.

**Journal.** Принятие intent и фиксация разделены. PHP регистрирует `running`; Hub получает аренду по `(owner_id,owner_fence,expires_at)`, монотонный fence при каждой новой выдаче. Сперва читает подтверждённый бинарный checkpoint и непрерывный хвост до head; строит копию с теми же Yjs IDs. Один последовательный обработчик комнаты пропускает client envelope, серверную команду и replay через общий порядок. Strict connections технически read-only на обычном sync; разрешённый пишущий клиент посылает envelope. `DirectConnection.transact` и штатный Redis sync отключены в строгом профиле. Awareness не пишет содержимое. На копии валидируются binding/schema, разрешённые shared types, непрерывность входных зависимостей, ожидаемый блок и постусловия; исключение отбрасывает копию.

PHP под T→N→D→head→command сверяет право/approval, generation, binding, исход команды, позицию основы, актуальные owner fence/срок по `clock_timestamp()`. Ровно одним commit сохраняет принятые байты, update receipts, голову, pending marker, бизнес-квитанцию с evidence и outbox. Это обязательная граница и для браузерных updates, no-op и terminal reject строгой комнаты. При base moved Hub догоняет голову и перепроверяет цель. При stale owner этот экземпляр прекращает запись. До commit другие клиенты эффекта не получают. [Протокол A42](../spec/collaboration.md)

**Replay и crash.** Owner outbox несёт `event_id`, scope/ссылки, `document,generation,from_seq,to_seq` для journal, хеш или ссылку на принятые bytes. Payload для клиентов выдаётся через авторизованное чтение. Relay доставляет минимум один раз; dispatch, проекции и UI потребляют событие по ID, при сбое доступны retry и повтор из журнала. Выполнение пользовательской команды запускает хостовый dispatch, повтор события `committed` только догоняет результат. Hub воспроизводит именно сохранённые bytes с committed origin, который capture не дописывает в журнал. `applied_seq` продвигается по непрерывному префиксу; разрыв догоняется чтением, повтор позиции и хеша безопасен, другой хеш на позиции — ошибка целостности. После kill между commit и apply новый Hub загружает основу и хвост до приёма следующей команды. Старое поколение отсеивается до apply. Доставки в разные системы не образуют распределённую транзакцию.

| Факт | Пользовательский статус и восстановление |
| --- | --- |
| Hosts `decision=approved` и dispatch долговечны | «Принято рецензентом». Worker может ещё не начинать commit. |
| Owner `running` или исход неизвестен | `status` по исходному ключу. `operation_unknown` в действующем окне даёт право на тот же commit. Доставка события может отставать. |
| Owner `committed` | «Сохранено владельцем». `status` возвращает тот же `receipt_id`/Marker. Worker записывает ссылку в шаг run, затем вызывает `verify`. |
| `verify(at_commit)` прошла | «Результат проверен» на позиции квитанции. Позднее `verify(current)` может не пройти; это наблюдение о текущем состоянии. В многошаговом run первый verified шаг остаётся завершённым, конфликт второго даёт частичный итог и новое чтение только второй цели. |

**Квитанция.** Публичный Office v1 возвращает `command_id,state,receipt_id,marker{generation,position}`; `verify` возвращает `receipt_id,mode,outcome,marker,checks`. В записи владельца также есть scope/resource/owner, `proposal_id,digest,fingerprint`, версия команды/схемы, момент фиксации, цели, actor и ссылка на решение, версия evidence и контрольная сумма/ссылка на принятый диапазон bytes либо immutable snapshot/evidence. Историческое доказательство берётся из результата сохранения. Для текста сохраняются block ID, границы, новый текст и marks с attrs; в journal для current сохраняется окно с Yjs relative endpoints и соседними символами. `at_commit` сверяет полный Marker; `current` читает подтверждённое состояние того же поколения на позиции не ниже квитанции. После restore current возвращает `generation_changed`, при утрате evidence историческая проверка возвращает `evidence_unavailable`. Для формул применяются сохранённые row IDs/формулы/значения и маркер пересчёта. История и ключ удерживаются по опубликованной политике. ## 4. История, restore, offline и обсуждения

**Порядок restore.** Использовать существующий `POST documents/{node}/revisions/{revision}/restore` с обязательным If-Match и Idempotency-Key. Fingerprint включает scope, actor, документ, исходную revision и ожидаемую голову. Повтор авторизованного запроса восстанавливает тот же restore outcome и новое поколение. Preview читает immutable revision; diff вычисляется на отдельной read-only модели на ProseMirror и не отправляет update. Именованная версия фиксирует схему, generation, подтверждённую позицию и удержанную основу.

1. Проверить право на исходную ревизию и restore, pin её immutable bytes/JSON. Для journal дождаться подтверждённого checkpoint текущей головы или собрать его из непрерывного префикса. Доступ к Hub, сборка и проверка совместимости идут до SQL-lock. Для нового journal подготовить отдельный seed из проверенной проекции R с сохранением block IDs и новыми CRDT identities. Исторический бинарный checkpoint R остаётся доступен для истории. Поддерживаемый путь может вернуть `document_state_pending` при недоступном drain и оставить старую голову. Офлайн-ввод, который никогда не был подтверждён владельцем, в drain не входит.
2. Под T→N→D→head сначала авторизованно вернуть ранее зафиксированный outcome данного restore key или проверить конфликт fingerprint. Для нового restore снова проверить политику, прежнюю голову/версию и префикс, pin/hash исходника и совместимость. При появлении новых принятых bytes подготовить снова или вернуть конфликт. В одной транзакции закрепить предыдущую подтверждённую историю, закрыть старый journal, погасить права его аренд, написать payload восстановленной ревизии и pointer на новую голову `G+1` (journal checkpoint at seq 0; snapshot продвигает state_version), создать restore revision/receipt и outbox. Старые bytes/квитанции остаются в историческом контуре по retention. Новый journal сохраняет согласованный seed, который можно прочесть после перезапуска.
3. После commit `document.restored` закрывает текущую старую комнату и инвалидирует проекции; потеря сигнала безопасна за счёт checks generation на authenticate/renew/append/lease/checkpoint. Клиент при reconnect получает свежую сессию, уничтожает старый provider/Y.Doc, открывает новый Y.Doc из `G+1`. Браузер хранит pending queue по tenant/actor/resource/generation. Сервер проверяет исходное поколение токена и envelope до decode/apply. Независимая stale-вставка может примениться на свежем CRDT seed, если bypass обойдёт generation gate. При обычном обрыве в том же поколении повторяет тот же update_id/байты. При смене поколения замораживает старую очередь и выводит статус «черновик из прежней версии». При наличии доступа пользователь может просмотреть/скопировать черновик и явно внести новые правки. При отзыве доступа черновик недоступен в UI и локальное хранилище очищается по политике хоста. Старые Yjs bytes не пересылаются в новую комнату.

**Привязки и предложения.** Discussion и replies живут отдельно от тела документа. Restore переводит anchors к прежнему телу в исторические; в новом поколении они показываются как detached, даже при совпадении block ID. Первый профиль требует ручного reattach с новой проверкой диапазона и generation. Pending proposals/suggestions старого поколения больше не исполнимы; текущий список показывает «требуется новое предложение». Это вычисляется при чтении и проверяется при commit, поэтому обработчик события инвалидирует только проекцию: терминальное решение и история остаются читаемыми при действующих правах.

**Удаление текста.** Для живой комнаты selector использует Yjs RelativePosition c направлением внутрь диапазона. В snapshot используются block ID, UTF-16 позиции и проверяемый контекст на сохранённом маркере; разрешение переносит anchor только при однозначном отображении редакторского изменения. Версионный resolver сужает диапазон при частичном удалении; исчезновение блока, пустой или неразрешимый диапазон даёт detached. Snapshot при неоднозначном remap также даёт detached. Thread и ответы сохраняются; пользователь может перепривязать discussion. В первом профиле якорь ограничен одним блоком. SQL anchor хранится атомарно с созданием discussion после проверки подтверждённой головы. Декорации UI выводятся из авторитетных записей и позиции проекции. После задержки проекции UI показывает ожидание либо разрешает anchor против подтверждённого тела; он не должен показывать старую привязку как актуальную. Подделка автора/anchor через произвольный Yjs root не принимается. [Comments и versions](comments-versions-design.md) · [Yjs RelativePosition](https://docs.yjs.dev/api/relative-positions)

**Расширенный review.** Accepted content остаётся источником Office read по умолчанию. P/Q и структурные suggestions хранятся отдельно. UI показывает `original` (принятый текст), `proposed(selected IDs)`, `review` (diff/decorations). В review mode клиентская транзакция превращается в структурированное предложение до публикации; remote/replay не проходят повторное отслеживание. Accept использует ту же owner-границу, что и содержательная команда, включая version/base check, и только по указанному ID или явной группе replacement. Не пересекающиеся предложения сохраняются; для пересечения v1 оставляет второе для повторного чтения/решения, сохраняя исходного автора. Узлы/marks/attrs/список/таблица добавляются только с обратимым представлением каждого вида. Импортированных авторов отображать как provenance. [Наблюдаемое поведение Tracked Changes](tracked-changes-design.md)

## 5. Возобновляемый чат

AI Core добавляет `chat_sessions` (tenant/project/участники/retention), `chat_messages` (неизменяемый принятый ввод), `chat_events(session_id,seq,event_id,run_id,type,payload_ref)` и `tool_calls(run_id,call_id,tool_version,input_digest,state,proposal_id,command_id,receipt_id)`. Использовать существующие проектные runs/steps. Уникальность клиентского `message_id` в session даёт один run на финальный input; тот же ID с другим содержимым конфликтует. Ledger принимает только законченный валидированный tool input. В стабильный `call_id` входит сохранённая идентичность шага/turn и вызова, а не ID нового сетевого исполнения. Ключ повторной доставки tool и бизнес-command ID остаются разными. Повтор доставки адресуется по сохранённому серверному call_id. Новый вывод модели с теми же аргументами — отдельное намерение, которое проходит разрешение и согласование.

POST сообщения сохраняет вход, run и dispatch атомарно. И вкладка, и фоновый worker используют тот же порт Office v1 и те же статусы; вкладка отправляет ограниченные ссылки на цели, показывает результаты и подтверждает через доверенный handler review. Worker строит каталог как пересечение установленных дескрипторов, профиля/версии, хостовой политики и актуальных прав субъекта. Права снова проверяются при tool call и у владельца. Текст модели и содержимое договора не влияют на scope. В конфиге профиля хранится имя подключения, сам provider key разрешается на сервере через secret store хоста. Vue, tool logs, события и тестовые артефакты его не содержат.

`GET /office/chat/sessions/{id}/events` отдаёт SSE с `id=seq`; reconnect использует `Last-Event-ID` или explicit cursor, читает сохранённый хвост и затем ждёт новых записей. В транзакции перехода состояния взять строку сессии, увеличить `last_seq` и атомарно сохранить событие. Уникальный ключ `(session_id,seq)`. При серии дельт можно резервировать пачку только в транзакции записи этой пачки. Обычный глобальный ID выделяется до commit и способен развернуть порядок видимости. Outbox/notify будит чтение, упорядоченный хвост читается из SQL. Сначала persist, затем emit. События `assistant.delta`, `tool.requested`, `approval.required`, `tool.committed`, `tool.verified`, `run.finished` следуют устойчивому порядку внутри session. При пропуске retention клиент перечитывает авторизованную сводку и новый cursor. Авторизация повторяется при чтении событий и долгом соединении. Для каждого ответа модели сохранять scope ресурсов, использованных в контексте turn. Выдача дельт, сообщения и tool results требует текущего доступа к этому набору, включая восстановление по cursor. UI может пропустить запрещённое содержимое, корректно продвинув непрозрачный cursor. Закрытие вкладки не меняет состояние run. [SSE и Last-Event-ID](https://html.spec.whatwg.org/multipage/server-sent-events.html)

Worker использует lease с fencing на переходах ledger. Для prepare закрепляет один proposal на нормализованный вызов в той же CORE-транзакции, что и ссылку из ledger. При потере ответа между разными процессами внутренний адаптер prepare использует тот же ключ вызова и восстанавливает ссылку. Модель повторно не планирует уже исполненный шаг на основе незавершённых дельт. После повторной доставки вызова с прежним digest он возвращает прежний результат либо разрешает тот же `command_id` через status/verify. Новый digest под тем же call_id конфликтует. При перезапуске генерации передать в контекст модели сохранённые завершённые вызовы и результаты. Новый текст может начаться с новой попытки turn, дельты незавершённой попытки показываются как прерванные, уже записанные вызовы остаются в журнале. Отмена прекращает дальнейшее планирование и переводит отправленный commit в сверку статуса. Приёмка использует детерминированный executor с точками остановки после delta, после сохранения tool call и после owner commit до записи результата в ledger. ## 6. DOCX и граница файлов

Один versioned mapping `Tiptap JSON/review → intermediate model ↔ OOXML` на открытых компонентах. Выбор конкретного ZIP/XML parser и версии `docx` закрепить после corpus spike. Для богатого импорта читать package parts и relationships напрямую с лимитами архива/распаковки/связей, отключёнными внешними загрузками и entity expansion. Проверять relationships и выбранный профиль до публикации. [OOXML и OPC](https://ecma-international.org/publications-and-standards/standards/ecma-376/) · [Разбор conversion probe](conversion-design.md)

| Corpus | Сохраняется при DOCX → model → DOCX → model | Что допускается с диагностикой |
| --- | --- | --- |
| D1 body/table | Порядок строк/ячеек, grid и merges, текст и marks внутри ячейки, заголовок таблицы, явные widths и единицы поддержанного профиля. Текстовая таблица остаётся таблицей документа. | Незначительные различия рендеринга ширины, неподдержанные темы/автоматический layout. Потеря ячейки или merge блокирует заявленный профиль. |
| D2 sections | Две секции, default/first/even header/footer по правилам профиля, правильные связи и наследование, явные page break, текст/marks. | Пиксельная пагинация, подстановка отсутствующего шрифта, динамические поля вне поддержанного набора. Диагностика указывает секцию и свойство. |
| D3 discussions | Привязка в выбранном режиме экспорта, текст и авторство комментария, связь reply, порядок, состояние resolve для заявленного threaded-формата. Обратная совместимость отдельным legacy corpus. | Legacy профиль без threaded metadata сообщает о flattening, detached anchor отображается в отчёте. Хостовые ACL и audit IDs остаются в Vaulter. |
| D4 revisions | Текстовые insert/delete/replace, исходная/предлагаемая проекции, связь половин replacement, порядок и provenance автора. Сравниваем семантику после принятия и отмены. | Native formatting/structural revisions вне первого профиля помечаются отдельно. В режиме review нельзя молча превратить их в принятый стиль. Можно выбрать явный экспорт принятого текста с диагностикой. |

Отчёт `{profile,source_marker,diagnostics:[{code,severity,feature,location,action}]}` читается в preview/результате. До применения импорта пользователь видит потери; обязательное свойство со статусом error блокирует публикацию. Допустимые потери требуют явного выбора профиля/подтверждения при записи. DOCX IDs сопоставляются по нормализованной структуре, порядок package parts, служебные ID и timestamps могут меняться. В собственном review-профиле перенос групп replacement опирается на versioned metadata с контрольной привязкой к `w:ins`/`w:del`. Если сторонний редактор потерял metadata, импорт показывает отдельные insert/delete. Потерю группы можно подтвердить сравнением с экспортным manifest. Для произвольного файла без таких данных сообщать, что связь не подтверждена. То же правило применимо к потерянному reply. Совпадение соседних диапазонов само по себе группы не создаёт. Поддержку такого сохранения с внешним редактором публиковать только после corpus-теста. Original asset сохраняется по политике удержания; повторный импорт создаёт новые локальные идентичности и хранит импортное авторство как provenance.

Локальный экспорт по явному действию генерирует bytes только из уже разрешённого клиенту подтверждённого snapshot и доступных ему assets. Он показывает профиль и потери, скачивает файл устройству, не создаёт серверное задание. Серверный обмен нужен для импорта, фонового экспорта, истории, защищённых assets и долговечного результата. `POST /documents/{id}/exchange-jobs` закрепляет input blob или revision/marker, профиль, scope и идемпотентный ключ; `GET …/{job}` выдаёт статус/отчёт; `GET …/{job}/file` проверяет актуальные View/export/history перед выдачей. Worker с ограниченной арендой сначала записывает immutable файл в Media, затем фиксирует ссылку/отчёт/outbox; непривязанный blob собирается GC. Подготовленный импорт отдаёт preview; `POST …/{job}/apply` вызывает версионированную owner-команду с CAS текущей головы, правами и отдельным command ID, возвратом receipt при повторе. Повтор задания конвертации не запускает повтор записи документа. Модуль Sheets для XLSX/CSV остаётся типизированным соседом. [Смежная схема заданий](../spec/database/sql/sheets-exchange.sql)

## 7. Входы, события и подтверждённые границы

Office v1 сохраняет опубликованную форму семи RPC через `POST /api/vaulter-ai/v1/operations` (префикс настраивается) и PHP-порт. Оба адаптера проводят один handler. Новые пути `/office/…` и `…/exchange-jobs` в этом документе относительны к versioned API проекта. Для review `GET /office/proposals/{id}` и `POST …/decision`, для статуса поручения `GET /office/runs/{id}`. Discussion использует существующий вход `nodes/{node}/comments`. Для ranged create добавить `{body,anchor,marker}` и Idempotency-Key, reply сохраняет `parent_id`. Новые reopen/reanchor используют CAS по версии записи и текущий marker для нового anchor. `GET /office/chat/sessions/{id}` возвращает сводку и cursor, `POST …/{id}/messages` принимает `message_id,body,targets` и возвращает `run_id`. Версии схемы согласуются отдельно от HTTP-маршрутов. [Office v1](../spec/agent-sdk.md) · [Маршруты Documents](../../packages/documents/routes/documents.php)

| Событие проекта | Транзакция и потребитель |
| --- | --- |
| `proposal.decided`, `proposal.dispatch_requested` | Host decision, UI и dispatch worker. `v_ai_dispatches` реализует долговечную диспетчеризацию. У отклонённого P только решение. |
| `command.committed`, `command.rejected`, `document.updated` | Владелец, его outbox и relay; run status, Hub replay, projection. Отклонённая запись не порождает событие изменения документа. |
| `document.restored`, `discussion.changed` | Documents, текущий Marker и идентичность записи; комнаты, anchors/projections и UI. Имена поверх существующих доменных событий Documents по карте реализации. |
| `run.*`, `tool.*`, `exchange.finished` | Соответствующий журнал/задание и outbox; авторизованный API выдаёт детали. Событийный конверт содержит ссылки/версии и correlation, защищённый текст остаётся в владельце. |

**Наблюдения.** Cloud Test ранее подтвердил offline/reconnect, replies/resolve и сохранение discussion после restore, isolated preview, удалённый accept/reject, Node 15→30 с bold/p71, fresh browser, отказ адаптера при 20 и повтор тех же bytes. Таймауты свежего WebSocket оставили отдельные readback-попытки непроверенными; REST readback для comments/versions прошёл независимо. Registry 403 оставляет без исходников, среди прочих, Client AI Toolkit, Compare и Import DOCX. Локальный DOCX probe доказывает доступный экспорт, включая текстовые revisions, и фиксирует потерю native formatting revision. AI mock проверяет протокол и preview, live LLM/удалённый toolkit не проверялись. Эти данные пригодны для выбора собственного mapping, интерфейсов и fallback. [Findings](findings.md) · [Каталог](module-catalog.md) · [Разбор исходников](source-level-review.md)

**Решения Vaulter.** Единственность P/Q, SQL-граница, at-least-once, поколения, правила anchor, ledger чата и DOCX roundtrip — проектные гарантии. Перезапуск автономных эталонов SQL, snapshot и A42 подтверждает только охваченные ими сценарии. Локальный restore E2E остановился до restore на несовместимости тестового адаптера с публичной сессией, а после временной адаптации — на HTTP 404 при Hub authenticate. Полная гонка review/отзыва, offline-restore в целевой установке, chat SSE и corpus собственного импорта требуют проверок по [матрице](acceptance-matrix.md). Новых Cloud-вызовов в этой сессии не было.

Дополнительные локальные прогоны сузили риски expiry, replay SSE, fencing Yjs и межоперабельности файлов. [Команды и результаты](follow-up-research.md)
