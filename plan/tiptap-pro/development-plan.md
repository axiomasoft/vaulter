# Этапы разработки собственной реализации Tiptap Pro

Первый результат — **V1, согласованная точечная правка одиночного договора**. После закрытия всех вкладок worker меняет p42 с 15 на 30, сохраняет bold и соседний p71, возвращает прежнюю квитанцию после потери ответа. P и Q независимы. Вся работа принимается в изолированном потребителе Vaulter. [Проект backend](backend-design.md) · [Матрица приёмки](acceptance-matrix.md)

Карточки ниже можно переводить в задачи по указанным подэтапам. `V1` поставляет текстовую часть 7.1 поверх задач 1.0 и 3.1–3.4. Полный критерий фазы 7 основного плана по-прежнему требует 5.1 для книг и отдельного прогона 7.2. Сценарии и контракты, общие для типов, сохраняют форму Office v1. ## V1. Одиночный договор, согласование и квитанция

**Зависимости.** Базовая установка 0.x, универсальная Documents head из 1.0 и граница snapshot/journal DB0. Если ещё отсутствуют, V1.1 поставляет зависимые изменения в базовом пакете. Установленный Hub, настоящий ключ модели, DOCX и поставка Sheets для текстового профиля не нужны.

| Задача | Backend и миграция | Frontend | Приёмка |
| --- | --- | --- | --- |
| V1.1 — режим, ID и мутация | Добавить/заполнить `write_mode` по доказанному пути записи, отделить epoch от обычного autosave, сохранить совместимые ETag. Для перехода существующих активных комнат нужен drain и проверенный marker; не классифицировать по `collab_protocol`. Стабильные block IDs и явная CAS-нормализация старых документов. Порт `AtomicDocumentMutation` со свежим Edit под T→N→D. Документный content и API исходной CMS проходят исходные сценарии. | Подключить `attrs.blockId` в Tiptap, унифицировать split/join/paste/move, использовать Vue editor slot. Сохранить UI локального конфликта ETag. | BASE, RIGHTS; 3.1-A/B и история старого документа. |
| V1.2 — семь операций SDK и исход | Закрытые ai-core и ai-documents: миграции read tokens, proposal/payload/routes, outcome/evidence и проекции согласно SQL; PHP/HTTP, JCS, семантическая замена, независимый verifier; outbox. Начать с одного writer. Переиспользовать owner lock и storage contract. | Только интерфейс ограниченного preview и отображение Marker/квитанции. UI читает подтверждённый документ через штатный вход. | COMMIT, RIGHTS, VERIFY. Негативы schema и адаптера. |
| V1.3 — P/Q и рестарт worker | Добавить runs/steps и durable dispatch из SQL AI Core. Политика review хоста, проверка срока по времени БД после lock P и локальная проверка ревьюера перед commit. Детерминированный профиль в PHP и HTTP, контрольные барьеры на решение, отзыв и commit; после рестарта status → verify. | Тестовая панель с P/Q, diff, инициатором, безопасными действиями, тремя статусами и восстановлением по run ID. | PQ, COMMIT, RIGHTS, VERIFY. Два браузерных контекста и тот же контракт с закрытыми вкладками. |

**Порядок.** V1.1 → V1.2 → V1.3 end-to-end. Дизайн и компонентные тесты панели V1.3 можно вести параллельно с V1.2 по закреплённым wire fixtures. Детерминированный адаптер можно готовить параллельно с owner-портом.

**Завершение.** Из новых артефактов собрать профиль базы и профиль text-review. В свежем потребителе для approve-ветки P/Q — одно решение, одна запись P, столько же квитанций, p42=30 с bold, p71 сохранён, Q pending. Для reject-ветки P — ноль записей и dispatch. Прервать ответ после owner commit, перезапустить worker, открыть новую вкладку: исходный receipt и `verify(at_commit)=passed`. Отзыв Edit/review перед commit блокирует эффект, отзыв View перед чтением скрывает результат. Ручные правки с прежним ETag продолжают возвращать 412. Для отключения закрытого профиля оставить read-only доступ к действующим квитанциям по ACL и приостановить новые dispatch.

## V2. Живая комната и восстановление поколения

**Зависимости.** V1.1 и базовая тройка пакетов для V2.1. V1.2 и V2.1 для V2.2. Для проверки живого P/Q и старого предложения при restore нужна V1.3.

| Задача | Backend и миграция | Frontend | Приёмка |
| --- | --- | --- | --- |
| V2.1 — транспорт, checkpoint и generation | Закрепить совместимые версии пакетов и обновить E2E-адаптер публичной сессии и restore, согласовать morph type HTTP-fixture с Hub resolver. Если отказ сохраняется, проверить фактически связанный resolver, материализацию principal и `referenceContext` по tenant/drive/node, затем повторить authenticate/restore в изолированном потребителе. Ввести предел compaction lease, атомарный переход режима/restore с fencing старой головы и аренд, seed нового поколения с прежними block IDs и новой CRDT-основой, публикацию restore через outbox. Существующие журналы мигрировать с подтверждённым checkpoint; при pending дать drain. | Исправить upgrade URL `protocol=2`; привязать очередь и локальный черновик к поколению. Новый пустой Y.Doc после 4409/session generation change. Отдельные статусы транспорта, pending и сохранения. | RESTORE, JOURNAL, BASE. Крестовые тесты истечения, scope, повторных ACK и компактора. |
| V2.2 — строгий владелец | Новые `owner_fence/holder/expires`, command table и связь с принятым диапазоном. Расширить PHP routes/Hub, добавить sequencer, validate-copy-append-replay, pinned owner route и journal verifier. Технический read-only обычного sync и один envelope путь, штатный Redis sync выключен для строгого профиля. | Сохранить UX локального ввода, доставлять только authoritative ACK/updates, отличать draft от canonical, отображать расхождение current/at_commit. | LIVE, JOURNAL, RIGHTS, RESTORE. Реальные Laravel + PostgreSQL + Hub + браузеры, все 11 вариантов A42 из плана. |

**Завершение.** Kill Hub после commit и до apply не теряет ни p42, ни соседнюю правку. Новая комната читает непрерывный префикс, старый Hub не пишет. При offline-restore старый payload/токен/checkpoint не принимаются, новый клиент читает восстановленное состояние, офлайн-черновик можно перенести только явно. Пока любой штатный путь обходит барьер, профиль live commit остаётся выключенным. Измерить задержку обычного ввода и восстановление после checkpoint на тех же синтетических данных; срок и профиль эксплуатации закрепляет хост по замеру.

## V3. История, range comments и расширенный review

**Зависимости.** V1 для snapshot. Реализация snapshot-части и тестовых fixtures возможна параллельно V2; выпуск journal-части требует V2.2. Данные плотного review и DOCX header/footer могут развиваться независимо.

| Задача | Backend и миграция | Frontend | Приёмка |
| --- | --- | --- | --- |
| V3.1 — история и discussions | Достроить неизменяемые revision refs и pin при compaction, добавить таблицу range anchors к root comment и их versioned состояние. Текущие comments без range сохраняются как обсуждения узла. Поддержать CAS resolve/reopen, replies, reanchor, restore-detach и канонический resolver после удаления. | Read-only preview/compare в отдельном editor, sidebar active/resolved/detached, восстановление привязки и индикатор актуальности. | COMMENTS, RESTORE, REVIEW-HISTORY. Обе схемы записи; отзыв прав и чистый read-only просмотр. |
| V3.2 — текстовый review | Таблица suggestions и отношение к proposal; версионированные high-level операции insert/delete/replace, явная группа, автор из сеанса; атомарный accept/reject через порт владельца. | Tiptap OSS/PM: review overlay, преобразование локального действия перед общим dispatch, выбор отдельных предложений, original/proposed/review. Undo и IME проверяются на этом поднаборе. | REVIEW. Встречные решения, P/Q, непересечение, конфликт второго, отсутствие retrack при replay. |
| V3.3 — структурный review | Контракты marks/attrs, split/join, списков, atom и текстовых таблиц отдельными поддерживаемыми профилями. Для пересечения v1 сохраняет неподтверждённое предложение и явный конфликт. | Review diff по структурным IDs, отображение исходных/предлагаемых attrs и однозначного scope. | REVIEW по каждому разрешённому виду и rollback кандидата при неподдерживаемом типе. |

**Завершение.** Удаление целевого текста переводит привязку в detached, обсуждение и ответы доступны по ACL. Restore сохраняет историю, но делает старые ожидающие предложения неприменимыми. Preview и compare создают ноль live updates. После авторизованного accept только явная группа меняет canonical. Функции для неподдерживаемых структур скрываются по capability, а API отклоняет соответствующую операцию до изменения.

## V4. Возобновляемый AI-чат

**Зависимости.** V1.3 для пишущих tools в snapshot. Скелет SSE, журнал и synthetic executor можно начинать после V1.2, параллельно V2/V3. Пишущие tools в journal включаются только после V2.2; Review UI V3 подключается отдельно.

- **V4.1 Backend.** Миграции chat sessions/messages/events и tool ledger; стабильная связь с runs/steps, scoped input digests, lease, транзакционный счётчик на строке session и replay по cursor. Один POST пользователя или финальное событие канала создаёт один run; дубликат после перезапуска получает прежний результат. Одним handler пользуются PHP и ограниченный HTTP клиент. Детерминированный исполнитель управляет точками остановки.
- **V4.1 Frontend.** Панель диалога и route run ID, ограниченный editor selection, подписка на SSE и восстановление курсора. UI показывает прерванную дельту, waiting approval, owner commit и verify отдельными состояниями. При отзыве ресурса свернуть защищённый фрагмент и завершить/обновить поток.
- **V4.2.** Добавить Laravel AI и опциональный AgenTools: профиль сервера, secret reference, каталог tools по установленным версиям и правам, bounded context и нормализованный tool call. Зафиксировать лимиты и retry. Внешний эмулятор принимает промежуточное/финальное сообщение, переотправляет финальное, восстанавливает ссылку на run.
- **Завершение.** CHAT, CHANNEL, COMMIT и RIGHTS через детерминированный исполнитель при открытой и закрытой вкладке. Обрыв SSE и остановка worker после owner commit дают тот же run/tool/receipt и один эффект. Настоящая модель квалифицируется отдельным smoke после детерминированной приёмки. [H4 и фаза 7.2](../phases/07-agent-workspace.md)

**Зависимости.** Corpus и локальный mapper можно начать с V1.1 параллельно V2–V4. Применение серверного импорта зависит от V1.2 и для строгого journal от V2.2. Импорт/экспорт живых discussions и revisions по профилю review включается после V3.

| Задача | Backend и миграция | Frontend | Приёмка |
| --- | --- | --- | --- |
| V5.1 — корпус и локальный экспорт | Выбрать и закрепить версии OSS XML/ZIP/OOXML; промежуточная модель, явные стили/единицы и loss report. Основы D1/D2 по синтетическим fixtures с отдельным сравнением эффективной геометрии и исходной структуры. Затем D3/D4 с отдельными профилями legacy, threaded и review. LibreOffice 24.2.7.2 требует собственной квалификации из-за потери reply и custom XML группы. | Экспорт подтверждённой доступной версии локально, выбор профиля и вида проекции, preview предупреждений. | DOCX; браузерный export с fetch trap и равенство semantic report с Node. |
| V5.2 — server jobs и import | Миграция `document_exchange_jobs` с арендой, key/fingerprint, source/output Media refs и owner receipt для apply. Ограниченные parse/validate, удержание исходника, immutable artifact, явный owner commit и контроль поколения. | Загрузка, статус задания после reconnect, просмотр отчёта, выдача файла по свежим правам, явное принятие импорта или выбор другого профиля. | DOCX, FILES. Roundtrip, worker kill, отзыв прав, устаревший apply и повтор ключа, битый пакет. |

**Завершение.** D1–D4 проходят сравнение заявленных свойств при повторном импорте, а заявленные потери читаемы до применения. Неподдерживаемый обязательный элемент блокирует соответствующий профиль. Наличие локального экспортера не включает server job и не меняет политику файлов. [Профили и корпус](backend-design.md#6-docx-и-граница-файлов)

## Параллельная работа и блокирующие решения

- **Параллельно после базовых контрактов.** V2.1, Vue панель V1.3, чтение/preview V3.1 и D1/D2 fixtures V5.1. После V1.2 также SSE/ledger V4.1. Sheets следует своему графу фаз 4–5; общее — доверенный scope, conformance Office v1 и форма квитанции.
- **До включения V1.** Выбрать хостовый источник актуальных прав, точку сериализации отзыва и сроки хранения ключей, evidence и истории. В изолированном профиле V1 этот источник — локальная PostgreSQL и repeatable test clock. Точная конфигурация внешних ACL, старых работающих комнат и retention нужна для выпуска соответствующего профиля.
- **До включения V2.2.** Совместимый Hub/JS/PHP и доказательство, что все писатели строгой комнаты используют один барьер. Согласовать допустимую задержку ввода, предел восстановления и размер локального черновика после замеров.
- **До включения V3.3/V5.** Утвердить policy сложных пересечений и формат Word threaded comments на реальном roundtrip corpus, версии редакторов для межоперабельности и поддержку structural/formatting revisions. Зафиксировать профили, прежде чем обещать пользователю их свойства.
- **До подключения реальной модели V4.2.** Хост закрепляет доступные модели, лимиты и политику хранения сообщений/фрагментов. От этого не зависит детерминированный тест. Для полного 7.1/7.2 добавить typed Sheets runtime и прогнать partial-result двух ресурсов.

Каждая поставка проверяется на собственной миграции и на чтении данных предыдущей комплектации. Запись новых возможностей включается после прохождения их критериев, с возможностью остановить новые задания, сохранить историю и восстановить незавершённые исходы через status. Браузеры и worker в проверках используют чистые тестовые профили и синтетические документы. Репозитории продуктовых приложений подключаются после приёмки пакетов.
