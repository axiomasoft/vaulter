Первый browser-сценарий создаёт UUID-комнату `tiptap-pro-lab-smoke-*`, два независимых browser context, по два отдельных Y.Doc/provider в каждом. Проверяет доставку baseline, отключение обоих клиентов второго контекста, независимые offline и online вставки, reconnect и сходимость всех четырёх клиентов. После закрытия первых контекстов свежий контекст получает итоговый текст от того же процесса локального сервера.

Второй сценарий проверяет публичный `/api/config` на отсутствие signing material, запрет mint JWT вне исследовательского prefix, точный resource в JWT и срок 600 s. Подпись и room permission затем реально принимает локальный Hocuspocus в первом сценарии.

Ещё два сценария в `tests/permissions.spec.mjs` проверяют серверные ограничения. Read-only клиент меняет Y.Doc напрямую, обходя `editable: false`; сервер отвечает `SyncStatus(applied=false)`, изменения отсутствуют у пишущих клиентов и у нового read-only клиента. При этом отклонённая правка остаётся в прежнем локальном Y.Doc — отказ сервера не откатывает CRDT-состояние клиента. Правильные записи продолжают доходить до read-only клиента. Токен для другой комнаты получает отказ аутентификации. Эти сценарии можно отдельно повторить с `TIPTAP_PERMISSION_MODE=cloud`, когда будут настроены доступы.

После установки Pro-пакетов добавлен `tests/tracked-changes.spec.mjs`: Alice создаёт proposal, Bob удалённо отклоняет его; затем Alice создаёт второе предложение, Bob принимает. После обоих действий проверена сходимость текста и отсутствие pending suggestions у первого клиента. Это проверка настоящего установленного `TrackedChanges` поверх локального OSS transport.

Совместный запуск после добавления permission/schema-сценариев: `npm test` → **6 passed, 1.7 s** (системный Chrome). Исходный browser-сценарий и token test остаются в наборе. Эти локальные тесты не проверяют durability после рестарта процесса, SQL-транзакции, Tiptap Cloud, Comments или Snapshot Compare. Их Cloud-проверки выполняются отдельными runner-сценариями и описываются в отдельных отчётах.

Первый запуск `npm test` обнаружил отсутствие bundled Chromium. Системный Chrome поддерживается через `PLAYWRIGHT_CHANNEL=chrome`; он использует отдельный headless profile и не затрагивает пользовательскую сессию Chrome. Загрузка bundled Chromium с CDN сначала завершалась timeout; скачанный headless shell затем завершился SIGSEGV на этой машине. Поэтому конфигурация использует системный Chrome по умолчанию. Канал можно переопределить `PLAYWRIGHT_CHANNEL`. Результаты выше получены на системном Chrome.
