## PQ — два решения по P, независимое Q

| Вектор | Начальное состояние и действия | Клиент | Сервер и доказательства |
| --- | --- | --- | --- |
| PQ/approve-wins | Договор G3/27, p42 «15» с bold, p71 уже независимо изменён после prepare. P/Q pending, R1 и R2 имеют View+review. Отдельные сеансы: R1 approve, R2 reject. Барьер удерживает решение P перед commit, второй запрос ждёт; отпустить с победой approve. Вручную повторить оба запроса. Закрыть вкладки до исполнения. | Оба рецензента получают одно решение P при сохранении прав. Q pending. После выполнения свежая вкладка видит «принято», «сохранено», «проверено», p42=30 с bold и актуальный p71. | Одна терминальная запись P и один host dispatch, один `command_id`, один owner effect/receipt и одна эффективная новая позиция. Q без decision, route и dispatch. SQL-снимки host/owner и trace двух соединений, fingerprint, marker, readback текста и marks. |
| PQ/reject-wins | Те же данные, порядок линеаризации обратный; повторить approve после reject. | Оба видят reject, Q pending. p42=15. | Ноль dispatch, owner effects и receipts P. База фиксирует единственного рецензента/момент; другой digest или scope не получают решение. |
| PQ/invalid | С сохранённым P послать другой digest, другой tenant или запрос от view-only. Отдельно просрочить P до первого решения и в момент, когда запрос уже ждёт блокировку. Держатель lock отпускает неизменившуюся строку после expiry. | Разрешённый пользователь видит конфликт digest или expiry; постороннему не раскрывается P. | P не меняется, Q pending, нет dispatch. Сверить до/после и отсутствие diff в ответе. |

**Запуск.** Будущий `bash plan/tiptap-pro/checks/run.sh PQ` для V1.3. Текущий SQL-проверочный `schema.sh` проверяет ограничения, в том числе approval/route; это простая проверка ограничений. `python3 plan/tiptap-pro/probes/postgres-probes.py` добавляет реальную SQL-гонку approve/reject/rollback и проверку срока после lock. HTTP, ACL и полный эффект у владельца остаются испытаниями V1.3. Базовые бизнес-ключи и конкурирующие owner commit уже покрыты `atomic-mutation/run.sh`. ## COMMIT — ответ потерян после owner commit

| Вектор | Начальное состояние и действия | Клиент | Сервер и доказательства |
| --- | --- | --- | --- |
| COMMIT/snapshot | `read → prepare` P по p42=15; reviewer принимает P. Остановить owner/worker после COMMIT и до HTTP-ответа/записи receipt в CORE. Принудительно закрыть UI и затем перезапустить worker. После commit можно перевести документ snapshot→journal. Повторить первоначальный commit. | Пока есть только решение, UI показывает «принято». После рестарта status возвращает «сохранено», verify по прежнему ID — «проверено». Новый браузер видит 30 с bold и соседнюю правку. | Независимый SQL-клиент видит effect/outcome/evidence/outbox после kill. Адаптер по сохранённому `owner_key` получает ту же квитанцию и Marker даже после смены режима; отозванному субъекту receipt не виден. Ровно один effect и один командный outcome. |
| COMMIT/before | Убить процесс до owner commit, затем передать ту же host job второму worker. Дополнительно повторить с конкурентным тем же ключом и с другим digest. | Происходит безопасное возобновление, разные digest под одним ключом явно конфликтуют. | Прерванная транзакция не оставляет эффекта/outbox. `status` running или operation_unknown в пределах окна приводит к прежнему commit; конкурент получает тот же исход. Истёкший ключ не допускает записи. |
| COMMIT/outbox | Остановить relay после commit, затем доставить события дважды и с разрывом позиции. Повторить остановку между publish и отметкой доставки. | До догоняния проекции status уже показывает «сохранено». Подтверждённое чтение показывает новую позицию либо явное ожидание. | Хостовый dispatch возобновляет исходный command; owner event не вызывает преобразование ещё раз. Gap восстанавливается по журналу/владельцу; один business outcome, projection без регресса. Сопоставить event_id, consumer cursor, маркер и хеши. |

Для journal — `PG_BIN=/usr/lib/postgresql/18/bin bash plan/checks/collaboration/live-write.sh`. Будущий `bash plan/tiptap-pro/checks/run.sh COMMIT` проверяет эти границы поставляемыми worker, REST и outbox relay. ## Как запускать и сохранять доказательства

Команды эталонов из корня. SQL-скрипты создают собственный кластер PostgreSQL 18, Unix socket и БД. SDK использует PHP 8.4, Node и Python согласно скрипту. Тест WebSocket с `missing` фиксирует дефект данного checkout, команда без переменной нужна после изменения V2.1. Для package smoke установить зависимости из lockfiles в соответствующих workspace, для Hub использовать Node 26 по его `engines`.

```bash
python3 plan/checks/verify-plan.py
python3 plan/checks/verify-fixtures.py
PG_BIN=/usr/lib/postgresql/18/bin bash plan/checks/schema.sh
PG_BIN=/usr/lib/postgresql/18/bin bash plan/checks/atomic-mutation/run.sh
PG_BIN=/usr/lib/postgresql/18/bin bash plan/checks/collaboration/live-write.sh
bash plan/checks/sdk/run.sh
node --test plan/tiptap-pro/scripts/*.test.mjs
VAULTER_HANDSHAKE_EXPECT=missing node node_modules/vitest/vitest.mjs run plan/checks/collaboration/protocol.test.ts
node node_modules/vitest/vitest.mjs run plan/checks/collaboration/protocol.test.ts
npm test --workspace @vaulter/vue-collaboration
bash scripts/collab-e2e.sh
```

**Контракт нового runner.** Каждая карточка поставляет свой case для `bash plan/tiptap-pro/checks/run.sh <ID>` и независимый запуск из корня. Путь пока проектный. Runner обязан поднять новую БД и процессы для кейса, создать два независимых браузерных контекста при необходимости, применять явные барьеры (SQL lock wait, commit hook, ACK или управляемый kill) при гонках. Этап завершён, когда runner выдаёт нулевой код и отчёт с assert по всем состояниям этого ID. Для браузера проверять новый контекст, для owner — независимое авторизованное чтение и минимальный SQL trace. Скрин UI фиксирует статус, а доказательство эффекта включает маркер, peer/fresh read и хеш либо разрешённую структурную выборку.

Под `plan/tiptap-pro/` складываются проверяемые прототипы, синтетический corpus, команды и очищенные результаты. Отчёт включает ID кейса, версии пакетов и БД, исходный marker, последовательность барьеров, outcome и receipt IDs, счётчики строк, outbox deliveries и exact assertions. Не записывать токены, ключи, auth-кадры или production payload. Для дополнительного эксперимента Cloud допустимы только Test и `tiptap-pro-lab-*`; в этой сессии обращения к Cloud не требовались. ## Выполненные проверки этой сессии

| Запуск | Результат и предел проверки |
| --- | --- |
| Plan, fixtures, schema, SDK | Все завершились с кодом 0. PostgreSQL 18.4 проверил эталонный SQL и гонки документа. SDK проверил JCS, форматированную замену, различие at_commit/current, обмены и негативы. |
| Snapshot atomic-mutation | Прошли SIGKILL после commit, восстановление прежнего marker после смены режима, двухпроцессный повтор, отказ при Edit revoke, изменённая цель и SQL retry. Это автономный эталон с двумя БД. |
| A42 live-write | Прошёл kill между commit/apply, точный replay, повтор доставки и смена владельца. Подтверждены пути обхода штатного Hocuspocus. Из 11 векторов 7 покрывает автономный эталон, 4 требуют целевых пакетов: `precondition_changed`, `edit_revoked`, `read_revoked` и `projection_behind`. |
| Локальные тесты checkout | 84 теста Vue Collaboration, 308 тестов Hub на Node 26.13.1, 12 лабораторных unit tests прошли. Проверка upgrade воспроизвела `/editor?tenant=sample` без `protocol=2`. |
| Existing restore E2E | Root vendor не соответствует checkout, поэтому стенд поднят отдельно с чистыми Composer-зависимостями и временной SQLite. Публичный HTTP 201 возвращает `mode: write/read`, `generation` и `options.room`. Исходный E2E ожидает `rw/ro`, `epoch` и верхнеуровневое `room`. Три исходных теста упали до проверки restore. Во временном адаптере поля приведены к текущей форме и добавлен If-Match. Повтор остановился на sync: прямой локальный запрос к Hub authenticate воспроизвёл HTTP 404 `node_not_found` на свежеизданной session. Отдельный PHP-прогон подтвердил несовместимость morph types в fixture. Повтор с выравниванием типа во временной копии provider также не дошёл до sync. Restore/read-only/schema E2E остаются непроверенными. |
| Tiptap Cloud / DOCX / AI | Использованы сохранённые очищенные отчёты. Новых Cloud-вызовов не было. В отдельные попытки Cloud readback остановился до handshake по таймауту, REST-повтор для comments/versions прошёл. Registry 403 для Client AI Toolkit, Compare и Import DOCX оставляет соответствующие реализации закрытыми. Собственный owner/stream/OOXML проект опирается на локальные эталоны и открытые контракты. |
