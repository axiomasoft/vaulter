# Приёмка одной задачи

1. Выбрать ID в [указателе фаз](README.md). Прочитать строку «После» и критерии в карточке. Для условной 4.3 взять из профиля поставки заказанные форматы обмена. Задачи с другими ID принимаются по собственным критериям и указанным зависимостям.
2. Выполнить команды критерия на закреплённых ревизиях. Сохранить короткий фактический вывод с проверяемыми значениями: ETag/код ответа, позицию журнала, квитанцию, значение ячейки, число записей или digest артефакта. Использовать изолированного потребителя, указанного в задаче.
3. Заполнить JSON по шаблону ниже в каталоге результатов конкретного прогона. Один файл описывает одну задачу. Ревьюер сверяет вывод каждой команды с критерием из карточки.
4. Проверить отчёт командой ниже. Метка задачи вычисляется из критериев. Запись результата не меняет статус других задач и не требует сборки продуктов.

```bash
python3 plan/checks/verify-plan.py
python3 plan/checks/verify-plan.py --report /tmp/vaulter-task.json
```

Первая команда проверяет ссылки на фазы, уникальность ID, критерии и граф зависимостей. Для второй сохраните шаблон в `/tmp/vaulter-task.json`. До выполнения проверки он даёт `1.1 partial` с кодом 3. При сдаче замените исходную ревизию на проверяемую и заполните фактическое свидетельство.

```json
{
  "version": 1,
  "task": "1.1",
  "repos": {"vaulter": "b230f6e27b53c92145fa81be2fdeb89ea5c8ae03"},
  "commands": [],
  "gates": {
    "1.1-A": {"state": "not_run", "actual": "Ожидает проверки установки архивов", "evidence": []}
  }
}
```

| Поле отчёта | Значение |
| --- | --- |
| `version`, `task` | Число 1 и существующий ID задачи |
| `exchange_formats` | Только для 4.3. Массив заказанных форматов в нижнем регистре. Например, `["csv"]` требует проверки обмена CSV по 4.3-B и отсутствия XLSX в выдаче API по 4.3-A. При `[]` поставка не заказывает обмен, эту задачу можно пропустить |
| `repos` | Имя каждого испытанного репозитория → полная Git SHA (40 или 64 hex). При проверке совместимости приложить ревизии обеих сторон; если программа проверки из другого комплекта, указать его в фактическом результате |
| `commands[]` | Уникальный `id`, ключ репозитория `repo`, фактическая `command` из корня этого репозитория, целый `exit_code`, непустой `output` с существенной частью вывода. Секреты в отчёт не включать |
| `gates` | Ровно все ID критериев выбранной задачи. Каждый содержит `state`, `actual` и список ID команд `evidence`. Для `not_run` указать причину и пустой список. Для измеренного исхода указать факты и хотя бы одну команду. В 4.3 значение `disabled` подтверждает успешную проверку отсутствия незаказанного формата, `pass` подтверждает обмен заказанным форматом |

| Итог / код возврата | Условие |
| --- | --- |
| `pass` / 0 | Все критерии испытаны и приняты в заказанной конфигурации. Для 4.3 заказан хотя бы один формат. У каждого критерия есть успешная проверочная команда. Для испытания ожидаемого отказа обёртка проверяет нужный отказ и сама завершает работу с кодом 0 |
| `fail` / 1 | Хотя бы один критерий испытан и дал расхождение |
| `invalid` / 2 | Повреждён граф, неизвестный ID, отсутствующий критерий/свидетельство или противоречивые поля отчёта |
| `partial` / 3 | Остались `not_run` либо представлен отчёт 4.3 с пустым списком заказанных форматов. Измеренных расхождений нет |

Проверяющая программа использует Python 3.9+ и стандартную библиотеку. Она валидирует структуру и сопоставление свидетельств. Оценку достаточности конкретной проверки делает ревьюер.
