# Адресное чтение и проверка результата

Эта спецификация относится к закрытым адаптерам документов и книг. Цель первой реализации — при действующем доступе прочитать три абзаца или 20 ячеек и сказать, какие подтверждённые изменения в них видны. Вход агента определён в контракте SDK. Чистая CMS продолжает пользоваться существующим сохранением Documents.

## S1. Источники и владельцы

| Объект | Единственный путь содержательной записи | Позиция для чтения |
| --- | --- | --- |
| Одиночный текст | Операция Documents с повторной проверкой права Edit и версии внутри транзакции. Подготовленная семантическая правка применяется к свежей версии. Путь полной замены остаётся путём обычного одиночного редактора | Поколение и версия рабочего состояния. Именованная ревизия имеет свою идентичность |
| Совместный текст | Принятый журнал бинарных Yjs-обновлений и двоичный checkpoint. Последовательность регистрации команды и публикации в живой комнате описана отдельно | Поколение комнаты и позиция принятого обновления. Экспорт/чтение JSON учитывают покрытие checkpoint. Спецификация записи |
| Книга | В первом выпуске приватный Sheets применяет команду в движке, проверяет версию и публикует нативный снимок одной книги. Если снимок вынесен в Media, сначала записывает неизменяемый объект, затем атомарно публикует ссылку и квитанцию | Поколение и позиция сохранения. Позиция, до которой подтверждён расчёт зависимостей, возвращается отдельно. Спецификация книг |

Таблицы Drive и Documents, правила доступа, хранилище Media и outbox сохраняют нынешнее владение. При разных процессах командой владеет сервис документа. Он связывает эффект с ключом команды в собственном долговечном хранилище. AI может позже догнать его по квитанции. Вызов другого сервиса во время удержания SQL-блокировки документа запрещён.

Выбор источника под блокировкой определяется `v_documents.write_mode`. У одиночного документа `snapshot` разрешена семантическая запись через Documents, поколение стабильно между соседними обычными правками. У `journal` источником позиции служит принятый журнал и его поколение. В действующей исходной реализации у rich text `collab_protocol` уже заполнен при создании, даже без Hub, и обычная запись с этим полем повышает epoch; после изменения владельца в DB0 такой признак использовать нельзя. Захват журнала/управляемое закрытие и восстановление повышают поколение и ограждают старые задания. Открытие читателем не меняет режим. Проверить prepare в snapshot, включить journal до commit и попытаться дописать прежнее задание. Маркер из старого поколения отклоняется, пользовательская правка из журнала сохраняется. ## S2. Добавляемые данные

Логические наборы ниже задают ключи, условия и владельцев. Префикс таблиц, тип ID и подключение берутся из существующей схемы Vaulter. Для текстовых документов структуры адресного чтения поставляет закрытый адаптер AI Documents, для табличных данных — Sheets. Оба используют одинаковую форму маркера чтения в SDK. PostgreSQL — первый стенд. Бенчмарк в приложенном архиве использует фиксированные числовые ключи и отдельную схему для испытаний. [Правила схемы](/adr/0030-package-ownership-and-schema) · [Типы идентификаторов](/adr/0011-id-strategy)

| Логическая запись | Уникальность и содержимое | Когда меняется |
| --- | --- | --- |
| Указатель опубликованной проекции | область доступа + узел + вид проекции. Поля: поколение, позиция источника, идентификатор сборки, версия проектора | Только вместе с готовыми данными, после сверки поколения и исходной позиции |
| Абзац/заголовок | область + узел + поколение + сборка + block_id. Порядок, родитель, заголовок, текст для поиска, форматированный узел и хеш. Индекс по порядку внутри того же документа/сборки | Удаление или split/join обрабатывается как изменение набора ID. Порядок соседей читается по индексу. При paste копия получает новый ID, при исчезновении цели запись по старому ID прекращается |
| Непустая ячейка | область + книга + поколение + сборка + лист + номер строки + номер столбца. Тип, введённое значение либо формула, вычисленное значение, формат и статус расчёта | Структурная правка меняет адреса. Для типизированной таблицы Sheets отдельно сохраняет логические ID таблицы, строк и столбцов. Координата A1 пригодна для показа, устойчивость цели проверяется по логическому ID |
| Предложение и исход команды | AI владеет предложением и его неизменяемым digest. Доменный обработчик хранит уникальную запись по (tenant_id, project_scope, effective_subject, resource_id, command_id) с хешем входа, результатом, маркером и квитанцией. Субъектом исполнения остаётся инициатор. Идентичность утвердившего рецензента хранится рядом с решением по предложению. Существенное для последующей проверки сохраняется либо в неизменяемом фрагменте, либо по ссылке на удерживаемую ревизию | Повтор с тем же намерением получает тот же результат при наличии текущих прав. Другой digest под тем же ключом отклоняется. Если сведения уже вышли за срок хранения, возвращать определённый контрактом исход; слепая повторная запись недопустима |

Идентичность организации, области проекта и субъекта выводится из доверенного контекста хоста. Для установки без отдельных проектов хост определяет одну стабильную область на организацию. Проверка актуального доступа к диску и ресурсу выполняется внутри этой области. В фоновой обработке используем область из проверенной записи задачи. Отбор видимых узлов и проверка прав выполняются до выдачи списка, сниппетов и содержимого, в том числе при попадании в кэш. Прямой и наследуемый доступ разрешает существующий механизм Drive.

## S3. Публикация и чтение

1. Писатель фиксирует изменение и outbox либо связь с восстанавливаемым журналом в домене. Проектор получает идентичность документа, поколение и интервал исходных позиций.
2. Для дельты проектор сравнивает поколение и позицию начала с опубликованной основой. Точный дубль игнорируется. При пропущенной позиции обработчик дочитывает недостающий участок либо строит полную проекцию. Событие прежнего поколения после restore отбрасывается.
3. Абзацы/ячейки и указатель версии публикуются одной транзакцией. Для большой перестройки заполняется новая сборка. Перед переключением указателя перепроверяются источник, поколение и основа. Читатель одного ответа фиксирует один снимок БД либо выполняет единый запрос с присоединением указателя. Нельзя совместить заголовок новой сборки со строками старой.
4. Текущее чтение после квитанции принимает минимум из доверенной квитанции. Если опубликованная позиция меньше, обработчик может сразу прочитать ограниченный фрагмент из авторитетного состояния с повторной проверкой доступа либо вернуть ожидание. После ожидания снова проверяются поколение и права. При смене поколения нужен новый запрос к восстановленному документу. Условие на позицию включает совпадение поколения.
5. Для проверки на момент фиксации используется неизменяемая квитанция с проверяемым результатом либо историческое состояние соответствующей позиции. Такой ответ переживает последующие правки человека в пределах срока хранения доказательства. Контроль текущего содержимого может закономерно дать другой ответ. Кэш формулы считается актуальным только при подтверждённых зависимостях и согласованной позиции расчёта.
6. Удаление документа закрывает его сразу на пути авторизованного чтения. Старую проекцию и блобы очищают после освобождения ссылок. Повтор события удаления и перезапуск уборки безопасны. Очистка одной организации не затрагивает данные другой.

### Векторы проверки для ревью

| Условие | Ввод | Ожидаемый результат |
| --- | --- | --- |
| Текст догоняет запись | Абзац p17, индекс (3,41), квитанция (3,42), сохранён текст «30 дней» | Актуальный авторизованный ответ «30 дней» с позицией ≥42 либо явное ожидание. Ответ «15 дней» под маркером 42 — дефект |
| Смена поколения | До публикации 42 восстановлена ревизия в поколении 4 | Обработчик поколения 3 не меняет текущий указатель. Проверка commit в поколении 3 использует историческое доказательство и текущий доступ |
| Отзыв разрешения | В момент поиска чтение разрешено, до выдачи фрагмента пользователь лишился доступа | SDK скрывает ресурс. Сниппет, название, позиция и квитанция не раскрываются |
| Расчёт отстаёт | B2 = 12, B3 = 8, D2 = SUM(B2:B3). Записано B2 = 15, прежний кэш D2 = 20 | Ответ о принятой записи и отдельный статус расчёта. Проверенное D2 равно 23. Значение 20 не маркируется пересчитанным |
| Задание повторилось | Две доставки одного события, затем событие с пропуском позиции | Одна публикация, догоняющее чтение с верной основой. Построенный заново индекс возвращает тот же форматированный фрагмент |
| Права двух организаций | Одинаковые локальные ID ресурсов, другая организация или actor | Никакой маркер предыдущей области не авторизует операции. Проверка по SDK и обычному доменному входу согласуется |

## S4. Измерить стоимость адресного чтения

На отдельном PostgreSQL 18 сравнить полный JSONB с проекцией по одному набору данных. В договоре из 1 100 блоков прочитать p16–p18, в книге из 100 000 непустых ячеек прочитать 20 адресов B2:E6. Провести 10 прогревочных и 50 измеренных чтений каждого из восьми вариантов на одном соединении. Для каждого сценария сверить хеш фактического ответа с ожидаемым до сравнения p95.

Из корня репозитория на Linux, от непривилегированного пользователя с PostgreSQL 18 и Python с psycopg 3, выполнить команду с новым именем файла. Скрипт создаёт собственный кластер и Unix-сокет. [Скрипт замера](https://github.com/axiomasoft/vaulter/blob/main/load/storage/run.sh)

```bash
PG_BIN=/usr/lib/postgresql/18/bin bash load/storage/run.sh /tmp/vaulter-storage-warm.json
```

В отчёте отделить SQL execute + fetch от времени HTTP, расчёта формул и работы модели. Записать число и размер ответов, сырые замеры времени, p95, план запроса и счётчики буферов. Для выбора физической схемы повторить ответы на корпусе 1× и 10×, измерить холодный доступ на выделенном стенде, стоимость записи, WAL, задержку публикации проекции и время перестроения после restore. Для холодного запуска отдельно указать состояние shared buffers и файлового кеша ОС. Критерии задачи 5.2
