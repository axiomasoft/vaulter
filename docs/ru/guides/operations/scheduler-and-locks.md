# Планировщик и блокировки

Vaulter ставит свои команды обслуживания в планировщик Laravel. Важны два переключателя:

- `vaulter.schedule.enabled` — `false`, если хост планирует команды сам;
- ключ каждой задачи (`outbox_relay`, `uploads_sweep`, …) — `null` выключает задачу.

Сервер должен запускать `php artisan schedule:run` каждую минуту. При нескольких серверах
`onOneServer` работает, только если кеш общий и поддерживает атомарные блокировки (redis, database,
memcached — не `file` и не `array`). Проверка:

<!-- snippet: shell -->

```bash
php artisan vaulter:doctor --check=core.scheduler
```

<!-- snippet: shell -->

```bash
php artisan vaulter:doctor --check=core.cache
```

Задача, идущая дважды, обычно означает неразделяемое хранилище блокировок; задача, которая не идёт
никогда, — что планировщик не запускается или `schedule.enabled` равен `false`.

## Диагностика и восстановление

1. Выполните `php artisan schedule:list` на каждом сервере планировщика. Сверьте параметры задач, окружение, часовой пояс и кеш. Проверьте последнее обращение к планировщику Laravel.
2. Если задача запускается на двух серверах, проверьте общее хранилище блокировок и одинаковый префикс кеша. Восстановите один планировщик и подключайте остальные после проверки одного запуска на интервал.
3. При остановке убедитесь, что прежний процесс завершён, прежде чем очищать зависшую блокировку. Запустите нужную команду один раз в документированной области и проверьте следующий запуск по расписанию.

При переходе на 64-битные advisory locks PostgreSQL остановите старые HTTP-процессы, воркеры загрузки
и фоновые задачи CAS перед запуском обновлённых процессов. После переключения проверьте загрузку и
сверку CAS. При откате к версии с 32-битными блокировками повторите остановку процессов.
