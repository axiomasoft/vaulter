# Резервное копирование и восстановление

Процедура для владельца host-приложения. Страница описывает действия, но не разрешает и не исполняет их.

## Симптом

Потеря БД или объектов, несогласованное восстановление либо репетиция требуют единой точки восстановления. При отсутствии байтов возможен `content_unavailable` (HTTP 423).

## Диагностика без изменений

Зафиксируйте tenant/drive id, версию и lockfile, состояние схемы, время и манифест копии. Проверьте доступность версий объектов без изменения рабочего хранилища.
<!-- snippet: shell -->

```bash
php artisan vaulter:doctor --json --check=core.schema
```
Doctor проверяет таблицы и типы ключей, но не возможность восстановления. На изолированной восстановленной копии выполните ограниченную выборку; замените `TENANT_ID` проверенным реальным id tenant.
<!-- snippet: shell -->

```bash
php artisan vaulter:blobs:scrub --dry-run --scope='tenant:TENANT_ID' --limit=100 --max-bytes=104857600 --max-seconds=30
```
Выборка не подтверждает целостность всего хранилища.

## Ограниченное действие

До замены БД, байтов или ключей получите явное разрешение владельца и проверенную резервную копию. Остановите writers, workers и плановые задания средствами host-приложения. Сохраните согласованно БД (включая ссылки, outbox, receipts), все диски/версии объектов с нужными blob и соответствующие ключи шифрования/подписания в приватном хранилище секретов. Вместе сохраните release, конфигурацию и манифест; сырые секреты не включайте в отчёт.

В изолированной среде сначала подготовьте соответствующие release/config/ключи, затем восстановите БД и объекты одной точки. Исходящие доставки до сверки отключены. Проверьте принадлежность ссылок tenant: общий scope хранения не является экспортом tenant. Встроенной команды backup/restore Vaulter нет.

## Проверка результата

Повторите диагностику схемы и выборку scrub, запишите число объектов/байтов, ошибки, непрочитанные объекты и причину остановки. Сверьте хеши манифеста и ссылки, разрешённое чтение tenant и запрет чтения чужому tenant. Перед подключением клиентов оцените необходимость инвалидировать change-journal cursors после восстановления БД. Переключение разрешает владелец; этот документ не квалифицирует runtime-восстановление.

## Откат

Сохраните исходный согласованный набор БД/объектов/ключей до переключения. При неуспехе оставьте writers остановленными и вернитесь к нему с разрешения владельца. Одна старая БД может потерять новые записи и нарушить ссылки; не смешивайте точки восстановления. См. [целостность CAS](./cas-integrity-incident).
