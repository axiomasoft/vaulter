# Мёртвые доставки outbox

Процедура для владельца host-приложения. Страница описывает действия, но не разрешает и не исполняет их.

## Симптом

Есть dead-доставки consumer, растёт очередь due либо записан gap. Доставка outbox и доставка endpoint webhook — разные сущности.

## Диагностика без изменений

Начните с существующих проверок:
<!-- snippet: shell -->

```bash
php artisan vaulter:doctor --json --check=core.outbox
```
Проверьте `core.outbox.dead`, `core.outbox.lag`, `core.outbox.consumer_gaps`, `core.outbox.leases`. Из записей событий/доставок только для чтения получите consumer id, state, attempts и минимальный затронутый интервал seq. Убедитесь, что события ещё удерживаются retention, и сначала исправьте причину отказа consumer. Счётчики doctor не доказывают применение события получателем. Для endpoint см. [webhook runbook](./webhook-delivery-failures-and-redelivery).

## Ограниченное действие

Replay меняет состояние и может повторить внешние эффекты. Получите явное разрешение владельца, проверенную копию БД и подтверждение идемпотентности получателя. Замените `CONSUMER_ID`, `FROM_SEQ`, `TO_SEQ` проверенными значениями (положительные числовые seq, from ≤ to). Начните с малого согласованного интервала: placeholders ниже не готовы для production.
<!-- snippet: shell -->

```bash
php artisan vaulter:relay:replay --consumer=CONSUMER_ID --from=FROM_SEQ --to=TO_SEQ
php artisan vaulter:relay --once --consumer=CONSUMER_ID --limit=100
```
Replay возвращает удерживаемые done/dead в pending с новым бюджетом попыток и подтверждает покрытые gaps. `--ack-only` лишь подтверждает потерю без replay и доставки; это не восстановление dead letters. Если события уже удалены retention, команда сообщает ошибку, а потеря требует отдельного решения владельца. Limit relay ограничивает доставки consumer за проход; регистрация и holds всё ещё охватывают всех consumers.

## Проверка результата

Запишите покрытый интервал и число dead→pending. Сверьте конкретные доставки и эффекты у consumer, повторите doctor и убедитесь в отсутствии необъяснённых gaps и повторного dead. Успешный exit relay подтверждает проход, а не успех каждого получателя; отслеживайте pending retries до завершения.

## Откат

При неверных эффектах остановите последующие relay средствами host-приложения. Команды отмены доставки нет: компенсация согласуется с владельцем consumer. Не восстанавливайте старую БД при активных consumers — это может повторить эффекты. Сохраните доказательства и копию; подтверждение невосстановимой потери — отдельное явное решение владельца.
