# Ротация ключей

Процедура для владельца host-приложения. Страница описывает действия, но не разрешает и не исполняет их.

## Симптом

Получатель webhook отклоняет подписи, секрет мог утечь либо требуется замена ключа шифрования приложения.

## Диагностика без изменений

По редактированным журналам определите endpoint, версию ключа и время смены. Проверьте состояния доставок и ошибки проверки у получателя, не записывая ключи, подписи или секреты payload.
<!-- snippet: shell -->

```bash
php artisan vaulter:doctor --json --check=core.webhooks
```
Исправная конфигурация не доказывает наличие верного секрета у получателя. Сопоставьте ошибки с изменением `APP_KEY` и возможностью расшифровки receipts/секретов.

## Ограниченное действие

Требуются явное разрешение владельца и защищённая проверенная копия зашифрованных данных вместе с соответствующими ключами. Для одного endpoint используйте существующую авторизованную операцию ротации из [Webhooks](/ru/guides/webhooks); CLI-команды ротации Vaulter нет. `vaulter-webhooks.secret_rotation_overlap` по умолчанию 86400 секунд, максимум семь дней. В overlap используются обе подписи; нулевой overlap сразу убирает старый секрет. Передайте новый секрет один раз приватно и обновите получателя. Не делайте вторую ротацию до его готовности: хранится лишь один предыдущий секрет.

Замена `APP_KEY` — отдельная миграция: она может лишить возможности расшифровать receipts и webhook-секреты. Сначала отрепетируйте поддерживаемую host-приложением миграцию шифрования с защищённым доступом к старым ключам. Direct URL подписываются учётными данными storage-провайдера: согласуйте их смену с ним. Изменение ACL Vaulter не отзывает ранее выданные URL; используйте короткий TTL и режим `strict`, если нужна немедленная проверка доступа. Ключи хаба описываются только в приватных инструкциях.

## Проверка результата

Проверьте контролируемую доставку с новым секретом и после истечения overlap. Проверьте конечные состояния доставок и расшифровку выбранных записей без вывода содержимого. Новые direct URL должны работать; учтите TTL старых. Общая HTTP-ошибка сама по себе не определяет проблемный ключ.

## Откат

При плановой смене внутри overlap можно вернуть получателю ещё действующий предыдущий секрет. После expiry или второй ротации такого возврата нет. Не возвращайте скомпрометированный секрет: изолируйте доставку и согласуйте новую ротацию. При неуспехе миграции шифрования остановите writers и восстановите согласованную пару данных/ключей, учитывая последующие записи.
