# Целостность блобов и сборка мусора

За сохранёнными байтами следят две задачи пакета media: **сборщик мусора** (`vaulter:blobs:gc`) удаляет байты,
которые никому не нужны, а **scrub** (`vaulter:blobs:scrub`) проверяет, что нужные байты остались теми, что были
записаны. Модель — в [Хранилище и блобы](/ru/concepts/storage-and-blobs).

## Когда блоб удаляется

Блоб удаляется, только если выполнено всё ниже; проверка повторяется внутри транзакции sweep:

1. В `v_blob_references` **нет ни одного pin**. Pins — истина, `ref_count` — кэш.
2. Блоб `tombstoned` и его `delete_after_at` прошёл (grace), либо он `pending` дольше orphan grace и без pins.
3. Pins перечитываются под lock `(scope, sha256)` и строкой блоба, затем `markDeleting → unlink → markDeleted`.

Следствия:

- Pins выключенного или удалённого из Composer модуля **не** снимаются; они держат байты. Pin снимает только
  purge или repair владельца, доказавший, что ссылки больше нет.
- Одинаковые байты в двух scope дедупликации — две строки; сборка одной не затрагивает другую.
- Тот же sha256 с другим размером отвергается при ingest, не перезаписывается.
- Pin на tombstoned-блоб без байтов или на `deleting`/`deleted` отвергается (`BlobUnavailableException`) и
  лечится новым коммитом байтов.
- Pending-блоб, получивший pin, коммитится или pin отвергается; блоб не теряется.

## Scrub

<!-- snippet: shell -->

```bash
php artisan vaulter:blobs:scrub                       # до 100 блобов
php artisan vaulter:blobs:scrub --limit=500 --max-bytes=5000000000 --max-seconds=600
php artisan vaulter:blobs:scrub --scope='tenant:42' --dry-run
```

Он выбирает committed-блобы без chunked-хранения по `integrity_checked_at`: сначала ни разу не проверенные, затем
самые старые. Каждый блоб читается потоком через драйвер хранилища и сверяется по размеру и sha256.

| Опция | Смысл |
|---|---|
| `--limit` | блобов за запуск (по умолчанию `vaulter-media.scrub.limit`, 100) |
| `--max-bytes` | остановиться после стольких прочитанных байт (`vaulter-media.scrub.max_bytes`, без лимита) |
| `--max-seconds` | остановиться по времени (`vaulter-media.scrub.max_seconds`, без лимита) |
| `--scope` | только один scope дедупликации |
| `--dry-run` | прочитать и сообщить, ничего не записывая |

Запуск заканчивается на **первом** исчерпанном бюджете. Полное чтение бакета S3 медленно и тарифицируется по
запросам, поэтому scrub по умолчанию **не планируется**: выберите размер выборки и периодичность под своё
хранилище (например, ночной запуск с `--limit` и `--max-seconds`); порядок «старые первыми» обеспечивает обход
всего за серию запусков.

Прошедший блоб получает новый `integrity_checked_at`. Отсутствующий блоб, а также блоб с другим размером или
дайджестом получает `integrity_failed_at`. Scrub **никогда** не удаляет байты, pins и строки и не пишет в
scan-таблицы drive.

| Код выхода | Смысл |
|---|---|
| 0 | сбоев не найдено |
| 1 | найден хотя бы один сбой |
| 2 | неверные опции |

### Как увидеть сбой и что делать

- `vaulter:doctor` — `media.blobs.integrity` предупреждает, пока у какого-либо блоба есть `integrity_failed_at`.
- Метрики — `vaulter_blobs_scrub_checked_total`, `vaulter_blobs_scrub_bytes_total`,
  `vaulter_blobs_scrub_failed_total{reason=missing|size|digest}`.
- Скачивание — `Blob::isIntact()` для сбойного блоба ложно, и drive отказывается отдавать его содержимое
  (`content_unavailable`, `423`), а не отдаёт повреждённые байты.

Для восстановления верните объект из резервной копии или загрузите те же байты заново: ingest того же sha256 в
тот же scope перезаписывает объект и снимает отметку под lock блоба — так же, как повторный коммит лечит
tombstone. Иначе отметка остаётся, и doctor продолжает предупреждать.
