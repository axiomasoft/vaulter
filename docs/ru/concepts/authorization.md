# Авторизация

Vaulter отвечает ровно на один вопрос авторизации: **может ли этот актор выполнить эту
способность над этим узлом?** Ответ вычисляет единственный движок, принадлежащий самому
Vaulter, — `AccessResolver`. Он складывает две полосы (lanes):

1. **пер-нодовый ACL** (строки `v_node_grants`) — собственное хранилище грантов Vaulter;
2. **сменную ролевую полосу хоста** (`PermissionDriver`) — мост к системе ролей вашего
   приложения.

Сам резолвер **не** контракт и **не** сменный — сменна только ролевая полоса (драйвер).

::: info Две полосы, один авторитет
`AccessResolver` (`Vaulter\Access\AccessResolver`) — единственный авторитет, к которому
обращаются все Policy, `DriveHandle`, контроллеры и Resource. Хост подключается к нему
через контракт `PermissionDriver`, но никогда не подменяет сам резолвер.
:::

## Публичная поверхность

| Метод | Возвращает | Назначение |
|---|---|---|
| `can(Authorizable $actor, Ability $ability, Node $node)` | `bool` | Единая точка «да/нет», которую зовут Policy и `DriveHandle`. |
| `effectiveGrants(Authorizable $actor, Node $node)` | `GrantSet` | Свёрнутый результат всего алгоритма — allow-маска, deny-маска, уровень. |
| `abilitiesFor(Authorizable $actor, Node $node)` | `array<string, bool>` | Каждая `Ability` → разрешена/запрещена; заполняет объект `abilities` для UI. |
| `canCreateInWorkspace(Authorizable $actor, Storage $storage)` | `bool` | Гейт создания папок/загрузок, где ещё нет узла. |
| `sharedNodeIds(Authorizable $actor)` | `list<int\|string>` | Кандидаты-узлы, на которые у актора есть живой allow-грант. |
| `filterSharedWith(Authorizable $actor, iterable $candidates)` | `list<Node>` | Перепроверяет кандидатов «поделились со мной» полным алгоритмом. |

```php
use Vaulter\Access\AccessResolver;
use Vaulter\Enums\Access\Ability;

$resolver = app(AccessResolver::class);

if ($resolver->can($user, Ability::Edit, $node)) {
    // актор может редактировать этот узел
}
```

`can()` — это сахар над `effectiveGrants($actor, $node)->allows($ability)`: алгоритм
живёт в одном месте, остальные методы лишь читают его результат.

## Способности, уровни и битовая маска CRUDS

Vaulter рассуждает в терминах одного целого числа. Любой грант сводится к **битовой
маске CRUDS** (`Vaulter\Enums\Access\Permission`), а каждая способность объявляет нужные
ей биты.

```
READ = 1   UPDATE = 2   CREATE = 4   DELETE = 8   SHARE = 16   ALL = 31
```

### Способности → требуемые биты

| Способность | Требуемые биты |
|---|---|
| `View`, `Download`, `Comment` | `READ` |
| `Edit` | `UPDATE` |
| `Create`, `Copy` | `CREATE` |
| `Move` | `UPDATE \| CREATE` |
| `Trash`, `Restore`, `Delete` | `DELETE` |
| `Share` | `SHARE` |
| `Manage` | `ALL` (31) |

Способность выполнима, только когда присутствуют **все** её биты.

### Уровни грантов → биты

| Уровень | Ранг | Биты |
|---|---|---|
| `Reader` | 1 | `READ` |
| `Commenter` | 2 | `READ` |
| `Writer` | 3 | `READ \| UPDATE \| CREATE` |
| `Organizer` | 4 | `READ \| UPDATE \| CREATE \| DELETE` |
| `Owner` | 5 | `ALL` (добавляет `SHARE` / управление) |

Более высокий ранг включает все нижние. Строка гранта может нести **и** уровень, **и**
дополнительные биты `permissions` — они объединяются по ИЛИ.

::: tip Нет отдельного действия delete
Отдельного «delete»-уровня нет: безвозвратное удаление сворачивается в бит `DELETE`
(`Organizer`/`Owner`), поэтому `Trash`, `Restore` и `Delete` требуют один и тот же бит.
:::

## Алгоритм

`effectiveGrants()` выполняет канонический алгоритм в пять шагов — ровно так, как описано
ниже, без скрытого поведения.

```
1. Override хоста (супер-админ) — абсолютный, в обе стороны.
2. Обход предков от ближнего к дальнему, ОГРАНИЧЕННЫЙ корнем хранилища;
   собираются прямые гранты + гранты scope=subtree для набора субъектов актора;
   СТОП на первом предке с inherit_grants = false.
3. aclAllow = max(allow-биты/уровни); deniedBits = ИЛИ deny-битов.
   Более БЛИЗКИЙ явный allow пробивает более ДАЛЬНИЙ унаследованный deny.
4. granted = max(aclAllow, roleAllow), где roleAllow приходит из драйвера.
5. ФИНАЛЬНОЕ ВЕТО: если deniedBits покрывает запрошенную способность → ЗАПРЕТ,
   независимо от ролевого гранта.
```

### Шаг 1 — override хоста

Резолвер сперва спрашивает у активного драйвера `override($actor, $scope)`. Override
уровня супер-админа (в стиле `Gate::before`) замыкает весь обход:

- `Effect::Allow` → `GrantSet::superAllowed()` (полный доступ);
- `Effect::Deny` → `GrantSet::superDenied()` (нет доступа);
- `null` → override нет, переходим к обходу ACL.

Override **абсолютен** — ни одна строка ACL на него не влияет.

### Шаг 2 — ограниченный обход предков

Драйвер разворачивает актора в **набор субъектов** через `subjectsFor($actor)` (сам
пользователь плюс его роли/команды на стороне хоста). Резолвер идёт по цепочке предков
узла **от ближнего к дальнему** — сам узел, его родитель, … до корня хранилища — собирая
живые гранты, адресованные этому набору субъектов.

Применяемость гранта на узле решают два правила:

- грант **на самом узле** применяется напрямую при любом scope;
- грант на **предке** применяется только при scope `subtree`.

Обход **ограничен хранилищем**: он никогда не пересекает `storage_id`, так что решение не
может выйти за пределы своего рабочего пространства. Срок действия проверяется на чтении
в запросе грантов — просроченная строка до резолвера не доходит, крона срока нет.

#### Отсечка inherit_grants

У каждого узла есть булево `inherit_grants`. Когда обход доходит до предка с
`inherit_grants = false`, **его собственные** гранты ещё учитываются, но **всё, что выше
него, — нет**: обход останавливается. Это отсечка наследования — узел можно «запечатать»,
чтобы он игнорировал гранты, заданные выше по дереву.

::: warning Deny на запечатанном узле — несокрушимая стена
Поскольку обход останавливается на узле с `inherit_grants = false`, deny на этом узле
оказывается на самой дальней достижимой глубине — пробить его более дальним allow нельзя.
Это постоянное вето для поддерева ниже отсечки.
:::

### Шаг 3 — свёртка deny-veto (явное важнее унаследованного)

Обход раскладывает allow-биты и deny-биты **по глубине** (ближний = глубина 0). Затем
свёртка применяет одно правило:

> `deny` на глубине *d* финален, **кроме** битов, разрешённых на *строго более близкой*
> глубине (`< d`). allow той же глубины НЕ пробивает deny той же глубины.

Следствия:

- более **близкий явный allow** пробивает более **дальний унаследованный deny** (доступ
  можно вновь открыть ближе к узлу);
- `allow` и `deny` на **одном узле** ⇒ побеждает **deny** (deny на том же узле —
  абсолютное вето).

### Шаг 4 — добавление ролевой полосы

Для каждого субъекта `resolve($subject, $actor, $scope)` драйвера может вернуть
`Decision` (уровень + allow + биты). allow-`Decision` объединяется по ИЛИ с allow-маской,
уровень сворачивается через `max()`:

```
allowedBits = aclAllowBits | roleAllowBits
level       = max(aclLevel, roleLevel)
```

Ролевая полоса складывается **до** вето, поэтому может **повысить** доступ, но **никогда
не воскресит запрещённый бит**. `AccessScope`, передаваемый драйверу, node-blind: он несёт
панель + координаты рабочего пространства и владельца узла, но не сам `Node`.

### Шаг 5 — финальное вето

Вето живёт в `GrantSet::allows(Ability $ability)`:

```php
public function allows(Ability $ability): bool
{
    if ($this->superDeny) return false;   // override-deny важнее всего
    if ($this->superAllow) return true;   // override-allow важнее всего

    $required = $ability->requiredBits();

    // Любой требуемый бит в deny-маске убивает способность.
    if (($this->deniedBits & $required) !== 0) {
        return false;
    }

    return ($this->allowedBits & $required) === $required;
}
```

Требуемый бит в deny-маске убивает способность **независимо** от allow-маски — поэтому
ролевой грант из шага 4 не может перебить ACL-deny.

## Флаги способностей для UI

Резолвер вычисляет плоскую карту способностей, чтобы фронтенд показывал только доступные
действия — без дублирования логики прав в JavaScript и лишних запросов.

`NodeResource` заполняет свой объект `abilities` через
`Vaulter\Access\ValueObjects\NodeAbilities::for($actor, $node, $resolver)`, который зовёт
`abilitiesFor()`. Когда актора нет, **все флаги false** (клиент показывает read-only
оболочку, а не рекламирует недоступные действия).

```json
{
  "data": {
    "id": "01J...",
    "name": "Q3 Proposal",
    "abilities": {
      "view": true, "download": true, "comment": true, "edit": true,
      "create": true, "move": false, "copy": true, "trash": false,
      "restore": false, "share": false, "manage": false, "delete": false
    }
  }
}
```

На клиенте каждый ресурс узла отдаёт свою карту `abilities` — привязывайте UI напрямую к этим
флагам (отсутствующее право трактуется как `false`).

## Гейт создания (узла ещё нет)

У создания папок и загрузок нет узла для проверки, поэтому они идут через
`canCreateInWorkspace($actor, $storage)`, который делегирует напрямую полосе драйвера
`canCreateInWorkspace($actor, $workspaceType, $workspaceId)`.

## «Поделились со мной»

`sharedNodeIds()` быстрым проходом по индексу субъектов в `v_node_grants` собирает
кандидатов-узлы, на которые у актора есть живой **allow**-грант. Затем кандидаты
**перепроверяются** полным алгоритмом в `filterSharedWith()` — потому что более близкий
`deny` мог отозвать видимость, которую подразумевал «сырой» грант.

## Fail-loud: null-драйвер

Драйвер по умолчанию — `database` (полностью автономная полоса без зависимостей от
хоста). Для локального старта есть **открытый** драйвер `Vaulter\Testing\NullPermissionDriver`,
дающий любому актору полный доступ через абсолютный override `Allow`.

`PermissionDriverManager` отвергает null-драйвер **в продакшене**:

```php
if (is_a($class, NullPermissionDriver::class, allow_string: true) && $this->isProduction) {
    throw MissingPermissionDriverException::nullDriverInProduction($key);
}
```

::: danger Никогда не выкатывайте null-драйвер
`null` выбираем только вне продакшена и существует лишь для того, чтобы потребитель мог
запустить и пощупать Vaulter без настройки реальной системы ролей. Отсутствующий или
`null`-драйвер **никогда** не откроет продакшен молча — он падает громко на этапе
резолвинга.
:::

Драйвер `azgard` требует `composer require axioma-studio/vaulter-azgard`.
Provider моста сам регистрирует драйвер и реальный адаптер guard; настройки находятся
в `vaulter-azgard.*`, а модель пользователя должна реализовать `AzgardBackedUser`.
