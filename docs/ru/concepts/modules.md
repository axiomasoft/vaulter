# Модули

Каждый пакет Vaulter — **модуль**: его сервис-провайдер только *предлагает* манифест, а ядро
модулей core решает, что активно, и затем регистрирует конфиг, связывания контейнера, маршруты,
команды, расписания и проверки doctor активных модулей (ADR-0027). Неактивный модуль ничего не
регистрирует во время работы; его схема базы данных при этом устанавливается.

## Активация

| Модуль | Пакет | Политика | Требует |
|---|---|---|---|
| `core` | `vaulter-core` | auto | — |
| `media` | `vaulter-media` | auto | `core` |
| `drive` | `vaulter-drive` (со срезами, пока лежащими в `vaulter-core`) | auto | `core`, `media` |
| `documents` | `vaulter-documents` | auto | `core`, `drive` |
| `azgard` | `vaulter-azgard` | auto (выбирается через `vaulter.access.permission_driver`) | `core`, `drive` |
| `filament` | `vaulter-filament` | auto (плагин панели хост подключает сам) | `drive` |
| `webhooks` | `vaulter-core` (пока у него нет своего пакета) | **opt-in** | `core`, `drive` |

*Auto*-модули активны, пока их не выключили; *opt-in*-модули — те, что открывают исходящую сеть
или требуют секретов, — только когда их включили. Политику переопределяет один ключ конфига:

```php
// config/vaulter.php
'modules' => [
    'webhooks' => true,   // включить исходящие вебхуки
],
```

Значения — только `true` или `false`, ключи — только установленные модули. Активный модуль,
чья зависимость неактивна, делает граф невалидным — зависимость молча не включается. Выключение
drive (`'drive' => false`) убирает его целиком, включая маршруты, команды и связывания, лежащие в
`vaulter-core`; каждый модуль, который его требует, тоже нужно выключить. Команда
`php artisan vaulter:modules` показывает каждый модуль, его политику, активен ли он и почему.
Ключа `vaulter.features.webhooks` больше нет; конфиг хоста, который его задаёт, падает при загрузке
с указанием на `vaulter.modules.webhooks`.

## Невалидный граф модулей

Граф компилируется один раз — после регистрации всех провайдеров и до загрузки любого из них,
без обращения к базе данных и сети. Если он невалиден (неизвестный ключ, не булево значение,
отсутствующая или неактивная зависимость, конфликт объявлений), **ни один** модуль не активен:

- artisan работает; `vaulter:modules` и `vaulter:doctor` печатают причины и завершаются с кодом `1`;
  остальные команды `vaulter:*` не определены;
- каждый маршрут под префиксом Vaulter отвечает `503` с кодом проблемы `module_graph_invalid`.

## Кэш маршрутов и конфига

`php artisan route:cache` замораживает набор маршрутов: закешированное приложение не перечитывает
маршруты из модулей. Каждая группа маршрутов модуля несёт middleware `vaulter.module:<id>` —
закешированный маршрут модуля, выключенного позже, отвечает `404` — и отпечаток модулей той
загрузки, при которой кэш собран. `vaulter:doctor` (`core.modules.cache`) сообщает о кэше,
собранном при другой активации, и об активном модуле, маршрутов которого в кэше нет. После смены
`vaulter.modules` пересоберите кэши (`php artisan optimize:clear && php artisan optimize`) и
перезапустите воркеры.

## Удаление модуля

Выключение модуля сохраняет его таблицы и данные. `php artisan vaulter:module:uninstall <module>`
строит план удаления схемы модуля в режиме dry run — его миграции и таблицы, модули, которые его
требуют, внешние ключи других владельцев на его таблицы — и сообщает причины отказа. Пока
create-миграции не разложены по владельцам, `--force` и `--purge` отказывают.
