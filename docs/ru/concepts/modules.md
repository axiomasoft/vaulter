# Модули

Каждый пакет Vaulter — **модуль**: его сервис-провайдер только *предлагает* манифест, а ядро
модулей core решает, что активно, и затем регистрирует конфиг, связывания контейнера, маршруты,
команды, расписания и проверки doctor активных модулей (ADR-0027). Неактивный модуль ничего не
регистрирует во время работы; его схема базы данных при этом устанавливается.

## Активация

| Модуль | Пакет | Политика | Требует |
|---|---|---|---|
| `core` | `vaulter-core` | auto | — |
| `media` | `vaulter-media` | auto | `core` |
| `drive` | `vaulter-drive` | auto | `core`, `media` |
| `documents` | `vaulter-documents` | auto | `core`, `drive` |
| `azgard` | `vaulter-azgard` | auto (выбирается через `vaulter-drive.access.permission_driver`) | `core`, `drive` |
| `filament` | `vaulter-filament` | auto (плагин панели хост подключает сам) | `drive` |
| `webhooks` | `vaulter-webhooks` (ставится отдельно) | **opt-in** | `core`, `drive` |
| `collaboration` | `vaulter-collaboration` (ставится отдельно) | **opt-in** | `core`, `drive`, `documents` |

*Auto*-модули активны, пока их не выключили; *opt-in*-модули — те, что открывают исходящую сеть
или требуют секретов, — только когда их включили. Политику переопределяет один ключ конфига:

```php
// config/vaulter.php
'modules' => [
    'webhooks' => true,       // включить исходящие вебхуки
    'collaboration' => true,  // включить редактирование в реальном времени (нужны URL хаба и два секрета)
],
```

Значения — только `true` или `false`, ключи — только установленные модули. Активный модуль,
чья зависимость неактивна, делает граф невалидным — зависимость молча не включается. Выключение
drive (`'drive' => false`) убирает его целиком — маршруты, команды, связывания и doctor-проверки; каждый модуль,
который его требует, тоже нужно выключить. Команда `php artisan vaulter:modules` показывает каждый модуль, его
политику, активен ли он и почему. Вебхуки переключаются только ключом `vaulter.modules.webhooks`
(`vaulter.features.webhooks` не существует; конфиг хоста, который его задаёт, падает при загрузке с указанием на
ключ модуля). Пакет нужно установить заранее: `composer require axioma-studio/vaulter-webhooks`. Коллаборация
переключается только ключом `vaulter.modules.collaboration`; активный opt-in модуль без обязательной конфигурации (URL
хаба и два секрета) — ошибка загрузки, а не тихий no-op ([Совместное редактирование](/ru/guides/collaboration)).

## Невалидный граф модулей

Граф компилируется один раз — после регистрации всех провайдеров и до загрузки любого из них,
без обращения к базе данных и сети. Если он невалиден (неизвестный ключ, не булево значение,
отсутствующая или неактивная зависимость, конфликт объявлений), **ни один** модуль не активен:

- artisan работает; `vaulter:modules` и `vaulter:doctor` печатают причины и завершаются с кодом `1`;
  остальные команды `vaulter:*` не определены;
- каждый маршрут под префиксом Vaulter отвечает `503` с кодом проблемы `module_graph_invalid`.

## Кэш маршрутов и конфига

`php artisan route:cache` замораживает набор маршрутов: закешированное приложение не перечитывает
маршруты из модулей. Каждая группа маршрутов модуля несёт middleware `vaulter.module:<id>` —
закешированный маршрут модуля, выключенного позже, отвечает `404` — и отпечаток модулей той
загрузки, при которой кэш собран. `vaulter:doctor` (`core.modules.cache`) сообщает о кэше,
собранном при другой активации, и об активном модуле, маршрутов которого в кэше нет. После смены
`vaulter.modules` пересоберите кэши (`php artisan optimize:clear && php artisan optimize`) и
перезапустите воркеры.

## Удаление модуля

Выключение модуля сохраняет его таблицы и данные. `php artisan vaulter:module:uninstall <module>`
строит план удаления схемы модуля в режиме dry run — его миграции и таблицы, строки в них, модули, которые его
требуют, внешние ключи других владельцев на его таблицы и media-пины, которые он держит, — и сообщает причины
отказа.

- `--force` откатывает миграции собственных schema-путей модуля (сначала новые). Отказ, пока в таблицах модуля есть
  строки или он держит пины, пока его требует другой установленный модуль, и для `core`.
- `--force --purge` сначала удаляет строки модуля и снимает его **собственные** media-пины, затем откатывает.
  `--purge` без `--force` — ошибка использования.
- Команда никогда не дропает, не удаляет и не снимает ничего у другого владельца, и никакой lock не удерживает
  писателей: сначала выключите модуль и остановите его трафик. То, что прочитал dry run, перечитывается внутри
  транзакции purge и перед каждым откатом; появившаяся строка или пин останавливает удаление.

Коды выхода: `0` — спланировано или выполнено, `1` — отказ или сбой без изменений, `2` — ошибка использования
(неизвестный модуль, `--purge` без `--force`), `3` — применено частично. На SQLite и PostgreSQL purge и откаты
идут одной транзакцией; на драйвере, где DDL коммитится (MySQL), сбой после purge оставляет модуль удалённым
частично — повторите `--force`. Байты media удалённого модуля остаются в хранилище до следующей сборки мусора.
