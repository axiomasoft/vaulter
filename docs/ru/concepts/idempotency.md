# Идемпотентность

Клиент, у которого запись оборвалась по таймауту, не знает, выполнилась ли она. С ключом идемпотентности он
просто повторяет запрос: Vaulter делает не больше одного эффекта на ключ и отвечает каждому повтору результатом
первого запроса ([ADR-0029](/adr/0029-idempotency)).

## Как передать ключ

Из PHP — ключ на handle; по HTTP — заголовок `Idempotency-Key`.

```php
$folder = Vaulter::drive($project)
    ->actingAs($user)
    ->withIdempotencyKey($request->header('X-Client-Request-Id'))
    ->folders()
    ->create('Reports');
```

```http
POST /api/vaulter/v1/drives/01J…/folders
Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"
Content-Type: application/json

{"name": "Reports"}
```

Ключ непрозрачен: 1–255 байт, сравнивается точно — без trim и смены регистра. По HTTP это одна Structured Field
String (`"…"`) или один токен без пробелов, управляющих символов и запятых; иное — `422 validation_failed`.
Берите новый случайный ключ (UUID) на каждый логический запрос и повторяйте его только для повторов этого запроса.

Ключ принимает каждая операция с политикой идемпотентности `receipt` (см. [Покрытие](#покрытие)); остальные
записи отклоняют ключ в PHP и игнорируют заголовок по HTTP, потому что их повтор и так безопасен по собственной
политике.

## Что получает повтор

| Ситуация | Ответ |
|---|---|
| тот же ключ, тот же запрос, первый закоммичен | сохранённый результат; по HTTP добавляется `Idempotent-Replayed: true` |
| тот же ключ, другой запрос (другое имя, родитель, `If-Match`, …) | `422 idempotency_key_reused`, ничего не выполняется |
| тот же ключ, пока первый запрос ещё выполняется | ждёт до 2 секунд, затем `409 operation_in_progress` с `Retry-After` |
| первый запрос упал и откатился | ничего не сохранено: повтор выполняется как новый запрос |
| позже 24 часов | квитанция истекла: повтор выполняется как новый запрос |

Воспроизведение никогда не выполняет запись повторно: ни второй папки, ни второго события, ни webhook. ETag в
ответе — тот, что был в первом ответе, пока узел вам виден (права в теге пересчитываются; для удалённого узла все выключены,
и тег отличается); сам по себе он не проходит последующий `If-Match`.

Ключ ограничен актором, tenant, диском и операцией: другой пользователь или тот же пользователь на другом диске
вашу квитанцию не увидит. Актор — это его тип и id, закодированные так, что разделитель внутри morph-алиаса или id
не склеивает двух акторов в одного; системный актор один и тот же при любой причине (reason).

## Авторизация при каждом воспроизведении

Воспроизведение отвечает только после того, как владелец проверит текущее право актора, как для нового запроса:

- ресурс существует → право на него **там, где он сейчас** (перенесён в невидимую папку → `404`);
- ресурса нет → право на папку, в которой он был записан, иначе на диск;
- grant отозван, ссылка истекла или диска нет → те же `404`/`403`, что получил бы новый запрос.

Отказ не меняет сохранённую квитанцию.

Квитанции update, snapshot и restore документа дополнительно требуют доступного узла
документа. Отсутствующий узел или узел в корзине отвечает `404 node_not_found` и в PHP:
Edit на корне не открывает прежнее содержимое или checkpoint из квитанции.

По HTTP маршрут называет только узел, поэтому повтор запроса к узлу, **удалённому насовсем**, не находит свой диск и
отвечает `404`. Другие квитанции узла могут воспроизводиться после перемещения в корзину с текущей проверкой
scope; перечисленные выше операции содержимого документа требуют исходного доступного узла.

## Какие отказы сохраняются

Каждый [код ошибки](/ru/reference/errors) объявляет политику **receipt**. Детерминированный отказ запроса —
`cacheable`: устаревший `If-Match` (`412`), конфликт имени (`409`), квота или лимит размера (`413`), недопустимое
имя (`422`) — сохраняется и воспроизводится, поэтому повтор не «проскочит» за счёт параллельного изменения.
Запись сначала откатывается к savepoint: от неё не остаётся ничего, кроме квитанции.

Отказы аутентификации, авторизации и видимости, `validation_failed`, `precondition_required`, `rate_limited`,
`dependency_unavailable`, `5xx` и временные сбои не сохраняются никогда (`never`): claim ключа откатывается вместе
с ними, и следующий повтор выполняется заново.

## Покрытие

Политика каждой операции объявлена в [каталоге операций](/ru/reference/operations)
([ADR-0032](/adr/0032-operation-catalog-and-concurrency)); маршрут операции `receipt` несёт middleware
`Idempotency-Key`.

| Политика | Операции | Повтор |
|---|---|---|
| `receipt` | создание, переименование, перенос, копирование, свойства, корзина, восстановление, purge, очистка корзины; восстановление и удаление ревизии файла; начало загрузки; гранты, наследование, шары, архивирование/разархивирование/удаление диска; документы: создание, обновление, снимок, восстановление; комментарии; endpoint'ы вебхуков и повторная доставка | сохранённый результат, `Idempotent-Replayed: true` |
| `natural` | star, unstar, флаги хранения, завершение или отмена загрузки, сессия коллаборации | второго эффекта нет и без ключа |
| `conditional` | content `PUT` документа, новая ревизия файла, загрузка файла | отвечает по предусловию: тот же `If-Match` после коммита — `412`, второй ревизии нет |
| `protocol` | хаб коллаборации, Tus `PATCH` | собственная дедупликация протокола (`update_id`, `Upload-Offset`, поколение) |

Перенос воспроизводится относительно **нового** места: право на узел и право создавать там, где он сейчас.
Purge и удаление сохраняют scope авторизации, под которым выполнены, и повтор проверяет текущее право актора на
этот scope. Квитанция `trash.empty` хранит счётчик по всему диску, поэтому её повтор требует текущего права
Delete на корне диска: актор, потерявший там Delete, получает `403` (профиль, который теперь исключает владельца
диска, отвечает своим отказом), актор, который больше не видит корень, — `404`, и никто из них не получает старый
счётчик. Это строже новой очистки, которая пропускает каждый узел корзины без права Delete и может ответить `0`:
актор с Delete только в поддереве очищает свою часть заново, но повтор такой очистки по ключу отклоняется, а не
возвращает сохранённый счётчик.

Грант только на удалённом узле исчезает вместе с ним и не даёт Delete на оставшегося
родителя. Первый purge может пройти, а повтор — получить отказ текущей проверки scope.
Квитанция сохраняется; повторного удаления и второго события не происходит.

## Операции, возвращающие секрет

Создание и ротация шара (токен), регистрация и ротация секрета endpoint'а вебхука (секрет подписи) возвращают
значение, которое нельзя вычислить заново. Их квитанции кодируются через `Crypt::encryptString` (`APP_KEY`),
поэтому открытого секрета нет в `v_idempotency_keys` в течение 24 часов. Повтор возвращает тот же секрет только
в том же scope (актор входит в digest ключа) и только после текущей авторизации. Смена `APP_KEY` делает старые
квитанции такого рода нечитаемыми; они игнорируются, как истёкшие.

## Хранение

`vaulter.idempotency.ttl_seconds` (86400 — 24 часа) — сколько квитанция отвечает повторам. Плановая команда
`vaulter:idempotency:prune` (`vaulter.schedule.idempotency_prune`, ежедневно в 03:30) удаляет истёкшие квитанции;
истёкшая квитанция игнорируется и до удаления.

**Повтор после истечения** — это новый запрос. Он не отвечает из старой квитанции и не является ошибкой: он
выполняется против текущего состояния. Повтор создания может создать вторую строку; повтор защищённой записи
(`If-Match`) отклоняется `412`, если агрегат ушёл вперёд. Повторяйте в пределах TTL и держите предусловие на
каждой записи, которая не должна повториться.

## Для авторов модулей

Операция становится идемпотентной, передав `IdempotentWrite` в `OperationRunner::write()`: версионируемый
`ReceiptCodec` результата, `ReplayAuthorizer`, который повторяет её авторизацию для воспроизведения (codec без него
не принимается), и отпечаток входа — идентификаторы ресурсов, поля, семантические опции и предусловия, но не
correlation id и не время. У составной записи одна квитанция — её корня.


Receipts сохраняют исторический семантический результат без ключа
читателя `sync_key` и HTTP ETag представления. После текущей авторизации replay ответ
проецирует текущего читателя и поколение ключа на этот результат; ETag представления
может измениться при повышении поколения. Отказ не меняет receipt и не создаёт запись,
event или webhook. `MutationContractCoverageTest` проверяет каталог мутаций и ссылки на
behavioral cases; эта структурная проверка не означает runtime qualification.
