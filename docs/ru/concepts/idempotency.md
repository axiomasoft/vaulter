# Идемпотентность

Клиент, у которого запись оборвалась по таймауту, не знает, выполнилась ли она. С ключом идемпотентности он
просто повторяет запрос: Vaulter делает не больше одного эффекта на ключ и отвечает каждому повтору результатом
первого запроса ([ADR-0029](/adr/0029-idempotency)).

## Как передать ключ

Из PHP — ключ на handle; по HTTP — заголовок `Idempotency-Key`.

```php
$folder = Vaulter::drive($project)
    ->actingAs($user)
    ->withIdempotencyKey($request->header('X-Client-Request-Id'))
    ->folders()
    ->create('Reports');
```

```http
POST /api/vaulter/v1/drives/01J…/folders
Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"
Content-Type: application/json

{"name": "Reports"}
```

Ключ непрозрачен: 1–255 байт, сравнивается точно — без trim и смены регистра. По HTTP это одна Structured Field
String (`"…"`) или один токен без пробелов, управляющих символов и запятых; иное — `422 validation_failed`.
Берите новый случайный ключ (UUID) на каждый логический запрос и повторяйте его только для повторов этого запроса.

В 1.0 ключ принимают `folders()->create()` (`POST …/folders`) и `nodes()->rename()` (`PATCH v1/nodes/{node}`);
остальные записи отклоняют ключ в PHP и игнорируют заголовок по HTTP, пока не объявят идемпотентность.

## Что получает повтор

| Ситуация | Ответ |
|---|---|
| тот же ключ, тот же запрос, первый закоммичен | сохранённый результат; по HTTP добавляется `Idempotent-Replayed: true` |
| тот же ключ, другой запрос (другое имя, родитель, `If-Match`, …) | `422 idempotency_key_reused`, ничего не выполняется |
| тот же ключ, пока первый запрос ещё выполняется | ждёт до 2 секунд, затем `409 operation_in_progress` с `Retry-After` |
| первый запрос упал и откатился | ничего не сохранено: повтор выполняется как новый запрос |
| позже 24 часов | квитанция истекла: повтор выполняется как новый запрос |

Воспроизведение никогда не выполняет запись повторно: ни второй папки, ни второго события, ни webhook. ETag в
ответе — тот, что был в первом ответе; сам по себе он не проходит последующий `If-Match`.

Ключ ограничен актором, tenant, диском и операцией: другой пользователь или тот же пользователь на другом диске
вашу квитанцию не увидит.

## Авторизация при каждом воспроизведении

Воспроизведение отвечает только после того, как владелец проверит текущее право актора, как для нового запроса:

- ресурс существует → право на него **там, где он сейчас** (перенесён в невидимую папку → `404`);
- ресурса нет → право на папку, в которой он был записан, иначе на диск;
- grant отозван, ссылка истекла или диска нет → те же `404`/`403`, что получил бы новый запрос.

Отказ не меняет сохранённую квитанцию.

## Какие отказы сохраняются

Каждый [код ошибки](/ru/reference/errors) объявляет политику **receipt**. Детерминированный отказ запроса —
`cacheable`: устаревший `If-Match` (`412`), конфликт имени (`409`), квота или лимит размера (`413`), недопустимое
имя (`422`) — сохраняется и воспроизводится, поэтому повтор не «проскочит» за счёт параллельного изменения.
Запись сначала откатывается к savepoint: от неё не остаётся ничего, кроме квитанции.

Отказы аутентификации, авторизации и видимости, `validation_failed`, `precondition_required`, `rate_limited`,
`dependency_unavailable`, `5xx` и временные сбои не сохраняются никогда (`never`): claim ключа откатывается вместе
с ними, и следующий повтор выполняется заново.

## Хранение

`vaulter.idempotency.ttl_seconds` (86400 — 24 часа) — сколько квитанция отвечает повторам. Плановая команда
`vaulter:idempotency:prune` (`vaulter.schedule.idempotency_prune`, ежедневно в 03:30) удаляет истёкшие квитанции;
истёкшая квитанция игнорируется и до удаления.

## Для авторов модулей

Операция становится идемпотентной, передав `IdempotentWrite` в `OperationRunner::write()`: версионируемый
`ReceiptCodec` результата, `ReplayAuthorizer`, который повторяет её авторизацию для воспроизведения (codec без него
не принимается), и отпечаток входа — идентификаторы ресурсов, поля, семантические опции и предусловия, но не
correlation id и не время. У составной записи одна квитанция — её корня.
