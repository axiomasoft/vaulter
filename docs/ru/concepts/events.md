# Журнал изменений

Каждый drive ведёт журнал изменений своих узлов. Клиент, который зеркалирует drive —
приложение синхронизации, поисковый индекс, кэш, — один раз обходит drive, берёт курсор и дальше
читает только то, что изменилось после него. Вебхуки остаются сигналом «проснуться»: журнал —
авторитетная упорядоченная запись (так устроены Dropbox, Microsoft Graph и Google Drive).

```php
$changes = Vaulter::drive($project)->actingAs($user)->changes();

$cursor = $changes->startCursor();          // после первоначального полного обхода
// … позже или когда пришёл вебхук:
do {
    $page = $changes->list($cursor, limit: 500);
    foreach ($page->changes as $change) {
        $replica->apply($change);
    }
    $cursor = $page->cursor;                 // сохраните его вместе с репликой
} while ($page->hasMore);
```

По HTTP тот же журнал — это два [маршрута REST v1](/ru/reference/rest-api#журнал-изменений):

```bash
# После первоначального обхода:
curl https://app.test/api/vaulter/v1/drives/01J.../changes/start -H 'Authorization: Bearer <token>'
# → { "data": { "cursor": "…" } }

curl 'https://app.test/api/vaulter/v1/drives/01J.../changes?cursor=…&limit=500' -H 'Authorization: Bearer <token>'
# → { "data": [ {"node_id", "operation", "reason", "subtree", "node_sequence", "node"} … ],
#     "meta": { "next_cursor": "…", "has_more": false } }
```

`node` — узел v1 так, как его сейчас видит читатель, со способностями и `etag`, или `null` для
`remove`. `meta.next_cursor` есть всегда: сохраняйте его, даже если страница пуста. При
выключенном журнале маршруты отвечают `403 profile_restriction`; поддельный или чужой курсор —
`400 invalid_cursor`, истёкший — `410 cursor_expired`.

HTTP-журнал доступен, если вызывающий видит хотя бы один узел этого drive, включая корень
корзины. Гранта на вложенную папку достаточно. Полностью невидимый drive отвечает
`404 drive_not_found` до выдачи или чтения курсора, как и неизвестный id.
Записи удаления сохраняют id, чтобы синхронизирующийся читатель удалил ранее сохранённый узел
после удаления, перемещения или потери доступа.

## Начало

1. Возьмите `startCursor()`.
2. Обойдите drive (`nodes()->children()`, рекурсивно) и сохраните результат.
3. Читайте `list($cursor)` от курсора из шага 1.

Курсор берётся **до** обхода, поэтому изменение, сделанное во время обхода, будет прочитано из
журнала ещё раз; применить его дважды безвредно.

## Применение страницы

`list(string $cursor, int $limit = 100): ChangePage` возвращает `changes` (список `NodeChange`),
следующий `cursor` и `hasMore`. Применяйте изменения по порядку, сохраняйте курсор и, пока
`hasMore` истинно, сразу запрашивайте снова. `limit` — 1..`changes.max_page_size` (по умолчанию
1000).

У каждого `NodeChange` есть `nodeId`, `operation`, `reason`, `subtree`, `node` и `nodeSequence`:

| Изменение | Что делать |
|---|---|
| `upsert` | Сохраните `node` (`NodeSnapshot` узла в его текущем состоянии) под `nodeId`; `nodeSequence` — его текущий sequence. |
| `upsert` с `subtree = true` | Сохраните `node`, затем перечитайте поддерево папки обходом: перемещение, копирование, восстановление или изменение доступа папки касается всех потомков, а запись есть только у папки. |
| `remove` | Удалите `nodeId` и, для папки, всё, что у вас есть под ней. `node` равен null. |

Журнал хранит последнее состояние узла, а не каждый шаг: узел может встретиться на странице
несколько раз — побеждает последнее вхождение. Храните копию деревом по id (`nodeId` →
`parentId`): переименованная или перемещённая папка не перечисляет потомков заново.

`reason` объясняет, почему узел удалён:

| `reason` | Смысл |
|---|---|
| `deleted` | Узел ушёл в корзину (папка — вместе с поддеревом). |
| `moved_out` | Узел перемещён туда, где этот читатель его не видит. |
| `permission_lost` | Изменение доступа (отзыв гранта, ограничение наследования) отняло его у этого читателя. |

Восстановление из корзины или грант, снова делающий узел видимым, — это `upsert` позже в журнале.

## Что видит читатель

Журнал фильтруется по доступу читателя **сейчас**, по тем же точным правилам, что и листинг:
`upsert` несёт снимок только для узла, который читатель видит; невидимый узел появляется только как
`remove` с причиной, когда его исчезновение объясняется перемещением или изменением доступа, и
иначе пропускается. Узел в корзине или удалённый навсегда никогда не показывается как upsert.
Системный актор (`asSystem()`) видит все узлы.

## Курсоры

Курсор — непрозрачная подписанная строка: храните её как есть. Он называет свой drive, арендатора
drive, эпоху журнала и позицию и подписан ключом, производным от `app.key`, — поддельный курсор или
курсор другого drive или арендатора отклоняется с `invalid_cursor` (400). Смена `app.key` делает
недействительными все сохранённые курсоры.

## Истёкшие курсоры

`list()` бросает `CursorExpiredException` (`cursor_expired`, 410), когда записей после курсора
больше нет:

- их удалил `vaulter:changes:prune` — записи живут `changes.retention_days` (по умолчанию 30) дней;
- `vaulter:changes:reset` начал новую эпоху журнала drive (после восстановления из бэкапа).

Пересинхронизируйтесь: возьмите новый `startCursor()`, обойдите drive заново и замените копию.
Читатель никогда не пропускает записи молча: prune в той же транзакции отмечает, до какого места
удалил, а чтение проверяет эту отметку после чтения.

## Хранение

Запускайте prune ежедневно:

```php
Schedule::command('vaulter:changes:prune')->daily();
```

Клиент, бывший офлайн дольше окна хранения, пересинхронизируется при следующем чтении. См.
[Команды](/ru/reference/commands#vaulter-changes-prune) и
[Конфигурация → Журнал изменений](/ru/reference/config).

## Вебхуки

Конверт вебхука несёт `changes.seq` — позицию его события в журнале. Используйте вебхук, чтобы
разбудить клиента и прочитать журнал от сохранённого курсора; доставки не упорядочены и могут
повторяться, журнал — нет. См. [Вебхуки → Конверт](/ru/guides/webhooks#конверт).

## Что попадает в журнал

`folder.created`, `file.uploaded`, `file.revision_added`, `node.renamed`, `node.moved`,
`node.copied`, `node.updated`, `node.trashed` (remove), `node.restored`, `document.created`,
`document.updated` (каждое сохранение содержимого), `document.restored`, `grant.created`,
`grant.revoked` и `access.inheritance_changed` — одна запись на событие, для узла, которого оно
касается. Жизненный цикл drive, загрузки, комментарии, ссылки и удаление ревизий — не изменения
состояния узлов и в журнал не попадают; полное удаление уже стало `remove` из корзины.

Журнал пишется в транзакции самого изменения, последним шагом: изменение и его запись коммитятся
вместе, а записи становятся видимыми в порядке своих позиций. По умолчанию он включён
(`features.changes`); выключение и повторное включение оставляет разрыв, который закрывает только
`vaulter:changes:reset`.
