# Журнал изменений

Журнал drive обеспечивает синхронизацию с ключами конкретного читателя (PLAN4-D20).
Вебхук будит клиент; упорядоченные изменения читает журнал. Начальная синхронизация:

## Начало

1. Получите `C0 = $drive->changes()->startCursor()` вне внешней транзакции.
2. Рекурсивно обойдите видимые узлы, сохранив `sync_key` каждого узла и локальное дерево.
3. Читайте `$drive->changes()->list(C0)` по порядку. Сохраняйте каждый новый курсор,
   включая пустые страницы; продолжайте, пока `hasMore` равен true.

C0 до обхода исключает потерю изменений во время обхода. Проекция проверяет текущие права;
курсор не даёт доступа. HTTP требует хотя бы один видимый узел drive (вложенный grant или
видимый корень корзины достаточен); полностью невидимый drive отвечает 404.

## Применение страницы

Upsert содержит `operation`, `sync_key`, `node_id`, `subtree`, `node_sequence` и `node`.
Снимок узла отражает текущие права. Храните ключ читателя вместе с id. При `subtree: true`
повторно обойдите потомков папки. Обычные списки, show и кэшированные снимки тоже проецируют
ключ текущего читателя; он входит в хеш ETag представления читателя. У анонимного upsert ключ null;
анонимному читателю remove не выдаётся.

Remove содержит ровно `operation: remove` и `sync_key`: без raw id узла, причины, снимка,
subtree и sequence. По сохранённому ключу удалите локальный узел и известных локальных
потомков. Неизвестный ключ безопасно игнорировать. Повторное применение допустимо;
побеждает последнее изменение. Минимизация идентичности не скрывает корреляцию активности
и времени: журнал не обещает анонимность.

## Курсоры

Непрозрачный подписанный feed cursor формата 2 аутентифицирован, но не зашифрован. Он связан
с tenant, drive, типизированным principal (включая system reason), поколением ключа, epoch,
позицией, исходным временем выпуска и зафиксированным deadline. Повреждённый, чужой или
курсор формата 1 даёт `400 invalid_cursor`: удалите локальное соответствие и начните заново.
Ротация `app.key` без перекрытия ключей тоже может дать этот ответ.

## Истёкшие курсоры

Deadline — минимум прежнего deadline, исходного времени выпуска плюс текущий
`cursor_max_age_seconds` и ближайшего непустого срока живого grant из набора subjects
читателя в этом drive. Отсутствие срока не добавляет ограничения. Страницы не обновляют
время выпуска и не продлевают deadline. Deadline, поколение и epoch/prune проверяются до
и после проекции. Истечение, смена поколения, reset epoch или удалённая история дают
`410 cursor_expired`: повторите bootstrap и замените локальное соответствие.

`vaulter-drive.changes.key_generation` по умолчанию 1; владелец повышает его на всех
инстансах после выключения/включения журнала или ротации ключевого материала. Это меняет
все sync keys. При выключенной функции HTTP отвечает `403 profile_restriction`; одно
включение не исправляет пропуск истории. `cursor_max_age_seconds` по умолчанию 86400,
не больше 2592000 и retention.

Записи узлов/доступа журналируются транзакционно. Existing access invalidation повышает
head epoch, включая tenant/global invalidation, без второго permission framework.
Receipt хранит нейтральный снимок: replay заново проверяет права и проецирует ключ текущего
читателя. Ключ читателя не сохраняется в общей receipt; ETag представления зависит от этого ключа.

## Списки и feed

По PLAN4-D21 продолжение списка зашифровано и аутентифицировано, связано с endpoint,
tenant, типизированным subject, query и version. Оно скрывает sort keys просмотренных
строк, сохраняет прогресс через невидимые строки; пустая страница может иметь продолжение.
Читайте до null. HTTP grants/shares ограничены страницами; публичные PHP array
`list()`/`grants()` сохранены. Этот контракт отделён от подписанного feed cursor выше.

## Retention и квалификация

Запускайте `vaulter:changes:prune` ежедневно; `retention_days` по умолчанию 30.
`vaulter:changes:reset` начинает новый epoch. См. [Команды](/ru/reference/commands) и
[Конфигурацию](/ru/reference/config). PostgreSQL/MySQL isolation, конкурентная invalidation,
Redis/relay races, остановка процесса и реальные consumers остаются pending в runbook
владельца P8.2; SQLite и структурные проверки не квалифицируют эти окружения.

Для независимо закреплённых/shared roots remove родителя инвалидирует известную ветвь,
после чего клиент заново проверяет уже известные affected ids через find/list. Сохраните
корни с действующим прямым nested grant и перечитайте их поддеревья. Корневой listing
не перечисляет все независимо выданные descendants. Скрывайте stale records при
reconciliation; применяйте страницу и checkpoint атомарно только после успешной сверки.
Viewer-null/domain events, outbox, webhook, activity, export и ShareSession не содержат
пользовательский sync key. Старый кэш после feature-off требует полного bootstrap.
Host вызывает `AccessInvalidation::changed()` после commit внешнего role/profile/tenant
изменения и обеспечивает durable retry. Ошибка не означает успешный отзыв; до уведомления
есть интеграционное окно, ограниченное текущими правами и конечным горизонтом курсора.
