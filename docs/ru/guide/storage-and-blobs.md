# Хранилище и блобы

Vaulter никогда не копирует байты файлов в собственные таблицы. Каждый загруженный файл
хранится **один раз** как неизменяемый контент-адресуемый **блоб** на диске Flysystem, а
база данных держит только метаданные: `sha256`, размер, диск, ключ с учётом области,
статус жизненного цикла и рёбра, которые удерживают блоб живым при версиях файла.

Это **контент-адресуемое хранилище (CAS)**. Оно даёт вам прозрачную дедупликацию, чёткое
разделение между *байтами на диске* и *строками в базе данных*, а также сборщик мусора,
который безопасно запускать даже во время идущих загрузок.

::: info Где это живёт
Реализация CAS — в `Vaulter\Media\Cas\*` (пакет `axioma-studio/vaulter-media`;
обращённый к хосту `BlobLock` остаётся в core как `Vaulter\Cas\BlobLock`), модель строки —
`Vaulter\Models\Cas\Blob`, enum жизненного цикла — `Vaulter\Enums\Cas\BlobStatus`, а
конфигурация лежит под ключами `cas`, `dedup`, `gc` и `storage` файла `config/vaulter.php`.
:::

## Ментальная модель

```
поток загрузки
     │
     ▼
ContentStore::stage()   ─► локальный перематываемый temp-файл, sha256 пересчитан с ТЕХ байтов
     │
     ▼
BlobStore::commit()     ─► одна залоченная транзакция: find-or-create строку v_blobs по (scope, sha256)
     │                       └─ попадание в дедуп?  переиспользуем строку, пропускаем физическую запись
     ▼
ContentStore::promote() ─► пишем staged-байты в "<scope>/ab/cd/<sha256>" на диске
     │
     ▼
v_file_version_blobs    ─► РЕБРО, которое удерживает блоб живым (истина о живучести)
```

Работу делят три контракта, и все три сменяемы через `config('vaulter-media')`:

| Контракт | По умолчанию | Ответственность |
|---|---|---|
| `Vaulter\Contracts\Cas\BlobStore` | `Vaulter\Media\Cas\BlobStore` | Высокоуровневый жизненный цикл: `commit` / `attach` / `detach` / `read`. Единственная точка входа в CAS. |
| `Vaulter\Contracts\Cas\ContentStore` | `Vaulter\Media\Cas\Sha256ContentStore` | Байтовая сторона: `stage` / `promote` / `get` / `exists` / `delete` / `keyFor`. Знает байты, хэши и ключи — но никогда строку `v_blobs`. |
| `Vaulter\Contracts\Cas\StorageDriver` | `Vaulter\Media\Cas\FlysystemStorageDriver` | Тонкая абстракция над Flysystem: `put` / `get` / `exists` / `delete` / `temporaryUrl` / `disk`. |

```php
// config/vaulter-media.php
'content_store'  => \Vaulter\Media\Cas\Sha256ContentStore::class,
'storage_driver' => \Vaulter\Media\Cas\FlysystemStorageDriver::class,
'blob_store'     => \Vaulter\Media\Cas\BlobStore::class,

```

Все три биндятся в сервис-провайдере и резолвятся через контейнер, поэтому значения безопасны
для кэша конфига (только FQCN, никаких замыканий). Направьте любой из них на свой класс, чтобы
изменить, как байты стейджатся, хэшируются, промоутятся или хранятся — см.
[Рецепты › Свой storage-драйвер](/ru/guide/recipes).

## Байты на диске, метаданные в базе

Блоб — это лишь метаданные. Строка `v_blobs` (модель `Vaulter\Models\Cas\Blob`) несёт:

| Колонка | Смысл |
|---|---|
| `sha256` | Контент-адрес в нижнем регистре hex (всегда пересчитывается на сервере). |
| `size_bytes` | Авторитетный размер устойчивых байтов. |
| `disk` | Диск Flysystem, на котором живёт канонический объект. |
| `storage_key` | Путь объекта с учётом области — `"<scope>/ab/cd/<sha256>"`. |
| `status` | Состояние жизненного цикла (см. [Жизненный цикл блоба](#blob-lifecycle)). |
| `ref_count` | **Согласуемый кэш** количества живых рёбер — *не* истина о живучести. |
| `dedup_scope` | `tenant` \| `drive` \| `off` (`global` у ещё не исправленных блобов) — граница, в пределах которой адрес уникален. |
| `tenant_id` / `storage_id` | Дискриминаторы области (присутствуют всегда; индексируется только релевантный). |
| `first_seen_at` / `committed_at` / `delete_after_at` | Метки времени стейджинга, коммита и grace-окна GC. |

Сами байты никогда не появляются ни в одной колонке. Метки времени модели отключены
(`public $timestamps = false`) — CAS сам управляет своими тремя метками.

### Ключ хранилища квалифицирован областью

`ContentStore::keyFor()` строит путь из области дедупа плюс двухуровневый шард по первым
четырём hex-символам дайджеста:

```php
// Vaulter\Media\Cas\Sha256ContentStore::keyFor()
"{$scope}/{$a}/{$b}/{$sha256}"   // напр. "t42/ab/cd/abcd…ef"  (scope = tenant 42)
```

::: warning Почему сегмент области важен
При дедупе по областям две области могут вполне законно держать один и тот же `sha256`. Без
сегмента области, вшитого в ключ, сборщик мусора *одной* области мог бы удалить живые байты
*другой* области. Сегмент области гарантирует, что разные области никогда не резолвятся в один
и тот же физический объект.
:::

Сегмент области выводится из области дедупа:

- `tenant` → `t-{id}` или `d-{id диска}`, если у диска нет тенанта
- `drive` → `d-{id}`
- `off` → `o-{ulid}` — собственная область для каждой загрузки

Объекты упразднённой общей области (`g` и устаревший сегмент `global`) остаются читаемыми,
пока их не перенесёт `vaulter:blobs:repair-scopes`.

## Хэширование: staged-файл, никогда не живой поток

`Sha256ContentStore::stage()` сливает входящий поток в **локальный, перематываемый temp-файл**
(чанками по 1 MiB) и вычисляет `sha256` с *тех устойчивых байтов*.

::: danger Vaulter никогда не доверяет хэшу от клиента
Контент-адрес **всегда** пересчитывается на сервере из staged-файла — лживый клиентский
`sha256`, `expected_sha256` резюмируемой загрузки или `ETag` многочастевой загрузки S3 никогда
не используются как контент-адрес. Хэширование происходит *вне* транзакции БД, поэтому
хэширование загрузки в несколько ГБ никогда не держит блокировку строки/advisory.
:::

Staged-объект (`Vaulter\Media\Cas\StagedTempObject`, реализующий
`Vaulter\Contracts\Cas\StagedObject`) отдаёт `path()`, `sha256()`, `sizeBytes()`,
`readStream()` и идемпотентный `discard()`, который удаляет temp-файл, как только байты
запромоучены (или коммит откатился).

## Дедупликация и `vaulter-media.dedup.scope`

Область дедупа решает границу, в пределах которой контент-адрес уникален:

```php
// config/vaulter-media.php
'dedup' => [
    'scope' => env('VAULTER_DEDUP_SCOPE', 'tenant'), // tenant|drive|off
],
```

| Область | Уникальность | Эффект |
|---|---|---|
| `tenant` | `UNIQUE (scope_key, sha256)` | Один объект на тенант — без утечки существования между тенантами; диск без тенанта дедуплицируется только в себе. **По умолчанию.** |
| `drive` | `UNIQUE (scope_key, sha256)` | Один объект на диск (`storage` читается как `drive`). |
| `off` | `UNIQUE (scope_key, sha256)` | Каждая загрузка хранится отдельно. |

Дедупликация никогда не пересекает тенанта (PLAN2.D49): общая для инсталляции область позволила бы
одному тенанту узнать, что другой хранит данный файл. Прежняя настройка `global` отклоняется при
загрузке с `InvalidConfigurationException`; существующие `global`-блобы переносятся в тенанта (а без
тенанта — в диск) каждой ссылающейся ревизии командой
`php artisan vaulter:blobs:repair-scopes --dry-run`, затем `--execute`. Ответы загрузки и квота
никогда не зависят от того, сдедуплицировались ли байты.

Эта единственная настройка приводит в движение **обе** стороны дизайна разом:

1. **Форму дедуп-UNIQUE-индекса.** `SchemaBuilder::dedupUniqueColumns()` выдаёт индекс
   по `(sha256)`, `(tenant_id, sha256)` или `(storage_id, sha256)`. Колонки `tenant_id` /
   `storage_id` *всегда* существуют в `v_blobs`; только UNIQUE-индекс покрывает
   релевантное области подмножество.
2. **Ключ с учётом области**, описанный выше.

::: tip UNIQUE-индекс — переносимый гоночный хребет
Когда два запроса загружают идентичные байты одновременно, ограничение `UNIQUE (scope, sha256)`
служит кросс-БД хребтом: один `INSERT` выигрывает, проигравший ловит нарушение уникальности,
пере-`SELECT`-ит выигравшую строку и переиспользует её. Это работает на PostgreSQL, MySQL и
SQLite даже там, где advisory-блокировка ниже — no-op.
:::

::: warning Выбор области — дверь в одну сторону
Область вшита в `storage_key` каждого блоба *и* в уникальный индекс. Выберите её на этапе
установки. `tenant` — безопасное значение по умолчанию для мультитенантных приложений, потому
что мешает одному тенанту узнать, что другой держит данный файл (утечка существования), ценой
хранения идентичных байтов по одному разу на тенант. О том, как `vaulter-media.dedup.scope = tenant`
взаимодействует с тенантностью хоста, см. [Мультитенантность](/ru/guide/multi-tenancy).
:::

## Поток коммита

`BlobStore::commit()` — единственная точка входа в CAS. Он запускает **одну** транзакцию,
**первый оператор** которой — блокировка по `(scope, sha256)`, поэтому каждое решение о
живучести принимается по строкам, прочитанным *после* блокировки:

```php
// Vaulter\Media\Cas\BlobStore::commit() — упрощённо
$staged = $this->content->stage($stream);          // 1. stage + hash ВНЕ транзакции
$key    = $this->content->keyFor($scope, $staged->sha256());

DB::transaction(function () use (…) {
    $this->lock->acquire($scope, $staged->sha256());          // 2. lock = оператор №1

    $result = $this->blobs->findOrCreate(…);                  // 3. find-or-create по дедуп-ключу
                                                              //    (совпавший tombstone ВОСКРЕШАЕТСЯ)

    if ($result['created'] || !$this->content->exists($key)) { // 4. промоутим байты только когда нужно
        $this->content->promote($staged, $key, $disk);
    }

    return $result['blob'];
});
```

Ключевые свойства (все из `Vaulter\Media\Cas\BlobStore`):

- **Стейджинг происходит вне транзакции.** Блокируется только решение о живучести.
- **Попадание в дедуп пропускает физическую запись.** Байты промоутятся только когда строка
  создана заново (или канонический объект почему-то отсутствует — `promote()` идемпотентен и
  условен, так что воскрешённая строка, чей объект исчез, безопасно перепромоучивается).
- **Никакого синхронного `ref_count++`.** Истина о живучести — это *ребро* в
  `v_file_version_blobs`; `ref_count` — согласуемый кэш, который может отставать.

### Прикрепление и чтение

Закоммиченный блоб удерживается живым **ребром версия↔блоб**:

```php
$blobStore->attach($fileVersion, $blob, ['role' => 'data', 'ordinal' => 0]);
$blobStore->detach($fileVersion, $blob);   // байты здесь НЕ удаляются — этим занимается GC
$stream = $blobStore->read($blob);         // resource|null над каноническими байтами
```

В Drive это связывается через `Vaulter\Drive\Actions\Files\IngestFileAction`: он зондирует размер,
проверяет квоту хранилища *до* коммита байтов, вызывает `BlobStore::commit()` внутри
транзакции, затем создаёт `File` / `FileRevision` и ребро. `tenant_id` и `storage_id`,
переданные в `commit()`, читаются прямо из строки владеющего `Storage`.

## Выдача байтов по HTTP

Чтение блоба — внутренняя операция. До HTTP-клиента байты доходят только через точку
[выдачи файлов](/ru/reference/rest-api#выдача-файлов) REST v1, которая на **каждый** запрос заново
проверяет доступ, арендатора, профиль и состояние проверки и фиксирует **точную ревизию** (голову
или явно указанную). Способ выбирает `vaulter.downloads.delivery_mode`:

| Режим | Что получает клиент | Отзыв |
|---|---|---|
| `strict` (по умолчанию) | байты потоком через приложение, `Cache-Control: private, no-store` | проверяется каждый новый запрос; уже начатый поток не обрывается |
| `direct_signed` (по выбору) | `302` на URL, подписанный вашим `Vaulter\Contracts\Cas\DirectContentUrlSigner` для этой версии объекта, действующий `vaulter.downloads.direct_ttl_seconds` (1–300) | уже выданный URL действует до истечения — отзыв доступа его не отменяет |

Для `direct_signed` нужен signer в контейнере; он получает неизменяемую идентичность содержимого
(блоб, ключ хранилища, версия объекта, sha256, размер) и должен подписать ровно её. Выбирайте этот
режим, только если ограниченное окно отзыва приемлемо для ваших данных. Ревизия с нечистым
состоянием проверки в обоих режимах даёт `423 content_unavailable` до любого байта или URL;
скачивания по публичным ссылкам всегда идут потоком. Диапазоны байтов в 1.0 не отдаются
(`Accept-Ranges: none`).

## Жизненный цикл блоба

`Vaulter\Enums\Cas\BlobStatus` — это конечный автомат:

```
Pending → Committed → Tombstoned → Deleting → Deleted
              ↑____________|
             (воскрешение)
```

| Состояние | Смысл |
|---|---|
| `Pending` | Строка есть, байты застейджены, но ещё не устойчивы+проверены. Упавший стейджинг оставляет строку `Pending`, которую подметут по таймауту. |
| `Committed` | Байты устойчивы, `sha256` проверен — живое состояние. |
| `Tombstoned` | GC пометил как неудерживаемый; `delete_after_at` несёт grace-дедлайн. Конкурентный коммит **воскрешает** его обратно в `Committed`. |
| `Deleting` | Sweep захватил его; физическое удаление в процессе. |
| `Deleted` | Байты удалены; строка сохраняется как идемпотентный tombstone, чтобы повторный запуск sweep был no-op. |

Enum обеспечивает легальные переходы через `allowedTransitions()` / `canTransitionTo()`, а
`isLive()` возвращает true для `Pending` и `Committed` (оба удерживают свои байты).

## Сборка мусора (двухфазная, безгоночная)

Когда вы удаляете файл в корзину и очищаете её, рёбра версий отцепляются. Блоб без оставшихся
рёбер — *мусор*, но безопасно удалить его байты, пока загрузки могут воскрешать именно этот
`sha256`, — самое сложное. GC Vaulter (`Vaulter\Media\Cas\BlobGarbageCollector`) решает это в две
фазы, **слепой к ACL** и работающий от имени системы (узел, который пользователь не видит, всё
равно удерживает свой блоб).

### Фаза 1 — mark

Сканируем `committed ∧ ref_count <= 0` (запрос `scopeGarbageCollectable`). Для каждого
кандидата, под блокировкой по `(scope, sha256)`, **перепроверяем**, что:

- статус всё ещё `Committed` (дешёвый скан может быть устаревшим), и
- в `v_file_version_blobs` нет живого ребра.

Если оба условия выполняются, `tombstone()` ставит `status = Tombstoned` и `delete_after_at =
now + grace`. Grace-дедлайн взводится *здесь*, поэтому sweep никогда не сможет удалить в
пределах grace-окна.

### Фаза 2 — sweep

Берём `tombstoned`-блобы за пределами их grace (`scopeSweepable`). Под блокировкой
перепроверяем, что блоб всё ещё `Tombstoned`, у него всё ещё нет живого ребра и он за
пределами `delete_after_at`. Только тогда: `markDeleting` → физическое удаление объекта с
учётом области → `markDeleted` (идемпотентный tombstone; отсутствующий объект — норма).

::: tip Инвариант безопасности
Каждая транзакция, меняющая живучесть контент-адреса — upload-commit, GC-mark, GC-sweep —
берёт блокировку по `(scope, sha256)` **первым оператором** и решает по строкам, прочитанным
*после* неё. Именно это делает онлайн-GC безопасным: коммит, выигравший блокировку, воскрешает
tombstone-блоб *до того*, как sweep его увидит; sweep, выигравший блокировку, перепроверяет
существование ребра *до* удаления.
:::

По драйверам БД (`Vaulter\Cas\BlobLock`):

- **PostgreSQL** — `pg_advisory_xact_lock(hashtext(scope||sha256))`, настоящий мьютекс,
  удерживаемый всю транзакцию. Sweep дополнительно работает в `SERIALIZABLE` с
  повтором-по-`40001` (до 5 попыток).
- **MySQL / MariaDB** — нет transaction-advisory-блокировки, которая жила бы как в PG, поэтому
  хранилище опирается на `SELECT … FOR UPDATE` по строке блоба; advisory-хелпер — no-op.
- **SQLite** — один писатель; сама транзакция сериализует.

Ограничение `UNIQUE (scope, sha256)` — переносимый хребет, работающий на всех трёх даже когда
advisory-блокировка — no-op.

### Sweep pending-строк

`sweepPending()` вычищает строки от упавшего стейджинга — строку `Pending` старше grace-окна
(`first_seen_at < now − grace`), не несущую ребра. Её, возможно, частичный объект удаляется, а
строка финализируется как удалённый tombstone, под блокировкой, чтобы медленный-но-живой коммит
никогда не был украден.

### Запуск сборщика

```bash
# Обе фазы (mark + sweep), grace из config('vaulter-media.gc.grace_hours'):
php artisan vaulter:blobs:gc

# Переопределить grace-окно (нижняя граница 1h):
php artisan vaulter:blobs:gc --grace=48

# Ещё и вычистить PENDING-строки от упавшего стейджинга:
php artisan vaulter:blobs:gc --pending
```

Команда печатает подсчёт по фазам — `Tombstoned X, swept Y, skipped Z (grace Nh)`.

```php
// config/vaulter-media.php
'gc' => [
    'grace_hours'        => env('VAULTER_GC_GRACE_HOURS', 24),
    // Отдельное, обычно более щедрое окно для обхода диска на orphan-объекты
    // (см. «Согласование» ниже). По умолчанию равно gc.grace_hours, нижняя граница 1h.
    'orphan_grace_hours' => env('VAULTER_ORPHAN_GRACE_HOURS', env('VAULTER_GC_GRACE_HOURS', 24)),
],
```

::: warning Grace-окно должно переживать вашу самую медленную загрузку
Tombstone-блоб может быть воскрешён идущей загрузкой того же `sha256`. Grace должно быть
**≥ худшей задержки многочастевого коммита**, чтобы загрузка успела воскресить первой. Оно
ограничено снизу 1h в `MediaConfig::gcGraceHours()` вне зависимости от конфига — никогда не ставьте
его в ноль в расчёте на мгновенную очистку.
:::

::: details Запланируйте это сами
`vaulter:blobs:gc` и `vaulter:blobs:reconcile` регистрируются пакетом, но **не** ставятся в
планировщик автоматически — Vaulter не трогает ваш scheduler. Добавьте их туда, где вы
планируете обслуживание, например в `routes/console.php`:

```php
use Illuminate\Support\Facades\Schedule;

Schedule::command('vaulter:blobs:reconcile')->daily();
Schedule::command('vaulter:blobs:gc --pending')->dailyAt('03:00');
```

Запускайте reconcile *до* GC, чтобы `ref_count` отражал реальность, когда mark-скан его читает.
:::

Полный операционный рецепт — в [Рецепты › Cron для GC блобов и reconcile](/ru/guide/recipes).

## Согласование: пересборка кэша `ref_count`

`ref_count` — кэш, а не истина, поэтому он дрейфует. `vaulter:blobs:reconcile` (за которым стоит
`Vaulter\Media\Cas\BlobReconciler`) пересобирает его из счётчиков рёбер `v_file_version_blobs` —
реального источника живучести — и сообщает об угрозах целостности. Он **никогда ничего не
удаляет**.

```bash
php artisan vaulter:blobs:reconcile
```

Он обходит каждый блоб, переписывает любой устаревший `ref_count` и помечает **висячие строки**
— блоб `Committed`, чей канонический объект *отсутствует на диске* (недопромоученный коммит или
запоротое ручное удаление). Команда завершается с ненулевым кодом и предупреждает о
ключах проблемных блобов:

```
Reconciled 1240 blobs, corrected 3 ref_count caches.
Dangling rows (committed blob, missing object): 01J…ABC, 01J…XYZ
```

### Orphan-объекты: обход диска

Висячая строка — одна из двух обратных угроз целостности; другая — **orphan-объект** — байты на
диске, совпадающие с раскладкой ключей закоммиченного CAS, но **вообще без строки блоба**
(коммит, который запромоутил байты, а потом откатил строку, или утёкшие байты). Обнаружение
требует обхода *диска* — обратной операции к row-side reconcile выше. Флаг `--orphans`
добавляет этот обход диска в ту же команду:

```bash
# Обнаружить orphan-объекты (только отчёт) в дополнение к row-side reconcile:
php artisan vaulter:blobs:reconcile --orphans

# Сканировать конкретный диск и переопределить orphan-grace-окно (часы, нижняя граница 1h):
php artisan vaulter:blobs:reconcile --orphans --disk=s3 --orphan-grace=48

# УДАЛИТЬ найденные orphan-объекты — только PostgreSQL/MySQL (на SQLite отклоняется; см. ниже):
php artisan vaulter:blobs:reconcile --orphans --prune
```

Он печатает свою строку рядом с подсчётом reconcile:

```
Orphan walk (report-only): scanned 1240, found 2, pruned 0, skipped 1238 (disk s3, grace 24h).
Orphan objects (bytes with no blob row): t42/ab/cd/abcd…ef, t42/12/34/1234…99
```

::: warning По умолчанию только отчёт — и запуск ЗАВЕРШАЕТСЯ С ОШИБКОЙ при найденных orphan-объектах
Без `--prune` обход только **обнаруживает и сообщает** об orphan-объектах (безопасный dry-run на
любом драйвере). Как и проверка висячих строк, запуск в режиме отчёта, нашедший хоть один
orphan, **завершается с ненулевым кодом**, чтобы cron/CI увидел угрозу. Только запуск с
`--prune`, который реально их удалил, завершается успехом.
:::

Sweep построен так, чтобы *трогать только* настоящие канонические orphan-объекты. Его защиты,
по порядку:

1. **Точная раскладка CAS-ключа, проверенная round-trip.** Путь становится кандидатом только
   когда он в точности совпадает с `"<scope>/<a>/<b>/<sha256>"` *и* `keyFor(scope, sha256)`
   пере-выводит **тот же** путь — так что байты шарда действительно являются шардом этого
   дайджеста. Staging/tmp-части, фрагменты резюмируемой загрузки, чужие файлы и любой
   неправильно шардированный путь никогда не совпадают и **никогда** не рассматриваются к
   удалению.
2. **Любая строка блоба означает «принадлежит».** Совпавший объект, у которого есть *любая*
   строка `v_blobs` (в любом статусе, ищется без учёта диска, поскольку `storage_key` глобально
   уникален), принадлежит системе, а не является orphan-объектом.
3. **Orphan-grace-окно.** Объект без строки — удаляемый orphan только когда он **старше
   orphan-grace** — только что запромоученный объект может быть коммитом-в-процессе, чья строка
   ещё не устойчива. Всё моложе grace (или чей возраст диск не может сообщить) пропускается,
   никогда не удаляется.
4. **Залоченная перепроверка перед удалением.** Удаление по `--prune` происходит под той же
   блокировкой по `(scope, sha256)`, что использует GC, перепроверяя и отсутствие строки, и
   grace *после* взятия блокировки, затем удаляет идемпотентно — так что у коммита, который
   только что создал владеющую строку, никогда не выметут байты из-под ног.

::: danger `--prune` отклоняется на SQLite — только PostgreSQL/MySQL
Prune удаляет байты под **write-less** критической секцией, которая сериализует против
конкурентного коммита только на драйвере, чья блокировка упорядочивает секцию без записи строк
(advisory xact lock PostgreSQL; `FOR UPDATE` MySQL). На **SQLite** такое упорядочивание никогда
не включается — конкурентный коммит мог бы вставить владеющую строку между перепроверкой и
удалением — поэтому prune там **отклоняется** (команда предупреждает и деградирует до режима
отчёта). **Обнаружение работает на любом драйвере**; только деструктивный `--prune` требует
PostgreSQL/MySQL. Запускайте отчёт локально или prune против продовой БД.
:::

::: info Диск, который нельзя перечислить, пропускается, а не роняет запуск
Обходу диска нужен CAS content store, умеющий листить диск (`ListableContentStore`). Если
активный store его **не** реализует, обход сообщает `"listing unsupported"`, ничего не
сканирует и завершается чисто. Listable-store поверх бэкенда, который не возвращает записей
(например, не-`FilesystemAdapter`-диск, который нельзя перечислить), просто сканирует **ноль**
объектов — так же безопасно: ничего не перечислено, значит ничего не удалено. В любом случае
результат row-side reconcile остаётся в силе.
:::

::: details Orphan-grace отделён от GC-grace
Обход orphan-объектов использует `config('vaulter-media.gc.orphan_grace_hours')` (env
`VAULTER_ORPHAN_GRACE_HOURS`), который **по умолчанию равен `vaulter-media.gc.grace_hours`** (24) и ограничен
снизу 1h. Держите его ≥ вашей худшей задержки многочастевого коммита по той же причине, по
которой GC-grace должно быть щедрым: идущая резюмируемая загрузка может запромоутить свои байты
задолго до коммита своей строки, и свежий объект нельзя принять за orphan.
:::

## Диски Flysystem: `local`, S3 и per-storage

Блобы живут на стандартном диске Laravel Flysystem. Диск для данного блоба резолвится на каждый
вызов через `FlysystemStorageDriver::disk()`: колонка `disk` самого блоба (заданная из
владеющего `v_storages.disk`) выигрывает, иначе — дефолт инсталляции:

```php
// config/vaulter.php
'storage' => [
    'default_disk' => env('VAULTER_DISK', 'local'),
],
```

Поскольку это просто диск Flysystem, работает любой драйвер — `local`, `s3` или свой —
настроенный в `config/filesystems.php` вашего приложения. CAS делает только потоковые записи
плюс несколько удобств объектных хранилищ, которые деградируют изящно:

- **Условное создание.** На объектном хранилище `put()` с `ifNoneMatch` мапится в
  `If-None-Match: *`, так что конкурентный загрузчик идентичных байтов не может затереть; `412`/
  `409` отдаётся как возврат `false` (пере-`SELECT` + переиспользование), а не исключение. На
  `local`/SQLite-test условного PUT нет, поэтому оно деградирует до best-effort-охраны
  `exists()` — реальным сериализатором там служит блокировка по `(scope, sha256)`.
- **Server-side-контрольная сумма.** На S3 `promote()` прикрепляет `x-amz-checksum-sha256`
  (base64 сырого дайджеста), так что S3 проверяет staged-байты; локальный драйвер её
  игнорирует, поэтому передавать её безопасно и с учётом конфига.
- **Подписанные URL.** `temporaryUrl()` выпускает короткоживущий подписанный URL только на
  дисках, которые это поддерживают (`providesTemporaryUrls()`); диск `local`/SQLite-test
  возвращает `null`, а не бросает исключение.

::: danger Держите CAS-бакет БЕЗ ВЕРСИОНИРОВАНИЯ
Канонический CAS-бакет **не** должен использовать lifecycle/versioning S3 как механизм удаления
блобов. Авторитет удаления — двухфазный GC Vaulter; правило lifecycle S3, удаляющее блобы
из-под него, породит висячие строки. (Правило lifecycle `AbortIncompleteMultipartUpload` для
*резюмируемых загрузок* — это другой, рекомендуемый предохранитель — см. конфиг `uploads`.)
:::
