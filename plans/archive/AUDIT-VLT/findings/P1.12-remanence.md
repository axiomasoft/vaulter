## 2. Находки

### F-P1.12-01 — Узел в корзине остаётся скачиваемым и экспортируемым (trash не влияет на авторизацию/резолвинг) · Severity: Major · Уверенность: high

**Где:** `packages/core/src/VaulterServiceProvider.php:195-199` (route-bind `node` = `findOrFail`), `packages/drive/src/Http/Controllers/DownloadController.php:79-115` (нет проверки `trashed_at`), `packages/core/src/Access/AccessResolver.php` (алгоритм H.2 не консультирует `trashed_at`), `packages/documents/src/Http/Controllers/DocumentNodeController.php:182-228` (`export`/`guardDocument` без trash-проверки).
**Что:** Мягкая корзина (`trashed_at`) — отдельная от Laravel-SoftDeletes (`deleted_at`) колонка. Route-model-binding `{node}` резолвит узел через `findOrFail`, чей софт-делит-скоуп исключает только `deleted_at`, но НЕ `trashed_at`. `AccessResolver::can` и `DownloadController` нигде не сверяются с `trashed_at`. Итог: `GET nodes/{node}/download`, `.../versions/{v}/download` и `GET nodes/{node}/export` на узле, лежащем в корзине, отдают его содержимое, если у актора сохранился грант.
**Почему опасно:** G4.1 — «удалённые» файлы остаются доступны по прямым URL. Пользователь считает файл удалённым (он в корзине, скрыт из листингов — `NodeReadRepository` везде `whereNull('trashed_at')`), но содержимое живёт ещё 30 дней (`trash.retention_days`) и всё это время скачивается/экспортируется по прямому object-id любым актором с непогашенным грантом. Share-канал этот путь закрывает (C2), а identity-канал скачивания и экспорта — нет. Ассиметрия: `ShareResolver` явно бьёт по `trashed_at`, а download/export — нет.
**Доказательство:** repro `plans/AUDIT-VLT/artifacts/repro/P1.12/RemanenceReproTest.php`, runtime-вывод: `C1 live_can_download=true … trashed_can_download=true` (тот же грант, узел переведён в корзину `trashed_at=…`, `deleted_at=null`, `AccessResolver::can(Download)` по-прежнему `true`). Source: `DownloadController` не содержит `trashed_at`/`trashed(`; `AccessResolver` не содержит `trashed_at`.
**Норма, которая нарушена:** G4.1 (`findings/P0-audit-gaps.md` §2) — тест «доступ после soft-delete»; S3.1 (авторизация на каждом запросе не учитывает жизненный цикл). Плановый критерий C1.
**Сверка с ADR:** ADR о корзине/ремоненции нет (`docs/adr/` — только 0006 blobs-gc). Докблок `VaulterServiceProvider.php:185` сознательно резолвит trashed-узел, чтобы работали restore/force/download — но download/export trashed-узла есть непреднамеренное следствие, а не осознанное разрешение раздавать корзину. Дефект (недостающий контроль), не «ADR устарел».
**Рекомендация:** В `guardDownload` и `guardDocument` (или в отдельном item-safety-слое, симметрично `ShareResolver::safeTargetNode`) добавлять отказ (404/403) при `trashed_at !== null` для read/download/export-путей, оставляя резолвинг trashed-узла только для restore/forceDelete. Альтернатива — read-only-эндпоинты биндят через явный `whereNull('trashed_at')`, мутационные (restore/force) — через `withTrashed`-эквивалент.

### F-P1.12-02 — «Force-delete»/purge никогда не удаляет строки физически: контент документных версий остаётся в БД навсегда · Severity: Major · Уверенность: high

**Где:** `packages/drive/src/Actions/ForceDeleteNodeAction.php:41-72`, `packages/core/src/Repositories/Drive/NodeStoreRepository.php:123-137` (`softDeleteSubtree` = `->delete()` по SoftDeletes-модели), `packages/core/src/Schema/PanelTablesBuilder.php:582-585` (FK `node_document_versions.node_id` `cascadeOnDelete`), `packages/drive/src/Console/PurgeTrashCommand.php:49-52`.
**Что:** Операция, называемая «force delete» / «permanent purge», физически ничего не удаляет: `ForceDeleteNodeAction` вызывает `softDeleteSubtree`, который делает `$model::query()->whereKey(...)->delete()` по модели `Node` с трейтом `SoftDeletes` — это ставит `deleted_at`, а не удаляет строку. Поскольку узел удаляется мягко, DB-каскад `cascadeOnDelete` на `v_node_document_versions` НЕ срабатывает. Строки версий документов, хранящие контент ИНЛАЙН (`content`, `yjs_state`), остаются в базе бессрочно — и после `vaulter:purge-trash` (retention-истечения) тоже, потому что purge зовёт тот же soft-delete.
**Почему опасно:** G4.2 — история версий удерживает чувствительный контент после «зачистки». Здесь хуже: не только историю, а весь контент «навсегда удалённого» документа. Нарушает ожидание безвозвратности (право на удаление / GDPR erasure, регуляторные требования DMS): администратор, выполнивший purge-trash, уверен, что содержимое уничтожено, а `SELECT content FROM v_node_document_versions` его возвращает. Файловые блобы при этом освобождаются (рёбра отцеплены → GC байтов), что создаёт ложное впечатление полной зачистки — на деле документный контент и метаданные (`v_nodes`, `v_file_versions`) не физически удаляются нигде в пакете (грепом `->forceDelete()`/hard-delete по узлам/версиям — 0).
**Доказательство:** `softDeleteSubtree`: `$model::query()->whereKey($ids->all())->delete();` при `Node use SoftDeletes` (`Node.php:62`) → `deleted_at`-tombstone (докблок `NodeStoreRepository.php:123` сам называет это «soft-delete … deleted_at tombstone»). FK `->cascadeOnDelete()` (`PanelTablesBuilder.php:585`) срабатывает лишь на физический `DELETE`, которого не происходит. Ни один код-путь не делает hard-delete строк узлов/версий.
**Норма, которая нарушена:** G4.2 (`findings/P0-audit-gaps.md` §2). ADR-0006 (жизненный цикл содержимого) — покрывает GC байтов CAS, но не at-rest-строки инлайн-контента документов.
**Сверка с ADR:** ADR-0006 говорит о двухфазном GC блобов, но НЕ о физическом удалении строк версий/узлов при purge; document-версии инлайновые и вне CAS. Пробел, не осознанное решение → дефект.
**Рекомендация:** На стадии `vaulter:purge-trash` (после истечения retention) выполнять действительный hard-delete: `Node::withTrashed()->...->forceDelete()` по поддереву, чтобы каскад `cascadeOnDelete` физически снёс `v_node_document_versions`/`v_file_versions`; либо явным `delete` по `node_document_versions` в `ForceDeleteNodeAction`. Разделить семантику: «force-delete» (в корзину-стадия-2 = `deleted_at`) vs «purge» (физическое уничтожение). Задокументировать политику ретеншена контента в ADR.

### F-P1.12-03 — `keep_forever` невозможно снять: закреплённая версия никогда не попадёт в prune · Severity: Minor · Уверенность: high

**Где:** `packages/documents/src/Http/Controllers/DocumentNodeController.php:137-149` (установка), `packages/documents/src/Repositories/NodeDocumentVersionStoreRepository.php:82-92` (prune уважает флаг), отсутствие write-пути сброса.
**Что:** `keep_forever` выставляется при снапшоте именованной версии (`storeVersion`, гвард `Edit`), но пакет не имеет ни эндпоинта, ни Action, сбрасывающего `keep_forever` обратно в `false` (грепом по write-путям — только установка `'keep_forever' => $data->keepForever`). Prune навсегда исключает такие строки (`where('keep_forever', false)`).
**Почему опасно:** G4.2/remanence — версия, закреплённая `keep_forever`, удерживает контент в истории неограниченно и не может быть выпущена в окно prune иначе как force-delete всего узла (который, к тому же, не удаляет строки физически — F-P1.12-02). Пользователь не может «раскрепить» и дать системе очистить старый чувствительный снапшот.
**Доказательство:** установка — `CreateNamedVersionData::keepForever`/`storeVersion`; сброса нет (нет `keep_forever => false` в апдейтах, нет соответствующего маршрута в `documents.php`). Prune-исключение — `NodeDocumentVersionStoreRepository.php:86`.
**Норма, которая нарушена:** G4.2 (управляемость жизненного цикла версий). Плановый критерий C6.
**Сверка с ADR:** осознанного решения «keep_forever односторонний» в ADR нет → дефект точности (недостающая операция).
**Рекомендация:** добавить операцию снятия `keep_forever` (PATCH по версии, гвард `Edit`), после которой версия снова подпадает под окно prune; либо задокументировать одностороннюю семантику как сознательную.

## 3. Не проверено / ограничения

- **Истинная HTTP-эксплуатация C1/C10** не воспроизведена сквозным запросом: repro доказывает решение `AccessResolver::can`=true на trashed-узле (runtime) и отсутствие trash-проверки в download/export-путях (source), но полный `GET nodes/{node}/download` через роутер с реальным binding не гонялся. Уверенность high по конструкции (binding `findOrFail` + отсутствие guard).
- **F-P1.12-02 at-rest** доказан статически (SoftDeletes + soft-delete в `softDeleteSubtree` + каскад только на физический DELETE + отсутствие hard-delete в коде); фактический `SELECT` из БД после purge-trash в runtime не выполнялся.
- **Файловые версии без prune**: `v_file_versions` не имеют механизма ограничения числа версий (в отличие от документных `max_versions`) — рёбра на блобы живут, пока жив узел. Это ретеншн-политика, не утечка; отдельной находкой не завожу (пересечение с C5/ретеншеном), но отмечаю как смежный риск бесконтрольного роста.
- **C9 throttle** — не дублирую в REGISTER: находка уже F-P1.8-01 (Major). Здесь только пересечение.
- **MySQL/PG каскад** для F-P1.12-02 подтверждён по схеме (`cascadeOnDelete` объявлен), но не измерен на реальном PG — вывод «каскад не срабатывает на soft-delete» верен на уровне ORM независимо от драйвера.
