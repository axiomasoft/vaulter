## 2. Находки

### F-P1.1-01 — Докблок объявляет «un-overridable wall», но deny на `inherit_grants=false` пробивается более близким allow · Severity: Major · Уверенность: high

**Где:** `packages/core/src/Access/AccessResolver.php:41` (докблок класса), `:205-210` и `:273-276` (докблок/комментарий `resolveAcl`), фактический fold — `:291-301`.
**Что:** Класс-докблок утверждает: «a deny on an inherit_grants=false node is an un-overridable wall», а комментарий cut-off — «a deny on this wall is permanent … no farther/**nearer** allow can ever pierce it». Код же в фазе 2 вычитает из deny-маски биты allow со **строго меньшей** глубины (`$allowDepth < $depth`) без исключения для узла-стены. Более близкий allow (между целью и стеной) снимает deny стены.
**Почему опасно:** Администратор, полагающийся на «глухую стену» (`inherit_grants=false` + deny) для локдауна поддерева, получает НЕ то, что обещает докблок: пользователь с ранее выданным allow на промежуточной папке сохраняет доступ сквозь deny-стену. Рассинхрон объявленной гарантии безопасности и реального поведения — источник тихой over-permission при аудите прав силами оператора по докблоку.
**Доказательство:** repro `plans/AUDIT-VLT/artifacts/repro/P1.1/AccessResolverAuditTest.php` (тест `C6`), дерево `top → wall(inherit_grants=false, deny READ subtree) → mid(allow READ subtree) → target`:
```
[C6] wall-deny pierced by nearer allow => View allowed on target: TRUE
{"tool":"pest","result":"passed","tests":4,"passed":4,"assertions":8}
```
**Норма, которая нарушена:** Расхождение кода с докблоком H.2 (Code Guidance item'а P1.1: «расхождение кода с докблоком = находка Major»). Косвенно — S1.4 (семантика hard-deny маркера должна быть однозначной).
**Сверка с ADR:** `docs/adr/0007-pluggable-authorization.md` — «a nearer explicit `allow` beats a farther inherited `deny`», без исключения для стены. **Код соответствует ADR-0007; неверен именно докблок** (заявляет гарантию, которой ADR не давал). Это НЕ «ADR устарел». Открытый вопрос дизайна: должна ли пара `inherit_grants=false`+deny быть абсолютным барьером (как трижды подразумевает докблок) — продуктовое решение, требует эскалации (rule conflict между intent докблока и ADR-0007).
**Рекомендация:** Либо привести докблок/комментарии в соответствие с кодом и ADR-0007 (удалить утверждение «un-overridable»/«nearer allow can never pierce»), либо — если абсолютный барьер действительно нужен — ввести явный признак «wall-deny» и исключить его биты из `$nearerAllow` в `resolveAcl`. Выбор — за владельцем (эскалация).

### F-P1.1-02 — Нет механизма «explain access» (какой ACE дал вердикт) · Severity: Minor · Уверенность: high

**Где:** `packages/core/src/Access/AccessResolver.php:73-115` (`effectiveGrants`), `:124-135` (`abilitiesFor`), `packages/core/src/Access/ValueObjects/GrantSet.php` (несёт только маски/уровень).
**Что:** Резолвер отдаёт итоговый `GrantSet` (allow-маска, deny-маска, level) и bool-флаги abilities, но не сохраняет провенанс — какой грант на каком узле и с какой глубиной дал allow либо deny. Инструмента «почему у актора такой вердикт» нет.
**Почему опасно:** Прямой эксплуатируемой уязвимости нет; цена — отладка эффективных прав на дереве практически невозможна (S1.7: без explain-access неверный вердикт не локализовать), что повышает риск нераспознанных ошибок конфигурации ACL в проде.
**Доказательство:** во всём публичном API `AccessResolver` (`can`, `effectiveGrants`, `abilitiesFor`, `filterSharedWith`, `sharedNodeIds`) нет возврата решающего ACE; `resolveAcl` (`:215-304`) вычисляет `allowByDepth`/`denyByDepth` локально и отбрасывает их после fold.
**Норма, которая нарушена:** S1.7 (`findings/P0-dms-security.md`) — «обязателен инструмент explain access».
**Сверка с ADR:** `docs/adr/0007` explain-access не упоминает и не отвергает — сознательного решения нет, значит это пробел, а не «ADR устарел».
**Рекомендация:** добавить диагностический путь (напр. `explain(actor, ability, node): AccessExplanation` с цепочкой ACE/глубин), не меняя горячий `can()`.

### F-P1.1-03 — Driver-вернувший `Decision::deny()` тихо игнорируется, вопреки докблоку «folded the same way the ACL deny path is» · Severity: Major · Уверенность: high

> **ОПРОВЕРГНУТО ВЕРИФИКАЦИЕЙ** (2/3 скептиков), см. `artifacts/repro/verify-F-P1.1-03/`. В REGISTER не вносится.

**Где:** `packages/core/src/Access/AccessResolver.php:315-336` (`resolveRole`) и его докблок `:306-312`; точка сборки `:98-105`.
**Что:** Докблок `resolveRole` заявляет: «a driver-returned deny is folded the same way the ACL deny path is». Фактически метод возвращает только `[bits, level]` (allow-маску) и на `:327` пропускает любое решение, у которого `!$decision->isAllow()` — deny-решение драйвера отбрасывается и структурно не может попасть в `deniedBits` (в `effectiveGrants` берётся лишь `$roleAllowBits`). `HostRoleDriver::resolve`, вернувший `Decision::deny(...)`, не влияет на вердикт.
**Почему опасно:** Хост-драйвер, использующий `Decision::deny()` как отзыв доступа (ожидая, по докблоку, что deny сработает как вето), получает молчаливый no-op: ACL-allow сохраняется, доступ не отзывается. Эксплуатация требует драйвера, эмитящего deny (шипнутые драйверы — предмет P1.2), поэтому это контрактный пробел, а не подтверждённый обход на дефолтном `database`-лейне.
**Доказательство:**
```php
// AccessResolver::resolveRole()
foreach ($subjects as $subject) {
    $decision = $driver->resolve($subject, $actor, $scope);
    if (!$decision instanceof Decision || !$decision->isAllow()) {
        continue;                       // <-- deny-решение выпадает здесь
    }
    $bits |= $decision->bits;           // копится ТОЛЬКО allow
    ...
}
return [$bits, $level];                 // deny-маски нет в возврате
```
`Decision::deny()` существует и публична (`ValueObjects/Decision.php:37-40`), т.е. контракт допускает deny-решения драйвера.
**Норма, которая нарушена:** Расхождение кода с докблоком H.2 (Code Guidance P1.1: Major). Потенциально S1.1 (deny должен участвовать в вето независимо от источника).
**Сверка с ADR:** `docs/adr/0007` описывает роль-лейн как «primarily contributes allows», а «final veto computed from ACL deny» — т.е. ADR действительно не обязывает драйверный deny быть вето. Значит: **код соответствует ADR, неверен докблок `resolveRole`** (обещает fold, которого нет). Класс — «докблок вводит в заблуждение»; при желании поддержать driver-deny нужно осознанное решение (эскалация). Проверить в P1.2, не рассчитывает ли какой-либо шипнутый драйвер на driver-deny.
**Рекомендация:** привести докблок `resolveRole:306-312` в соответствие с кодом (роль-лейн только повышает allow, driver-deny не участвует); если driver-deny нужен как контроль — вернуть из `resolveRole` и deny-маску и OR-ить её в `deniedBits`.

## 3. Не проверено / ограничения

- **Реализации `HostRoleDriver`** (`database`/`spatie`/`gate`/`null`, `azgard`) — вне scope P1.1 (item P1.2). Не проверено, эмитит ли какой-либо шипнутый драйвер `Decision::deny()` (см. F-P1.1-03) и раздаёт ли владельцу узла неявные права (C11 закрыт только по резолверу).
- **Policies / DriveContext / контроллеры** — фактические вызовы `can()` и возможные обходы ACL мимо резолвера здесь не аудировались (P1.3, P1.9, P1.10).
- **Порядок `ancestors()`** (staudenmeir): код `ancestorChain` предполагает nearest-first и делает `break` на первом чужом `storage_id`. C4 подтверждён для случая «первый предок — чужой storage»; сценарий «чередование storage в цепочке» физически недостижим в корректном дереве (одно дерево = один storage) и не строился.
- **Уникальный частичный индекс grant-uniq** (`PanelTablesBuilder.php:962-993`) прочитан, но гонки записи грантов и корректность на MySQL generated-column здесь не воспроизводились (ось P1.5/P4).
- **Эскалация (не выполнена как правка плана):** F-P1.1-01 и F-P1.1-03 содержат вопрос дизайна (должен ли wall-deny / driver-deny быть абсолютным вето). Триггер `rule conflict` — intent докблока против ADR-0007. Требует решения владельца в P5; здесь зафиксированы оба варианта.
