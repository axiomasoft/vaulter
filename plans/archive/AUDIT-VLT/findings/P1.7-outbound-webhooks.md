## 2. Находки

### F-P1.7-01 — Исходящие webhook без SSRF-защиты (endpoint-URL — управляемый пользователем примитив) · Severity: Blocker · Уверенность: high

**Где:** `packages/core/src/Http/Requests/Webhooks/RegisterWebhookEndpointRequest.php:27`; `packages/core/src/Jobs/Webhooks/DeliverWebhook.php:96-108`
**Что:** URL эндпоинта проверяется только правилом `url` (+`max:2048`). Правило `url` в Laravel не отсекает приватные/loopback/link-local диапазоны. Перед доставкой (`DeliverWebhook::post`) хост не резолвится и IP не проверяется, а Guzzle-клиент вызывается без `allow_redirects=false` (грепом `allow_redirects`/`withoutRedirecting` — пусто), т.е. редирект на внутренний адрес будет проследован по умолчанию.
**Почему опасно:** Аутентифицированный актор с ability `manage` (или любой залогиненный, если `manage_ability=null`) регистрирует эндпоинт `http://169.254.169.254/…` / `http://127.0.0.1:6379/` / внутренний адрес. Relay заставляет сервер слать POST на внутреннюю сеть (blind/semi-blind SSRF: HTTP-статус и текст ошибки транспорта возвращаются в `last_error`/`status` доставки — оракул для перебора внутренних портов/эндпоинтов). Классический вектор к cloud-metadata и внутренним state-changing API.
**Доказательство:** repro `artifacts/repro/P1.7/OutboundWebhookAuditTest.php`, тесты «C1: registration validation accepts SSRF target URLs» и «C1: DeliverWebhook POSTs to a private/link-local endpoint» — оба зелёные; `Http::assertSent` подтверждает фактический POST на `169.254.169.254`. Вывод: `tests: 5 passed, 15 assertions`.
**Норма, которая нарушена:** `findings/P0-upload-hardening.md` §U6.1 (SSRF-принцип: пользовательский URL → резолв+allow-list диапазонов); чеклист P1.7 C1 («Отсутствие валидации = Blocker»).
**Сверка с ADR:** ADR по webhooks/SSRF нет (`docs/adr/` — 0001–0014, ни одного про outbox/webhook). Решение не сознательное → дефект, не «ADR устарел».
**Рекомендация:** Валидировать URL и при регистрации, и непосредственно перед доставкой: только `https` (или `http` по явному флагу), резолвить хост и отвергать приватные/loopback/link-local/`169.254.169.254`; отключить следование редиректам (`->withoutRedirecting()`), либо перепроверять IP после каждого редиректа (защита от DNS-rebinding — C2).

### F-P1.7-02 — `signing_secret` хранится в открытом виде · Severity: Major · Уверенность: high

**Где:** `packages/core/src/Schema/PanelTablesBuilder.php:802`; `packages/core/src/Models/Webhooks/WebhookEndpoint.php:74-83`
**Что:** HMAC-секрет пишется в колонку `string('signing_secret')` без `encrypted`-cast и без шифрования на уровне приложения. В БД он лежит plaintext.
**Почему опасно:** Компрометация БД (SQLi, дамп бэкапа, доступ read-replica) сразу отдаёт все HMAC-ключи всех подписчиков. Атакующий подделывает валидно подписанные webhook-запросы к любому получателю — обходит основной механизм доверия канала.
**Доказательство:** `$table->string('signing_secret');` — обычная строковая колонка; в `casts()` модели `signing_secret` отсутствует (только `events`/`is_active`/`last_triggered_at`/`failure_count`).
**Норма, которая нарушена:** чеклист P1.7 C4 («хранение в открытом виде = Major»); `findings/P0-collab-seam.md` §C3.5 (секреты webhook — инфраструктурные ключи, защищать).
**Сверка с ADR:** ADR отсутствует → дефект. Хешировать нельзя (ключ нужен для подписи), но применим `encrypted`-cast.
**Рекомендация:** Добавить `'signing_secret' => 'encrypted'` в `casts()` (Laravel шифрует через `APP_KEY`). Существующие строки мигрировать разово. Показ один раз при регистрации уже реализован — расшифрованное значение из БД читать только внутри `WebhookSigner`.

### F-P1.7-03 — Outbox стейджится после коммита, а не в транзакции мутации (окно потери события) · Severity: Major · Уверенность: medium

**Где:** `packages/core/src/Webhooks/RecordsOutbox.php:26-38, 84-94`; `packages/core/src/Webhooks/OutboxRecorder.php:131-161`
**Что:** Доменные события — `ShouldDispatchAfterCommit`, поэтому `RecordsOutbox` пишет outbox-строку ПОСЛЕ коммита бизнес-мутации, а не внутри той же транзакции. Дополнительно исключение рекордера гасится (`safely()`), так что провал стейджинга не откатывает мутацию.
**Почему опасно:** Инвариант transactional outbox — атомарная запись мутации и outbox-строки в одной транзакции: только он даёт at-least-once. Здесь при краше процесса между коммитом мутации и записью строки (или при исключении рекордера) событие теряется навсегда, а мутация остаётся. Для DMS это молчаливая потеря `grant.created`/`share.created` — downstream пропускает изменение ACL. Семантика фактически at-most-once в окне краша, а не заявленная at-least-once.
**Доказательство:** докблок `RecordsOutbox.php:26-33` прямо описывает «small crash window … the event is lost to the outbox»; `safely()` (:84-94) ловит и логирует Throwable, не пробрасывая.
**Норма, которая нарушена:** скилл `php:transactional-outbox-relay` (write+outbox в одной транзакции — единственный источник at-least-once).
**Сверка с ADR:** ADR по outbox нет; трейд-офф задокументирован в докблоке, но не в ADR. Класс — дефект инварианта с сознательным трейд-оффом (не «ADR устарел», т.к. ADR отсутствует).
**Рекомендация:** Либо писать outbox-строку внутри транзакции мутации (снять `ShouldDispatchAfterCommit`, дёргать рекордер из транзакции доменного действия), либо зафиксировать ослабленную гарантию отдельным ADR и явно объявить её в доках канала.

### F-P1.7-04 — Все три webhook-модели полностью незащищены (`$guarded = []`) · Severity: Minor · Уверенность: high

**Где:** `packages/core/src/Models/Webhooks/WebhookEndpoint.php:39`; `Outbox.php:41`; `WebhookDelivery.php:40`
**Что:** У моделей `$guarded = []` — mass-assignment открыт для всех полей, включая `signing_secret`. Текущий HTTP-путь безопасен (Request не принимает секрет, репозиторий хардкодит поля), но защита держится исключительно на дисциплине вызывающего кода.
**Почему опасно:** Любой будущий код, передавший `request()->all()`/`->fill()` в эти модели, немедленно откроет инъекцию `signing_secret`/произвольных полей. Defense-in-depth отсутствует.
**Доказательство:** repro `artifacts/repro/P1.7/…` тест «C13» — `WebhookEndpoint::create([... 'signing_secret'=>'ATTACKER-CHOSEN-SECRET' ...])` присваивает атакующий секрет; `getGuarded() === []`.
**Норма, которая нарушена:** чеклист P1.7 C13 (mass-assignment секрета); Laravel best-practice (`$fillable`/`$guarded` явный для чувствительных полей).
**Сверка с ADR:** нет ADR → дефект слабого дефолта.
**Рекомендация:** Явно защитить `signing_secret` (минимум `$guarded = ['signing_secret']`) либо перечислить `$fillable` без секрета.

### F-P1.7-05 — Две команды re-dispatch над не-терминальными доставками → окно двойной доставки · Severity: Minor · Уверенность: medium

**Где:** `packages/core/src/Console/RelayOutboxCommand.php:48-60`; `packages/core/src/Console/RetryWebhooksCommand.php:32-43`
**Что:** И `vaulter:relay-outbox` (re-arm), и `vaulter:retry-webhooks` диспатчат `DeliverWebhook` для `dueForRetry()` (`status in pending|failed`). Выборка не берёт row-lock (в отличие от `OutboxRelay::claimPending`). Если хост планирует обе команды (или одну без `withoutOverlapping`), два job'а для одной `failed`-доставки могут выполниться параллельно и оба сделать POST — `isTerminal` покрывает только `delivered|dead`, но не `failed`/`pending`.
**Почему опасно:** Двойная доставка одного события. Митигируется дизайном (at-least-once + дедуп по `event_id` у получателя), поэтому Minor, но противоречит заявлению «single owner».
**Доказательство:** обе команды вызывают `dueForRetry()->get()->each(dispatch DeliverWebhook)` без блокировки/флипа статуса перед диспатчем.
**Норма, которая нарушена:** скилл `php:transactional-outbox-relay` (relay — единственный владелец ретрая; отсутствие второго диспатчера того же множества).
**Сверка с ADR:** нет ADR → дефект.
**Рекомендация:** Оставить один re-dispatch-путь либо клеймить доставку под row-lock/atomic-флипом перед диспатчем (как `claimPending`), и задокументировать обязательный `withoutOverlapping()` для расписания.

### F-P1.7-06 — Размер тела ответа получателя не ограничен · Severity: Minor · Уверенность: medium

**Где:** `packages/core/src/Jobs/Webhooks/DeliverWebhook.php:96-108`
**Что:** Таймаут задан (`Http::timeout(5)`), но ответ получателя читается целиком в память без лимита размера.
**Почему опасно:** Вредоносный/сломанный получатель отдаёт гигантское тело → OOM воркера доставки (DoS канала).
**Доказательство:** в `post()` нет `->maxRedirects`/ограничения тела; `Response` формируется Guzzle с полным чтением body.
**Норма, которая нарушена:** чеклист P1.7 C11 (ограничение размера тела ответа).
**Сверка с ADR:** нет ADR → дефект слабого лимита.
**Рекомендация:** Не читать тело ответа (для доставки нужен только статус) либо ограничить размер через stream + лимит.

## 3. Не проверено / ограничения

- **Tenant-изоляция эндпоинтов (C12).** `v_webhook_endpoints` — глобальная таблица без tenant-колонки: эндпоинты install-global by design (докблок `WebhookEndpointPolicy.php:18-21`). Следствие — один подписчик получает события ВСЕХ тенантов. Оценка мульти-тенантной утечки событий — предмет P1.9 (tenant-изоляция), здесь только зафиксировано.
- **Guzzle allow_redirects по умолчанию.** Вывод «редиректы следуются» основан на дефолте Guzzle (`allow_redirects=true`) — код Vaulter его не переопределяет; фактического прогона с 3xx-редиректом на приватный адрес не делал (C2 отмечен fail как подмножество C1).
- **F-P1.7-03 severity/confidence — medium:** окно потери требует краша процесса в узком интервале; воспроизводящего краш-теста не писал (репро краша между коммитом и after-commit-листенером нетривиально в sync-очереди).
- `UpdateWebhookEndpointRequest.php`, `DeactivateWebhookEndpointAction`, `DeleteWebhookEndpointAction`, `OutboxStoreRepository`/`WebhookDeliveryStoreRepository` прочитаны по вызовам, но не построчно — вне узла риска item'а.
