## 2. Находки

### F-P2.1-01 — Докблок фасада не покрывает 5 из 12 публичных методов манагера · Severity: Minor · Уверенность: high

**Где:** `packages/core/src/Facades/Vaulter.php:11-17` (докблок) vs
`packages/core/src/VaulterManager.php:142,153,161,166,187`
**Что:** `@method`-аннотации фасада перечисляют 7 методов; `registerHandler`, `handlers`,
`registerExporter`, `exporter`, `exporterFormats` реально вызываются через фасад
(делегирование `Facade` работает независимо от докблока), но IDE их не подскажет и
статический анализ по докблоку их не увидит.
**Почему опасно:** DX-цена, не runtime-баг — метод рабочий, просто невидим для
автокомплита/статанализа поверх фасада; интегратор находит его только через
`app(VaulterManager::class)` или чтение исходника.
**Доказательство:**
```php
/**
 * @method static \Vaulter\Contracts\Drive\DriveHandle for(...)
 * ...
 * @method static array<string, array<string, mixed>>  documentTypes()
 *
 * @see VaulterManager
 */
final class Vaulter extends Facade
```
`grep -c '@method' packages/core/src/Facades/Vaulter.php` → `7`.
**Норма, которая нарушена:** item P2.1 C3 («докблок фасада согласован с фактическими
методами `VaulterManager`»); косвенно E3.2/E4.3 (фасад как SemVer-контракт).
**Сверка с ADR:** нет применимого ADR; `docs/reference/facade.md:47-55` уже фиксирует
этот же факт как «известное» ограничение («they are simply not (yet) in the `@method`
block») — расхождение осознано авторами доки, но не исправлено в коде.
**Рекомендация:** дописать 5 отсутствующих `@method`-строк в докблок `Vaulter.php`.

### F-P2.1-02 — Reference-доки описывают публичный API, удалённый ADR-0014 · Severity: Major · Уверенность: high

**Где:** `docs/reference/facade.md:36,109-126` (методы `resolvePermissionsWith`,
`permissionResolver`, `driver()`); `docs/reference/contracts.md:38-53` (контракт
`Access\PermissionResolver`), `docs/reference/contracts.md:285-304` (контракт
`Collaboration\CollaborationDriver`, «legacy»)
**Что:** Доки документируют три метода фасада/манагера и два интерфейса, которых в
коде репозитория больше нет: `VaulterManager.php` не содержит `resolvePermissionsWith`,
`permissionResolver` или `driver()` (полный список публичных методов — §0.1);
`grep -rn "class PermissionResolver\|interface PermissionResolver" packages/*/src`
и одноимённый поиск по `CollaborationDriver` (legacy, `Contracts\Collaboration`
namespace) не находят файлов — только `NodeCollaborationDriver` в `vaulter-documents`
существует. `config('vaulter.permission_resolver')`, который доки называют как способ
биндинга, отсутствует среди 34 ключей `config/vaulter.php` (P0.1 §2б).
**Почему опасно:** интегратор, следующий доке `docs/reference/facade.md` или
`contracts.md`, напишет `Vaulter::resolvePermissionsWith($resolver)` или реализует
несуществующий интерфейс `PermissionResolver` — вызов упадёт `BadMethodCallException`
(манагер не имеет метода, фасад делегирует в `__callStatic` → `Manager` без такого
метода), а реализация интерфейса окажется мёртвым кодом хоста. Это прямой DX-регресс
после рефакторинга ADR-0014, не просто устаревшая формулировка.
**Доказательство:**
```
$ grep -rn "function resolvePermissionsWith\|function permissionResolver\|function driver(" packages/core/src/
packages/core/src/Access/HostRoleDriverManager.php:40:    public function driver(?string $key = null): HostRoleDriver
packages/core/src/Cas/BlobLock.php:90:    private function driver(): string
```
(ни одного совпадения на `VaulterManager.php`; `HostRoleDriverManager::driver()` —
другой класс, не публичный факасный метод).
**Норма, которая нарушена:** item P2.1 C13 («доки не описывают символов, которых нет
в коде»); `CHANGELOG.md` `[Unreleased]` сам объявляет удаление: «the
`Contracts\Access\PermissionResolver` seam (`Vaulter::resolvePermissionsWith()` /
`permissionResolver()` and the `vaulter.permission_resolver` config key)» — удаление
задокументировано в CHANGELOG, но не отражено в `docs/reference/*`.
**Сверка с ADR:** ADR-0014 (legacy strangler) — сознательное решение об удалении
подтверждено CHANGELOG; расхождение — не «ADR устарел» (ADR корректен), а
«справочные доки не обновлены синхронно с CHANGELOG» — дефект актуальности доки.
**Рекомендация:** убрать `resolvePermissionsWith`/`permissionResolver`/`driver()` из
`docs/reference/facade.md` и секции `PermissionResolver`/`CollaborationDriver` (legacy)
из `docs/reference/contracts.md`, либо явно пометить «removed in ADR-0014» со ссылкой
на миграционный путь (`Vaulter::for()` / node-эндпоинты — CHANGELOG уже формулирует).

### F-P2.1-03 — `docs/reference/contracts.md` не перечисляет 7 существующих публичных контрактов · Severity: Minor · Уверенность: high

**Где:** `docs/reference/contracts.md` (таблица «Domain / Contract / Swap via»,
строки 15-32) vs `packages/core/src/Contracts/{Access/GrantAuthoritativeDriver.php,
Cas/ListableContentStore.php,Cas/ListableStorageDriver.php,Documents/DocumentContent.php,
Documents/HandlerRegistry.php,Documents/NodeHandlerResolver.php}`,
`packages/permissions-azgard/src/Contracts/AzgardBackedUser.php`
**Что:** Семь интерфейсов без `@internal`-пометки, реально используемых публичной
поверхностью (`HandlerRegistry` — контракт за `Vaulter::handlers()`/`registerHandler()`;
`NodeHandlerResolver` — резолвер за `GET .../handler`; `AzgardBackedUser` — контракт,
который обязан реализовать `User`-модель хоста при `drivers.permission=azgard`),
отсутствуют в справочной таблице contracts.md.
**Почему опасно:** для DX/встраиваемости — не ошибка кода, а слепое пятно
документации: интегратор, включающий azgard-драйвер или пишущий кастомный
document-handler-резолвер, не найдёт контракт через reference-доку и будет читать
исходник вручную.
**Доказательство:** см. таблицу §0.2 — колонка «В `docs/reference/contracts.md`?»,
7 строк со значением «нет».
**Норма, которая нарушена:** item P2.1 C13 (обратное направление — «в коде есть, в
доках нет — тоже находка»).
**Сверка с ADR:** не применимо — доковый пробел, не архитектурное решение.
**Рекомендация:** добавить 7 строк в таблицу `contracts.md` (домен + swap-точка,
по аналогии с существующими).

### F-P2.1-04 — Namespace `UploadProtocolHandler` в доке не совпадает с кодом · Severity: Nit · Уверенность: high

**Где:** `docs/reference/contracts.md:419-442` (`Vaulter\Contracts\Uploads\UploadProtocolHandler`)
vs `packages/drive/src/Uploads/Contracts/UploadProtocolHandler.php:5`
(`namespace Vaulter\Drive\Uploads\Contracts;`)
**Что:** Дока называет FQCN `Vaulter\Contracts\Uploads\UploadProtocolHandler`

### F-P2.1-05 — Статический реестр-кеш вне фасада · Severity: Minor · Уверенность: high

**Где:** `packages/core/src/Support/EnumCaseAttributeResolver.php:18,26-43`
**Что:** `private static array $cache` — процесс-широкий кеш reflection-атрибутов
enum-кейсов, живущий вне `VaulterManager`/фасада.
**Почему опасно:** литеральное нарушение E3.3 («никакого глобального состояния
помимо фасадов»). Практический риск низкий: ключ кеша — `ClassName::caseName#attributeFQCN`,
значение — неизменный атрибут enum-кейса, не зависит от тенанта/запроса/пользователя,
поэтому под Octane/long-running воркером кросс-запросная утечка данных не
демонстрируется. Риск — архитектурный прецедент (следующий такой кеш может быть
менее безобидным) и непрозрачность для тестов (`::flush()` существует, но не
вызывается автоматически между тестами/запросами).
**Доказательство:**
```php
final class EnumCaseAttributeResolver
{
    private static array $cache = [];

    public static function forCase(UnitEnum $case, string $attribute): ?object
    {
        $key = $case::class.'::'.$case->name.'#'.$attribute;
        if (!array_key_exists($key, self::$cache)) { /* … */ }
        return self::$cache[$key];
    }
}
```
**Норма, которая нарушена:** item P2.1 C7 / E3.3.
**Сверка с ADR:** нет применимого ADR.
**Рекомендация:** минимально — задокументировать (докблок) почему кеш безопасен
(ключ не тенант-зависим), либо перевести на request-scoped/контейнерный биндинг,
если когда-нибудь понадобится сброс между тестовыми прогонами не через ручной `flush()`.

### F-P2.1-06 — Split PHP-пакеты (Packagist-артефакт) не получают ни один CHANGELOG · Severity: Major · Уверенность: high

**Где:** `.github/workflows/monorepo-split.yml:36-41` (`package_directory: packages/${{matrix.package}}`),
`.changeset/config.json:6,9` (`"linked": [["@vaulter/vue","@vaulter/client"]]`, `"ignore": ["@vaulter/hocuspocus-server"]`),
корневой `CHANGELOG.md` (единственный файл, вне `packages/*`)
**Что:** ADR-0010 фиксирует «PHP — path-repos locally, subtree-split on publish»:
на тег `.github/workflows/monorepo-split.yml` форс-сплитит **только**
`packages/<name>` в отдельный репозиторий `axioma-studio/vaulter-<name>`, который
и регистрируется на Packagist. Корневой `CHANGELOG.md` физически находится вне
`packages/<name>` и, соответственно, не входит в split-поддерево. Changesets
(`.changeset/`) — второй потенциальный источник per-package changelog — явно
скоупится только на npm-пакет `@vaulter/vue` (`"linked"` для `@vaulter/vue`/`@vaulter/client`,
`"ignore"` для `hocuspocus-server`); ни одного `.changeset/*.md` для PHP-пакета в
дереве нет.
**Почему опасно:** конечный потребитель, поставивший `composer require
axioma-studio/vaulter-core`, получает split-репозиторий **без единого файла
changelog** — ни общего (он не переносится), ни per-package (Changesets его не
генерирует для PHP). История изменений для реального Packagist-артефакта не
существует нигде, кроме монорепо-разработчика.
**Доказательство:**
```yaml
# .github/workflows/monorepo-split.yml
- uses: danharrin/monorepo-split-github-action@14e42e2437f674b8987c1f50ca3689116aea1893 # v2.4.5
  with:
    package_directory: packages/${{ matrix.package }}
    repository_name: vaulter-${{ matrix.package }}
```
```json
// .changeset/config.json
{ "linked": [["@vaulter/vue", "@vaulter/client"]], "ignore": ["@vaulter/hocuspocus-server"] }
```
`git ls-tree HEAD .changeset/` → только `README.md`, `config.json`,
`initial-release.md` (последний — `"@vaulter/vue": minor`, npm-only).
**Норма, которая нарушена:** item P2.1 C10 («per-package changelog отсутствует —
проверить, объявлен ли changesets как канонический механизм, и покрывает ли он
PHP-пакеты… отсутствие покрытия = находка»); E4.4 (deprecation/changelog для
SemVer-контракта).
**Сверка с ADR:** ADR-0010 описывает МЕХАНИКУ сплита и релиза, но не упоминает
changelog-судьбу split-репо вообще — не «ADR устарел» (ADR не принимал решения по
этому вопросу), это незакрытый пробел в решении, а не расхождение с решением.
**Рекомендация:** минимально — включить копирование/генерацию changelog-фрагмента
в `package_directory` перед сплитом (например, `CHANGELOG.md` пакета, собранный из
корневого по секциям, копируется в `packages/<name>/CHANGELOG.md` шагом workflow
до `monorepo-split-github-action`), либо явный README-указатель в каждом
`packages/<name>` на корневой changelog по URL монорепо.
