## 2. Находки

### F-P4.1-01 — Purge корзины сканирует `v_nodes` без индекса на `trashed_at` · Severity: Minor · Уверенность: high

**Где:** `packages/core/src/Repositories/Drive/NodeReadRepository.php:203-219` (предикат);
`packages/core/src/Schema/PanelTablesBuilder.php:177-223` (определение таблицы `v_nodes`, индексы `:210-212`)
**Что:** `PurgeTrashCommand` (плановая команда) выбирает кандидатов на permanent-purge через
`WHERE trashed_at IS NOT NULL AND trashed_at <= ?`, но `trashed_at` не входит ведущей колонкой
ни в один индекс таблицы — единственное вхождение `trashed_at` в индекс `(storage_id, kind,
trashed_at)` не используется планировщиком без фильтра по `storage_id`/`kind` (leftmost-prefix).
**Почему опасно:** `vaulter:purge-trash` — фоновая scheduled-команда (§2.10), гоняется по
расписанию по ВСЕЙ таблице узлов. Без индекса каждый прогон — полный seq-scan `v_nodes`,
стоимость растёт линейно с общим числом узлов инсталляции (не только трэшнутых), а не с числом
кандидатов на purge. Дополнительно `trashedBefore()` несёт коррелированный `NOT EXISTS`-подзапрос
по `parent_id` на каждую строку-кандидата (`NodeReadRepository.php:213-217`) — без внешнего
индекса на `trashed_at` даже отбор кандидатов для этого подзапроса уже дорог.
**Доказательство:**
```php
// NodeReadRepository.php:203-210
public function trashedBefore(Carbon $threshold): Builder
{
    ...
    return $this->query()
        ->whereNotNull('trashed_at')
        ->where('trashed_at', '<=', $threshold)
```
```php
// PanelTablesBuilder.php:209-212 — индексы v_nodes, ни один не ведёт с trashed_at
$table->index(['storage_id', 'parent_id']);
$table->index(['storage_id', 'parent_id', 'position']);
$table->index(['storage_id', 'kind', 'trashed_at']);
```
**Норма, которая нарушена:** проектная норма item'а P4.1 (индекс должен покрывать ведущую
колонку фактического предиката, `phases/P4.md` C5); общий принцип «фоновая команда по
расписанию без индекса под свой предикат = Minor» (Code Guidance P4.1).
**Сверка с ADR:** `docs/adr/0005-unified-node-tree.md` описывает soft-trash triplet
(`trashed_at`/`trashed_by`/`trashed_from_parent_id`) как намеренный дизайн дерева, но НЕ
объявляет индексную политику под сканирование по `trashed_at` — отсутствие индекса не является
задокументированным сознательным решением ADR. Классификация: дефект, не «ADR устарел».
**Рекомендация:** добавить индекс `(trashed_at)` (или `(trashed_at, storage_id)`, если нужен
per-storage retention) на `v_nodes` в `PanelTablesBuilder::defineNodes`; на PostgreSQL/SQLite
можно частичный `WHERE trashed_at IS NOT NULL` — предикат `trashedBefore()` уже фильтрует
`whereNotNull`, так что partial-индекс полностью покрывает и минимизирует объём.

### F-P4.1-02 — Избыточные индексы с общим префиксом (`v_nodes`, `v_blobs`, `v_activity`) · Severity: Nit · Уверенность: high

**Где:** `packages/core/src/Schema/PanelTablesBuilder.php:210-211` (`v_nodes`);
`packages/core/src/Schema/PanelTablesBuilder.php:248,277` (`v_blobs`);
`packages/core/src/Schema/PanelTablesBuilder.php:740,873,883-888` (`v_activity`)
**Что:** Три таблицы несут индекс, чей столбцовый набор — строгий префикс (или, для `v_activity`,
буквальный дубликат) другого индекса на той же таблице: `v_nodes.(storage_id,parent_id)` ⊂
`(storage_id,parent_id,position)`; `v_blobs.status` ⊂ `(status,ref_count,delete_after_at)`;
`v_activity.created_at` индексируется ДВАЖДЫ — одноимённый inline `->index()` (:740) и явный
`_created_idx` (:883-888), оба на единственный столбец `created_at`.
**Почему опасно:** лишний индекс не ускоряет ни один читающий путь (планировщик всегда предпочтёт
более специфичный/тот же составной индекс), но платится на КАЖДЫЙ `INSERT`/`UPDATE`/`DELETE` этой
таблицы — двойная запись индексной страницы. Для `v_activity` (append-only, самая «горячая» на
запись таблица пакета, §2.9) дублирующий одноколоночный индекс на `created_at` — чистая потеря:
двойная стоимость записи журнала при нулевой пользе для чтения (более специфичные `_storage_idx`
/`_target_idx`/`_actor_idx`/`_verb_idx` уже покрывают `created_at`-хвост).
**Доказательство:**
```php
// PanelTablesBuilder.php:740 — первый индекс на created_at (inline)
$table->timestamp('created_at')->nullable()->index();
...
// PanelTablesBuilder.php:883-888 — второй, явный индекс на ТОТ ЖЕ единственный столбец
private function addActivityCreatedAtIndex(string $table): void
{
    Schema::table($table, static function (Blueprint $blueprint) use ($table): void {
        $blueprint->index('created_at', "{$table}_created_idx");
    });
}
```
**Норма, которая нарушена:** Implementation Rules P4.1 `C7` («индексы, дублирующие префикс
друг друга … лишний индекс тормозит запись» — Nit).
**Сверка с ADR:** ни ADR-0005, ни ADR-0006 не объявляют намеренного дублирования индексов;
дублирование внутри `PanelTablesBuilder` — не задокументированное решение, классификация:
дефект (артефакт последовательного наращивания схемы одним и тем же файлом), не «ADR устарел».
**Рекомендация:** убрать избыточные одноколоночные индексы (`v_nodes` inline `(storage_id,
parent_id)`, `v_blobs` inline `status`), заменить их на комментарий «покрыт составным Х»; для
`v_activity` удалить один из двух `created_at`-индексов (оставить `_created_idx`, убрать `->index()`
на строке 740, либо наоборот) новой миграцией (не переписывать применённую — правило пакетных
миграций).

## 3. Не проверено / ограничения

- **Repro/EXPLAIN не прогонялся.** Item закрыт по чтению кода + миграций (`file:line` предиката
  и индекса для каждой строки чеклиста); Testbench-SQLite `->toSql()`/`EXPLAIN QUERY PLAN` не
  запускался — repro в этом item'е опционален (Implementation Rules), а покрытие «индекс ↔
  ведущая колонка предиката» доказуемо чтением DDL без прогона. Не заведено как `⚠ partial`,
  т.к. ни один вердикт не зависел от факта, доказуемого только исполнением (leftmost-prefix —
  детерминированное свойство B-tree индекса, не требует EXPLAIN для установления факта
  присутствия/отсутствия колонки).
- **PostgreSQL-специфичная стоимость seq-scan (F-P4.1-01) не измерена на реальном объёме
  данных** — находка констатирует отсутствие индекса под фактический предикат (структурный
  факт), не измеренную latency на конкретном датасете; калибровка severity (Minor, не Major)
  сделана по частоте (фоновая scheduled-команда, не путь на каждом листинге), как того требует
  Code Guidance item'а.
- **`v_node_shares`, `v_node_comments`, `v_node_document_versions`, `v_outbox`,
  `v_webhook_endpoints/deliveries`** прочитаны в `PanelTablesBuilder.php` при построении C6/C7,
  но НЕ входят в Scope Included P4.1 (это не одна из пяти горячих троп); потенциальные
  избыточные индексы в этих таблицах (напр. `v_node_shares.revoked_at` одноколоночный `:450`
  рядом с составным `(node_id,revoked_at)` `:464` — РАЗНЫЕ ведущие колонки, не строгий префикс,
  поэтому не заведено как находка) за пределами закрытого чеклиста этого item'а.
