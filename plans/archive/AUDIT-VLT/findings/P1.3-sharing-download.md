## 2. Находки

### F-P1.3-01 — Скачивание редиректит на presigned-URL бакета в обход PHP (нарушение D15) · Severity: Major · Уверенность: high

**Где:** `packages/drive/src/Http/Controllers/DownloadController.php:104-111`, `packages/core/src/Http/Controllers/Sharing/PublicShareController.php:190-197`, шов `packages/media/src/Cas/FlysystemStorageDriver.php:124-134`
**Что:** Оба пути скачивания (identity `DownloadController` и публичный `PublicShareController::download`) при диске, умеющем `providesTemporaryUrls()` (любой S3-совместимый), возвращают `RedirectResponse` на короткоживущий presigned-URL. Байты уходят из бакета напрямую, минуя PHP.
**Почему опасно:** D15 объявляет прямую раздачу из бакета **не поддерживаемым режимом**: presigned-URL становится bearer-токеном, права по нему не перепроверяются на каждом запросе, мгновенный отзыв невозможен (S4.3 «presigned не одноразовый», S4.4 «нужны два уровня отзыва»). Для публичного share: URL продолжает работать 5 минут даже после отзыва ссылки/исчерпания бюджета (use уже списан до редиректа). Переключение на этот режим происходит молча и автоматически при S3-конфигурации, без флага отключения. Модель угрозы: держатель presigned-URL пересылает его — второй потребитель качает файл без токена, без авторизации, вне журналирования.
**Доказательство:**
```php
// DownloadController.php:104-111 (идентично PublicShareController.php:190-197)
$signedUrl = $this->driver->temporaryUrl(
    key: $blob->storage_key,
    expiresAt: now()->addMinutes(self::SIGNED_URL_TTL_MINUTES),
    disk: $blob->disk,
);
if (is_string($signedUrl)) {
    return new RedirectResponse($signedUrl);
}
```
repro `ShareInvariantsTest.php` C16 (3 теста) — passed.
**Норма, которая нарушена:** `plan.md` D15 (скачивание только через PHP, авторизация на каждом запросе); S4.3, S4.4 (`findings/P0-dms-security.md`).
**Сверка с ADR:** прямого ADR, санкционирующего presigned-download, нет. D15 — сознательное решение владельца ПРОТИВ этого режима; код ему противоречит (docblock `DownloadController.php:23-27` прямо описывает редирект как штатный). Это дефект (нарушение принятого решения), не «ADR устарел». TTL=5мин и single-object скоуп присутствуют → Major (по правилу C16: без TTL/скоупа было бы Blocker).
**Рекомендация:** Убрать ветку `temporaryUrl → RedirectResponse` из обоих контроллеров; всегда `streamFromDisk`. Если presigned-оптимизация нужна — вводить её отдельным осознанным решением с фиче-флагом (default off), одноразовым серверным маркером и минимальным TTL, но это выходит за рамки D15.

### F-P1.3-02 — Issuer-права не перепроверяются при потреблении ссылки (confused deputy) · Severity: Major · Уверенность: medium

**Где:** `packages/core/src/Sharing/ShareResolver.php:49-92`
**Что:** `resolve()` проверяет liveness (revoked/expired/exhausted), пароль, require-login и item-safety (trash/soft-delete/storage), но НЕ проверяет, что создатель ссылки (`granted_by`) до сих пор обладает правами на узел. Ссылка продолжает раздавать доступ после того, как её автор потерял доступ к узлу.
**Почему опасно:** Классический confused deputy (S2.2): бэкенд действует привилегированным принципалом по предъявлению токена, не сверяясь, что выдавший ещё авторизован. Сценарий: редактор минтит публичную ссылку на узел → его грант на узел отзывают / его удаляют из проекта → ссылка живёт и раздаёт файл. Отзыва по «увольнению автора» нет — только ручной отзыв конкретной ссылки, которую надо ещё найти.
**Доказательство:** repro `ShareInvariantsTest.php` C5 — passed: `ShareResolver.php` не содержит `granted_by`, `AccessResolver`, `->can(`. Резолвер строит `ShareContext` из битовой маски записи без обращения к identity-ACL автора.
**Норма, которая нарушена:** S2.2 (`findings/P0-dms-security.md`) — на потреблении проверять, что issuer до сих пор имеет права.
**Сверка с ADR:** ADR-0013 сознательно решил оценивать share «в отдельном проходе, пересечённом с item-safety (tenant/trash/quarantine), НИКОГДА не объединяя с identity-ACL». Перепроверка прав issuer в перечень item-safety не включена. Это **осознанный пробел ADR** → класс «ADR устарел»: ADR-0013 покрыл tenant/trash/quarantine, но упустил S2.2 (issuer-revocation). Требует явного дополнения ADR либо признания риска.
**Рекомендация:** В `ShareResolver` (или в item-safety-пересечении) добавить проверку: `granted_by` всё ещё имеет `Ability::Share` (или хотя бы соответствующий bit) на узле; иначе — NotFound. Обновить ADR-0013, зафиксировав issuer-re-check как часть шва.

### F-P1.3-03 — Ссылки без явного expiry не истекают никогда (нет дефолтного TTL) · Severity: Major · Уверенность: high

**Где:** `packages/core/src/Http/Requests/Sharing/StoreShareLinkRequest.php` (`expires_at` nullable), `packages/core/src/Data/Sharing/CreateShareLinkData.php:29`, `packages/core/config/vaulter.php:448-452` (блок `share` без ttl)
**Что:** `expires_at` необязателен на всём пути; в конфиге `share` нет ключа дефолтного TTL. Ссылка, созданная без явного `expires_at`, живёт бессрочно (`NodeShare::scopeLive` трактует `expires_at IS NULL` как «никогда не истекает» — `NodeShare.php:88-89`).
**Почему опасно:** S4.1 требует TTL минуты/часы (потолок 24–72ч для email-шэра). Бессрочная публичная bearer-ссылка — постоянная поверхность утечки: URL попадает в историю браузера, referer, чаты; отозвать можно только вручную, поштучно.
**Доказательство:** repro `ShareInvariantsTest.php` C8 — passed. `'expires_at' => ['nullable', 'date', 'after:now']` + `?Carbon $expiresAt = null` + отсутствие ttl-ключа в `share`-конфиге.
**Норма, которая нарушена:** S4.1 (`findings/P0-dms-security.md`). Правило C8: бесконечный TTL по умолчанию = Major.
**Сверка с ADR:** ADR-0013 говорит «revocation and expiry are link-local», но не задаёт дефолтный потолок. Осознанного решения о бессрочности нет → дефект (недостающий контроль), не «ADR устарел».
**Рекомендация:** Ввести `config('vaulter.share.default_ttl_hours')` (напр. 72) и `max_ttl_hours`-потолок; при отсутствии `expires_at` подставлять дефолт в `CreateShareLinkAction`; валидацией ограничивать `expires_at` сверху потолком.

### F-P1.3-04 — `Content-Type` скачивания берётся из пользовательских метаданных без whitelist и без `nosniff` · Severity: Minor · Уверенность: medium

**Где:** `packages/drive/src/Http/Controllers/DownloadController.php:102,144-147`, `packages/core/src/Http/Controllers/Sharing/PublicShareController.php:188,226-229`
**Что:** `Content-Type` ответа = `$version->mime_type ?? $node->mime_type ?? 'application/octet-stream'` — прямо из метаданных, записанных при загрузке, без whitelist. Заголовок `X-Content-Type-Options: nosniff` не выставляется.
**Почему опасно:** Загрузивший может задать `mime_type: text/html` и получить HTML/JS, отдаваемый браузеру inline на домене приложения (stored XSS через скачивание). `Content-Disposition: attachment` (streamDownload) частично смягчает, но без `nosniff` браузеры могут сниффить. Пересекается с осью P1.11 (контентная безопасность/заголовки скачивания).
**Доказательство:** `$contentType = $version->mime_type ?? $node->mime_type ?? 'application/octet-stream';` и заголовки `['Content-Type' => $contentType, 'Content-Length' => ...]` — без `X-Content-Type-Options`.
**Норма, которая нарушена:** C13 (whitelist Content-Type); заголовки скачивания (`findings/P0-audit-gaps.md` §2 G4 — `nosniff`).
**Сверка с ADR:** релевантного ADR нет → дефект. Строго проверяется в P1.11; здесь фиксируется как обнаруженное на пути P1.3.
**Рекомендация:** Добавить `X-Content-Type-Options: nosniff` на оба ответа; при inline-раздаче — whitelist безопасных MIME, иначе `application/octet-stream`. Финальная сила — за P1.11.

### F-P1.3-05 — Публичный `SharedNodeResource` отдаёт сырой ключ узла; при bigint-стратегии — последовательный id · Severity: Minor · Уверенность: high

**Где:** `packages/core/src/Http/Resources/Sharing/SharedNodeResource.php` (`'id' => $node->getKey()`, а также `parent_id`)
**Что:** Публичный ресурс безусловно сериализует `getKey()` (и `parent_id`). Дефолт `ids.default=ulid` (`config vaulter.php:131`) неугадываем, но пакет поддерживает `bigint`/`id_type=id` (`config:118,131`) — при такой конфигурации публичная share-выдача выставляет последовательный числовой id.
**Почему опасно:** S3.3 — последовательные id наружу утекают счётчик/порядок создания и включают IDOR-разведку по другим эндпойнтам. Здесь это defense-in-depth (S3.1: неугадываемость не заменяет авторизацию, а share-путь токен-гейтед), поэтому Minor, но для bigint-хоста — реальная утечка порядковых идентификаторов анонимному держателю ссылки.
**Доказательство:** `'id' => $node->getKey()` в `toArray`; конфиг допускает `VAULTER_ID_STRATEGY=bigint` / `id_type=id`.
**Норма, которая нарушена:** S3.3 (`findings/P0-dms-security.md`).
**Сверка с ADR:** дефолт ulid — сознательный выбор (config docblock:124-131). Утечка возникает лишь при осознанном выборе bigint хостом → пограничный «ADR/дефолт ок, но публичная поверхность не защищена от небезопасной конфигурации». Классифицирую как дефект уровня Minor.
**Рекомендация:** На публичной поверхности отдавать непрозрачный идентификатор (hashid/ulid-проекция) независимо от внутренней стратегии, либо документировать, что публичный share несовместим с bigint-id по S3.3.
