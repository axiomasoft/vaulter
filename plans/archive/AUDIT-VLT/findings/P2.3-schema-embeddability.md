## 2. Находки

### F-P2.3-01 — Деструктивная миграция `000023` не сопровождена явным предупреждением в пользовательских доках · Severity: Major · Уверенность: medium

**Опровергнуто верификацией, см. `artifacts/repro/verify-F-P2.3-01/`** — в REGISTER не внесена (отвергнута 3/3 скептиками).

**Где:** `packages/core/database/migrations/2026_06_13_000023_drop_legacy_docvault_tables.php:9-19,28-37`; `docs/guide/installation.md` (целиком); `docs/guide/configuration.md:43-51`.
**Что:** `000023` безвозвратно удаляет шесть legacy-таблиц (`document_shares`, `document_comments`, `document_permissions`, `document_versions`, `documents`, `document_folders`) у любого хоста, который уже прогнал старые миграции `000001`–`000006` (эти create-миграции исключены из репозитория, поэтому единственный способ узнать о риске — прочитать сам файл `000023` или ADR-0014). `down()` пуст — отката на уровне БД нет. Ни `docs/guide/installation.md`, ни `docs/guide/configuration.md`, ни `docs/guide/database-compatibility.md`, ни `docs/guide/multi-tenancy.md` не содержат явного предупреждения об этом сценарии обновления.
**Почему опасно:** Хост, разрабатывавший на dev/staging БД до этого рефакторинга (сценарий, который сам докблок миграции признаёт реальным: «for dev/staging databases that already ran the old creates»), потеряет данные легаси-документов при обычном `composer update && php artisan migrate`, не получив ни одного предупреждения из пользовательской документации.
**Доказательство:** `000023_drop_legacy_docvault_tables.php:9-19` (докблок, признающий риск) + `:28-37` (тело `up()`, реальный список удаляемых таблиц); отсутствие совпадений по `grep -rn -i "backup\|irreversible\|000023" docs/guide/*.md docs/README.md` (кроме двух несвязанных `::: danger Irreversible` про корзину/пробное удаление файла в `docs/guide/{drive,trash}.md`, не про миграцию).
**Норма, которая нарушена:** пункт плана P2.3 `C2` («отсутствие предупреждения = находка Major»); правило миграций пакета `.claude/rules/package-migrations.md` («уже применённые миграции не менять… down() корректен и обратим» — здесь обратимость сознательно принесена в жертву, но это тем более требует явного user-facing предупреждения).
**Сверка с ADR:** `docs/adr/0014-legacy-docvault-strangler.md` — необратимость `000023` ЯВНО сознательна («No backfill, no deprecation window… nothing to migrate and no released consumer to protect», Context 3). Значит формулировка находки — «необратимость сознательна, но не предупреждена в пользовательских доках», а не «миграция без down()» (D5). ADR обосновывает отсутствие backfill фактом «нет релизнутых потребителей», но НЕ рассматривает dev/staging-хостов, уже прогнавших старые creates, — именно этот пробел не закрыт документацией.
**Рекомендация:** добавить в `docs/guide/installation.md` (или отдельную upgrade-заметку) явный блок: «Если вы устанавливали пакет ДО версии X и уже мигрировали legacy DocVault-таблицы — сделайте бэкап БД перед обновлением: миграция `000023` удаляет их безвозвратно». Дополнительно — упомянуть это в `CHANGELOG.md` (не проверено этим item'ом, см. §3).

### F-P2.3-02 — Соединение БД (`connection`) не параметризовано: таблицы Vaulter нельзя вынести в отдельную БД · Severity: Major · Уверенность: high

**Где:** `packages/core/src/Schema/PanelTablesBuilder.php` (все `Schema::create`/`Schema::table`/`DB::statement` вызовы — используют дефолтные фасады без `->connection(...)`); `packages/core/src/Models/Drive/Node.php`, `Models/Access/NodeGrant.php`, `Models/Activity/Activity.php` и остальные Vaulter-модели — ни одна не объявляет `protected $connection`; `packages/core/config/vaulter.php` — ключа `connection` нет ни в одной релевантной секции.
**Что:** Пакет всегда пишет схему и данные на дефолтное Laravel DB-соединение хоста. Нет ни конфиг-ключа, ни механизма назначить Vaulter-таблицам отдельное соединение (шардирование, вынос тяжёлого DMS-хранилища в отдельную БД, реплику).
**Почему опасно:** Хост, которому нужно физически изолировать Vaulter-схему (масштабирование, соответствие требованиям к размещению данных, отдельный инстанс БД под тяжёлый CAS/activity-фид), не может этого сделать без форка пакета. Это прямое нарушение E2.3 (RAG `findings/P0-embeddable-laravel.md`).
**Доказательство:** repro `plans/AUDIT-VLT/artifacts/repro/P2.3/C6NoConnectionParamTest.php` — искусственно выставленный `config('vaulter.connection', 'vaulter_other')` не переносит создаваемую таблицу на второе (реально зарегистрированное) соединение: `Schema::hasTable('conntest_storages')===true` на дефолтном, `Schema::connection('vaulter_other')->hasTable('conntest_storages')===false`; `Node::getConnectionName()===null`. Вывод: `{"result":"passed","tests":6,"passed":6,"assertions":32}` (тест внутри общего прогона).
**Норма, которая нарушена:** E2.3 (`findings/P0-embeddable-laravel.md`) — «Соединение параметризовано… иначе мультитенант/несколько БД ломаются».
**Сверка с ADR:** ADR-0003, ADR-0009, ADR-0011 (все три — про модель данных/панели/id-стратегию) НЕ упоминают `connection` вообще — это не осознанное решение, зафиксированное в ADR, а пробел (D5: находка — дефект, не «ADR устарел»).
**Рекомендация:** добавить `config('vaulter.connection')` (nullable, дефолт `null` = использовать `DB::getDefaultConnection()`), прокинуть его через `Panel`/`PanelTablesBuilder` в `Schema::connection(config('vaulter.connection'))->create(...)` и через `getConnectionName()` в базовой Vaulter-модели/трейте.

### F-P2.3-03 — Morph map не зарегистрирован: полиморфные колонки хранят сырой FQCN · Severity: Major · Уверенность: high

**Опровергнуто верификацией, см. `artifacts/repro/verify-F-P2.3-03/`** — в REGISTER не внесена (отвергнута 2/3 скептиками).

**Где:** `packages/core/src/Schema/PanelTablesBuilder.php:143` (`owner_type`), `:381` (`subject_type`), `:495` (`author_type`), `:714,721` (`actor_type`/`target_type`); все шесть `Vaulter*ServiceProvider.php` (нет `Relation::morphMap`/`enforceMorphMap`); `packages/core/src/Models/Access/NodeGrant.php:76-79` (`subject()` возвращает `Subject` из сырых `subject_type`/`subject_id`).
**Что:** Ни один провайдер пакета не регистрирует `Relation::morphMap()`. Пять полиморфных колонок (`owner_type`, `subject_type`, `author_type`, `actor_type`, `target_type`) активно заполняются в штатных операционных путях (`StorageManager::provision()`, `NodeGrant`/`Subject`-присвоение, `ActivityRecorder`) через `$model->getMorphClass()`, который без зарегистрированной карты возвращает полный FQCN класса.
**Почему опасно:** Переименование/перемещение неймспейса хостовой модели (или подмена `config('vaulter.models.*')` на другой класс) молча портит уже записанные строки — грант/активность/владение остаются привязаны к более не существующему FQCN и перестают резолвиться. Это прямое нарушение E6.2 (RAG); цена — коррупция данных при рутинном рефакторинге хоста, без единого сообщения об ошибке в момент порчи.
**Доказательство:** `grep -rn "morphMap\|enforceMorphMap" packages/*/src/*ServiceProvider.php` → 0 совпадений; `PanelTablesBuilder.php:493` — докблок сам констатирует зависимость от «the host's enforceMorphMap» (то есть пакет полагается на то, что ХОСТ, возможно, её зарегистрирует, но не гарантирует и не документирует это как обязательный шаг установки).
**Норма, которая нарушена:** E6.1/E6.2 (`findings/P0-embeddable-laravel.md`) — «`Relation::morphMap` с пространственно-именованными алиасами… в полиморфных колонках никогда не хранить FQCN».
**Сверка с ADR:** Ни один ADR (0003/0005/0007/0009/0011) не рассматривает morph map как сознательно отложенное решение — пробел, не «ADR устарел».
**Рекомендация:** зарегистрировать `Relation::morphMap()` в `VaulterServiceProvider::boot()` с алиасами вида `vaulter_storage_owner`, `vaulter_grant_subject_user`/`_role`/`_team` и т.д., собранными из `config('vaulter.models.*')`; задокументировать зарезервированные алиасы (закрывает C9 автоматически).

### F-P2.3-04 — Политика изменения схемы для будущих версий не объявлена · Severity: Minor · Уверенность: high

**Где:** `docs/guide/database-compatibility.md` (целиком); отсутствие в `docs/adr/*`, `ROADMAP.md`.
**Что:** Нет документа, формулирующего правила безопасной эволюции схемы после `v0.1.0`: добавление колонки только с `default`, запрет блокирующих `ALTER` на непустой таблице в проде, запрет `NOT NULL` без `default`.
**Почему опасно:** Сегодня цена нулевая (пакет pre-release, таблицы либо create-only, либо пусты у любого потребителя). Но начиная с первого тега это становится реальным риском для потребителей с боевыми данными — без объявленной политики любой будущий PR может внести блокирующий `ALTER TABLE … NOT NULL` без обсуждения.
**Доказательство:** `grep -rn -i "NOT NULL without default\|backward.compat\|breaking migration\|alter table\|schema change polic" docs/` — 0 релевантных совпадений.
**Норма, которая нарушена:** пункт плана P2.3 `C12`.
**Сверка с ADR:** Ни один ADR не формулирует такую политику сознательно — не «ADR устарел», а незакрытый пробел, ожидаемый до первого релиза.
**Рекомендация:** добавить раздел в `docs/guide/database-compatibility.md` (или `CONTRIBUTING.md`) — политика минимальна: новые колонки — nullable/с default; деструктивные операции — только через явно помеченную миграцию с записью в CHANGELOG; `NOT NULL` на непустой таблице — только двухшаговый backfill+constrain.
