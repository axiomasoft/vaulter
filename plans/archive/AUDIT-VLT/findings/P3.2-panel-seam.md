## 2. Находки

### F-P3.2-01 — «Validated on boot» не соответствует фактическому ленивому резолву `PanelRegistry` · Severity: Major · Уверенность: high

**Где:** `packages/core/src/VaulterServiceProvider.php:56-66` (биндинг), `packages/core/src/VaulterServiceProvider.php:113-118` (`packageBooted()` не резолвит `PanelRegistry`), `packages/core/src/Panels/PanelRegistry.php:93-114` (`validate()`), `docs/adr/0009-storage-panels.md` (Decision, п.3), `packages/core/src/Exceptions/Panels/InvalidPanelException.php:9-17`
**Что:** ADR-0009 и докблок `InvalidPanelException` заявляют, что кривая панель «fails loud at boot (not at runtime)». Фактически `PanelRegistry::class` зарегистрирован ленивым singleton-замыканием в `packageRegistered()` (зона `register()`, PT5.1) и НИЧТО не резолвит его эагерно в `packageBooted()` или где-либо ещё на этапе загрузки приложения. `PanelRegistry::fromConfig()` (а значит и `validate()`) реально выполняется только на первом фактическом обращении к панели из бизнес-кода.
**Почему опасно:** Потребитель может задеплоить конфиг с битым `StoragePanelProvider` (несуществующий FQCN модели, `idStrategy()` без own-tables и т.п.) — приложение стартует, `php artisan config:cache`/`route:cache` проходят без ошибки, healthcheck зелёный. Исключение `InvalidPanelException` вылетает только на ПЕРВОМ живом запросе/джобе, который реально коснётся панели (например, первый вызов `Vaulter::for($host, panel: 'broken')`, первое обращение `HasVaulterPanel::getTable()`, или отложенная `vaulter:panel:migrations`). Это прямое нарушение цены, которую ADR-0009 объявляет обязательной («keeps a broken panel from silently corrupting reads/writes once a request lands») — фактически «request lands» и получает 500 именно потому, что валидация не произошла раньше.
**Доказательство:**
```php
// VaulterServiceProvider.php:60-66 (packageRegistered — register()-зона)
$this->app->singleton(
    PanelRegistry::class,
    static fn (): PanelRegistry => PanelRegistry::fromConfig(
        providerClasses: Config::panels(),
        defaultClass: Config::defaultPanel(),
    ),
);
// packageBooted() (113-118) резолвит только:
// registerRouteBindings(); registerPolicies(); registerActivitySubscriber(); registerOutboxSubscriber();
// — ни один из них не обращается к PanelRegistry::class.
```
`grep -rn "PanelRegistry::class\|make(PanelRegistry\|app(PanelRegistry" packages/*/src/*ServiceProvider.php` — совпадений нет ни в одном из шести провайдеров пакета.
**Норма, которая нарушена:** ADR-0009 (Decision, п.3: «validated on boot»); E7.3 (`findings/P0-embeddable-laravel.md`: «На boot из config читаются: биндинги контрактов…»).
**Сверка с ADR:** `docs/adr/0009-storage-panels.md` — решение о валидации НА BOOT зафиксировано как часть архитектуры (не альтернатива, отклонённая сознательно); текущий код его не реализует. Это НЕ случай «ADR устарел» (D5) — ADR описывает целевое поведение, код его не достиг; классифицируется как дефект.
**Рекомендация:** Эагерно резолвить `PanelRegistry::class` в `packageBooted()` (например, `$this->app->make(PanelRegistry::class);` после регистрации route bindings) — минимальная правка без изменения публичного API.

### F-P3.2-02 — Хуки `fillNode()`/`presentNode()`/`pipes()` объявлены, но нигде не вызываются · Severity: Major · Уверенность: high

**Где:** `packages/core/src/Panels/StoragePanelProvider.php:34-65` (объявления); отсутствие вызовов во всём `packages/*/src`
**Что:** `StoragePanelProvider` документирует пять точек расширения («Optional hooks let a panel enrich the node pipeline and the node representation without forking the package», `StoragePanelProvider.php:8-11`): `panel()`, `fillNode()`, `presentNode()`, `pipes()`, `booted()`. Реально вызываются только `panel()` (в `resolve()`) и `booted()` (в `PanelRegistry::registerProvider()`). `fillNode()`, `presentNode()` и `pipes()`/`Panel::pipesList()` не имеют НИ ОДНОГО сайта вызова за пределами собственного объявления.
**Почему опасно:** Потребитель, реализующий `fillNode()`/`presentNode()`/`pipes()` по докблоку (единственный документированный способ «обогатить» узел или пайплайн без форка пакета — заявленный headline-сценарий ADR-0009), получает МОЛЧАЛИВЫЙ no-op: код компилируется, панель регистрируется и валидируется (в т.ч. `pipesList()` проверяется на существование классов, создавая ложное впечатление, что значение используется), но ни данные `fillNode`, ни `presentNode`, ни дополнительные pipe-классы никогда не попадают в реальный узел/пайплайн/представление. Это не «неполный шов» (Minor по формулировке item'а), а полностью нефункциональная, но выглядящая рабочей поверхность — обнаруживается только чтением кода потребителем, отладкой либо этим аудитом.
**Доказательство:**
```
$ grep -rn "fillNode(\|presentNode(\|->pipes(" packages/*/src --include="*.php"
packages/core/src/Panels/StoragePanelProvider.php:39:    public function fillNode(array $data): array
packages/core/src/Panels/StoragePanelProvider.php:51:    public function presentNode(array $node): array
```
(третий греп на `pipesList()` — единственное использование в `PanelRegistry.php:105` это `foreach ($panel->pipesList() as $pipeClass) { $this->assertClassExists(...); }`, т.е. только валидация существования класса, не выполнение/инъекция.)
**Норма, которая нарушена:** E5.2 (`findings/P0-embeddable-laravel.md`: «Интеграция с воркфлоу хоста — через события пакета…», здесь — заявленный хук-шов, но нерабочий); ADR-0009 (Decision, п.1 — «feature flags + permission driver + format handlers + id strategy + fill/present hooks»); Implementation Rules C4 самого item'а («хуки… покрывают заявленные ADR-0009 сценарии обогащения без форка»).
**Сверка с ADR:** `docs/adr/0009-storage-panels.md` перечисляет «fill/present hooks» как часть состава панели (Decision, п.1) — ADR не описывает их как заглушки на будущее; это не сознательное решение оставить хуки пустыми, а незавершённая реализация. Дефект, не «ADR устарел».
**Рекомендация:** Либо подключить `fillNode()`/`presentNode()`/`pipes()` к реальному пути создания/представления узла и пайплайну (минимально — один вызов на панель в соответствующем сервисе), либо, если решение принято отложить эту функциональность, явно пометить хуки `@todo`/`@unimplemented` в докблоке и снять формулировку «enrich the node pipeline… without forking the package» до реализации.

## 3. Не проверено / ограничения

- Repro через Testbench (регистрация тестовой панели через config + прогон boot-валидации на кривом FQCN) не запускался: доказательная база C3/C4 построена на исчерпывающем статическом грепе по всему `packages/*/src` (единственные сайты вызова уже перечислены выше), что даёт `high`-уверенность без необходимости живого прогона; при желании усилить доказательство — тривиальный unit-тест на `PanelRegistry::validate()` с кривым FQCN.
- `PanelTableResolver` (`packages/core/src/Panels/PanelTableResolver.php`) прочитан как тонкий делегат к `PanelRegistry::get($panel)->table($base)` — отдельного чеклист-пункта под него нет, добавочных находок не incurred.
- Коллизия имён таблиц/индексов между несколькими own-tables панелями с одинаковым `tablePrefix` НЕ проверялась предметно — вне Scope Included item'а (P2.3 владеет этой осью, `F-P2.3-02` уже фиксирует смежный факт про `connection`); C6 подтверждает только механизм вывода имени, не отсутствие коллизий между разными префиксами.
- Поведение `vaulter:panel:migrations` (`PanelMigrationsCommand`) как консольной команды прочитано только транзитивно через `PanelMigrationGenerator`; сам файл команды (`packages/core/src/Console/PanelMigrationsCommand.php`) не входил в Required Reads item'а и не читался построчно — Deliverable-риск не переоткрывается, т.к. вне Scope Included.
