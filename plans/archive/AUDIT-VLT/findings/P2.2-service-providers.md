## 2. Находки

### F-P2.2-01 — `VaulterDocumentsServiceProvider` обходит `mergeConfigFrom`, читает файл с диска на каждый запрос · Severity: Major · Уверенность: high

**Где:** `packages/documents/src/VaulterDocumentsServiceProvider.php:59-73`
**Что:** Вместо `$this->mergeConfigFrom($path, $key)` (унаследован от `Illuminate\Support\ServiceProvider`, используется во ВСЕХ остальных провайдерах пакета) `packageRegistered()` делает `require __DIR__.'/../config/vaulter-documents.php'` напрямую, затем ручной `array_merge` трёх ключей (`vaulter.models`, `vaulter.handlers`, `vaulter.exporters`) и `config([...])`. Этот код НЕ обёрнут в `if (!$this->app->configurationIsCached())`.
**Почему опасно:** Это ровно тот I/O, который `.claude/rules/service-provider.md` запрещает в `register()`: «НИКАКОГО I/O (БД/HTTP/файловая система): контейнер ещё не готов, цена платится на каждый запрос каждого потребителя». `mergeConfigFrom` существует именно чтобы платить эту цену ОДИН раз (при построении кеша) и затем пропускать её (PT4.2) — данный код платит её на КАЖДЫЙ запрос КАЖДОГО хоста, даже под `config:cache`, что противоречит самой цели фичи «config-cache safety», которую этот item обязан проверить.
**Доказательство:**
```php
// packages/documents/src/VaulterDocumentsServiceProvider.php:59-73
$defaults = require __DIR__.'/../config/vaulter-documents.php';
$existingModels = config('vaulter.models', []);
$existingHandlers = config('vaulter.handlers', []);
$existingExporters = config('vaulter.exporters', []);
config([
    'vaulter.models' => array_merge($defaults['models'], $existingModels),
    'vaulter.handlers' => array_merge($defaults['handlers'], $existingHandlers),
    'vaulter.exporters' => array_merge($defaults['exporters'], $existingExporters),
]);
```
**Норма, которая нарушена:** PT4.2 (`findings/P2-package-tools.md`) + `.claude/rules/service-provider.md` («НИКАКОГО I/O... register()»).
**Сверка с ADR:** нет ADR, обсуждающего это конкретное место; комментарий в коде (`:53-58`) объясняет ЗАЧЕМ мержить три ключа (документировано), но не объясняет, почему `mergeConfigFrom` (уже унаследованный метод, использованный в drive/media строкой выше по аналогии) не подошёл технически — три ключа МОГУТ мержиться тремя вызовами `mergeConfigFrom($path, 'vaulter.models')`/`(..., 'vaulter.handlers')`/`(..., 'vaulter.exporters')` с ОДНИМ И ТЕМ ЖЕ файлом (он возвращает массив с тремя под-ключами `models`/`handlers`/`exporters`, а `mergeConfigFrom` мержит ПО КЛЮЧУ верхнего уровня своего второго аргумента — потребовалось бы 3 отдельных небольших config-файла ИЛИ 3 вызова с одним и тем же `require`d массивом через отдельный метод). Это выглядит как непреднамеренное упущение при экстракции пакета (ADR-0015 упоминается в докблоке провайдера), а не сознательное архитектурное решение.
**Рекомендация:** заменить ручной `require`+`array_merge`+`config([...])` на три вызова `$this->mergeConfigFrom(...)` (по образцу `VaulterDriveServiceProvider`/`VaulterMediaServiceProvider`), либо явно обернуть текущий код в `if (!$this->app->configurationIsCached())`.

### F-P2.2-02 — `runsMigrations()`+`discoversMigrations()`: публикация после автозапуска ведёт к повторному прогону под новым именем · Severity: Major · Уверенность: high

**Где:** `packages/core/src/VaulterServiceProvider.php:39-40` (конфигурация провайдера); `docs/guide/installation.md:75-80` (документация канонического режима)
**Что:** Провайдер одновременно объявляет `discoversMigrations()` (публикуемость) и `runsMigrations()` (автозапуск из `vendor/`). Документация верно называет вендорный автозапуск каноническим режимом, но НЕ предупреждает, что `vendor:publish --tag=vaulter-migrations`, вызванный ПОСЛЕ того, как автозапуск уже накатил миграции, генерирует файлы с НОВЫМИ timestamp-префиксами (не совпадающими с уже выполненными именами в таблице `migrations`), и что после публикации хост обязан отключить/не смешивать вендорный автозапуск с прогоном опубликованных копий — иначе `php artisan migrate` попытается выполнить «новые» (по имени) миграции, создающие уже существующие таблицы.
**Почему опасно:** цена — сломанный `migrate` у хоста, решившего кастомизировать схему (ровно тот сценарий, для которого предусмотрена публикация — `docs/guide/installation.md:78`: «Publish them... to tweak the schema before a custom panel»): `SQLSTATE[42S01]: Base table or view already exists` при первом же `migrate` после публикации, если исходные (вендорные) миграции уже отработали.
**Доказательство:** repro `plans/AUDIT-VLT/artifacts/repro/P2.2/PublishTagsTest.php`, ключ `paths per group['vaulter-migrations']` фактического вывода:
```
".../database/migrations/2026_06_13_000007_create_v_storages_table.php":
  ".../bootstrap/cache/laravel/database/migrations/./2026_07_10_101542_create_v_storages_table.php"
```
(источник и назначение — РАЗНЫЕ базовые имена: `2026_06_13_000007_...` → `2026_07_10_101542_...`); повторено для всех 17 файлов миграций пакета.
**Норма, которая нарушена:** PT2.2 (`findings/P2-package-tools.md`): «Одновременная публикуемость + автозапуск создаёт риск двойного прогона... каноничность режима обязана быть объявлена в доках» — объявлена НЕЧЕТКО: канон назван, последствие смены режима — нет.
**Сверка с ADR:** нет ADR по миграционной стратегии пакета; `docs/guide/installation.md` — единственный нормативный источник, и он неполон, а не сознательно отклоняется от нормы → классифицируется как дефект документации (не «ADR устарел»).
**Рекомендация:** дописать в `docs/guide/installation.md` явное предупреждение: «после `vendor:publish --tag=vaulter-migrations` для правки схемы — работайте ТОЛЬКО с опубликованными файлами (`database/migrations/`), не оставляйте вендорный автозапуск активным на тех же таблицах» ИЛИ (архитектурно) отказаться от одновременного `discoversMigrations()+runsMigrations()` в пользу одного режима.

## 3. Не проверено / ограничения

- **C13 — полноценный `config:cache`-смоук с валидным cached-конфигом НЕ подтверждён.** Причина: `vendor/orchestra/testbench-core/laravel/bootstrap/cache/packages.php` в этом чекауте — устаревший composer package-discovery кеш (датирован до выделения `vaulter-media`/`vaulter-drive`/`vaulter-documents` из `vaulter-core`, P2 #5): содержит ТОЛЬКО провайдер `axioma-studio/vaulter-core`. И литеральный `vendor/bin/testbench config:cache` (root `testbench.yaml`), И `Illuminate\Foundation\Console\ConfigCacheCommand` внутри Pest/Testbench (`Artisan::call('config:cache')`, которая согласно исходнику Laravel сама бутстрапит СВЕЖЕЕ приложение через `bootstrap/app.php` для получения «чистого» конфига перед дампом) полагаются на этот кеш и поэтому не видят media/drive/documents — итоговый дамп теряет `vaulter.cas`/доп.-модели, резолв `StorageDriver`/`BlobStore`/`ContentStore` после падает с `CAS storage driver not configured`. Это дефект ОКРУЖЕНИЯ (устаревший discovery-кеш), исправление которого (`composer dump-autoload`/`package:discover`) — изменение вне `plans/AUDIT-VLT/` и вне read-only границы аудита (D2), поэтому НЕ выполнено. Косвенные данные (C3: `featureEnabled` читает `config()` напрямую, без пере-мержа в рантайме; C5: точечные merge-ключи корректны под реалистичной публикацией) указывают, что САМ ПАКЕТ спроектирован cache-safe (за вычетом F-P2.2-01), но прямое подтверждение C13 остаётся неполным.
- Точный механизм, ПОЧЕМУ `ConfigCacheCommand`'s внутренний `getFreshConfiguration()` (через `bootstrap/app.php`) не подхватывает `getPackageProviders()`-провайдеры Testbench-теста, не прослежен до конца в исходнике Laravel/Testbench (гипотеза: `bootstrap/app.php` полагается ИСКЛЮЧИТЕЛЬНО на composer-discovery + `bootstrap/providers.php`, а не на тестовый оверрайд) — подтверждено эмпирически (repro), не построчным чтением фреймворка.
- `permissions-azgard`-провайдер не тестировался в СОСТАВЕ полного 6-провайдерного стека (root vendor не тянет `vaulter-filament`/`vaulter-permissions-azgard` — у каждого своя `vendor/`, ни одна не требует ВСЕ шесть пакетов вместе); C9 закрыт чтением исходника (детерминированно, без двусмысленности токсина schema), C7/C8 для azgard — НЕ прогнаны через `ServiceProvider::publishableGroups()` (тег `vaulter-azgard-config` виден напрямую в коде — `publishes([...], 'vaulter-azgard-config')`, однозначен, RAG-note о запрете «выводить теги из чтения `->name(...)`» относится к ТУЛКИТ-провайдерам с неявной схемой имён, azgard — голый `ServiceProvider` с явным литералом тега, что не тот случай).
- Гонка/конкурентность двойного прогона миграций (F-P2.2-02) не воспроизведена ФАКТИЧЕСКИМ прогоном `migrate` дважды (SQLite in-memory теряется между отдельными `testbench`-вызовами) — вывод построен на несовпадении имён файлов (детерминированный факт) + документированном поведении Laravel-миграций (трекинг по имени файла, общеизвестный факт фреймворка, не переверифицированный чтением `Illuminate\Database\Migrations\Migrator` в этом item'е).
