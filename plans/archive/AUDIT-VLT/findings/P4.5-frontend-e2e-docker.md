## 2. Находки

### F-P4.5-01 — `@tiptap/*` в `packages/vue` на устаревшем мажоре (2.x, текущий стабильный — 3.x) · Severity: Minor · Уверенность: high

**Где:** `packages/vue/package.json:53-55` (`@tiptap/pm: ^2.10`, `@tiptap/starter-kit: ^2.10`, `@tiptap/vue-3: ^2.10`); тот же констрейнт продублирован в `e2e/package.json:19-21` (не входит в основную поставку, но использует ту же устаревшую линию для e2e-плейграунда).
**Что:** Пакет `@vaulter/vue` объявляет зависимость от TipTap `^2.10`, тогда как актуальный стабильный мажор экосистемы TipTap — 3.x (`@tiptap/core@3.27.3` на дату проверки, релиз 3.0 состоялся ранее в 2026 и с тех пор поддерживается как current).
**Почему опасно:** Currency-долг: линия 2.x не получает новых фич и рано или поздно перейдёт в security-only/EOL-режим; апгрейд на мажор выше откладывается тем дольше, чем больше расходится API (TipTap 3.0 несёт breaking changes относительно 2.x). Прямого известного CVE на констрейнт `^2.10` (сверх уже зафиксированного `F-P1.11-01/04` про `href`-схему в TipTap-link) не найдено — это ось «долг», не «уязвимость».
**Доказательство:**
```json
"@tiptap/pm": "^2.10",
"@tiptap/starter-kit": "^2.10",
"@tiptap/vue-3": "^2.10",
```
WebSearch 2026-07-10: «latest version of `@tiptap/core` is 3.27.3 … current major version is 3.x … Tiptap 3.0 is stable».
**Норма, которая нарушена:** P4.5 `C3` (Code Guidance P4.5: «Currency мажоров сверяется с … не памятью»); норма — не отставать от актуального поддерживаемого мажора внешней зависимости, формирующей контент-безопасность документа (пересечение с G2-осью P1.11, но здесь — версия, не конфигурация фильтрации).
**Сверка с ADR:** Нет ADR, фиксирующего сознательный выбор линии TipTap 2.x; расхождение не является осознанным архитектурным решением — дефект (currency-долг), не «ADR устарел».
**Рекомендация:** Запланировать апгрейд `@tiptap/*` на актуальный мажор (3.x) с оценкой breaking changes API редактора; минимально — зафиксировать решение о поддерживаемой линии в документации пакета (симметрично `F-P4.4`-политике версий, если такая заведена).

### F-P4.5-02 — hocuspocus-стек (`@hocuspocus/server`+extensions, `@hocuspocus/provider`) на устаревшем мажоре (2.x, актуальны v3/v4) · Severity: Minor · Уверенность: medium

**Где:** `hocuspocus-server/package.json:16-19` (`@hocuspocus/extension-logger\|redis\|throttle: ^2.15`, `@hocuspocus/server: ^2.15`); `packages/vue/package.json:52` (`@hocuspocus/provider: ^2.13`); тот же провайдер-констрейнт в `e2e/package.json:16`.
**Что:** Весь hocuspocus-стек пакета — и серверная часть (Node-хаб `hocuspocus-server/`), и клиентская (`@hocuspocus/provider` в `packages/vue`) — объявлен на мажоре `2.x`, тогда как экосистема `ueberdosis/hocuspocus` ушла на v3 (последний релиз v3.2.3) и объявила v4 как новое стабильное поколение (T3, `findings/P0.2-rag-supplement.md`). `2.15.x` — хвост линии v2 (последний релиз 2.15.2 от 03.02.2025), т.е. на дату аудита (2026-07-10) — свежее издание этой линии старше года.
**Почему опасно:** Пакет стоит на неподдерживаемой (или близкой к неподдерживаемой) линии внешней зависимости, обслуживающей realtime-collab поверхность продукта. Собственный RAG (WebSearch 2026-07-10) не нашёл официального объявления EOL v2 или подтверждения, что v2 всё ещё получает security-патчи в 2026 — статус не подтверждён документально ни в одну, ни в другую сторону (см. «Не проверено»). Отставание на два мажора (2→3→4) увеличивает будущую стоимость и риск апгрейда «под давлением» CVE. T3 отдельно фиксирует breaking-путь v2→v4 (`request`/`requestHeaders`, IP только из заголовков) — апгрейд не тривиален.
**Доказательство:**
```json
// hocuspocus-server/package.json
"@hocuspocus/server": "^2.15",
"@hocuspocus/extension-logger": "^2.15",
"@hocuspocus/extension-redis": "^2.15",
"@hocuspocus/extension-throttle": "^2.15",
```
```json
// packages/vue/package.json
"@hocuspocus/provider": "^2.13",
```
`RAG:✅ 2026-07-10` (T3, `findings/P0.2-rag-supplement.md`) — «npm `latest` — v3.x (последняя опубликованная 3.2.3); последнее поколение проекта — v4.x … `v2.15.x` — хвост линии v2 … superseded линиями v3→v4».
**Норма, которая нарушена:** P4.5 `C5`/`C3` (Code Guidance: «Currency мажоров сверяется с T3, не памятью»); T3 (`findings/P0.2-rag-supplement.md`) — прямая констатация устаревшего мажора.
**Сверка с ADR:** `docs/adr/0001-collaboration-transport.md` фиксирует `HocuspocusCollaborationDriver` как **опциональную** надстройку (согласуется с D13), но не фиксирует конкретную поддерживаемую линию версий hocuspocus — расхождение не является осознанным ADR-решением о версии, дефект (currency-долг), не «ADR устарел».
**Рекомендация:** Запланировать апгрейд `@hocuspocus/*` (сервер+extensions+provider согласованно) на v3 либо сразу v4 с оценкой breaking changes (T3: `request`/`requestHeaders` API), либо явно задокументировать решение остаться на v2 с обоснованием (совместимость/стабильность) — на сегодня решение нигде не зафиксировано.

### F-P4.5-03 — e2e-стенд: `laravel`/`hub`/`vite` без healthcheck, `depends_on` без `condition: service_healthy` · Severity: Minor · Уверенность: high

**Где:** `e2e/docker-compose.yml:22-36` (сервис `laravel` — без `healthcheck`), `e2e/docker-compose.yml:37-49` (сервис `hub` — без `healthcheck`, `depends_on: - laravel` на строке 50 без `condition`), `e2e/docker-compose.yml:50-64` (сервис `vite` — без `healthcheck`, `depends_on: - laravel / - hub` на строке 64 без `condition`).
**Что:** Только сервис `postgres` объявляет `healthcheck` (строки 16-20) и только `laravel` ждёт его готовности через `condition: service_healthy` (строка 35). Сервисы `hub` и `vite` стартуют по факту ЗАПУСКА контейнера `laravel`/`hub` (`depends_on` без условия), а не по факту готовности их HTTP/WS-эндпоинтов — `laravel` поднимает `testbench serve` после `migrate:fresh`, что занимает заметное время, и `hub` может начать принимать WS-соединения раньше, чем backend готов отвечать на collab-callback'и.
**Почему опасно:** Классическая причина e2e-флейков: оркестратор стартует зависимый сервис до готовности зависимости. Contrast: собственный reference-деплой хаба (`hocuspocus-server/docker-compose.yml:44-48`) ЭТУ практику соблюдает (healthcheck на `/health`), а внутренний e2e-стенд — нет. Это не security-риск, а риск нестабильности CI/локального прогона (для не-security оси P4 — цена дефекта: время разработчика на диагностику ложных падений).
**Доказательство:**
```yaml
  hub:
    build:
      context: ../hocuspocus-server
    ...
    depends_on:
      - laravel
  vite:
    image: node:20-alpine
    ...
    depends_on:
      - laravel
      - hub
```
(`e2e/docker-compose.yml:37-64`) — ни один из трёх блоков `depends_on` для `hub`/`vite` не содержит `condition:`.
**Норма, которая нарушена:** P4.5 `C7` (Code Guidance: «отсутствие healthcheck/`depends_on: service_healthy` → находка Nit/Minor — оркестрация стартует до готовности сервиса → флейки»); практика уже применена в `hocuspocus-server/docker-compose.yml` того же репозитория (внутренняя несогласованность).
**Сверка с ADR:** Не относится к предмету ADR (инфраструктура e2e-стенда, не архитектурное решение продукта) — дефект, не «ADR устарел».
**Рекомендация:** Добавить `healthcheck` для `laravel` (HTTP-пинг `testbench serve`) и `hub` (уже есть `/health`-эндпоинт по коду `hocuspocus-server/src/index.js`, используется в `hocuspocus-server/docker-compose.yml:44-48` — симметрично применить в `e2e/docker-compose.yml`), перевести `depends_on` у `hub`/`vite` на `condition: service_healthy`.

## 3. Не проверено / ограничения

- **Прогон стенда** (`docker compose up`, `playwright test`, `vitest run`) НЕ выполнялся — Docker/сетевые ресурсы для полноценного e2e-прогона не поднимались в рамках read-only аудита (D2); вердикты C1/C2/C4/C7/C8 построены чтением конфигов и тела тестов, не фактическим запуском. Явно допустимо по Implementation Rules item'а («если Docker/Playwright недоступны → вердикт по чтению + `⚠ partial`» — здесь чтения было достаточно для `pass`/`fail`, кроме `C5`/`C7`, которые помечены `⚠ partial`/используют находку с открытым фактом).
- **Официальный статус EOL `@hocuspocus/server` v2.x не подтверждён документально** ни в T3, ни собственным WebSearch 2026-07-10 (нашёл только факт релиза 2.15.2 03.02.2025 и что v2.13.2 получал критический фикс в своё время) — severity `F-P4.5-02` калибрована как Minor/medium именно из-за этой неопределённости; если владелец плана найдёт официальное объявление EOL v2, severity подлежит пересмотру в Major.
- **`composer.lock`/`package-lock.json` фактически разрешённые версии** не сверялись построчно (совпадает с ограничением `P0.2-rag-supplement.md`/`P4-matrix-supply-chain.md`) — вердикты C3/C5 построены по объявленным констрейнтам `package.json`, не по lock.
- **npm audit / CVE-проверка** hocuspocus/tiptap/yjs — ось P4.4 `C8`, здесь не дублируется (Code Guidance item'а).
- **`hocuspocus-server/test/*.test.js`** (5 файлов) прочитаны только по списку имён (`websocket-hardening`, `webhook`, `security`, `config`, `on-connect`), не построчно — Scope Included item'а не требует построчного разбора Node-тестов хаба (это Required Read не входит в перечень; тела не читались, за исключением необходимости для чеклиста C1-C8, которые про них не спрашивают).
