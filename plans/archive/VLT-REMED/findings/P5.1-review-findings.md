## R-01 — Blocker — allow-list P0.1 отвергает узлы, которые пакет сам предлагает редактору

**Ось:** (а) корректность фикса Blocker'а P0.1 · (е) «зелёное, но не починенное».

**Сценарий отказа.** `packages/documents/src/Enums/DocumentType.php:22` объявляет
`#[TiptapExtensions(['StarterKit', 'Image', 'Table', 'Link'])]` (и `['StarterKit', 'Table']` для
второго типа). Этот список отдаётся клиенту как prop — редактор монтирует тулбар с картинкой и
таблицей. Пользователь вставляет картинку → клиент шлёт TipTap-JSON с узлом `image` →
`UpdateDocumentContentRequest` зовёт `TipTapContent::fromArray()` → `ALLOWED_NODE_TYPES` (doc,
paragraph, heading, text, hardBreak, horizontalRule, bulletList, orderedList, listItem, blockquote,
codeBlock) не содержит `image` → `InvalidTipTapContentException: unknown node type "image"`.
**Документ невозможно сохранить.**

Проверено исполнением:

```
REJECTED : image (StarterKit+Image)  -> unknown node type "image"
REJECTED : table (StarterKit+Table)  -> unknown node type "table"
REJECTED : underline mark            -> unknown mark type "underline"
```

**Второй, более тяжёлый удар — путь ЧТЕНИЯ.** `NodeDocumentVersion::tipTapContent()`
(`packages/documents/src/Models/NodeDocumentVersion.php:88-96`) зовёт тот же `fromArray()` при
гидрации из БД. Его собственный докблок обещает: *«An empty/invalid snapshot decays to an empty doc
rather than throwing on read»* — **это неправда**: decay срабатывает только когда `type !== 'doc'`;
корректный `doc` с недопустимым потомком бросает наружу. Значит **любая версия документа,
сохранённая ДО P0.1** и содержащая `image`/`table`/`underline`/`textStyle`/`highlight` — при
открытии, превью и экспорте даёт исключение. Это не деградация, а отказ.

**Почему это класс, а не строка.** Allow-list построен от того, что умеет рендерить
`TipTapRenderer` (докблок `TipTapContent:20` прямо это говорит), но множество узлов **редактора**
строго больше множества узлов **рендерера**. Верный барьер для F-P1.11-01 — «вычистить то, что
рендерер не умеет» (strip/sanitize), а не «отвергнуть документ». Расширить allow-list хост тоже не
может: `private const array`, конфиг-шва нет — при том что текст самого исключения советует
«extend the allow-list deliberately», а механизма для этого не существует.

**Рекомендованная диспозиция (P5.2).** Развести две задачи, которые P0.1 слил в одну:
(1) безопасность — запрет опасных схем `href` и опасных атрибутов (это allow-list делает верно, и
это надо сохранить); (2) полнота модели документа — набор узлов/марок обязан покрывать то, что
пакет отдаёт редактору (`Image`, `Table`+`tableRow`/`tableCell`/`tableHeader`, `underline`, и
`codeBlock.language`), и быть расширяемым хостом через конфиг. Путь чтения обязан деградировать
(strip неизвестного узла), а не бросать — иначе один старый документ роняет весь UI.
**BC-запись в `UPGRADE.md` обязательна (см. R-06).**

## R-02 — Major — tus-лок не покрывает sweep (ось (а) требовала именно этого)

**Сценарий отказа.**
1. Клиент шлёт PATCH → `TusUploadHandler::patch()` открывает `DB::transaction`, берёт
   `pg_try_advisory_xact_lock(hashtext('upload:'.$uploadId))`, читает свежую строку:
   `status=Uploading`, `received_bytes=N`.
2. Параллельно по расписанию идёт `vaulter:sweep-uploads`. `SweepUploadsCommand:40-43` берёт
   кандидатов `sweepable($now)` (открытые сессии с `expires_at <= now`) и зовёт
   `UploadSessionManager::expire($session)` — **не беря ни advisory-лок, ни `FOR UPDATE`**.
   `expire()` делает `staged->discard($session)` → **удаляет staged-объект** и
   `transition(..., Expired)`.
3. PATCH продолжает: `staged->append($locked, $chunk, $offset)`. Внутри — ветка
   `if ($offset > 0 && $disk->exists($key))`. Объекта больше НЕТ → перенос уже принятых `N` байт
   **молча пропускается** (R-03) → в staged-объект пишется ТОЛЬКО новый чанк.
4. `advanceReceived()` пишет `received_bytes = len(chunk)` и **форсит `status => Uploading`**
   (R-08), затирая `Expired`.

**Итог:** сессия воскресает из терминального статуса; первые `N` байт файла потеряны навсегда;
сервер отдаёт клиенту регрессировавший offset, клиент дошлёт «хвост» — и сборка завершится
файлом правильной длины с **переставленным/битым содержимым**. Это ровно тот исход, ради которого
F-P1.4-01 был Blocker'ом («тихая порча файла»), только пара акторов другая: не PATCH↔PATCH, а
PATCH↔sweep.

Ось (а) ТЗ P5.1 требует дословно: *«лок сессии tus — покрывает и путь конкурентного PATCH, и
sweep»*. Покрыт только первый.

**Рекомендованная диспозиция (P5.2).** `expire()` (и `abort()`) обязаны входить в ту же критическую
секцию: брать тот же advisory-лок / `FOR UPDATE` по строке и **перечитывать `status` под локом**
перед `discard()`. Плюс `advanceReceived()` обязан быть compare-and-set по статусу (R-08).
Регресс-тест — на PG, параллельные PATCH и sweep (шов `tests/Concurrency/` уже существует).

## R-03 — Major — `StagedUpload::append()` fail-open при отсутствии staged-объекта

**Сценарий отказа.** `append()` переносит уже принятые байты только под условием
`if ($offset > 0 && $disk->exists($key))`. Если объект отсутствует по ЛЮБОЙ причине (sweep —
R-02; ручная чистка бакета; сбой/расхождение стораджа; смена диска), условие ложно, ветка
пропускается **без единого сигнала**, и `writeStream()` перезаписывает ключ содержимым одного
чанка. Возвращается `size = len(chunk)`, который вызывающий принимает за новый authoritative
offset.

Путь целостности данных обязан быть fail-closed: `offset > 0` при отсутствующем staged-объекте —
это невозможное состояние, и оно должно бросать, а не тихо усекать файл.

**Рекомендованная диспозиция (P5.2).** При `$offset > 0 && !$disk->exists($key)` — доменное
исключение (сессия несостоятельна). Отдельный регресс-тест: удалить staged-объект, вызвать
`append(offset: N>0)`, ожидать исключение, а НЕ усечённый файл. Это фикс по классу, независимый от
R-02, и он же выбивает главный механизм R-02.

## R-04 — Major — Markdown-экспорт экранирует HTML, а не Markdown

**Сценарий отказа.** `markdownText()` экранирует текст через `htmlspecialchars($v, ENT_QUOTES)` —
это нейтрализует `& < > " '`, но НЕ трогает markdown-метасимволы `[`, `]`, `(`, `)`.
`markdownLink()` собирает `'['.$label.']('.$href.')'`. Отсюда две рабочие инъекции — обе прошли
store-time-валидацию (href легальный `https://`) и обе исполнены:

```
Вектор A — инъекция через label:
  text = 'click](javascript:alert(1))', mark link href = 'https://ok.example'
  → MD: [click](javascript:alert(1))](https://ok.example)

Вектор B — инъекция через href (символ ')' внутри разрешённой https-схемы):
  href = 'https://a.example/) [pwn](javascript:alert(1)'
  → MD: [safe](https://a.example/) [pwn](javascript:alert(1))
```

В обоих случаях экспортированный Markdown содержит **живую `javascript:`-ссылку**. Докблок
`TipTapRenderer` утверждает, что markdown-путь *«re-applies the same link-scheme allow-list plus
text escaping»* — allow-list применяется к href, но не к результату сборки, поэтому обход тривиален.
HTML-путь этим НЕ затронут (symfony-санитайзер держит; проверено — вектор B в HTML выходит
безопасным `https://`-URL).

**Рекомендованная диспозиция (P5.2).** Экранировать markdown-метасимволы в label (`\[`, `\]`) и
не собирать URL конкатенацией: href с `(`/`)`/пробелом — либо `<...>`-обёртка, либо
percent-encoding, либо отказ от ссылки. Регресс-тесты — оба вектора выше, красные на текущем коде.

## R-05 — Major — `follow_redirects=true` снимает SSRF-барьер целиком

**Сценарий отказа.** Барьер `DefaultOutboundUrlGuard::pin()` пинит проверенный IP на соединение
через `CURLOPT_RESOLVE` — но пинится **только исходный `host:port`**. Если хост включает
поддерживаемый конфиг-ключ `vaulter.webhooks.follow_redirects => true`
(`packages/core/config/vaulter.php:641`), `DeliverWebhook::post()` не вызывает
`withoutRedirecting()`, Guzzle идёт по 302 — и для НОВОГО хоста делает **обычный DNS-резолв без
guard'а**. `CURLOPT_REDIR_PROTOCOLS` ограничивает только схему (http/https), не адрес. Приёмник
webhook'а отвечает `302 Location: http://169.254.169.254/latest/meta-data/` → запрос уходит на
metadata-сервис. Blocker F-P1.7-01 воспроизводится полностью.

Что это не гипотеза, подтверждает сам регресс-тест: `OutboundUrlGuardTest` («it does not follow a
redirect onto a private address») в комментарии пишет — *«Redirects are off, so a 302 is the final
(non-2xx) response»*. То есть защита держится **исключительно** на дефолте `false`; включённый
случай не покрыт ни кодом, ни тестом.

**Рекомендованная диспозиция (P5.2).** Либо снять ключ (доставка webhook'а не обязана ходить по
редиректам), либо гнать редиректы вручную, прогоняя `pin()` на КАЖДОМ хопе. Комментарий у ключа
обязан сказать прямо: включение отключает SSRF-барьер. Регресс-тест — `follow_redirects=true` +
302 на приватный адрес → доставка обязана провалиться.

## R-07 — Major — второй эшелон D4 не имеет red-before-теста и на практике недостижим

**Сценарий отказа (два слоя).**

*Слой 1 — тест не красный.* Откат ТОЛЬКО не-тестового файла фикса
(`git checkout 6b5a52e -- packages/documents/src/Support/TipTapRenderer.php`) и прогон
`TipTapRendererTest`:

```
✓ it renders TipTap content to HTML with escaping          ← ЗЕЛЁНЫЙ на коде ДО фикса
✓ it rejects a javascript: link href at store time, F-P1.11-01   ← store-time, рендерер не при чём
✓ it rejects obfuscated javascript:/data: schemes ... ×4    ← store-time
✓ it rejects an unknown node type at store time, F-P1.11-02 ← store-time
⨯ it escapes raw text in markdown export, F-P1.11-04        ← единственный реально красный
✓ it keeps a valid link and drops disallowed link schemes in markdown ← ЗЕЛЁНЫЙ до фикса
```

10 из 11 кейсов зелены на дефектном коде. Кейсы, помеченные `F-P1.11-01` в файле **рендерера**, —
на деле ассерты `TipTapContent::fromArray()`, т.е. store-time-эшелона. Подключение
`symfony/html-sanitizer` (сердце D4) **не пиннится ни одним тестом**: D7 по нему фактически не
исполнен.

*Слой 2 — эшелон недостижим.* Единственный конструктор `TipTapContent` — приватный; все входы
(`NodeDocumentVersion::tipTapContent()`, `UpdateDocumentContentRequest`, `CreateDocumentNodeRequest`,
`NodeCollaborationController`) идут через `fromArray()`, который уже отверг всё опасное. Санитайзер
физически не может увидеть ни `javascript:`-href, ни скриптовый узел. Обоснование D4 («контент,
сохранённый ДО валидатора, читается вербатим и добирается санитайзером») **фактически неверно**:
такой контент не «читается вербатим», а **бросает исключение** на `fromArray()` (это и есть R-01).
Эшелон, который D4 задумывал, не работает — вместо него стоит отказ в обслуживании.

**Рекомендованная диспозиция (P5.2).** Связан с R-01 — чинить вместе. Когда путь чтения станет
деградирующим (strip вместо throw), санитайзер обретёт реальный вход, и тогда обязателен тест:
легаси-снапшот со скриптовым узлом/`javascript:`-href → рендер → доказать, что на выходе он
обезврежен. Сейчас такого теста нет и быть не может.

## Minor

**R-08 — `advanceReceived()` минует машину состояний.** `UploadSessionStoreRepository::advanceReceived()`
делает `forceFill(['received_bytes' => …, 'status' => UploadStatus::Uploading])->save()` безусловно.
Докблок соседнего `transition()` заявляет, что легальность перехода стережёт менеджер через
`UploadStatus::canTransitionTo` — `advanceReceived` не стережёт её никак и способен поднять сессию
из `Expired`/`Aborted` обратно в `Uploading` (механизм R-02). Диспозиция: compare-and-set
(`WHERE status IN (open…)`), 0 затронутых строк → конфликт.

**R-09 — коллизия ключа advisory-лока.** `pg_try_advisory_xact_lock(hashtext('upload:'.$id))`:
`hashtext` даёт int4, поэтому два РАЗНЫХ `upload_id` могут делить ключ лока. Последствие — ложный
409 на невиновной сессии (клиент перечитает HEAD и продолжит), порчи данных нет. Диспозиция:
принять (вероятность мала, отказ безопасен) либо перейти на двухаргументную форму
`pg_try_advisory_xact_lock(int, int)` с разнесением. Отмечено, чтобы будущий читатель не принял
ложный 409 за дефект лока.
