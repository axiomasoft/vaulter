# P5.4 — эскалация: коробящий шаг coverage в `mutation.yml` (НЕ известный SQLite-флейк)

**Дата:** 2026-07-12 · **Контекст:** первый шаг item'а P5.4 (D31/D32) — измерение реального MSI прогоном
`mutation.yml` в CI на ветке `remediation/audit-vlt`. Ветка запушена (`git push -u origin
remediation/audit-vlt`), лейн диспатчился дважды на её ref.

## Факт

Шаг `Generate coverage for Infection` (`vendor/bin/pest --coverage-xml=... --log-junit=... --min=0`,
`DB_CONNECTION=sqlite`, `DB_DATABASE=:memory:`) падает **детерминированно** на обоих прогонах:

- Диспатч №1 — `run id 29197430486` (2026-07-12T15:03:14Z): `Tests: 45 failed, 442 passed (1089
  assertions)`.
- Диспатч №2 (диагностический ретрай, БЕЗ каких-либо правок кода/конфига между прогонами) —
  `run id 29197647780` (2026-07-12T15:09:52Z): **тот же набор** 45 упавших тестов, тот же счёт.

Job не доходит до шага `Run Infection` ни разу → **MSI не измерен ни на одном из двух прогонов**.

**Упавшие тесты — идентичный набор оба раза** (все в `packages/core/tests/Webhooks` +
`packages/core/tests/Feature/PruneWebhooksTest`):

```
FAIL Packages\core\tests\Feature\PruneWebhooksTest
FAIL Packages\core\tests\Webhooks\DeliverWebhookTest
FAIL Packages\core\tests\Webhooks\OutboundUrlGuardTest
FAIL Packages\core\tests\Webhooks\OutboxRelayTest
FAIL Packages\core\tests\Webhooks\SigningSecretEncryptionTest
FAIL Packages\core\tests\Webhooks\WebhookEndpointCrudTest
FAIL Packages\core\tests\Webhooks\WebhookRetryDispatcherTest
```

Корневая причина в логе — **`Illuminate\Encryption\MissingAppKeyException`: "No application encryption
key has been specified."**, брошенная из `EncryptionServiceProvider::key()` при `config('app.key')`
пустом. Стек ведёт в `packages/core/src/Webhooks/SigningSecretEncryptor.php` (шифрование
`signing_secret` вебхук-эндпоинта) — единственный код пакета, реально резолвящий `Encrypter`
на чтении/записи.

## Это НЕ известный флейк из `findings/P5.4-msi-ci.md` §6

Документированный режим отказа — SQLite-флейк `StorageManagerTest` (панель `team`,
`UnknownPanelException`). Он в этом прогоне **не встретился ни разу**. Набор и причина падения —
другие: систематический `MissingAppKeyException`, специфичный для лейна `mutation.yml`.

## Локально — зелено

- `composer test` (полный корневой сьют, SQLite `:memory:`, идентичные env-переменные) —
  **487 passed / 1267 assertions**, 0 failed.
- Изолированный прогон именно упавших в CI файлов —
  `DB_CONNECTION=sqlite DB_DATABASE=:memory: vendor/bin/pest packages/core/tests/Webhooks
  packages/core/tests/Feature/PruneWebhooksTest.php --min=0` — **80 passed / 248 assertions**, 0 failed.

## Расхождение с `tests.yml` (тот же PHP 8.4 + SQLite + xdebug-coverage)

`tests.yml` использует ТОТ ЖЕ движок (`vendor/bin/pest --coverage ...`, `DB_CONNECTION=sqlite`,
`XDEBUG_MODE=coverage`), но ставит зависимости через `composer require ... --no-update` +
`composer update` (плавающий диапазон `laravel/framework`/`orchestra/testbench` под матрицу), тогда как
`mutation.yml` идёт строго `composer install --prefer-dist` по закоммиченному `composer.lock`.
Прошлые прогоны `tests.yml` на `main` (проверено `gh run list --workflow=tests.yml --branch main`,
последние 5 — все `failure`) падали по ДРУГОЙ причине — порог покрытия `--min=80` не достигнут
(`FAIL Code coverage below expected 80.0 %, currently 79.2 %`), НЕ `MissingAppKeyException`. Прямого
сравнения «`tests.yml` зелёный / `mutation.yml` красный на том же коде» в этой сессии не получено —
диагностический диспатч `tests.yml --ref remediation/audit-vlt` (Scope Included P5.4, п.7) ещё не
запускался на момент этой эскалации (порядок ТЗ ставит его последним).

## Почему это не чинится в рамках P5.4 (Scope Excluded)

ТЗ item'а прямо запрещает править прикладной код/тесты ради MSI и требует стоп+эскалацию для ЛЮБОГО
неизвестного провала шага coverage (Code Guidance P5.4, if-then D31): «падение не-флейкового теста в
CI при зелёном локальном сьюте — находка, а не помеха: item останавливается, статус 🔴, `Escalation
Needed: yes`… не лечится правкой CI-конфига». Диагностика (описанная выше) сделана в объёме,
достаточном для решения владельца; дальнейшее расследование корня (например, почему `Env::has('APP_KEY')`
в раннере `mutation.yml` ведёт себя иначе, чем локально/в `tests.yml`) и правка — вне Scope Included
этого item'а.

## Blast-radius этой сессии

Push ветки выполнен (ожидаемо и санкционировано D31). Диспатчи №1/№2 — тихие операции (не трогают
`main`, не публикуют релиз). **Код/конфиг НЕ изменены**: `git status --porcelain -- infection.json5
.github/workflows/mutation.yml packages composer.json composer.lock` — пуст. `infection.json5`
по-прежнему несёт провизорный `50/70`, `mutation.yml` по-прежнему несёт `|| true` — D32 не исполнялся
(измерение — предпосылка для порогов, а измерения нет).
