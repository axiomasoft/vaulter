# P5.5 — доказательная база: скрытая зависимость тестов от `APP_KEY` вне VCS

**Дата:** 2026-07-12 · **Автор:** plan-design/opus · **Назначение:** вход items P5.5/P5.6 (решения
владельца D33–D35). Собрано при проектировании; исполнитель НЕ восстанавливает этот контекст заново,
но обязан подтвердить п.1 диагностикой (см. ТЗ P5.5) прежде, чем чинить.

## 1. Repo-grounded факты (проверены грепом/чтением, не по памяти)

- **Ни один закоммиченный конфиг репозитория не задаёт `APP_KEY`.** `<php><env …>`-блоки несут только
  `APP_ENV`, `DB_CONNECTION`, `DB_DATABASE`, `CACHE_DRIVER`, `QUEUE_CONNECTION`:
  - `phpunit.xml` (корень, сьют `core`) — 5 переменных, `APP_KEY` нет;
  - `packages/{documents,drive,filament,media}/phpunit.xml` — те же 5, `APP_KEY` нет;
  - `packages/permissions-azgard/phpunit.xml` — 3, `APP_KEY` нет.
- `APP_KEY` встречается ровно в двух местах репо: `testbench.yaml` (стенд e2e — `env:`-блок
  `APP_KEY="base64:lRknxO3IznrZODHVPvLNKylvYP19ch+EXZ8dM+i3OlY="`; сам файл помечен «НЕ участвует в
  обычных тестах») и `e2e/docker/testbench.pgsql.yaml`. Обычный `vendor/bin/pest` **testbench.yaml не
  читает** (его читает CLI `vendor/bin/testbench`, а не `Orchestra\Testbench\TestCase`).
- Корневой `composer.json` **не имеет** post-install/post-autoload-dump скриптов → `.env` тестового
  скелета не генерируется установкой зависимостей ни локально, ни в CI.
- В локальном дереве **существует** `vendor/orchestra/testbench-core/laravel/.env` (`ls -a` показывает
  и `.env`, и `.env.example`). Laravel бутстрапит приложение Testbench'а из этого каталога, значит его
  dotenv-файл читается при обычном прогоне тестов.
- Единственный код пакета, реально резолвящий `Encrypter`, — `packages/core/src/Webhooks/
  SigningSecretEncryptor.php` (шифрование `signing_secret` эндпоинта). Именно все 7 Webhook-сьютов
  `core` и падают в CI с `MissingAppKeyException` (`findings/P5.4-coverage-app-key-failure.md`).

## 2. Рабочая гипотеза корня (H1) — подлежит подтверждению исполнителем

Тесты никогда не получали `APP_KEY` из закоммиченного источника. Локально он приходит из
**невоспроизводимого артефакта рабочей машины** — dotenv тестового скелета в `vendor/`, который
материализуется запуском стенда (`vendor/bin/testbench serve`, чей `testbench.yaml` несёт `APP_KEY`),
а не установкой зависимостей. В чистом CI-чекауте (`composer install` по lock-файлу, стенд никогда не
поднимался) этого файла/ключа нет → `config('app.key')` пуст → `MissingAppKeyException` на всех путях,
касающихся `Encrypter`.

**Следствие, выходящее за рамки MSI:** локальная зелень сьюта (487/487) — частично артефакт «грязного»
`vendor/`, а CI честен. Гейт D12, которым закрывались items всего плана, доказывал меньше, чем считалось
(отсюда D34: критерий 4 вердикта переоценивается по ФАКТУ CI-прогона).

**Конкурирующая гипотеза (H2):** ключ приходит из переменной окружения оболочки разработчика
(`printenv APP_KEY`). Различающий тест — одна команда (см. ТЗ P5.5, шаг 1). Практический вывод для
фикса **одинаков** при H1 и H2: закоммиченного источника ключа нет ни в одном сценарии.

## 3. Норма фикса (RAG:✅ 2026-07-12)

Канонический для Testbench-пакета способ — детерминированный `APP_KEY` в `<php><env>` файла
`phpunit.xml`; документация Orchestra прямо рекомендует держать dummy-ключ в `phpunit.xml`, когда сьют
задействует шифрование. Приоритет: PHPUnit кладёт `<env>` в окружение процесса ДО бутстрапа Laravel, а
`Env`-репозиторий Laravel не перетирает уже установленные переменные значениями из `.env` — то есть
`phpunit.xml` выигрывает у `vendor/.../laravel/.env` во всех окружениях, где тесты гоняет PHPUnit/Pest.

- Источник: docs/сообщество Orchestra Testbench — `https://github.com/orchestral/testbench/issues/211`
  (мейнтейнерский ответ: dummy `APP_KEY` в `phpunit.xml` — официальный/дефолтный подход; альтернатива с
  `useEnvironmentPath()` + `LoadEnvironmentVariables` нужна лишь тем, кто держит ключ вне VCS);
  `https://dev.to/dcblog/test-laravel-packages-with-pestphp-m14` (тот же паттерн `<env name="APP_KEY">`).
- Запрос RAG: «Testbench MissingAppKeyException APP_KEY phpunit.xml env vs vendor testbench-core
  laravel/.env precedence» (perplexity-web, 2026-07-12).
- Вердикт: ключ тестового сьюта — **не секрет** (он защищает нулевые данные тестовой БД в памяти),
  его коммит в `phpunit.xml` безопасен и является нормой экосистемы. Секретом он стал бы только в
  приложении с реальными данными — там ключ живёт в `.env` хоста, и пакет на это не влияет.

## 4. Почему red-before уже существует (и его не надо фабриковать)

D7 требует красного-до-фикса. Он **уже получен в CI, дважды, независимыми прогонами**: run
`29197430486` и `29197647780` — идентичный набор из 45 упавших тестов, `MissingAppKeyException`
(`findings/P5.4-coverage-app-key-failure.md`). Это и есть red-before для P5.5: доказательство фикса —
тот же лейн, тот же шаг, зелёный после правки. Локальный red-before структурно невозможен (локально
ключ есть — в этом и дефект), фабриковать его подменой vendor-файлов ЗАПРЕЩЕНО.

## 5. Что известно про второй CI-факт (вход D35)

`gh run list --workflow=tests.yml --branch main` (проверено в сессии P5.4): последние 5 прогонов —
`failure`, причина в логе — `FAIL Code coverage below expected 80.0 %, currently 79.2 %` (порог
`--min=80` скрипта `test:coverage`), НЕ `MissingAppKeyException`. То есть на `main` тестовый лейн CI
красный **по другой причине** и был таким всё время работы плана. Верифицировать это на ветке
`remediation/audit-vlt` (после фикса `APP_KEY`) — задача P5.6; диспозиция результата предрешена
владельцем (D35): порог не понижаем, тесты ради процента не пишем, красное — честный долг в вердикте.
