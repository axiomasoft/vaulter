## 1. Ветка ремедиации не запушена в origin (repo-grounded)

```
$ git ls-remote --heads origin remediation/audit-vlt
(пусто)
$ git status -sb | head -1
## remediation/audit-vlt            # ← upstream отсутствует
$ git remote -v
origin  https://github.com/axioma-studio/vaulter.git (fetch/push)
```

**Вердикт:** CI-прогона ремедиации не существовало НИ РАЗУ. Последний прогон `Mutation Testing`
(`gh run list`) — `29073395060`, 2026-07-10, ветка `main`, ДО начала ремедиации.
**Следствие:** без `git push` измерить MSI на коде ремедиации невозможно ни одним способом.

## 2. Push ветки `remediation/audit-vlt` НЕ триггерит ни одного лейна (repo-grounded)

Триггеры `push` всех workflow'ов ограничены ветками `main`, `feat/**`, `fix/**`, `hotfix/**`
(`tests.yml`, `static-analysis.yml`, `code-style.yml`, `drive.yml`, `documents.yml`, `frontend.yml`,
`media.yml`, `filament.yml`, `permissions-azgard.yml`), либо только `main` (`mutation.yml`,
`release-npm.yml`, `monorepo-split.yml`), либо только `pull_request` (`pr-check.yml`).
Имя `remediation/audit-vlt` не матчит ни один паттерн.

**Вердикт:** push ветки — **тихая операция**: ноль автоматических прогонов, ноль расхода CI-минут,
ноль публикаций в `main`. Единственные прогоны — те, что item явно диспатчит.
**Следствие для blast-radius:** решение владельца «push ветки + `workflow_dispatch`» (D31) не
затрагивает `main` и обратимо (`git push origin --delete remediation/audit-vlt`).

## 3. `workflow_dispatch` на ref ветки: что исполняется (RAG:✅ 2026-07-12)

Проверено: docs.github.com/actions/managing-workflow-runs/manually-running-a-workflow +
docs.github.com/actions/using-workflows/workflow-syntax-for-github-actions (запрос: «workflow_dispatch
--ref branch — какая версия YAML исполняется: с ветки или с default-ветки»).

Два условия, оба выполнены для `mutation.yml`:

1. **Диспатчабельность.** Workflow регистрируется как dispatch-able, только если файл с
   `on: workflow_dispatch` присутствует на **default-ветке**. Проверено repo-grounded:
   `git show origin/main:.github/workflows/mutation.yml` → секция `on:` несёт `workflow_dispatch:`
   (и `push: branches: [main]`). ✅
2. **Исполняемая версия YAML — с указанного ref, НЕ с default-ветки.** `gh workflow run mutation.yml
   --ref remediation/audit-vlt` исполняет job'ы по содержимому `.github/workflows/mutation.yml`
   **на ветке**; правки шагов, сделанные на ветке (снятие `|| true` по D32), вступают в силу
   немедленно, без мержа в `main`. ✅

**Следствие для D32:** контрольный (второй) диспатч ПОСЛЕ снятия `|| true` реально проверяет новый
гейт — job на ветке краснеет, если MSI ниже подставленных порогов. Без этого свойства D32 был бы
непроверяемым до мержа.

## 4. Формат вывода MSI (repo-grounded, `infection/infection` 0.33.3)

```
$ grep -rn "Mutation Score Indicator\|Covered Code MSI" vendor/infection/infection/src/
Reporter/ShowMetricsReporter.php:114:  "Mutation Score Indicator (MSI): <tag>{$mutationScoreIndicator}%</tag>"
Reporter/ShowMetricsReporter.php:123:  "Covered Code MSI: <tag>{$coveredMsi}%</tag>"
Metrics/MinMsiCheckFailed.php:59:     "The minimum required Covered Code MSI percentage should be %s%%, but actual is …"
```

**Вердикт:** обе метрики печатаются в stdout job'а построчно и извлекаются из лога прогона
(`gh run view <id> --log`) грепом по литералам `Mutation Score Indicator (MSI):` и `Covered Code MSI:`.
Артефакты/JSON-логгер настраивать не требуется (`infection.json5` секции `logs` не имеет).
`minMsi` сверяется с первой метрикой, `minCoveredMsi` — со второй.

## 5. Почему число нельзя получить в песочнице (repo-grounded)

```
$ php -m | grep -iE 'xdebug|pcov'      → пусто
$ php8.4 -m | grep -iE 'xdebug|pcov'   → пусто
```

Coverage-драйвера нет, установка (`sudo`/`pecl`) заблокирована харнессом — зафиксировано в
`phases/P4.md` P4.1 Known Deviations и `handoff.md` §Open risks за весь цикл плана. Infection без
coverage не считает MSI (`--skip-initial-tests --coverage=build/coverage` в `mutation.yml` предполагает
готовый `coverage-xml`, который производит шаг `pest --coverage-xml` под `XDEBUG_MODE=coverage`).
CI-лейн `mutation.yml` ставит `shivammathur/setup-php@v2` c `coverage: xdebug` — **это единственное
доступное окружение, где число измеримо.**

## 6. Предсказуемый режим отказа прогона (repo-grounded, не гипотеза)

Шаг `Generate coverage for Infection` в `mutation.yml` — `vendor/bin/pest --coverage-xml=… --min=0`
на **SQLite** (`DB_CONNECTION: sqlite`, `:memory:`). `--min=0` снимает порог покрытия, но НЕ игнорирует
падающие тесты: красный тест → ненулевой exit → шаг падает → job не доходит до Infection → **MSI не
измеряется**.

Известный долг, который может выстрелить ровно здесь: пред-существующий **SQLite-флейк
`StorageManagerTest`** (панель `team`) — `findings/P5.3-closure-matrix.md` §4 п.7. Диспозиция этого
случая — в Code Guidance P5.4 (if-then): флейк, физически блокирующий измерение, чинится минимальным
тестовым фиксом отдельным коммитом; ЛЮБОЙ другой провал шага — стоп и эскалация, а не «подгонка CI».
