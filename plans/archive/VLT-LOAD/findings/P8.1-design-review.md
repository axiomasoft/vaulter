# VLT-LOAD P8.1 — повторный независимый design audit

**РЕЖИМ:** независимый read-only design audit  
**ВХОД:** `task:plan-audit VLT-LOAD design`  
**СКОУП:** changed-risk delta после D37: `observability-spec.md`, P8.2–P8.7, §5 `slo-gates.md`, текущий `load/` SUT и объявленные package anchors  
**НЕ ТРОГАТЬ:** product code, реализацию P8.2+, соседние пакеты и несвязанные изменения

**Вердикт: RED**  
**Дата:** 2026-09-20  
**Аудитор:** `gpt-5.6-sol/frontier/xhigh`  
**Candidate fingerprint:** `592f131febd5e9eb231e08fb0abc11b261ddb6bc3944cbae43a12ba6bb886326`

D37 устранил существенную часть прошлого RED: выбран Redis-backed Prometheus pull, разведены package/
host/harness ownership, зафиксированы classic histogram templates, DI truth table и Redis worker для
readiness. Паритет реестра остаётся **50/50 = 12 + 10 + 28**. Однако repaired design всё ещё не может быть
исполнен в границах собственных items: reader не умеет выполнить нормативный PromQL, shared registry не
имеет атомарного и run-isolated контракта, а несколько обязательных producers отсутствуют в `Files` и в
самом load runtime. Поэтому P8.2 остаётся заблокирован.

## Метод и evidence

- Локальная трассировка design → item `Files`/rules → существующие `load/` reader/runtime → package anchors.
- Perplexity Deep Research по Redis aggregation, Prometheus text exposition, Laravel queue readiness и
  provider/route wiring; затем отдельная проверка по официальным первичным источникам.
- Позитивный контроль: registry parity остаётся 50/50; новый аудит рассматривает только changed-risk delta.

## Блокирующие находки

### F1 — P8.7 не может сделать 66 строк checkable существующим gate reader

**Severity:** BLOCKER  
**Evidence IDs:** `P8.7:GATE-READER-BARE-METRIC`, `P8.7:PERF-ASSERT-OUT-OF-SCOPE`

- `../../load/gates/perf-assert.py:145-171` извлекает имена из колонки `prom_metric`, выполняет запрос каждого
  **голого имени** и затем пытается применить простой scalar comparator. Он не читает и не исполняет
  нормативные шаблоны `observability-spec.md` §8.
- У classic histogram нет sample с base name: reader должен запрашивать `_bucket` и выполнять
  `histogram_quantile(... sum by (le) (...))`. Значит строки с histogram останутся `not-checkable` или
  `not-evaluated`, даже если P8.3–P8.5 корректно эмитят все families.
- P8.7 требует именно §8 PromQL и 66/66 checkable (`P8.7.md:23-38`), но его `Files` (`:19`) не включает
  `load/gates/perf-assert.py`, `_slo_table.py` или иной gate reader. В пределах item дефект исправить нельзя.
- `slo-gates.md:228-231` признаёт старые выражения неисполнимыми, но перенаправление на §8 само по себе не
  меняет исполняемый reader.

**Почему это блокирует:** главный acceptance P8.7 ложен при любом корректном metrics backend.

**Обязательная коррекция:** добавить gate reader и его fixtures в точные `Files` P8.7; определить machine-
readable mapping `SLO row → PromQL → threshold`; доказать на fixtures как минимум classic histogram,
counter, run-max gauge и compound expression, после чего требовать 66/66.

### F2 — Redis registry не имеет достаточного correctness/lifecycle контракта

**Severity:** BLOCKER  
**Evidence IDs:** `P8.7:HISTOGRAM-NONATOMIC`, `P8.7:RUN-ISOLATION-MISSING`, `P8.7:HOST-WIRING-OUT-OF-SCOPE`

- `observability-spec.md:251-262` задаёт только общий namespace `vaulter:metrics:*` и операции
  `INCRBYFLOAT`/`HINCRBY`/`MAX`/`SET`. Для одного histogram observation необходимо согласованно обновить
  все cumulative buckets, `_sum`, `_count` и `+Inf`; без Lua/Redis Function или другого atomic primitive
  scrape может увидеть разорванное состояние, где `+Inf != _count`.
- Не определены Redis key/label encoding, manifest зарегистрированных zero-series, порядок/escaping HELP,
  TYPE и samples, защита от duplicate labelsets и поведение при частичном backend failure. Фраза
  «`_created`/`_total 0` виден» (`:273-275`) не создаёт механизм регистрации family с нулём.
- Нет run-id namespace, reset/TTL/finalize policy. Повторные on/off прогоны используют те же ключи, а
  gauges с `MAX` сохраняют старый пик; P8.7 не сможет приписать scrape конкретному прогону или честно
  измерить overhead.
- §7 назначает route и compose P8.7 (`:257-264`), но `P8.7.md:19` не включает route, service-provider/
  bootstrap wiring и `load/docker-compose.load.yml`. Даже заявленный `/metrics` endpoint и Redis dependency
  нельзя полностью подключить в разрешённом write-boundary.

**Почему это блокирует:** получаемый scrape не доказан как консистентный, полный и относящийся к текущему
прогону; на нём нельзя строить blocking SLO verdict.

**Обязательная коррекция:** нормативно задать run-scoped key schema и lifecycle; одну atomic histogram
transaction; series manifest и exact exposition rules; backend-failure contract; затем расширить P8.7
`Files` всеми route/provider/bootstrap/compose/gate-reader точками и тестами инвариантов.

### F3 — item write-boundaries не покрывают объявленные producers и источники host signals

**Severity:** BLOCKER  
**Evidence IDs:** `P8.3:FILES-ANCHOR-GAPS`, `P8.4:FILES-ANCHOR-GAPS`, `P8.5:FILES-ANCHOR-GAPS`,
`P8.3:TIER-OPERATION-SOURCE-MISSING`, `P8.3:COLLAB-RUNTIME-ABSENT`,
`P8.4:FPM-STATUS-SOURCE-MISSING`

- Registry §3 назначает конкретные anchors, которых нет в соответствующих `Files`: P8.3 не перечисляет
  `ActivityController`, `NodeExportService` и `RecordBroadcastQueueWait`; P8.4 — `UploadFileAction` и
  `PublicShareController`; P8.5 — `OutboxRecorder`, `DeliverWebhook`, `RecordFailedJob` и точные purge/
  prune/reconcile paths. Обобщения вроде `Collaboration/*`, «HTTP-middleware» и «команды» не разрешают
  запись в другие конкретные файлы по протоколу плана.
- P8.3 определяет `operation` как имя route/OP (`P8.3.md:24-25`), но package routes не именованы, а k6
  OP tags не передаются server-side. Точный mapping/source и его wiring отсутствуют.
- `tier` объявлен host context, но `load/docker-compose.load.yml` не передаёт `TIER` в app; P8.3 `Files`
  compose не включает. Следовательно middleware не имеет определённого bounded source для S/S0/M/L.
- `collab_room_active` требует абсолютный count collaboration runtime, но текущий load stand не содержит
  Reverb/Hocuspocus service и k6-сценарий не открывает collaboration connection. Producer измерять нечего.
- `download_stream_active` требует php-fpm status или equivalent, но текущие `php-fpm.conf` и nginx не
  экспонируют status endpoint, а P8.4 не владеет этими конфигами.

**Почему это блокирует:** обещанные 50/50 emissions нельзя реализовать без выхода за `Files`; несколько
host gauges не имеют наблюдаемого источника даже концептуально в текущем SUT.

**Обязательная коррекция:** сделать `Files` точным superset всех 50 registry anchors и host wiring;
зафиксировать route→operation mapping, передачу tier в app, реальный collaboration runtime/collector и
FPM stream acquisition. Если signal нельзя получить в P8-minimum, изменить family/acceptance отдельным
решением, а не подменять нулём.

### F4 — readiness допускает stale ACK; buckets и часть label vocabulary не дают строгий verdict

**Severity:** BLOCKER  
**Evidence IDs:** `P8.6:STALE-HEARTBEAT-ACK`, `P8.1:BUCKETS-NOT-SLO-ALIGNED`,
`P8.1:LABEL-VOCABULARY-STILL-OPEN`

- Queue probe (`observability-spec.md:163-169`) использует один cache key `vaulter:queue-ready` с TTL.
  Остаточный ACK предыдущего запроса может сделать новый `/ready` зелёным до обработки его job. Не
  определены nonce/issued-at, удаление/одноразовое чтение, explicit connection+queue и deadline/polling.
- Общие bucket sets (`:301-308`) не ставят границы на нескольких blocking thresholds: например 0.008 и
  0.012 s попадают между 0.005/0.01/0.025, а 1.5/2 s — между 1/2.5. Для classic histogram ошибка
  квантиля определяется bucket boundaries; hard pass/fail около этих порогов неоднозначен.
- `format` остаётся «at minimum current formats» (`:324`), а `route` — «named route names» (`:333`) при
  отсутствии этих names. Это открытые, не перечисленные vocabulary вопреки заявленному closed contract.
- P8.6 имеет широкий `load/` scope, но не называет heartbeat job/controller/service/config/Dockerfile.
  Текущий `../../load/docker/Dockerfile.app:10-11` не устанавливает Redis PHP extension, поэтому заявленный
  Redis driver также требует неявной правки runtime image.

**Почему это блокирует:** readiness способен дать false-positive, а histogram/label contract не позволяет
повторяемый машинный verdict на границе SLO.

**Обязательная коррекция:** nonce-scoped heartbeat с явными connection/queue, bounded connect/read/poll
timeouts и stale-ACK negative test; family-specific buckets с границами blocking thresholds либо
документированная conservative decision rule; исчерпывающие `format`/`route` enums; точные P8.6 `Files`.

## Первичные источники

| Тема | Источник | Подтверждает |
|:--|:--|:--|
| Prometheus exposition | https://prometheus.io/docs/instrumenting/exposition_formats/ | grouping, unique series, histogram `_bucket`/`_sum`/`_count`, обязательный `+Inf == _count` |
| Prometheus histograms | https://prometheus.io/docs/practices/histograms/ | classic `sum by (le)` query и зависимость ошибки от bucket boundaries |
| Redis programmability | https://redis.io/docs/latest/develop/programmability/eval-intro/ | Lua script выполняет multi-key update атомарно |
| Laravel providers | https://laravel.com/docs/12.x/providers | `register` только для container bindings; routes/wiring принадлежат boot/bootstrap |
| Laravel queues | https://laravel.com/docs/12.x/queues | connection и queue различны; worker должен слушать выбранные connection/queue |

## Условия повторного аудита

1. Gate reader реально исполняет §8 PromQL и имеет fixtures для всех expression classes.
2. Redis registry определяет atomic observation, run isolation/lifecycle, series manifest и exact 0.0.4 output.
3. P8.3–P8.7 `Files` покрывают каждый producer и всё host/runtime wiring без неявных записей.
4. Tier/operation/collaboration/FPM signals имеют работающие источники в load stand.
5. Readiness доказывает обработку именно текущего nonce, buckets согласованы с blocking thresholds, все
   label vocabularies перечислены.
