## 1. Инструмент

**Стоковый `grafana/k6`**, официальный образ, пин минорной версии (D22, supersedes D3). Вывод метрик —
встроенный `--out experimental-prometheus-rw` (D24, supersedes D4), env `K6_PROMETHEUS_RW_SERVER_URL`.
Кастомный бинарник (`xk6-fasthttp` + `xk6-output-prometheus-remote`) **не собирается**.

### 1.1 Почему НЕ xk6-fasthttp (отменённое решение D3)

RAG-11 (`findings/P2-rag-k6-harness.md`): `xk6-fasthttp` **не эмитит** стандартные HTTP-метрики —
README расширения прямо перечисляет потерянные: `http_req_duration`, `http_req_failed`,
`http_req_blocked`, `http_req_connecting`, `http_req_receiving`, `http_req_sending`,
`http_req_tls_handshaking`, `data_received`, `data_sent`. На них стоит **весь** гейт `slo-gates.md` §1:
сквозные G-1/G-2 (§2 этого документа) и все строки класса B §3.1–§3.2. Перевод стриминговых сценариев
на fasthttp обнулил бы половину гейта. Дополнительно: `PATCH` — не документирован в README расширения,
а tus (OP-02, `PATCH resumable-uploads/{upload_id}`) целиком стоит на `PATCH`. Последний релиз
расширения — 2024-09-15 (RAG-11).

### 1.2 Почему НЕ Locust (отменённый резерв блупринта P0)

RAG-14: S3-multipart у vaulter — это **собственные** HTTP-роуты пакета
(`POST resumable-uploads/{upload_id}/parts` → `S3MultipartController.php:56`,
`.../complete` → `S3MultipartController.php:85`), а не прямые вызовы к S3. SigV4 подписывает
**сервер**, не клиент. Аргумент «Locust дешевле для boto3/SigV4-гимнастики» (`plan.md` §8.1) к пакету
неприменим — подписывать клиенту нечего.

### 1.3 Почему истинный стриминг тела не нужен вовсе

RAG-14 (`operations-catalog.md`, `slo.md` §0.2): ни один эндпоинт vaulter не принимает multi-GB тело
одним запросом.

| Путь | Максимальное тело ОДНОГО запроса | Источник |
|:--|:--|:--|
| tus PATCH (OP-02) | чанк, референс **8 MiB** | `slo.md` §0.2 |
| S3-multipart putPart (OP-06) | часть **≤ 64 MiB** (`uploads.max_chunk_bytes`) | `slo.md` §0.2 |
| single-shot (OP-17) | **≤ 32 MiB** (контрактная граница, sign-off владельца) | `slo.md` §0.2 |
| download (OP-08…10) | тело **ответа**, не запроса — снимается `discardResponseBodies` | RAG-10 |

5-ГиБ файл всегда приезжает чанками — «честный 5-ГиБ single-stream», ради которого блупринт вводил
кастомный бинарник, не является операцией этого пакета (D22).

## 2. Стенд

Docker-стенд в `load/` (D26, в этом же репозитории — не отдельный репо). Сервисы и роль:

| Сервис | Роль |
|:--|:--|
| `postgres` (16) | БД под конвертом `reference-env.md` §1.2 |
| `pgbouncer` | transaction-mode пул, `reference-env.md` §1.3 |
| `minio` | S3-совместимое хранилище, `reference-env.md` §1.4 |
| `app` (**nginx + php-fpm**) | SUT — не `testbench serve` (см. §2.2) |
| `prometheus` | приёмник `--out experimental-prometheus-rw` |
| `k6` | генератор, образ `grafana/k6` |

Полный железный конверт (cpuset-раскладка, `mem_limit`/`memswap_limit`, параметры PG/PgBouncer/MinIO
по тирам S/S0/M/L) — SSOT **`reference-env.md` §1**, этот документ его не дублирует построчно, только
ссылается.

### 2.1 Раскладка cpuset на lab-box'е

Только **физические** P-ядра, по одному потоку с ядра (L-2, `reference-env.md` §5). Команда проверки
раскладки на конкретном боксе:

```
lscpu -e=CPU,CORE,MAXMHZ
```

На lab-box'е этого плана (i7-14700K, 8 P-ядер + 12 E-ядер) тир **S** берёт 7 чётных CPU из диапазона
0–13 (по одному потоку с семи разных физических P-ядер), CPU 14/15 — резерв хоста
(`reference-env.md` §1.1). Тир **M** однородного cpuset'а на этом железе не получает (12 однородных
ядер нет — 8 P-ядер исчерпываются раньше) — фиксировано отдельно в §6 ниже (D25).

### 2.2 Почему SUT — nginx + php-fpm, а не `testbench serve` (D28)

`vendor/bin/testbench serve` — это `php artisan serve`, однопоточный dev-сервер: на нём
`pm.max_children` (8/32/96 по тиру, `reference-env.md` §1.6) и вся раскладка FPM-пула `slo.md` §0.1
физически не воспроизводятся — сервер обслуживает запросы последовательно, а именно раскладка пула
задаёт конкуренцию, на которой стоят все SLO. Существующий `e2e/docker-compose.yml`
(`testbench serve` + hub + Vite) — стенд коллаборации, переиспользуется P2.2 как **образец провайдера
хоста** (`packages/core/tests/E2E/E2eServiceProvider.php`), а не как SUT.

## 3. Фикстуры (D23)

**Файла на диске не существует.** `k6/experimental/fs` держит **одну полную копию файла в памяти**,
общую для VU (RAG-10) — «одна копия вместо N» всё равно означает, что 5-ГиБ фикстура на диске = 5 ГиБ
RSS генератора, что не помещается в лимит генератора ни на одном тире (2/4/8 ГиБ, `reference-env.md`
§1.5). Требование `reference-env.md` §1.5 «фикстуры на диске, не через `open()`» ловушку RAM **не
снимает** — она переезжает с `open()` на `fs`.

Вместо файла:

- общий `ArrayBuffer` **8 MiB** (tus-чанк) и **64 MiB** (S3-часть) генерируется **один раз** в
  init-контексте k6-скрипта, переиспользуется всеми VU и всеми итерациями;
- уникальность содержимого файла (нужна CAS-дедупу — иначе `BlobStore::commit()` находит существующий
  блоб по dedup-ключу `(sha256)`, и сценарий будет мерить дедуп вместо записи) — **16-байтовый salt** в
  первом чанке сессии, делающий sha256 каждой сессии уникальным;
- скачивание (download) не держит тело ответа в RAM: `discardResponseBodies: true` (RAG-10) —
  `res.body === null`, throughput считается из известного размера файла и `res.timings`, а не из
  накопленного тела.

Следствие: строка `reference-env.md` §1.5 «диск ≥ 20 ГиБ под фикстуры генератора» **снимается** —
5-ГиБ файла на диске стенда не существует ни для одного тира.

## 4. Раскладка executor'ов

Прямая трансляция `slo.md` §0.1 — FPM-пул **делится, а не суммируется** между тремя группами
сценариев:

| Группа сценариев | S | M | L | Источник |
|:--|--:|--:|--:|:--|
| interactive (`tree.js`, `docs-collab.js` — HTTP-часть, точечные чтения/мутации) | 4 | 16 | 48 | `slo.md` §0.1 |
| upload (`tus-upload.js`, `s3-multipart.js`, `single-shot.js`) | 2 | 8 | 24 | `slo.md` §0.1 |
| download (`download.js`) | 2 | 8 | 24 | `slo.md` §0.1 |
| **Итого = `pm.max_children`** | **8** | **32** | **96** | `slo.md` §0.1 / `reference-env.md` §1.6 |

Числа выше — **буквальная** копия таблицы `slo.md` §0.1; сумма по каждому тиру сходится с
`pm.max_children` того же тира (`reference-env.md` §1.1: `pm.max_children=8/32/96`). Расхождение здесь
было бы находкой (эскалация), а не поводом «подправить» одно из чисел — расхождения нет.

**Каждая группа — свой k6-executor `constant-vus`** с числом VU из таблицы выше (по тиру), не
`constant-arrival-rate`. Причина: RPS = конкуренция / p95 (`slo.md` §1.1 и далее — RPS в SLO-таблице
выведен именно так, не задан независимо). Гейтить целевой RPS напрямую значило бы протаскивать
латентный шум shared-раннера в класс A (`slo-gates.md` §6.3) — фиксируется конкуренция (детерминированный
вход), а латентность/throughput остаются тем, что измеряется, а не подгоняется под достижение RPS.

`mixed.js` (P2.4) запускает все три группы **одновременно**, каждую своим `constant-vus`-executor'ом с
долями операций внутри группы из `operations-catalog.md` (колонка «Доля в миксе»).

## 5. Контракт метрик и тегов

Копия `slo-gates.md` §1 — имена **байт-в-байт**, по ним строятся пороги P2.5; опечатка = молча
непроверяемый SLO.

### 5.1 Кастомные метрики

| Метрика k6 | Тип | Смысл | Теги |
|:--|:--|:--|:--|
| `stream_throughput_mibs` | `Trend` | MiB/s **на один стрим**, считается в скрипте (байты / длительность запроса) — не из агрегатного `data_sent` | `scenario`, `tier` |
| `upload_conflict_total` | `Counter` | HTTP 409 на NOWAIT advisory-lock — **не ошибка** (`slo.md` §0.4) | `scenario`, `tier` |
| `throttled_total` | `Counter` | HTTP 429 (`throttle:vaulter-public`) — **не ошибка** | `scenario`, `tier` |
| `ttfb_ms` | `Trend` | время до первого байта стрима/экспорта | `scenario`, `tier` |
| `broadcast_lag_ms` | `Trend` | коммент → приход по WS соседу (queue-time fan-out) | `tier` |

Агрегатный throughput — из встроенных `data_sent`/`data_received` (`Counter` → `rate`, байт/с);
отдельной кастомной метрики для него нет (`slo-gates.md` §1).

### 5.2 Теги на каждом запросе

`scenario` (имя сценария), `tier` (`S0`/`S`/`M`/`L`), `class` (`interactive`|`streaming` — на нём
матчатся сквозные G-1/G-2, `slo-gates.md` §2).

### 5.3 409/429 — протокол, не ошибка

`slo.md` §0.4: HTTP 409 на PATCH/putPart/complete (NOWAIT advisory-lock занят другим запросом той же
сессии) и HTTP 429 (`throttle:vaulter-public` на share-download) — **не входят** в `http_req_failed`.
Сценарии объявляют их ожидаемыми через `http.setResponseCallback(http.expectedStatuses({min:200,
max:399}, 409, 429))` (`expected.js`, P2.4) — без этого штатный протокол параллельного клиента валил бы
G-1/G-2. Они дополнительно инкрементят `upload_conflict_total`/`throttled_total`, бюджетируемые
сквозными порогами G-4/G-5 (`slo-gates.md` §2): 409 ≤ 5 % от PATCH-запросов, 429 ≤ 1 % от запросов
share-download.

## 6. Профили прогона

Копия `slo-gates.md` §7 — три профиля, каждый валит своё:

| Профиль | Где | Когда | Тир/объёмы | Классы | Длительность | Что валит |
|:--|:--|:--|:--|:--|:--|:--|
| **`smoke-perf`** | `ubuntu-latest` | на PR | **S0** (объёмы ≈ 1/50 S, файл ≤ 256 MiB) | A — блокирующий; B — пишет baseline, advisory | ≤ 6 мин (1 прогон, без медианы-3) | error-rate, checks, throughput стримов, RSS-потолки, счётчики батча/lock-set |
| **`regression`** | `ubuntu-latest` (nightly) | nightly на `main` + метка `perf` | S0 + «грязные» датасеты фоновых (усечённые) | A — блокирующий; B — медиана-3, относительное сравнение | 30–60 мин | всё из `smoke-perf` + фоновые SLO-58…78; обновляет baseline |
| **`lab`** | контролируемый lab-box (cpuset-конверт) | вручную / перед релизом | **S / M** (L — экстраполяция) | A и **B — блокирующие** | часы | авторитетные латентные числа; здесь и только здесь класс B имеет право валить |

Авторитетный тир прогонов P2 — **S** (D25): lab-box (i7-14700K, 8 P-ядер + 12 E-ядер) даёт честный
cpuset только для 7 физических P-ядер тира S; тир M требует 12 **однородных** ядер, которых на этом
боксе нет — M гоняется только как класс A с пометкой «латентность недостоверна» (как S0), L —
экстраполяция без прогона. Публично обещанный README-тир M остаётся **не подтверждённым прогоном**
(`open-questions.md` Q4, `plan.md` §8.5).

Медиана-из-3 в PR-лейн не помещается (лейн ≤ 6 мин) — она живёт в `regression`; PR получает один
короткий прогон с широкими guardrail-порогами (`slo-gates.md` §7).

## 7. Порядок прогона (лабораторные условия)

Что делается ДО замера, на каждом прогоне (`reference-env.md` §5, L-1…L-7):

1. `pg_stat_statements_reset()` — иначе профиль P3 смешивает seed и нагрузку (L-7).
2. Сброс счётчиков MinIO.
3. Явное объявление состояния кэша прогона — «холодный» или «прогретый» (L-6): смешивать в одном
   отчёте нельзя, «первый прогон медленнее» — не находка, а неуказанное условие.
4. На lab-box'е (тиры S/M/L, не S0): CPU governor = `performance`, turbo/boost выключен (L-1); тихий
   хост, ни одного стороннего процесса (L-3); отдельный диск под PG-данные, фикстуры и объекты MinIO
   на разных томах (L-4); swap выключен (L-5, = E-2).
5. На профиле **S0** ни одно из условий L-1…L-4 недостижимо (общий GitHub-hosted раннер) — латентные
   числа с S0 в отчётах помечаются **недостоверными**, не «пессимистичными» (`reference-env.md` §5,
   D15).

## 8. Что харнесс НЕ делает

- Не чинит находки L-01…L-08 (`plan.md` §7) — фаза нагрузки доказывает, dev-срез чинит (D-LOAD-5,

- Не выбирает инструмент заново — D22/D24 приняты в дизайне фазы, этот документ их транскрибирует.
