### P4.2 — Реальные path fixtures и матрица 5 MiB → 5 GiB

**Intent:** Добавить bounded генерацию fixtures и точные cases для tus final PATCH, S3 putPart,
post-fix complete, CAS stage и download, не буферизуя multi-GiB payload в k6 или load-host helper.
**Why:** Универсальный HTTP request не доказывает конкретный seam: complete должен стартовать после
готовых parts на свежем worker, CAS stage нужно отделить от FPM composite path, а download client не
должен сам удерживать response body.
**Scope Included:** streaming fixture preparation/cleanup на disposable tier-S dataset; exact
5 MiB/500 MiB/5 GiB case manifest; подготовка S3 parts отдельно от measured complete; final tus
PATCH; per-part S3 request; load-only CLI CAS-stage probe; current-version download; upload checksum,
download HTTP/client byte accounting и отдельный bounded streaming server/object checksum probe; k6
`responseType:none`; case-level fixed ceilings; unit/contract fixtures.
**Scope Excluded:** mixed/concurrent load; real AWS-native multipart benchmark; public load-probe
route; tmpfs fixture; production/shared dataset; изменение `packages/*/src`; сам live matrix run.

**Implementation Rules:** Fixture generator пишет/хеширует фиксированными chunks и сохраняет
`fixture_id`, exact bytes, sha256, storage key/session ids; PHP/k6 никогда не создают один 5 GiB
string/ArrayBuffer. S3 complete case готовит parts до свежего measured container. putPart verdict —
максимум одного request при bounded 64 MiB part, а не сумма клиентских buffers. CAS CLI вызывает
реальный `Sha256ContentStore::stage()` с file resource, измеряет свой PID и удаляет staged temp в
`finally`; его ceiling фиксируется как 64 MiB (существенно выше 1 MiB internal chunk, но ниже
size-dependent payload). Download при `responseType:none` сверяет HTTP status, `Content-Length` и
изолированную дельту k6 `data_received`, но не объявляет client payload checksum. SHA-256 объекта
сверяет отдельный server/object probe, читающий bounded chunks; его peak тоже входит в evidence и он
не materializes 5 GiB. Каждый case идемпотентен по `fixture_id`; cleanup ограничен exact run prefix.
**Code Guidance:** Текущий Vaulter handler — proxied multipart, не AWS-native
`CompleteMultipartUpload`; отчёт и case ids не смешивают эти механизмы. Не использовать
`file_get_contents`, `Storage::get`, `stream_get_contents` без bound, `ArrayBuffer(file_size)` или
shell command substitution для payload. Negative max-chunk cases проверяют part ceiling и сумму
многих разрешённых parts независимо.
**Validation:** load Pest test доказывает streaming fixture generation, exact sizes/checksums,
bounded reads, bounded server/object hashing и prefix-scoped cleanup; `k6 inspect
load/k6/scenarios/memory-paths.js`; S0 contract run 5 MiB проходит все пять cases и validator;
download verdict содержит HTTP status + `Content-Length` + isolated `data_received`, а checksum
имеет отдельный server/object carrier; 500 MiB/5 GiB остаются dry-run manifests; static scan
по новым Files не находит whole-file read helpers; `p4-memory-cases.sh list` выдаёт ровно 15 cells и
fixed ceilings 64/160/160/64/16 MiB.
**Deliverables:** reproducible path fixture commands, 15-cell matrix manifest, exact public-path k6
cases, isolated CAS probe, доказуемый download byte/checksum contract и cleanup/contract tests.
