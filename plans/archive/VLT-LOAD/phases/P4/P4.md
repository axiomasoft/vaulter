# P4 — Память и стриминг: бенчмарки ≤5 ГиБ

## Phase Context

**Цель.** Доказать на реальных путях Vaulter, что рост payload от 5 MiB через 500 MiB до 5 GiB
не превращается в рост памяти PHP-FPM/процесса пропорционально размеру файла. P4 не исправляет
горячие пути: L-01 уже доказан D7/D29 и должен быть закрыт отдельным dev-срезом по D11 до запуска
этой фазы. Здесь измеряется только post-fix `S3MultipartHandler::complete()` и ищутся новые
size-correlated пути в tus final PATCH, S3 putPart, CAS stage и download.

**Входной контракт.** D41 запрещает исполнение P4 до GREEN/accepted результата единственного
полного `task:plan-audit VLT-LOAD design`. Дополнительно нужен
`findings/L-01-streaming-fix-closure.md`: commit/дифф отдельного dev-среза, GREEN mutation evidence
`vaulter-drive ≥95`, регрессии multipart integrity и доказательство, что `complete()` больше не
конкатенирует сумму частей в PHP-строку. Отсутствующий carrier означает `dependency-not-ready`, а не
право выполнить известный O(file-size) код ещё раз.

**Плоскости memory evidence.** `vaulter_request_peak_memory_bytes` остаётся авторитетным пиком PHP
allocator (`memory_get_peak_usage(true)`), но не называется RSS. Внешний sampler отдельно снимает
worker `VmHWM` и `/proc/<pid>/smaps_rollup` (`Pss`, `Pss_Anon`, `Pss_File`), а cgroup v2 —
`memory.current`, `memory.peak`, `memory.stat` (`anon`, `file`, `sock`) и `memory.events`. Cgroup total
не приписывается PHP heap: page cache, nginx/socket buffers и другие процессы показываются отдельно.
Методика и verified sources зафиксированы в `findings/P4-rag-memory-streaming.md`.

**Изоляция.** Каждый case запускается в свежем benchmark app-container тира S с отдельным FPM pool:
`pm=static`, `pm.max_children=1`, health/status обслуживаются независимо от измеряемого worker.
Sampler разделяет PID namespace с app и читает cgroup filesystem read-only. До payload фиксируется
baseline, после ответа — lifetime high-water marks; container уничтожается до следующего case.
Исходные/временные файлы живут на дисковом volume, не в tmpfs. Swap, cpuset, image digests, kernel,
cgroup mode, FPM/PHP config, run/dataset/fixture ids и cache declaration входят в manifest.

**Матрица.** Пять путей: `tus_final_patch`, `s3_putpart`, `s3_complete_postfix`, `cas_stage_probe`,
`download`; размеры 5 MiB, 500 MiB, 5 GiB; три успешных повтора на cell. `s3_complete_postfix`
получает уже подготовленные parts и свежий worker, поэтому putPart peak не загрязняет complete peak.
CAS probe использует реальный `Sha256ContentStore::stage()` в отдельном PHP CLI process и явно
маркируется как process, не FPM. Download-клиент использует k6 `responseType: none` и доказывает
только HTTP status, `Content-Length` и изолированную дельту k6 `data_received`; payload checksum на
клиенте не заявляется. Отдельный bounded streaming fixture/server-object probe доказывает checksum
объекта без materialization тела. Upload-клиент переиспользует bounded chunk buffers.

**Гейт.** Для каждого размера применяются уже принятые SLO-40…54: tus PHP peak `<64 MiB`, S3
putPart/complete `<160 MiB`, download `<16 MiB`; CAS stage получает fixed ceiling из P4.2 до live
run на основании chunk contract. `bounded-at-envelope` означает: нет OOM/restart/partial transfer,
HTTP/client byte accounting и отдельный server/object checksum сходятся, и фиксированный ceiling
выполнен во всех трёх размерах. Три точки не
выдаются за математическое доказательство Big-O: profile также публикует raw curve и delta
`Pss_Anon`/`Pss_File`/cgroup anon/file. L-01 считается закрытым только если 5 GiB post-fix complete
проходит `<160 MiB`; иначе phase остаётся открытой и возвращает owning dev-slice без новой L-01.

**Выходы.** Raw evidence находится в `artifacts/P4/`; итоговый `memory-profile.md` связывает каждую
ячейку с PHP/process/cgroup evidence и SLO verdict; новые долги — в `findings/P4-memory-profile.md`.
Ни один `packages/*/src` файл и ни один production pool/config P4 не изменяет.

**Порядок.** P4.1 строит изолированный sampler/validator → P4.2 добавляет реальные path fixtures и
cases → P4.3 выполняет одну авторитетную tier-S matrix → P4.4 синтезирует profile/debt. P4.1–P4.2 —
recommended implementation batch; P4.3–P4.4 — recommended manual batch с одним immutable run family.
