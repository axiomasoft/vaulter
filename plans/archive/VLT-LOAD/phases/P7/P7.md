# P7 — Деградация инфраструктуры (chaos)

## Phase Context

**Цель.** Доказать на disposable tier-S стенде, что сбои object storage, PostgreSQL/PgBouncer и
локального temp не создают тихо повреждённых или фантомно committed данных, а после снятия сбоя
операции сходятся в объяснимое terminal/resumable состояние. P7 измеряет recovery и выпускает debt,
но не исправляет product hot paths по D-LOAD-5.

**Входной контракт.** P2 владеет стендом/seed, P5 — lock/pool baselines, P6 — queue/retry baselines,
P8.6/P8.7 — readiness и run-scoped observability. D41 запрещает исполнение до GREEN/accepted
результата единственного полного `task:plan-audit VLT-LOAD design`; P5.4 и P6.4 — обязательные
predecessors, а не optional context. Live run использует только отдельные DB/Redis/MinIO namespace,
prefix и volumes; production/shared endpoints запрещены.

**Четыре плоскости fault evidence.** (1) `product-realistic` — реальные HTTP/Artisan операции через
MinIO, PgBouncer и Redis; (2) `transport-control` — Toxiproxy latency/timeout/reset/down, доказывающий
поведение при TCP-сбое, но не AWS/PG failover; (3) `protocol-control` — load-only S3 reverse proxy,
детерминированно возвращающий 503 до upstream и не называемый реальным S3 outage; (4)
`storage-control` — выделенный tmpfs с принудительным ENOSPC для `php://temp`/`sys_get_temp_dir()`.
Отдельный `primary-transition` сценарий использует физический PostgreSQL 16 standby, явное promotion,
fencing старого primary и переподключение PgBouncer; kill/reset одной сессии failover не называется.

**Реальный S3-контракт Vaulter.** Текущий `S3MultipartHandler` проксирует части через Flysystem под
`tmp/uploads/<upload_id>.parts/*`; он не создаёт AWS `UploadId`. Поэтому P7 проверяет реальные
package invariants: part row/object, staged object, CAS row/object, file-version edge и session state.
AWS `AbortMultipartUpload`/embedded Complete error остаются RAG-границей для будущего host-swapped
handler и не служат ожидаемым поведением текущего пути.

**Матрица.** Object storage: tus PATCH, proxied S3 putPart/complete, CAS promote, abort и sweeper при
503/latency/timeout/reset/down, включая fault до upstream, после приёма request и на recovery. DB:
connection loss в upload PATCH/commit и outbox mutation, разрыв lock-holder, PgBouncer reconnect и
controlled primary promotion. Temp: ENOSPC при spill/stage/write, последующее освобождение и повтор.
Каждая ячейка имеет baseline → armed barrier → fault window → rollback → reconcile; arbitrary sleep
не является barrier.

**Инварианты и evidence.** Один `run_id` связывает injector events, monotonic/wall timestamps,
HTTP attempts, DB transaction/backend/lock snapshots, upload/part/blob/version/outbox states,
MinIO keys/checksums, queue lifecycle, temp capacity/write lengths, readiness и Prometheus. Жёсткие
вердикты: ни одного visible corrupt object, DB row без соответствующих durable bytes, duplicate
logical commit или ресурса вне run scope; все ambiguous outcomes reconciled по durable identity.
`T_detect`, `T_restore`, `T_converge` публикуются как измерения: утверждённого recovery SLO в P1 нет,
поэтому P7 не изобретает RTO/RPO и не смешивает injected-window 5xx с обычным steady-state budget.

**Выходы.** Raw evidence — `artifacts/P7/`; итог — `chaos-report.md`; bounded debt —
`findings/P7-degradation.md`. P7 не меняет `packages/*/src`.

**Порядок.** P7.1 строит lane/validator → P7.2 injectors, isolated topology и matrix → P7.3 выполняет
immutable tier-S run family → P7.4 выпускает report/debt. P7.1–P7.2 — recommended implementation
batch; P7.3–P7.4 — recommended manual batch.
