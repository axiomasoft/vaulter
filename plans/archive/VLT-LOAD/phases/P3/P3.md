# P3 — Профилирование запросов: PostgreSQL plans, индексы и N+1 под объёмом

## Phase Context

**Цель.** Получить воспроизводимый профиль DB-нагрузки Vaulter на объёмном датасете тира S и
отделить три разных класса проблем: дорогой query fingerprint в `pg_stat_statements`, неудачный
planner shape в `EXPLAIN`, и application-level multiplicity (N+1/повторный recursive CTE). Фаза не
оптимизирует код и не создаёт реальные индексы: она производит доказательства и bounded debt для
отдельных dev-срезов по D-LOAD-5/D11.

**Входной контракт.** P1 владеет SLO и каталогом 47 `OP-nn`; P2 владеет стендом, seed и k6 workload;
P8-минимум владеет server-side метриками. D41 запрещает исполнение P3 до GREEN/accepted результата
единственного полного `task:plan-audit VLT-LOAD design`, digest-bound reconciliation P8.4–P8.6 и
GREEN live gate P8.7. Аудит материализует `findings/D41-full-plan-audit.md`; до этого P3.1 —
`dependency-not-ready`, bundle не создаётся.

**Плоскости evidence.** k6 остаётся владельцем p95/p99 и SLO; `pg_stat_statements` ранжирует query
impact, `EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS, WAL, FORMAT JSON)` объясняет actual plan,
`pg_stat_io` даёт только cluster context, load-host `DB::listen` связывает normalized SQL с OP-id.
HypoPG подтверждает только planner choice обычным `EXPLAIN` без `ANALYZE`; runtime-ускорение и цена
реального индекса в P3 не заявляются (`findings/P3-rag-postgres-profiling.md`).

**Покрытие.** Каждая строка `operations-catalog.md` получает ровно один verdict:
`db-explain-covered`, `trace-only`, `no-db` или `excluded-with-reason`. Для каждого DB-bearing
fingerprint сохраняются representative parameter class, actual plan и code anchor. Обязательные
hotspots: `v_nodes`, `v_blobs`, `v_upload_sessions`, `v_upload_parts`, `v_file_versions`,
`v_activity`, `v_outbox`, `v_webhook_deliveries`; many-grant `candidateNodeIds()`, activity feed и
`subscribedEndpoints()` разбираются независимо от попадания в top-20.

**Измерительный протокол.** Авторитетен тир S на lab-box. Один run фиксирует `run_id`, `dataset_id`,
git SHA, image digests, PostgreSQL/version/settings/extensions, table/index sizes, row/dead-row counts,
statistics timestamps, cache declaration и P8.7 live-preflight. Перед workload выполняются
`ANALYZE` и изолированный reset; ненулевой рост `pg_stat_statements_info.dealloc` обесценивает
top-20 и требует повтора. «Cold» означает только явно доказанное состояние shared buffers; host page
cache не называется холодным без отдельного host-level evidence.

**Выходы.** Raw machine-readable evidence находится в `artifacts/P3/`; итоговая интерпретация — в
`db-profile.md`; новые L-долги — в `findings/P3-db-profile.md`. Ни один файл `packages/*/src`,
миграция или реальный индекс в фазу не входят.

**Порядок.** P3.1 строит профилирующий lane и валидатор → P3.2 выполняет controlled workload и
связывает OP→fingerprint → P3.3 снимает actual/hypothetical планы и ревизию индексов → P3.4
синтезирует verdict/debt. P3.2–P3.4 — один recommended manual batch: один dataset/run context
дешевле и надёжнее повторного прогрева/пересида, но каждый item сохраняет отдельный terminal result.
