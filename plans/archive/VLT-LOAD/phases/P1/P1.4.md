### P1.4 — Гейт-политика: SLO → k6-пороги + Prometheus-метрики + P8-минимум

**Intent:** Сделать каждый SLO **машинно-проверяемым**: для каждой строки `SLO-nn` — класс гейта
(A/B по D14), имя k6-метрики с тегом, выражение порога, политика baseline (для класса B) и имя
Prometheus-метрики, которую обязана поставить фаза P8. Побочный, но критичный выход — **явный
список P8-минимума**, выведенный из SLO, а не изобретённый в P8.
**Why:** Владелец выбрал SLO-как-CI-гейт (2026-07-14). Гейт, который флапает, отключают — поэтому
дизайн обязан считаться с тем, что в репо только GitHub-hosted `ubuntu-latest` (26×), где абсолютные
латентные пороги недостоверны. RAG:✅ 2026-07-14 (`findings/P1-rag-slo-ci-gate.md` RAG-6: «do not
gate on absolute latencies from noisy shared runners» → relative-to-baseline + median-of-N + широкий
абсолютный guardrail; `checks` сами не валят CI — нужен порог `checks: ['rate>0.99']`; ранний обрыв —
`abortOnFail` + `delayAbortEval`, иначе ramp-up-всплеск убивает прогон до steady state).
Второй выход — то, что закрывает противоречие D9: P8 — гейт для P3–P7, но «минимум» P8 до сих пор
описан прозой. Здесь он становится списком.
**Scope Included:** - `plans/VLT-LOAD/slo-gates.md`:
  - Таблица: `SLO-nn | Класс гейта (A/B) | k6-метрика + тег | Выражение порога | abortOnFail /
    delayAbortEval | Baseline-политика (только B) | Prometheus-метрика (вход в P8-минимум) |
    Блокирующий / advisory`.
  - **Класс A** (шумоустойчивый, блокирующий на `ubuntu-latest`): error-rate, checks-rate,
    throughput при фиксированной конкуренции, **потолок пиковой памяти** (RSS/`memory_get_peak_usage`),
    счётчики unbounded-scan (сколько строк тронул sweeper/GC/relay за тик). Абсолютные пороги.
  - **Класс B** (латентность p95/p99): абсолютный порог — только **широкий guardrail** (≈150 % цели
    тира, ловит катастрофу); острый гейт — **относительная регрессия к baseline** (`p95 ≤ baseline ×
    (1 + δ)`), медиана из N=3 прогонов, CV-guard (при CV выше порога — вердикт «недостоверно», не
    «провал»).
  - Раздел **«Baseline как версионированный артефакт»**: чем помечается (commit SHA, имя профиля,
    fingerprint окружения = тир + датасет + версии), где хранится, как выбирается (последний релиз /
    main), кто обновляет.
  - Раздел **«P8-минимум»**: итоговый список метрик-seam'ов, выведенный из колонки
    «Prometheus-метрика» — ровно то, без чего P3–P7 не могут вынести вердикт (D9). Плюс `/up`
    liveness/readiness (иначе харнесс P2 не отличает «упало» от «недоступно»).
  - Раздел **«Что НЕ гейтим и почему»**: явный список SLO, чья проверка в CI на `ubuntu-latest`
    недостоверна (D15) — они остаются advisory до появления dedicated perf-раннера.
- Профили прогона: `smoke-perf` (PR, 1–3 мин, широкие пороги) vs `regression` (nightly/по метке,
  длинный, относительное сравнение с baseline) — какие SLO в каком профиле.
**Scope Excluded:** - Сами k6-скрипты и workflow-файл CI — **фаза P2** (здесь — спецификация порогов, не их реализация).
- Реализация метрик-seam'ов в `packages/*/src` — **фаза P8** (здесь — список требований к ней).
- Решение «заводить ли self-hosted perf-раннер» — вопрос владельца (`open-questions.md` Q1);
  дизайн обязан работать **и без него** (класс B → advisory).

**Implementation Rules:** - **Синтаксис порогов k6 — только верифицированный** (RAG-6): тегированные пороги вида
  `'http_req_duration{scenario:tus_patch}': ['p(95)<300']`; `checks: ['rate>0.99']` обязателен, иначе
  провалившиеся проверки не валят CI; `abortOnFail` всегда с `delayAbortEval` (иначе ramp-up убивает
  прогон). Если понадобится синтаксис, которого нет в RAG-6, — **сперва верифицировать** (context7
  `grafana/k6` → perplexity), запись в `findings/`, потом в документ. Синтаксис «по памяти» — дефект.
- **Ни один SLO не остаётся без строки** в таблице гейтов: либо класс A, либо класс B, либо явно
  «не гейтим» с причиной в соответствующем разделе.
- Каждая метрика в колонке «Prometheus-метрика» — с **типом** (counter/gauge/histogram) и лейблами;
  это ТЗ для P8, а не пожелание.
- Пороги класса A — **абсолютные и жёсткие** (шумоустойчивые метрики можно и нужно гейтить строго).
  Пороги класса B — **относительные**, абсолютный guardrail широкий. Перепутать классы — значит
  получить флапающий гейт (RAG-6).
- Профиль `smoke-perf` на PR обязан укладываться в разумное время лейна (порядок — минуты);
  если для достоверности нужна медиана-из-3 × длинный прогон — это профиль `regression`, не PR.
**Code Guidance:** - **Не пиши код** (ни k6-скриптов, ни YAML workflow) — это фаза P2. Здесь спека: имя метрики,
  выражение, политика. Пример выражения в документе — иллюстрация, не файл в `load/`.
- **Анти-самообман (главная ловушка):** соблазн — объявить всё класс A и «гейтить строго», потому
  что так выглядит серьёзнее. RAG-6 прямо говорит, что это даёт флапающий гейт, который отключат;
  тогда фаза P1 произведёт CI-лейн, который через месяц стоит `continue-on-error: true`. Честный
  advisory-класс лучше, чем декоративный блокирующий.
- **Анти-подгонка:** не подбирай δ (допуск регрессии) так, чтобы «ничего не падало». δ выводится из
  измеренного CV окружения — а CV на момент P1 **неизвестен**. Значит: δ помечается как
  `[гипотеза, уточняется в P2 по факту CV]`, а item P2 обязан его подтвердить или пересмотреть.
  Это честный «unknown», а не дыра.
- **if-then эскалация:** если окажется, что даже класс A недостоверен на `ubuntu-latest` (напр.
  throughput при фиксированной конкуренции пляшет > 20 %) — **не ослабляй порог до бессмысленного**,
  а зафиксируй это D-записью-кандидатом («CI-гейт нагрузки невозможен без dedicated-раннера») и
  подними Q1 в `open-questions.md` до статуса «блокирует решение владельца». Гейт, который ничего не
  ловит, хуже отсутствия гейта: он даёт ложное чувство защищённости.
- **Запрещённый shortcut:** «P8-минимум допишем в P8». Тогда P8 сама решит, что ей удобно
  инструментировать, и вердикт «SLO нарушен» опять будет не на чем построить — ровно противоречие,
  которое D9 уже закрыл. Список P8-минимума выводится ЗДЕСЬ, из колонки Prometheus-метрик.
