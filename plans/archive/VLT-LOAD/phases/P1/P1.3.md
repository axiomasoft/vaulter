### P1.3 — SLO-таблица: latency/throughput/error-budget по OP × тир (SLO-nn)

**Intent:** Собственно числа: для каждой операции из каталога (P1.2) и каждого тира (P1.1) —
целевая конкуренция/RPS, размерный профиль, бюджет латентности (p50/p95/p99) или throughput (для
стриминговых), error-budget. Каждой строке — стабильный ID `SLO-nn` и явный источник числа.
**Why:** Это тот артефакт, ради которого существует фаза, и гейт для P2–P7 (D-LOAD-1). Числа —
обязательства: прогон без них отвечает на вопрос «упало ли», а нужен ответ «держит ли обещание».
**Scope Included:** - `plans/VLT-LOAD/slo.md`: `SLO-nn | OP-nn | Тир | Конкуренция/RPS | Размерный профиль |
  p50/p95/p99 (или throughput/RSS для стриминговых) | Error-budget | Источник числа | Статус`.
- Размерные распределения файлов задать явно (стартовая гипотеза из блупринта: p50 = 5 MiB,
  p95 = 500 MiB, max = 5 GiB) — и **обосновать или пересмотреть**, а не скопировать.
- Для стриминговых операций (upload-чанк, download) SLO — это **throughput + потолок RSS**, а не
  p95 полного запроса: у 5-ГиБ стрима «p95 длительности» — не обязательство, а описание размера.
  Латентность для них измеряется на TTFB / на одном чанке.
- Для фоновых — throughput (строк/с) и **потолок времени одного тика** + отсутствие роста backlog.
- Error-budget на класс операций (напр. `http_req_failed rate < 0.01`; для upload — доля 409 на
  advisory-lock, которая считается нормой, а не ошибкой).
- Статус строки: `proposed` (гипотеза исполнителя) → `approved` (item P1.5).
**Scope Excluded:** - Машинные выражения порогов и Prometheus-метрики — item P1.4 (здесь — только обязательство).
- Любые прогоны/замеры — фазы P3–P7. Числа P1 — **обещания**, а не измерения.
**Inputs:** `plans/VLT-LOAD/reference-env.md` (P1.1), `plans/VLT-LOAD/operations-catalog.md` (P1.2),
`plans/VLT-LOAD/findings/P1-rag-slo-ci-gate.md`, `plans/VLT-LOAD/plan.md` §1.2 (потолок
download-воркеров, N-CTE, глубина 64).
**Files:** `plans/VLT-LOAD/slo.md` (создать); `plans/VLT-LOAD/plan.md` (Update Log, Status Board).
**Required Reads:** 1. `plans/VLT-LOAD/reference-env.md` — тиры целиком (число FPM-воркеров задаёт потолок
   конкурентных download-стримов; это не свободный параметр).
2. `plans/VLT-LOAD/operations-catalog.md` — все OP-nn и их классы.
3. `plans/VLT-LOAD/plan.md` §1.2 — почему download занимает воркера целиком (AUDIT-VLT D15).
4. `plans/VLT-LOAD/findings/P0-rag-load-tooling.md` RAG-5 — форма SLO очереди (queue-time p95/p99,
   process-time, устойчивый throughput без роста backlog, error-budget failed_jobs/день).
**Implementation Rules:** - **Покрытие полное:** каждый `OP-nn` из каталога имеет ≥ 1 строку SLO (либо явную запись
  «SLO не даётся, потому что …» в разделе «Операции без SLO»). Дыра в покрытии — дефект.
- Каждое число несёт **источник**: `[инженерная гипотеза]` (по умолчанию — с обоснованием в одну
  строку), `[RAG:✅ дата]`, `[владелец]`, `[из кода]` (напр. потолок конкурентных download = число
  FPM-воркеров тира). «TBD» без метки — запрещён (DoD фазы).
- **Класс операции определяет форму SLO** (см. P1.2): не выписывай p95 для 5-ГиБ стрима.
- Латентные числа — с **запасом на конверт**: они привязаны к тиру, а не абсолютны. Строка SLO без
  колонки «Тир» бессмысленна.
- Error-budget — отдельная колонка, а не примечание: без него порог «p95 < X» не имеет права на
  существование (одна медленная секунда не должна валить гейт).
**Code Guidance:** - **Числа-гипотезы — это нормально; числа без обоснования — нет.** Каждая гипотеза сопровождается
  одной строкой «откуда»: «200 параллельных tus-сессий на тир M — потому что 32 FPM-воркера ×
  ~6 активных сессий на воркер при chunk-based PATCH».
- **Анти-подгонка (главная ловушка этого item'а):** соблазн — выставить числа так, чтобы код,
  который ты уже видел, их заведомо прошёл. Это инвертирует смысл фазы: SLO — обязательство перед
  пользователем, а не портрет текущей реализации. Если честное обязательство заведомо не
  выполняется сегодняшним кодом (напр. `complete()` держит весь файл в RAM — L-01) — **так и
  записать**: SLO ставится, строка помечается «сегодня не выполняется, см. L-01». Ослабить SLO под
  реализацию — дефект, который аудит найдёт.
- **Анти-самообман:** не превращай «мы это не мерили» в «здесь SLO не нужен». Отсутствие SLO
  допустимо только с причиной в разделе «Операции без SLO», и причина обязана быть про природу
  операции, а не про трудность замера.
- **if-then эскалация:** если для класса операций невозможно предложить число без бизнес-входа
  (напр. приемлемый лаг фида активности) — не выдумывай: строка получает статус `proposed` с явной
  пометкой `[решение владельца — P1.5]` и попадает в decision-sheet item'а P1.5.
- **Запрещённый shortcut:** одна таблица «на все тиры» с диапазонами («p95 100–800 мс»). Диапазон —
  не обязательство; на нём нельзя построить порог. Три числа на три тира.
**Validation:** - Покрытие OP → SLO полное (вывод должен быть пуст):
  `comm -23 <(grep -oE 'OP-[0-9]{2}' plans/VLT-LOAD/operations-catalog.md | sort -u) <(grep -oE 'OP-[0-9]{2}' plans/VLT-LOAD/slo.md | sort -u)`
  (любой OP-nn, не упомянутый в slo.md, — дыра; если он в разделе «Операции без SLO», он там
  упомянут и в вывод не попадёт).
- Ни одного «TBD»/«?» без метки: `grep -nE 'TBD|\?\?\?' plans/VLT-LOAD/slo.md | grep -v '\[решение владельца' || echo OK`
- Каждая строка SLO имеет источник:
  `grep -E '^\| *SLO-[0-9]{2}' plans/VLT-LOAD/slo.md | grep -vcE '\[инженерная гипотеза\]|\[RAG:|\[владелец\]|\[из кода\]'` → `0`
- Каждая строка SLO имеет тир: `grep -E '^\| *SLO-[0-9]{2}' plans/VLT-LOAD/slo.md | grep -vcE '\| *[SML] *\|'` → `0`
