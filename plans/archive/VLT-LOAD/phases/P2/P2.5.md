### P2.5 — Гейт: thresholds-модуль + perf-assert (PromQL) + baseline-артефакт

**Intent:** Перевести `slo-gates.md` (97 строк) в **исполняемый** гейт двух плоскостей (D18):
`load/gates/thresholds.js` — пороги k6 (клиентская плоскость, exit 99) и `load/gates/perf-assert.py` —
серверная плоскость (PromQL по снимку прогона + сравнение с baseline). Плюс формат и первый
baseline-артефакт.
**Why:** Гейт, который «описан в документе», не гейт. Половина класса A (RSS, батч, lock-set, backlog)
**невыразима порогами k6** (RAG-8b, `slo-gates.md` §0.2) — без второй плоскости она была бы
обязательством, которое никто не вычисляет. И баланс честности: серверные метрики появятся только в
P8 — значит perf-assert обязан **уметь сказать «метрики нет ⇒ SLO не проверяется»** (правило вердикта
`slo-gates.md` §8), а не выдавать зелёный на пустом месте.
**Scope Included:** - `load/gates/thresholds.js` — экспорт `thresholdsFor(profile, tier)`: сквозные G-1…G-5 (§2) + все
  строки §3, у которых есть k6-выражение. Класс B в профилях `smoke-perf`/`regression` —
  **advisory** (D20): не в `options.thresholds`, а в отдельный отчёт, чтобы не валить PR.
- `load/gates/perf-assert.py` (python3 — как `plan-lint`): вход — `summary.json` (из
  `handleSummary`), снимок Prometheus, `load/baselines/<profile>-<tier>.json`; выход — вердикт по
  каждой строке §3: `pass` / `fail` / **`not-checkable (метрика отсутствует)`** / `incomparable
  (другой env_fingerprint)`; exit ≠ 0 только на `fail` **блокирующих** строк.
- `load/baselines/<profile>-<tier>.json` — формат `slo-gates.md` §4.1: `meta{commit, profile, tier,
  env_fingerprint, dataset_id, runs}` + `metrics` (ключи агрегатов — `values["p(95)"]`, `values.count`,
  `values.rate`).
- `handleSummary(data)` в сценариях: дописывает `meta` (commit SHA, тир, `dataset_id`,
  `env_fingerprint`) — **вместо** `--summary-export` (RAG-8).
- `load/scripts/collect-container-stats.sh` — пиковая память контейнеров из cgroup (`memory.peak`) →
  `container-peak.json`. Это **грубый** заменитель `vaulter_request_peak_memory_bytes` (её нет до P8):
  ловит «контейнер съел лимит», не ловит «какой запрос виноват». Ограничение записывается явно.
- `load/gates/coverage.py` — машинная сверка: каждый `SLO-nn` из `slo-gates.md` §3 имеет ровно одно
  место вычисления (порог k6 ИЛИ строка perf-assert) — либо помечен `not-checkable` с причиной.
- Таблица «что сегодня не проверяется» (вывод coverage) → в Completion Notes и в handoff.
**Scope Excluded:** реализация Prometheus-метрик сервера (P8 — perf-assert их только читает); CI-лейн
(P2.6); измерение CV/δ (P2.7); ослабление любого порога (запрещено — числа SSOT в `slo-gates.md`).
**Inputs:** `slo-gates.md` целиком (§1 механика, §2 сквозные, §3 таблица, §4 baseline, §5 P8-минимум,
§6 что не гейтим, §7 профили); `plans/VLT-LOAD/harness.md` §5–§6; сценарии P2.4; манифест P2.3.
**Files:** `load/gates/{thresholds.js,perf-assert.py,coverage.py}`, `load/baselines/.gitkeep`,
`load/scripts/collect-container-stats.sh`, `load/k6/lib/summary.js` (`handleSummary`).
**Required Reads:** 1. `plans/VLT-LOAD/slo-gates.md` — целиком.
2. `plans/VLT-LOAD/harness.md` — §5 (контракт метрик), §6 (профили).
3. `plans/VLT-LOAD/findings/P1.4-rag-k6-threshold-syntax.md` — синтаксис агрегаций и границы
   применимости порогов k6 (`Counter` → `count`/`rate`, `Trend` → `p(N)`/`med`; `checks` сами не валят
   CI).
4. `load/k6/lib/metrics.js` (P2.4) — имена, на которые ссылаются пороги.
**Implementation Rules:** - Пороги **не переписываются своими словами** — переносятся из `slo-gates.md` §2/§3 буквально
  (значение, `abortOnFail`, `delayAbortEval: '30s'`). Любое расхождение — дефект.
- `checks: ['rate>0.99']` присутствует в **каждом** профиле (без него провалившийся `check()` не валит
  CI — RAG-6).
- Baseline с **другим `env_fingerprint`** не сравнивается: вердикт `incomparable`, а не «прошло»
  (`slo-gates.md` §4.2).
- Метрика отсутствует в Prometheus ⇒ вердикт **`not-checkable`**, и он **виден** в отчёте отдельной
  секцией со списком SLO. Молча пропустить = соврать про зелёный гейт (D9).
- Порог класса A **не ослабляется** «потому что сегодня красный»: SLO-46…48 (L-01) остаются
  блокирующими в спеке, а в CI включаются вместе с фиксом (`slo-gates.md` §6.4). До этого — вердикт
  `known-red` с ссылкой на L-01, **не** `|| true`.
- `env_fingerprint` = хэш от (cpuset-раскладка + `mem_limit` + версии PHP/PG/MinIO/k6 + `dataset_id`).
**Code Guidance:** - **Анти-самообман:** гейт, который «зелёный, потому что ничего не проверил», хуже отсутствующего.
  Итог perf-assert обязан печатать три числа: сколько строк `pass`, сколько `fail`, сколько
  `not-checkable` — и `not-checkable` в P2 будет БОЛЬШИНСТВОМ (серверных метрик нет до P8). Это
  нормально и должно быть видно.
- **Анти-подгонка:** соблазн «пусть класс B пока валит, зато строго» — против D20; и обратный «зачем
  считать advisory, всё равно не валит» — против §4.4 (advisory пишет baseline, из него потом растёт
  блокирующий гейт).
- **Дисциплина порога взята из `mutation.yml` этого репо:** число ставится по факту, с комментарием,
  откуда оно; декоративный `|| true` запрещён.
- **If-then:** порог `slo-gates.md` §3 невыразим ни в k6, ни в PromQL (нет метрики даже в P8-минимуме)
  → это дефект гейт-политики: НЕ выдумывать выражение, а эскалировать (`plan-protocol` §10, trigger
  «rule conflict») — правит `plan-design`, не исполнитель.
**Validation:** - `python3 load/gates/coverage.py` → «97/97 строк имеют место вычисления; N помечены not-checkable
  (список)» — ни одной строки без назначения.
- `python3 load/gates/perf-assert.py --summary <summary.json> --baseline load/baselines/…` на прогоне
  P2.4-smoke → печатает вердикты, exit 0 (нет `fail` блокирующих), `not-checkable` перечислены.
- Негативный тест гейта: искусственно занизить порог (напр. `stream_throughput_mibs med>10000`) →
  k6 выходит с **кодом 99**; вернуть. Гейт, который не умеет падать, — не гейт.
- `grep -c "delayAbortEval" load/gates/thresholds.js` > 0 (все `abortOnFail` — с задержкой).
**Deliverables:** thresholds-модуль, perf-assert, coverage-сверка, формат baseline, `handleSummary`,
сбор пиковой памяти контейнеров.
