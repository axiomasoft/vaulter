### P2.3 — Seed: объёмный конверт и «грязные» датасеты (`dataset_id`, снапшот)

**Intent:** Наполнить стенд данными до **объёмного конверта** `reference-env.md` §2 — включая
«грязные» состояния (просроченные сессии, orphan-блобы, outbox-backlog, много endpoint'ов, много
grant-якорей) — воспроизводимо, с версией датасета (`dataset_id`) и снапшотом для повторных прогонов.
**Why:** EXPLAIN на пустой БД врёт, а прогон на пустой БД меряет фикцию (D10): планировщик уходит в
seq-scan, GIN не платит за себя, N-CTE не болит. «Грязные» объёмы — единственный вход для L-02…L-06
(D-LOAD-3). `dataset_id` входит в `env_fingerprint` baseline'а (`slo-gates.md` §4.1): прогон на другом
датасете **несравним**, и это должно быть машинно видно, а не «на глаз».
**Scope Included:** - `load/seed/` — artisan-команда стенда (живёт в `load/app/`, регистрируется `LoadServiceProvider`),
  профили объёмов `S0`/`S`/`M` (числа — `reference-env.md` §2.1) + спека `L` (без прогона, D25).
- Наполнение: `v_nodes` (в т.ч. **глубокий хребет 64** = `DEFAULT_MAX_DEPTH` и **широкий узел**),
  `v_blobs` (+ доля orphan/tombstoned), `v_file_versions`, `v_activity`, `v_upload_sessions`
  (+ **просроченные**), `v_upload_parts`, `v_outbox` (backlog), `v_webhook_endpoints`,
  `v_webhook_deliveries` (due-строки), `v_node_grants` (**many-grant актор**: 20/200/1000 якорей),
  `v_node_shares`, `v_node_comments`, `v_node_document_versions`.
- **Горячий набор** реальных байт в MinIO (§2.2: 20 000 / 100 000 объектов; остальные строки `v_blobs`
  — «сиротские» метаданные без байт) — два разных числа, сливать запрещено.
- `load/seed/out/<dataset_id>.json` — манифест: числа по таблицам + **id-списки** для сценариев
  (узлы-папки, файлы с размерами, document-узлы, share-токены, актор many-grant, актор обычный).
- Снапшот/восстановление: `load/scripts/snapshot.sh` / `restore.sh` (tar томов PG + MinIO), чтобы
  повторный прогон не переплачивал seed'ом и стартовал с идентичного состояния.
- Sustained фоновая запись `v_activity` (20/200/1000 в секунду по тиру, §2.1) — как отдельный
  «фоновый писатель» (artisan-команда стенда), включаемый на время прогона: без неё фид меряет фикцию.
**Scope Excluded:** k6-скрипты (P2.4); прогон (P2.8); тир L (только спека, железа нет — D25);
изменение схемы/`PanelTablesBuilder` (SSOT схемы — пакет, seed под неё подстраивается, а не наоборот).
**Inputs:** `reference-env.md` §2 целиком (объёмы, §2.2 — байты vs строки); `plans/VLT-LOAD/harness.md`
§2; `packages/core/src/Schema/PanelTablesBuilder.php` (реальные колонки).
**Files:** `load/app/Console/SeedLoadDatasetCommand.php`, `load/app/Console/ActivityWriterCommand.php`,
`load/seed/profiles/{S0,S,M}.php` (или `.json`), `load/scripts/{snapshot.sh,restore.sh}`,
`load/README.md` (дополнить).
**Required Reads:** 1. `plans/VLT-LOAD/reference-env.md` — §2 целиком (включая оговорку §2.2).
2. `packages/core/src/Schema/PanelTablesBuilder.php` — какие таблицы/колонки/индексы существуют.
3. `packages/core/src/Repositories/Drive/NodeReadRepository.php:454-529` — что такое grant-якорь
   (почему их число — параметр датасета).
4. `packages/media/src/Cas/BlobStore.php` — как выглядит «живой» и «tombstoned» блоб (`ref_count`,
   `status`, `delete_after_at`) — orphan'ы обязаны быть валидными для GC, а не «мусором в колонках».
5. `packages/drive/src/Console/SweepUploadsCommand.php:37` — какие сессии считаются просроченными
   (scope `(status, expires_at)`), чтобы «грязь» реально попадала в кандидаты sweeper'а.
**Implementation Rules:** - Массовые вставки — **`COPY` / batch-insert**, не Eloquent-по-строке: 50 млн строк `v_activity` на
  тире M через ORM не заполнятся никогда.
- Данные обязаны быть **валидны для механизмов, которые их будут обходить**: просроченная сессия
  должна попадать в scope `SweepUploadsCommand`; orphan-блоб — в `candidates()` GC; due-доставка — в
  `claimDue()`. Seed, который «залил строки», но не попал в scope, обесценивает всю фазу P5/P6.
- Уникальность имён в родителе — partial-UNIQUE `(parent_id, lower(name))`: генератор имён обязан её
  соблюдать, иначе seed упадёт на середине.
- `dataset_id` — детерминированный хэш от (профиль + числа + версия seed-скрипта); он же пишется в
  манифест и попадает в `env_fingerprint` (P2.5).
- Seed **идемпотентен по `dataset_id`**: повторный запуск на том же id — no-op (или явный
  `--fresh`).
- Хэши блобов горячего набора — реальные sha256 залитых байт (иначе CAS-инварианты БД и содержимое
  MinIO разъедутся, и download отдаст 404/битый поток).
**Code Guidance:** - **Ни строки в `packages/*/src`.** Seed — код стенда (`load/app/`), а не пакета. Соблазн «добавить
  фабрику в пакет, чтобы удобнее» — это публичная поверхность пакета, стоп.
- **Анти-подгонка:** объёмы — из `reference-env.md` §2.1. Если «слишком долго сеется» — это факт для
  Completion Notes (и повод для снапшота), а не повод уменьшить `v_activity` до удобного числа.
- **Анти-самообман:** «строки залились» ≠ «датасет грязный». Item закрывается только с доказательством:
  `SELECT count(*)` по каждой таблице конверта + **проверка попадания в scope** (сколько сессий видит
  sweeper-скоуп, сколько блобов видит GC-скоуп) — числа в Completion Notes.
- **If-then:** если реальные байты горячего набора не помещаются на диск (S = ~20 ГиБ, M = ~80 ГиБ) →
  НЕ уменьшать молча: уменьшить горячий набор, записать фактическое число в манифест и в Known
  Deviations, отметить, какие SLO (download/GC-физика) на этом датасете **не проверяются**.
**Validation:** - `TIER=S0 php artisan load:seed --fresh` в контейнере app → выводит `dataset_id` и манифест.
- `docker exec <pg> psql -c "SELECT relname, n_live_tup FROM pg_stat_user_tables ORDER BY n_live_tup DESC LIMIT 15"` —
  числа совпадают с профилем тира (± 1 %).
- Scope-проверки (SQL из команд пакета): число кандидатов sweeper'а == число «просроченных» профиля;
  число кандидатов GC == число orphan-строк профиля.
- `mc ls --summarize` (или `aws s3 ls`) — число объектов горячего набора совпадает с манифестом.
- `load/scripts/snapshot.sh && load/scripts/restore.sh` → `dataset_id` после restore тот же.
**Deliverables:** seed-команда + профили объёмов + фоновый писатель `v_activity` + манифест
`dataset_id` с id-списками + снапшот/restore.
