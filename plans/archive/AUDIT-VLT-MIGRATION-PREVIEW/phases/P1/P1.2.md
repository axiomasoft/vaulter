### P1.2 — Ролевые драйверы и AzGuard-шов: fail-closed

**Intent:** Проверить четыре реализации `HostRoleDriver` (Gate / Spatie / Database / Azgard), менеджер драйверов и пакет `permissions-azgard` на fail-closed-поведение, корректность `subjectsFor`/`override`/`canCreateInWorkspace` и отсутствие связности с хостом.
**Why:** Шов ролей — единственный путь, которым внешняя система может ПОДНЯТЬ права (`granted = max(aclAllow, roleAllow)`); ошибка (fail-open при отсутствии драйвера, `override` → allow по умолчанию, `subjectsFor` возвращающий чужие субъекты) означает эскалацию привилегий. Нормы: централизованное разрешение (S1.6), per-subject-свёртка (S1.2), отсутствие связности с хостом (RAG:✅ 2026-07-10 — `findings/P0-embeddable-laravel.md` §E5).
**Scope Included:** `HostRoleDriverManager`, `Drivers/Permission/{Gate,Spatie,Database,Azgard}PermissionResolver`, `Contracts/Access/{HostRoleDriver,AzgardGuard,GrantAuthoritativeDriver}`, `Testing/{NullRoleDriver,FakeAzgardGuard}`, `Support/{GateConfig,SpatieConfig,AzgardConfig}`, `packages/permissions-azgard/src/*`, ключи `permission_drivers`/`gate`/`spatie`/`azgard` в конфиге.
**Scope Excluded:** сам алгоритм свёртки (P1.1); дизайн шва как расширяемости (P3.5); реальная интеграция с внешним AzGuard-пакетом (его репозиторий вне границ, D1).

**Implementation Rules:** Закрытый чеклист:
`C1` отсутствие/неверная конфигурация драйвера → исключение или отказ, НЕ «разрешить» (fail-closed); проверить `HostRoleDriverManager::driver()` и `MissingHostRoleDriverException`;
`C2` `NullRoleDriver` и `NullAzgardGuard` возвращают «ничего не разрешено» по всем методам (в т.ч. `override`, `canCreateInWorkspace`, `isSuperAdmin`);
`C3` `override()` каждого драйвера возвращает `Effect::Allow` ТОЛЬКО для явного супер-админа; нет пути, где неизвестный/гость получает Allow;
`C4` `subjectsFor()` не возвращает субъекты, к которым актор не принадлежит (в частности, у Azgard `subjectsFor = [actor]` — проверить, что ACL-гранты на группы/роли при этом не игнорируются молча, а это задокументированное ограничение);
`C5` `canCreateInWorkspace()` не даёт создать узел в чужом workspace (проверить, что `owner_type`/`owner_id` storage'а реально участвуют в проверке);
`C6` `DatabasePermissionResolver` строит запросы со скоупом (нет «голой» выборки по PK) — S3.2;
`C7` `SpatiePermissionResolver` и `GatePermissionResolver` не падают в fail-open при отсутствующих пакетах/гейтах (`Gate::has()`, наличие трейта);
`C8` `AzgardPermissionResolver` не имеет hard-dep на внешний пакет: `phpstan` зелёный при отсутствующем azguard (проверить `composer.json` core: azguard в `require` быть не должен);
`C9` карта `Ability → permission` (`config vaulter.azgard.permissions`) полна: КАЖДЫЙ кейс `Ability` имеет отображение; отсутствующий ключ не приводит к «разрешено»;
`C10` `permissions-azgard`: `AzgardGuardAdapter` не тянет `App\*` и не резолвит чужие ключи контейнера (E5.1/E5.3);
`C11` `GrantAuthoritativeDriver` — где используется, и не даёт ли он драйверу право переопределять deny-вето (пересечение с P1.1 C1);
`C12` тесты `packages/permissions-azgard/tests/*` покрывают fail-closed-путь (нет драйвера / нет guard'а).
Для `C1`, `C2`, `C3` — repro в `artifacts/repro/P1.2/` обязателен.
**Code Guidance:** Fail-open — приоритетный класс находок: любое место, где отсутствие данных/конфига/зависимости приводит к «разрешено», = **Blocker**, даже если сценарий «маловероятен». ЗАПРЕЩЕНО оценивать драйверы по докблокам и README — только по телу методов, `file:line`. Ограничение Azgard (`subjectsFor=[actor]`, не энумерит роли) зафиксировано в памяти проекта как осознанное — по D5 сверить с `docs/adr/0007`: если задокументировано, находка = «ограничение задокументировано, риск: ACL на группы не работают под Azgard» (Major, если не задокументировано; Minor, если задокументировано). ЗАПРЕЩЕНО помечать 🟢 при незакрытом `C8`: проверка «phpstan зелёный без azguard» подтверждается фактическим прогоном `/usr/bin/php8.4 vendor/bin/phpstan analyse --no-progress --memory-limit=512M` и цитатой вывода, не рассуждением.
