# Шаблон файла находок audit-item'а — `plans/AUDIT-VLT/findings/<Pn.m>-<slug>.md`

Копируется КАК ЕСТЬ, слоты `<…>` заполняются. Отступать от схемы запрещено:
по ней строится сводный отчёт P5.1 и `findings/REGISTER.md`.

Шкала severity (единая, из скилла `quality:artifact-review`):

| Severity | Определение |
|:--|:--|
| **Blocker** | Эксплуатируемая уязвимость / потеря или порча данных / обход авторизации. Релиз с ней невозможен. |
| **Major** | Реальный дефект: нарушен инвариант, отсутствует обязательный контроль. Эксплуатация требует условий. |
| **Minor** | Дефект без прямого риска: слабый дефолт, отсутствующий лимит, недостающий тест на несущий путь. |
| **Nit** | Стиль, именование, дубль, читаемость. |

Шкала уверенности: `high` (доказано кодом/прогоном) · `medium` (следует из чтения,
не воспроизведено) · `low` (гипотеза, нужен эксперт).

```markdown
# <Pn.m> — <Тема item'а>

**Дата:** <YYYY-MM-DD> · **Исполнитель:** <модель/effort> · **Режим:** read-only
**Область:** <перечень каталогов/файлов, реально прочитанных>
**RAG-основание:** <ссылки на findings/P0-*.md, конкретные пункты — напр. U2.2, C3.2>

## 1. Чеклист

Каждая строка чеклиста item'а обязана получить вердикт. Формулировки
«выглядит корректно», «вероятно, ок», «не нашёл проблем» — ЗАПРЕЩЕНЫ:
либо `✅ pass` с доказательством, либо `❌ fail` с находкой, либо `n/a` с причиной.

| # | Проверка | Вердикт | Доказательство (`file:line`) | Находка |
|:--|:--|:--|:--|:--|
| C1 | <текст проверки из item'а> | ✅ pass / ❌ fail / ⚠ partial / n/a | `packages/core/src/…php:42` | — / F-<Pn.m>-01 |

## 2. Находки

### F-<Pn.m>-01 — <заголовок> · Severity: <Blocker|Major|Minor|Nit> · Уверенность: <high|medium|low>

**Где:** `<file:line>` (все затронутые места)
**Что:** <что именно неверно — 1–3 предложения, без пересказа кода>
**Почему опасно:** <модель угрозы: кто, как, что получает; для не-security осей — цена дефекта>
**Доказательство:** <цитата кода ≤10 строк ИЛИ команда repro + фактический вывод>
**Норма, которая нарушена:** <пункт RAG-выжимки (U2.4 / C2.1 / E6.2 …) ИЛИ ADR/док проекта>
**Сверка с ADR:** <docs/adr/000X-*.md — решение сознательное? да → находка класса «ADR устарел» / нет → дефект>
**Рекомендация:** <минимальное исправление; без проектирования новой архитектуры>

## 3. Не проверено / ограничения

- <что осталось за границей: файлы, сценарии, среды; почему>

## 4. Источники

- <URL + дата, если в ходе item'а делалась своя RAG-верификация>
```

---

## Пост-условие каждого audit-item'а

1. Файл `findings/<Pn.m>-<slug>.md` создан по схеме выше.
2. Каждая находка добавлена строкой в `findings/REGISTER.md` (append, не переписывать).
3. Repro-скрипты/тесты — только в `plans/AUDIT-VLT/artifacts/repro/<Pn.m>/`.
4. Ни одного изменённого файла вне `plans/AUDIT-VLT/` (`git status` — доказательство).
