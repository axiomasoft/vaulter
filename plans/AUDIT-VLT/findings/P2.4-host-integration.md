## 2. Находки

### F-P2.4-01 — Документация advertises мёртвый config-ключ `permission_resolver`; реальный хост (FlexCRM) написал нерабочую интеграцию против него · Severity: Major · Уверенность: high

**Где:** `docs/guide/configuration.md:189` (документирует ключ и контракт); `packages/core/config/vaulter.php` (полный файл — ключ `permission_resolver` отсутствует); `packages/*/src` (интерфейс `Contracts\Access\PermissionResolver`/`Contracts\PermissionResolver` отсутствует нигде); `/home/vostrikov/projects/flexcrm/config/vaulter.php:20` и `/home/vostrikov/projects/flexcrm/app/Vaulter/AllowAuthenticatedResolver.php:7-8` (реальный хост, читается как потребитель, D21).

**Что:** `docs/guide/configuration.md` описывает `config('vaulter.permission_resolver')` как рабочую точку расширения («legacy document-path resolver», FQCN контракта `Contracts\Access\PermissionResolver`). Ни ключ, ни контракт не существуют в текущем коде пакета — они были частью легаси DocVault-пути, полностью удалённого по ADR-0014 («Build parity, then excise from core»), но документация не была обновлена вслед за excision-коммитом. Реальный внешний потребитель (FlexCRM), следуя ЭТОЙ документации, написал `AllowAuthenticatedResolver` (реализующий несуществующий `PermissionResolver`, типизирующий несуществующую модель `Document`) и подключил его через мёртвый ключ `permission_resolver` — код НИКОГДА не исполняется: текущий `VaulterServiceProvider`/`Support\Config` не читают `vaulter.permission_resolver` ни в одном месте (грep по `packages/core/src` — 0 совпадений).

**Почему опасно:** Автор FlexCRM (судя по докблоку `AllowAuthenticatedResolver.php:12-17` — «TEMPORARY development placeholder: grants every authenticated user full access… so the Vaulter integration can be smoke-tested end to end») ОШИБОЧНО полагает, что документы открыты для smoke-теста. Фактически авторизация идёт через дефолтный `drivers.permission => 'database'` (`config/vaulter.php:248`) и пустую таблицу `v_node_grants` — то есть РЕАЛЬНОЕ поведение полностью противоположно ожидаемому: не «всем можно», а «никому нельзя» (fail-closed по отсутствию грантов), без единой ошибки или предупреждения при загрузке. Для DX это скрытый источник часов отладки «почему у меня всё 403» с ложным чувством, что резолвер настроен; для аудита встраиваемости — прямое свидетельство того, что документация пакета не пережила собственный breaking change (ADR-0014) и увела реального потребителя на нерабочий путь.

**Доказательство:**
```

(нет совпадений)

$ grep -rln "interface PermissionResolver" packages/vaulter/packages 2>/dev/null
(нет совпадений)

$ find packages -iname "PermissionResolver.php" -o -iname "Document.php" -path "*/Models/*"
(нет совпадений)

# docs/guide/configuration.md:189
'permission_resolver' => null, // FQCN of a Contracts\Access\PermissionResolver, or null

# /home/vostrikov/projects/flexcrm/config/vaulter.php:17-24
return [
    'permission_resolver' => AllowAuthenticatedResolver::class,
    'middleware' => ['api', 'auth:sanctum'],
];

# /home/vostrikov/projects/flexcrm/app/Vaulter/AllowAuthenticatedResolver.php:7-8
use Vaulter\Contracts\PermissionResolver;
use Vaulter\Models\Document;
```

**Норма, которая нарушена:** E7.1/E7.3 (`findings/P0-embeddable-laravel.md`) — «разумные дефолты… биндинги контрактов… читаются из config на boot» подразумевает, что документированные ключи ДЕЙСТВУЮТ; косвенно E4.4 (депрекация: удаление публичного контракта без заметки в CHANGELOG/доках).

**Сверка с ADR:** ADR-0014 (статус accepted) сознательно решает удалить легаси DocVault «без бэкфилла и без deprecation window» именно потому, что «нет released consumer, которого нужно защищать» (Context 3). Само решение об excision — не находка. НО ADR-0014 нигде не рассматривает синхронизацию `docs/guide/configuration.md` как часть excision-чеклиста («Done: `grep -r 'Models\Documents\Document' packages/core/src` returns only `NodeDocumentVersion`» — только код, не доки). Оставшаяся в доках запись о `permission_resolver` — пробел исполнения ADR-0014, а не пересмотр решения: это дефект, не «ADR устарел».

**Рекомендация:** удалить строку `'permission_resolver' => null, …` из `docs/guide/configuration.md` (и любые другие упоминания легаси `PermissionResolver`/`Document` в `docs/`); в CHANGELOG/upgrade-заметке явно назвать `permission_resolver` удалённым легаси-ключом. Отдельно (не блокирует эту находку) — рассмотреть, стоит ли документировать `drivers.permission => 'null'` (`NullRoleDriver`) как штатный smoke-test путь в `quick-start.md`, раз он уже существует в коде для ровно этого сценария.

## 4. Не проверено / ограничения

- Реальный `vendor:publish --tag=vaulter-config` и последующая ручная правка `config/vaulter.php` в C1/C4/C12 НЕ выполнялись (сценарий намеренно «без публикации», как требует чеклист) — путь «частично опубликованный конфиг» проверен в P2.2, не дублируется здесь.
- `docker compose -f hocuspocus-server/docker-compose.yml up -d` не запускался (D13 требует ТОЛЬКО проверки факта наличия install-пути надстройки, не её функциональности — это P3.6/P2.5).
- Реальный прогон `composer require axioma-studio/vaulter-drive` в чистом НОВОМ Laravel-скелете (не Testbench) не выполнялся — репро использует Testbench/Orchestra как стандартный (и документированный самим RAG-основанием D9) эквивалент; это соответствует практике остальных P2.2/P2.3 repro этой фазы.
- Первый прогон C1-репро содержал харнесс-артефакт (см. докблок `NoPublishBase.php`): предыдущий item P2.2 физически опубликовал файлы миграций в общий `vendor/orchestra/testbench-core/laravel/database/migrations/` (не отслеживается git, вне области D2), что вызывало ложное «table already exists». Устранено удалением осевших файлов из `vendor/` перед финальным прогоном; сам факт («репро P2.2 загрязняет общий Testbench-скелет для последующих item'ов той же фазы») зафиксирован здесь как методологическое наблюдение, НЕ как находка про пакет (харнесс, не продакшн-код).
- `C6` (`App\*` grep) формально помечен `⚠ partial`, а не `pass`, т.к. буква нормы E5.1 не делает исключения для строк-шаблонов скаффолдера — решение не заводить находку принято по Code Guidance item'а (никаких новых архитектурных рекомендаций) и по духу нормы (нет реальной связности), но зафиксировано как пограничный случай для P5.1.
- Полная матрица «что именно FlexCRM должен был бы написать взамен» (реальный AzGuard-адаптер) не проектируется — за пределами read-only аудита (D2) и вне scope P2.4 (design — P3.5/P5.2).
