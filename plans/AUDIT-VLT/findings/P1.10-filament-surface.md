## Модель поверхности (установленный ФАКТ)

Из пяти ресурсов пакета **только `NodeResource`** скоупит листинг к актору: `getEloquentQuery()` (`NodeResource.php:191-214`) сужает выборку к grant-reachable candidate-set через `NodeReadRepository::constrainToAccessible` и отдаёт пустую таблицу при отсутствии актора; докблок класса (`:35-57`) прямо называет это «P1 #3». Остальные четыре ресурса — `StorageResource`, `NodeGrantResource`, `NodeShareResource`, `ActivityResource` — **не переопределяют** `getEloquentQuery()`, **не определяют** `canViewAny`/`canView`, и их модели (`Storage`/`NodeGrant`/`NodeShare`/`Activity`) **не имеют зарегистрированной политики** (в `VaulterServiceProvider.php:163-176` политики есть только у `Node` и `WebhookEndpoint`). В Filament 5 при отсутствии политики и выключенном strict-режиме (дефолт `isAuthorizationStrict = false`, `HasAuth.php:105`) `get_authorization_response('viewAny', …)` проваливается до `Response::allow()` (`helpers.php:60-93`), т.е. `canViewAny()` = `true`. Итог: любой аутентифицированный пользователь панели видит ВСЕ строки всех владельцев/тенантов в четырёх ресурсах.

## 2. Находки

### F-P1.10-01 — Четыре из пяти ресурсов панели не скоупят листинг: любой пользователь панели читает ACL/share/activity/storage всех тенантов · Severity: Major · Уверенность: high

**Где:** `packages/filament/src/Resources/StorageResource.php` (нет `getEloquentQuery`/`canViewAny`), `.../ActivityResource.php`, `.../NodeGrantResource.php`, `.../NodeShareResource.php` — те же пробелы; `packages/core/src/VaulterServiceProvider.php:163-176` (политики только у `Node`/`WebhookEndpoint`); контраст — `packages/filament/src/Resources/NodeResource.php:191-214` (скоуп есть).
**Что:** `StorageResource`, `NodeGrantResource`, `NodeShareResource`, `ActivityResource` не переопределяют `getEloquentQuery()` и не определяют `canViewAny`; их модели без политики. В Filament 5 при отсутствии политики и выключенном strict-режиме `canViewAny()` возвращает allow, а листинг отдаёт ВСЕ строки. Итог: аутентифицированный пользователь панели без единого гранта видит гранты, share-ссылки, activity и storage-контейнеры ВСЕХ владельцев/тенантов. `NodeResource` (единственный) скоупит листинг — доказывает, что скоуп и есть намеренный дизайн, а его отсутствие в четырёх ресурсах — упущение.
**Почему опасно:** В мультитенантном хосте, дающем доступ к панели тенант-ограниченным админам (штатный сценарий admin-панели), админ тенанта A читает: полный ACL тенанта B (`NodeGrantResource`: node_id + subject + level + bits + expiry — карта «кто-что-может»), его share-ссылки (`NodeShareResource`: node_id, token_prefix, scope, use_count, expiry), его аудит-фид (`ActivityResource`: ip, user_agent, actor/target, context), его storage-инвентарь (`StorageResource`: owner, disk, quota, usage). Это broken access control / раскрытие security-метаданных (S3.2 «запрос всегда несёт tenant/user-скоуп»; S1.6 «объектная авторизация на каждый доступ»). Мутации при этом закрыты per-row (`actorCanShare`), т.е. это раскрытие на чтение, не запись — поэтому Major, не Blocker (цепочки к скачиванию блоба нет: C5/C9 чисты).
**Доказательство:** repro `plans/AUDIT-VLT/artifacts/repro/P1.10/FilamentSurfaceReproTest.php`, запуск из `packages/filament`:
```
/usr/bin/php8.4 vendor/bin/pest ../../plans/AUDIT-VLT/artifacts/repro/P1.10/FilamentSurfaceReproTest.php
✓ [C1] grants canViewAny to a stranger with zero grants on the four unscoped resources
✓ [C3] StorageResource lists a storage the acting admin has no grant on
✓ [C3] NodeGrantResource lists another subject grant to a stranger
✓ [C3] NodeShareResource lists a foreign share-link to a stranger
✓ [C3] ActivityResource lists foreign activity (ip/context) to a stranger
✓ [CONTROL] NodeResource returns an empty listing for the same stranger (scoped)
Tests: 6 passed (10 assertions)
```
Механизм allow-по-умолчанию: `filament/filament/src/Resources/Resource/Concerns/HasAuthorization.php:139-142` → `src/helpers.php:60-93` (нет политики + strict off ⇒ `Response::allow()`).
**Норма, которая нарушена:** S3.2 (`findings/P0-dms-security.md`) — «запрос всегда несёт tenant/user-скоуп»; S1.6 — объектная авторизация на КАЖДЫЙ доступ; вердикт P1.9 `C3` (барьер = per-action скоуп; листинги обязаны скоупиться).
**Сверка с ADR:** `docs/adr/0007-pluggable-authorization.md`, `0002-authorization-delegation.md`, `0003-embeddability-data-model.md`, `0009-storage-panels.md` — ни один НЕ объявляет Filament-панель «только для доверенного super-admin» и не разрешает листингам обходить объектную авторизацию. Наоборот, `NodeResource` докблок (`:35-57`) объявляет скоуп листинга намеренным дизайном. Это **дефект**, не «ADR устарел».
**Рекомендация:** для `StorageResource`/`NodeGrantResource`/`NodeShareResource`/`ActivityResource` добавить `getEloquentQuery()`-скоуп к grant-reachable/owned set актора (по образцу `NodeResource`: пусто при `PanelActor::current() === null`) — для grant/share/activity скоупить через доступные узлы (join к node_grants актора), для storage — через владение/грант на корне; ЛИБО зарегистрировать политики этих моделей с `viewAny`, ведущим в `AccessResolver`. Плюс контрактный тест листинг-скоупа (закрывает C11).

### F-P1.10-02 — `PanelActor` берёт глобальный дефолтный guard, а не guard панели: рассинхрон субъекта с `AccessResolver` · Severity: Minor · Уверенность: medium

**Где:** `packages/filament/src/Support/PanelActor.php:28` (`Auth::user()`), `:41` (`Auth::user()` в `id()`).
**Что:** `PanelActor::current()`/`id()` резолвят актора через `Auth::user()` — пользователя **дефолтного** guard приложения (`config('auth.defaults.guard')`), а не guard, на котором аутентифицирована конкретная Filament-панель хоста (`Filament::auth()->user()`/`$panel->getAuthGuard()`). Если хост-панель настроена на отдельный guard (штатная практика Filament для админ-панелей), актор, которого видит `AccessResolver`, расходится с реально залогиненным в панель.
**Почему опасно:** При не-дефолтном guard панели типовой исход — `Auth::user()` (дефолтный web-guard) возвращает `null`, `PanelActor::current()` = `null`, все abilities false, таблицы пусты (панель нефункциональна — fail-closed, не утечка). Узкий опасный случай: если в одной сессии залогинены ОБА guard'а разными идентичностями (напр. web-user U и admin-A), `AccessResolver` оценивает гранты U, тогда как в панель вошёл A — панель действует правами не той идентичности. Требует специфичной конфигурации, потому Minor.
**Доказательство:** `PanelActor.php:26-31,38-50` — прямой `Auth::user()` без указания guard'а; ни `Filament::auth()`, ни `Filament::getCurrentPanel()->getAuthGuard()` не используются (grep по `packages/filament/src`).
**Норма, которая нарушена:** S1.6 (`findings/P0-dms-security.md`) — субъект авторизации должен быть тем же, кто аутентифицирован в данном контексте.
**Сверка с ADR:** `docs/adr/0007` — «HostRoleDriver … per-panel, identity-agnostic», guard — забота хоста; конкретный источник актора в Filament-шве ADR не фиксирует. Пробел реализации, не «ADR устарел».
**Рекомендация:** резолвить актора через guard активной панели (`Filament::auth()->user()` или `filament()->getCurrentPanel()->auth()->user()`), а не глобальный `Auth::user()`.

### F-P1.10-03 — Ресурсы панели не гейтятся на core feature-флаги: `ActivityResource` бьёт в отсутствующую таблицу при выключенной фиче `activity` · Severity: Minor · Уверенность: medium

**Где:** `packages/filament/src/VaulterPlugin.php:78-108` (`enabledResources`/`resourceEnabled` — гейт только по `vaulter-filament.resources.*`), `packages/core/src/Schema/PanelTablesBuilder.php:66-72,694-695` (таблица `activity` feature-gated).
**Что:** `VaulterPlugin` регистрирует ресурс, если включён его собственный toggle `config('vaulter-filament.resources.{key}')` (default `true`), НЕ консультируя core feature-флаги подсистем. Таблица `activity` создаётся только при включённой фиче `activity` (`createAll` пропускает выключенные сущности). Хост, отключивший фичу `activity` (или `uploads`/`document_versions`), но не тронувший дефолтный toggle ресурса, получит зарегистрированный `ActivityResource`, чей `getEloquentQuery` уйдёт в несуществующую таблицу → SQL-ошибка вместо «подсистема выключена».
**Почему опасно:** Не security-риск, а footgun встраиваемости (D13: опциональные подсистемы должны деградировать, а не падать). Цена — 500 в навигации панели при легальной конфигурации «DMS без активити-фида».
**Доказательство:** grep `feature` по `packages/filament/src` — 0 совпадений; `VaulterPlugin.php:104-108` читает только `vaulter-filament.resources.*`; `PanelTablesBuilder.php:694` «v_activity … Gated on 'activity'».
**Норма, которая нарушена:** D13 (продуктовое требование): опциональные подсистемы включаются гейтом и деградируют без краха; пересечение с P1.6 `C18` (гейт фиче-флага).
**Сверка с ADR:** `docs/adr/0009-storage-panels.md` описывает per-panel feature-set; связка «ресурс панели ⇄ feature-флаг» не специфицирована — пробел, не «ADR устарел».
**Рекомендация:** в `resourceEnabled` добавить AND-условие на соответствующий core feature-флаг (`Config::featureEnabled('activity')` и т.п.), чтобы ресурс не регистрировался, когда его подсистема выключена.

- **`AccessResolver`-алгоритм** — вне item'а (P1.1); опирался на его вердикты и на P1.9 `C3`/`C4`.
