## 2. Находки

### F-P1.4-01 — Гонка offset без блокировки → тихая порча файла · Severity: Blocker · Уверенность: high

**Где:** `packages/drive/src/Uploads/TusUploadHandler.php:80-108`, `packages/drive/src/Uploads/StagedUpload.php:93-115`, `packages/drive/src/Uploads/Repositories/UploadSessionStoreRepository.php:52-60`
**Что:** tus PATCH выполняет read-modify-write смещения (`offset()` → `staged->append` → `advanceReceived`) БЕЗ строкового лока (`SELECT … FOR UPDATE`) и вне транзакции. Два конкурентных PATCH, прочитавших один и тот же серверный offset до записи друг друга, оба проходят проверку `offset === serverOffset` и оба аппендят на этот offset; `StagedUpload::append` берёт `head = substr(existing, 0, offset)` и перезаписывает файл — байты первого PATCH теряются, `received_bytes` всё равно продвигается.
**Почему опасно:** тихая порча/потеря данных. Итоговый файл содержит не те байты, что загрузил клиент, но `BlobStore.commit` пересчитывает sha256 по УЖЕ испорченным байтам — интегрити-алярма нет, коммит проходит как успешный. Достижимо ретрай-штормом клиента или параллельными загрузчиками (U2.2 прямо требует row-lock).
**Доказательство:** repro `plans/AUDIT-VLT/artifacts/repro/P1.4/UploadsAuditReproTest.php` (тест C4):
```
[C4] staged content after two offset-0 patches = 'BBBBBBBBBB' (len 10)
[C4] received_bytes = 10
```
Байты `A` полностью потеряны, на диске только `B`, offset продвинут как будто всё в порядке.
**Норма:** U2.1/U2.2 (`findings/P0-upload-hardening.md`): «строка сессии читается под row-lock перед read-modify-write»; Code Guidance P1.4: «отсутствие блокировки при мутации offset = Blocker».
**Сверка с ADR:** отдельного ADR по resumable-загрузкам нет (`docs/adr/` — 0001–0014, upload/tus не покрыт) → дефект, не «ADR устарел».
**Рекомендация:** обернуть весь PATCH-цикл в транзакцию с `lockForUpdate` по строке `v_upload_sessions` (перечитать `received_bytes` под локом, отвергнуть несовпадение offset, аппендить, продвинуть — атомарно). `StagedUpload::append` должен писать по абсолютному offset (stream seek/`fseek`), а не читать весь файл в память.

### F-P1.4-02 — offset-mismatch отдаёт 302/422 вместо tus 409 · Severity: Major · Уверенность: high

**Где:** `packages/drive/src/Uploads/TusUploadHandler.php:90-96` (+ `patch` не мапит исключение), `packages/drive/src/Uploads/Http/Controllers/TusUploadController.php:132-165`
**Что:** при несовпадении `Upload-Offset` хендлер бросает `ValidationException`. Контроллер её не перехватывает и не мапит в 409 — Laravel рендерит её как 302-редирект (не-JSON запрос) либо 422 (JSON). Норма tus 1.0.0 требует ровно 409 Conflict, по которому клиент перечитывает HEAD и ресинхронизируется. Тот же путь — единственная защита от гонки C4, и его сигнализация сломана. Также C6: любой `offset < server` (валидный повтор чанка) отвергается без проверки совпадения диапазона.
**Почему опасно:** реальные tus-клиенты не восстанавливают загрузку — при рассинхроне получают 302 на web-роут вместо протокольного 409; resumable-семантика фактически не работает при любом рассогласовании.
**Доказательство:** repro `[C3]`: `offset-mismatch PATCH status = 302`.
**Норма:** U1.3/U2.4 (`findings/P0-upload-hardening.md`): несовпадение offset → 409; U2.3 (идемпотентный повтор по совпадению диапазона).
**Сверка с ADR:** ADR по tus нет → дефект.
**Рекомендация:** в контроллере (или выделенном tus-исключении) мапить рассинхрон offset в HTTP 409 с актуальным `Upload-Offset`; для `offset < received` при совпадении уже записанного диапазона возвращать 204 (идемпотентный повтор).

### F-P1.4-03 — S3 complete коммитит усечённый файл без сверки total bytes · Severity: Major · Уверенность: high

**Где:** `packages/drive/src/Uploads/S3MultipartHandler.php:132-153`, `packages/drive/src/Uploads/Http/Controllers/S3MultipartController.php:81-92`
**Что:** `complete()` сшивает любые записанные части и пишет их в staged temp, не проверяя `received_bytes == total_size_bytes`. Контроллер сразу `markAssembled`→`commit`. Клиент, загрузивший одну часть из объявленного большого файла, получает закоммиченный усечённый файл; `expected_sha256` тоже не сверяется. (В tus-пути гейт есть — `reachedTotal` использует `received >= total`; асимметрия.)
**Почему опасно:** нарушение целостности (U6.7/U5.4): в хранилище попадает файл, не соответствующий заявленному размеру/содержимому, без какого-либо сигнала.
**Доказательство:** repro `[C22]`: `complete status = 201 committed size = 10` при `total_size_bytes=1000`.
**Норма:** U6.7/U5.4 (`findings/P0-upload-hardening.md`): complete только при согласии по total bytes и целостности.
**Сверка с ADR:** ADR по multipart нет → дефект.
**Рекомендация:** в `complete()` (или контроллере) отвергать завершение при `total_size_bytes !== null && assembledSize !== total_size_bytes`; при наличии `expected_sha256` — сверять с серверным sha256 собранного объекта до commit.

### F-P1.4-04 — Нет пер-чанк лимита; append читает весь staged-файл в память · Severity: Major · Уверенность: high

**Где:** `packages/drive/src/Uploads/StagedUpload.php:93-115`, `packages/drive/src/Uploads/TusUploadHandler.php:98-102`
**Что:** потолок применяется только к суммарному `received_bytes` (≤ `max_bytes`, дефолт 5 GiB); лимита на размер одного PATCH-чанка нет. Хуже: `append` на КАЖДЫЙ PATCH делает `$disk->get($key)` (полное чтение накопленного файла в строку PHP), конкатенирует и перезаписывает — O(n) память и I/O на чанк. Для многогигабайтной resumable-загрузки финальные чанки пытаются загрузить весь файл в память.
**Почему опасно:** DoS по памяти/CPU (ASVS 12.1.1/12.7.1): единичный крупный PATCH или длинная последовательность чанков исчерпывают `memory_limit`; амплификация мелкими чанками (U3.4) не ограничена.
**Доказательство:** `StagedUpload.php:100-112` — `$existing = (string) $disk->get($key); … $bytes = $head.$appended; $disk->put($key, $bytes);` (полный RMW в памяти).
**Норма:** U3.3 (потолок на один PATCH), U3.4 (chunk-budget), T5/ASVS 12.7.1 (освобождение ресурсов).
**Сверка с ADR:** нет ADR → дефект.
**Рекомендация:** ввести `uploads.max_chunk_bytes` и отвергать PATCH сверх него; писать staged temp потоково по абсолютному offset (append-режим/`fseek`) вместо read-modify-write всего файла.

### F-P1.4-05 — PATCH принимает неверный Content-Type вместо 415 · Severity: Minor · Уверенность: high

**Где:** `packages/drive/src/Uploads/Http/Controllers/TusUploadController.php:132-145`
**Что:** `patch()` не проверяет `Content-Type: application/offset+octet-stream`; чанк с `text/plain` принимается и даёт 204.
**Почему опасно:** отклонение от tus 1.0.0 (U1.2); ослабляет контракт и может пропустить неверно сформированные клиентские запросы.
**Доказательство:** repro `[C2]`: `wrong-content-type PATCH status = 204`.
**Норма:** U1.2 (`findings/P0-upload-hardening.md`).
**Сверка с ADR:** нет ADR → дефект.
**Рекомендация:** проверять Content-Type в начале `patch()`, при несовпадении — 415.

### F-P1.4-07 — Нет OPTIONS-дискавери и необъявленное отсутствие расширений · Severity: Minor · Уверенность: high

**Где:** `packages/drive/routes/drive.php:62-71`, `packages/core/config/vaulter.php` (секция `uploads`)
**Что:** OPTIONS-эндпоинт для resumable-uploads не зарегистрирован → `Tus-Version`/`Tus-Extension`/`Tus-Max-Size` не анонсируются. checksum-расширение не реализовано, и его отсутствие не задекларировано (нет `Tus-Extension`). **Почему опасно:** клиент не может обнаружить возможности сервера и лимиты; необъявленное отсутствие расширений (U1.5/U1.6).

### F-P1.4-11 — Нет валидации mime/magic-bytes собранного объекта · Severity: Minor · Уверенность: medium

**Где:** `packages/drive/src/Uploads/Actions/CommitUploadAction.php:96-120`, `packages/drive/src/Actions/UploadFileAction.php:97-138`
**Что:** resumable-путь коммитит собранный объект без проверки соответствия расширения/заявленного mime реальному содержимому (magic-bytes) и без применения `drive.allowed_mime` (который есть у one-shot `UploadFileRequest`). `mime_type` берётся как заявлен клиентом.
**Почему опасно:** несоответствие типа содержимому (ASVS 12.2.1/U5.5); загрузка исполняемого/опасного контента под безобидным mime. Для DMS — существенная поверхность (смягчение — скачивание всегда через PHP, D15).
**Норма:** U5.5, T5/ASVS 12.2.1.
**Сверка с ADR:** нет ADR → дефект.
**Рекомендация:** на собранном объекте валидировать magic-bytes и применять тот же `allowed_mime`, что и в one-shot пути; хук под AV-скан до публикации.

### F-P1.4-12 — Право на сессию не привязано к владельцу (IDOR-by-ability) · Severity: Minor · Уверенность: medium

**Где:** `packages/drive/src/Uploads/Http/Controllers/TusUploadController.php:237-253`, `packages/drive/src/Uploads/Http/Controllers/S3MultipartController.php:105-121`
**Что:** `authorizeSession` проверяет право `Create`/`Edit` на целевую папку/узел, но НЕ сверяет `created_by` сессии с актором. Под реальным драйвером любой актор с правом Create в той же папке (или Edit на том же узле), узнав `upload_id`, может продвигать/завершать/прерывать чужую сессию.
**Почему опасно:** нарушение владения сессией (S3.1). Смягчено: `upload_id` — серверный UUID, отдаётся только создателю (неугадываемо), и требуется право на ту же папку.
**Доказательство:** авторизация на глаголах работает (repro `[C23]` = 403 без гранта), но проверки владельца в коде нет.
**Норма:** S3.1 (IDOR), U6.4 (серверная запись связывает user с сессией).
**Сверка с ADR:** нет ADR → дефект.
**Рекомендация:** дополнительно сверять `session.created_by` с текущим актором (или tenant) на HEAD/PATCH/DELETE/parts/complete.

### F-P1.4-13 — Жизненный цикл сессии не пишется в activity · Severity: Minor · Уверенность: medium

**Где:** `packages/drive/src/Uploads/UploadSessionManager.php` (initiate/abort/expire), `packages/drive/src/Uploads/Http/Controllers/*`
**Что:** финальный commit шлёт `FileUploaded`/`NodeVersionCommitted` (попадают в activity), но события create/abort/expire сессии не логируются (нет IP/tenant/key по create/abort).
**Почему опасно:** пробел наблюдаемости (U7.1): abort/expire и создание сессий не аудируются.
**Норма:** U7.1.
**Сверка с ADR:** нет ADR → дефект.
**Рекомендация:** эмитить activity-события на initiate/abort/expire (актор, tenant, storage, upload_id).

## 3. Не проверено / ограничения

- **Реальный S3-диск не поднимался:** presign/multipart проверены только на дефолтном ПРОКСИРУЮЩЕМ хендлере (`S3MultipartHandler` пишет байты через PHP). C19/C20 в части настоящих presigned-URL — вне прогона; при подмене хендлера хостом нормы U6.1–U6.3 надо перепроверять отдельно.
- **Конкурентность C4** смоделирована детерминированно (два `append` с одним захваченным offset), а не настоящими параллельными HTTP-процессами: SQLite `:memory:` не моделирует реальные row-lock/FOR UPDATE. Отсутствие лока доказано чтением кода + repro-порчей; на Postgres поведение под нагрузкой не воспроизводилось.
- **`drive.allowed_mime` / magic-bytes:** проверено отсутствие вызова в resumable-пути; глубину валидации one-shot пути (`UploadFileRequest`) как эталон не аудировал (вне Scope P1.4).
- **P1.5 (CAS-коммит после сборки), P1.11 (контентная безопасность), P1.12 (remanence)** пересекаются с F-P1.4-03/10/11 — окончательная квалификация утечек/контент-валидации там.
