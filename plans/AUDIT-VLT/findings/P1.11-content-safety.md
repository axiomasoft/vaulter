## 2. Находки

### F-P1.11-01 — Серверный TipTap-рендер не фильтрует схему URL в `href` (stored XSS) · Severity: Blocker · Уверенность: high

**Где:** `packages/documents/src/Support/TipTapRenderer.php:93` (HTML link-mark), :175 (Markdown link-mark); корень — отсутствие валидации в `packages/core/src/ValueObjects/Documents/TipTapContent.php:28-33`
**Что:** При рендере link-mark в HTML значение `href` только htmlspecialchars-экранируется, но схема URL не проверяется по allow-list. `javascript:`, `data:`, `vbscript:` проходят в атрибут `href` дословно.
**Почему опасно:** Актор с правом Edit сохраняет документ со ссылкой `href:"javascript:alert(1)"`; другой пользователь (или админ) экспортирует узел в HTML (`DocumentNodeController::export` → `HtmlExporter`) и хост-приложение показывает результат → выполнение произвольного JS в сессии жертвы (stored DOM-XSS). Клиентский рендер защищён только если хост подключил официальный `@tiptap/extension-link` ≥2.10.4; серверный путь беззащитен всегда.
**Доказательство:** repro `plans/AUDIT-VLT/artifacts/repro/P1.11/ContentSafetyReproTest.php` (C7), фактический вывод:
```
[C7] HTML output: <p><a href="javascript:alert(1)">click me</a></p>
[C9] uri=vbscript:msgbox(1) -> <p><a href="vbscript:msgbox(1)">x</a></p>
```
`/usr/bin/php8.4 vendor/bin/pest plans/AUDIT-VLT/artifacts/repro/P1.11` → 5 passed.
**Норма, которая нарушена:** G2.2 (allow-list схем: js/data/vbscript отвергаются), G2.4 (санитизация на исходящем HTML), G2.3 (ProseMirror не санирует значения атрибутов).
**Сверка с ADR:** `docs/adr/0004-content-format.md` — решение о TipTap JSON как каноне не касается санитизации схем; сознательного отказа от allow-list в ADR нет → дефект, не «ADR устарел».
**Рекомендация:** ввести серверный allow-list схем (`http`,`https`,`mailto`,`tel`) в `TipTapRenderer` перед эмиссией `href` (для HTML и Markdown), отвергая/выкидывая прочие; продублировать проверку на входе в `TipTapContent`.

### F-P1.11-02 — `TipTapContent` валидирует только корневой узел, не типы узлов и значения атрибутов · Severity: Major · Уверенность: high

**Где:** `packages/core/src/ValueObjects/Documents/TipTapContent.php:26-33`
**Что:** `fromArray()` проверяет лишь `type === 'doc'` и не валидирует ни допустимость типов узлов/марок, ни значения атрибутов (`href`, `src`, `style`, произвольные ключи). Любая структура с корнем `doc` принимается как валидный контент.
**Почему опасно:** Отсутствие входного контроля — enabling-слой для F-P1.11-01: недоверенные значения атрибутов доходят до рендера. Также позволяет хранить произвольные узлы/атрибуты, которые в будущих рендерерах/клиентах станут вектором.
**Доказательство:**
```php
public static function fromArray(array $doc): self
{
    if (($doc['type'] ?? null) !== 'doc') {
        throw InvalidTipTapContentException::missingDocNode();
    }
    return new self($doc);
}
```
**Норма, которая нарушена:** G2.1 (JSON не безопаснее HTML, фреймворк не граница безопасности), G2.3 (значения разрешённых атрибутов не санируются).
**Сверка с ADR:** ADR-0004 говорит, что VO «validates the root node … and enforces a size limit» — валидация схемы узлов ADR-ом не обещана, но и не запрещена → дефект недостающего контроля.
**Рекомендация:** валидировать белый список типов узлов/марок и значения чувствительных атрибутов при конструировании `TipTapContent` (или в выделенном санитайзере), а не только структуру JSON.

### F-P1.11-03 — Download- и share-пути не ставят `X-Content-Type-Options: nosniff` · Severity: Major · Уверенность: high

**Где:** `packages/drive/src/Http/Controllers/DownloadController.php:144-147`, `packages/core/src/Http/Controllers/Sharing/PublicShareController.php:226-229`
**Что:** Ответы со стримингом пользовательских байтов задают только `Content-Type` и `Content-Length`; заголовок `X-Content-Type-Options: nosniff` не выставляется ни в одном download-пути.
**Почему опасно:** Без `nosniff` браузер MIME-снифает polyglot-файл (валидный PDF + валидный HTML/JS) и может исполнить его как HTML. Усугубляется тем, что отдаваемый `Content-Type` в tus-пути берётся из клиентской метадаты (C14), а S3-redirect-путь (C12) вообще не форсит ни attachment, ни nosniff.
**Доказательство:** repro C11 (`ContentSafetyReproTest.php`) читает оба контроллера:
```
[C11] DownloadController.php sets nosniff: false
[C11] PublicShareController.php sets nosniff: false
```
**Норма, которая нарушена:** G3.1 (`nosniff` обязателен на всех отдачах пользовательского контента); G3.2 (изоляция inline-контента).
**Сверка с ADR:** нет ADR, легализующего отсутствие `nosniff`; D15 фиксирует «download всегда через PHP», но redirect-на-`temporaryUrl` в коде это нарушает и заголовки не контролирует → дефект.
**Рекомендация:** добавить `X-Content-Type-Options: nosniff` во все ответы обоих контроллеров; на S3-redirect-пути форсить `ResponseContentDisposition=attachment` и `ResponseContentType` в подписи, либо (по D15) убрать redirect-режим.

### F-P1.11-04 — Markdown-экспорт протаскивает сырой HTML и `javascript:`-ссылки · Severity: Minor · Уверенность: high

**Где:** `packages/documents/src/Support/TipTapRenderer.php:165-181` (`markdownText`), :148-160 (`markdownInline`)
**Что:** Текстовые узлы и `href` в Markdown-выводе не экранируются; сырой `<script>` и `javascript:`-URL уходят в результат как есть.
**Почему опасно:** Markdown допускает inline-HTML; потребитель, рендерящий экспорт без санитизации, получает stored XSS. Цена — скрытая передача активного контента через «безопасный» текстовый формат.
**Доказательство:** repro C9b:
```
[C9b] MD output: [<script>alert(1)</script>](javascript:alert(1))
```
**Норма, которая нарушена:** G2.4 (санитизация на исходящем рендере), G2.2 (схемы URL).
**Сверка с ADR:** ADR-0004 не адресует Markdown-экспорт → дефект.
**Рекомендация:** экранировать спецсимволы Markdown/HTML в тексте и применять тот же allow-list схем к `href` в Markdown-ветке; документировать, что вывод требует санитизации у потребителя.

### F-P1.11-05 — `max_document_size_kb` не применяется при сохранении документа · Severity: Minor · Уверенность: high

**Где:** `packages/core/src/ValueObjects/Documents/TipTapContent.php:63-72` (`ensureWithin`, не вызывается в prod), `packages/documents/src/Http/Requests/UpdateDocumentContentRequest.php:34-45` (правила без лимита размера), `packages/core/config/vaulter.php:583`
**Что:** Метод `ensureWithin()` и конфиг `max_document_size_kb=5120` существуют, но `ensureWithin` не вызывается ни в create-, ни в update-пути (единственные callers — юнит-тесты). Валидация запроса капит размер только косвенно (нет `max`).
**Почему опасно:** Контент документа неограничен на сохранении → DoS/раздувание хранилища и версий; заявленный лимит де-факто отсутствует.
**Доказательство:** `grep -rn "ensureWithin" packages --include=*.php` → определение + `packages/documents/tests/Unit/TipTapContentTest.php:23,29`; в `src` вызовов нет.
**Норма, которая нарушена:** ADR-0004 («enforces a size limit»); U3-класс лимитов (границы размера обязаны быть в коде).
**Сверка с ADR:** ADR-0004 прямо обещает применение лимита → расхождение кода с сознательным решением → дефект реализации ADR (не «ADR устарел»).
**Рекомендация:** вызывать `->ensureWithin(Config::maxDocumentSizeKb())` в `UpdateDocumentContentAction`/`CreateDocumentNodeAction` (или в `content()` реквеста) до персистенса.

## 3. Не проверено / ограничения

- Клиентский (Vue) рендер TipTap-JSON: анализ ограничен статикой lock-файла (C8). Runtime-поведение фронтенда и наличие/конфиг `Link`-расширения на клиенте не прогонялись (нет установленных `node_modules` в `packages/vue`).
- S3-redirect-путь (`temporaryUrl`) не прогонялся против реального бакета — вывод о неконтролируемых заголовках сделан по коду; глубина — P1.3 `C16`/D15.
- `Upload-Metadata`→`mime_type` доверие (C14) пересекается с P1.4 `C18`; здесь зафиксировано только следствие для download-`Content-Type`, полная оценка приёма — в P1.4.
- Антивирус/CDR (C16) в пакете не заявлен — рекомендация в бэклог P5.2, не находка.
- DOCX/OOXML→TipTap импорт объявлен как «registerable pipe, M4b+» (`TipTapHandler.php:52`) и в коде отсутствует — XXE/zip-бомба-поверхность импорта появится только при его реализации.
