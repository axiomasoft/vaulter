## 2. Находки

### F-P4.2-01 — Обход предков на пути авторизации не ограничен `withMaxDepth` · Severity: Major · Уверенность: high

**Где:** `packages/core/src/Access/AccessResolver.php:356-375` (`ancestorChain()`, вызов `$node->ancestors()->get()` на `:361`); также `packages/core/src/Repositories/Drive/NodeReadRepository.php:143-146` (`ancestors()`) и `:154-163` (`breadcrumb()`, `ancestorsAndSelf()`)
**Что:** `AccessResolver::ancestorChain()` — вызывается на КАЖДОЙ проверке `can()`/`effectiveGrants()`, то есть на каждом authorization-запросе, — тянет `$node->ancestors()->get()` без `withMaxDepth()`/`tree($maxDepth)`. Recursive CTE обходит весь путь до корня storage независимо от глубины дерева.
**Почему опасно:** T4 (`P0.2-rag-supplement.md`): без потолка PostgreSQL материализует полный путь на каждый вызов (стоимость растёт линейно с глубиной), а SQLite ограничивает рекурсию `SQLITE_MAX_RECURSION_DEPTH=1000` — глубокое дерево (1000+ уровней, в т.ч. случайно созданное хостом без валидации глубины при создании папок) роняет запрос ошибкой вместо деградации. Это происходит на КАЖДОЙ авторизации, а не на редком фоновом пути — согласно Code Guidance item'а («перф-регресс на пути авторизации — Major»).
**Доказательство:**
```php
// packages/core/src/Access/AccessResolver.php:356-375
private function ancestorChain(Node $node): array
{
    $chain = [$node];
    $ancestors = $node->ancestors()->get();   // ← без withMaxDepth
    foreach ($ancestors as $ancestor) {
        if ($ancestor->storage_id !== $node->storage_id) { break; }
        $chain[] = $ancestor;
    }
    return $chain;
}
```
Repro (окружение, см. §3): `plans/AUDIT-VLT/artifacts/repro/P4.2/NPlusOneReproTest.php` тест `C1: the AccessResolver ancestor walk has no withMaxDepth cap…` строит цепочку из 30 уровней и ищет депф-предикат в SQL рекурсивного CTE — не запущен (окружение сломано, см. §3), вердикт вынесен по чтению.
**Норма, которая нарушена:** T4 (`P0.2-rag-supplement.md`: «Без `withMaxDepth()`/`tree($maxDepth)` пакет НЕ ставит потолок… цикл в данных → бесконечная/раздутая рекурсия по движку»).
**Сверка с ADR:** `docs/adr/0005-unified-node-tree.md` раздел Decision, второй пункт: «Traversal (`descendants()`/`ancestors()`) uses staudenmeir's recursive relationships … **with `withMaxDepth()` for shallow loads**». ADR явно требует потолок на обходе — и на `descendants()`-стороне код это выполняет (`NodeReadRepository::descendants()/subtree()/descendantIdsOf()`, все три бьют `withMaxDepth(DEFAULT_MAX_DEPTH=64)`). На `ancestors()`-стороне (и в `AccessResolver`, и в `NodeReadRepository::ancestors()/breadcrumb()`) потолка нет — это расхождение кода с осознанным решением ADR, классифицируется как **дефект**, а не «ADR устарел» (ADR формулирует норму симметрично для обеих сторон обхода, код её выполняет только для половины).
**Рекомендация:** обернуть `$node->ancestors()->get()` в `ancestorChain()` (и `NodeReadRepository::ancestors()`/`breadcrumb()`) тем же паттерном `Config::nodeModel()::withMaxDepth($cap, …)`, используя `NodeReadRepository::DEFAULT_MAX_DEPTH` как разумный дефолт.

### F-P4.2-02 — Детект циклов выключен на чтении; митигирован только на записи через Action · Severity: Minor · Уверенность: high

**Где:** `packages/core/src/Models/Drive/Node.php:57-161` (отсутствие переопределения `enableCycleDetection()`); митигация — `packages/drive/src/Actions/MoveNodeAction.php:85-100`
**Что:** `Node` не переопределяет `enableCycleDetection()`, трейт-дефолт — `false` (`HasCycleDetection.php:14-20`). Единственная защита от цикла в `parent_id` — проверка в `MoveNodeAction::assertNoCycle()`, которая выполняется только при перемещении узла через Action.
**Почему опасно:** цикл, попавший в данные мимо `MoveNodeAction` (прямой SQL, сидер, легаси-импорт, будущий bulk-write путь), не детектируется ни на записи, ни на чтении — обход предков/потомков по такому узлу уходит в раздутую/бесконечную рекурсию (T4).
**Доказательство:** grep по `packages/*/src` на `enableCycleDetection` не находит переопределений ни в одной из моделей `Node` (core/drive/media/documents/filament — все используют один и тот же класс через `Config::nodeModel()`).
**Норма, которая нарушена:** T4 (`P0.2-rag-supplement.md`: «Cycle detection выключен по умолчанию… Без него цикл в данных → бесконечная/раздутая рекурсия по движку»).
**Сверка с ADR:** ADR-0005 не упоминает cycle detection явно (только `withMaxDepth`) — не находка класса «ADR устарел», а пробел нормы, которую ADR не покрывает.
**Рекомендация:** переопределить `enableCycleDetection(): true` на `Node` (или задокументировать письменно, что единственная гарантия — Action-путь, и запретить прямую запись `parent_id` мимо Action arch-тестом).

### F-P4.2-03 — N+1 на каждой странице листинга узлов через `AccessResolver::abilitiesFor` · Severity: Major · Уверенность: high

**Где:** `packages/drive/src/Http/Controllers/NodeController.php:81-94` (`index()`) → `packages/core/src/Http/Resources/Drive/NodeResource.php:138-148` (`abilities()`) → `packages/core/src/Access/AccessResolver.php:73-115` (`effectiveGrants()`), `:404-425` (`storageOf()`), `:356-375` (`ancestorChain()`, см. F-P4.2-01)
**Что:** `NodeController::index()` пагинирует детей БЕЗ `with([...])`; `NodeResource::toArray()` вызывает `abilities()` для каждого узла страницы; `abilities()` дергает `AccessResolver` заново на каждый узел. Внутри `AccessResolver::effectiveGrants()` на узел без предзагруженной `storage`-связи выполняется отдельный `StorageReadRepository::find()` (`packages/core/src/Repositories/Drive/StorageReadRepository.php:19-23` — без кеша/памоизации), плюс отдельный `ancestorChain()`-запрос (F-P4.2-01), плюс `GrantReadRepository::forSubjectsOnNodes()` — минимум 3 SQL-запроса НА УЗЕЛ страницы, при том что все узлы страницы принадлежат ОДНОМУ storage (значит `storage`-запрос идентичен N раз).
**Почему опасно:** число запросов масштабируется линейно с размером страницы (до 200 по `perPage()`-капу `NodeController.php:381-386`) — на малых фикстурах регресс незаметен, на реальных папках с десятками/сотнями файлов — заметная latency-деградация листинга, самого частого пути в файловом менеджере.
**Доказательство:**
```php
// packages/core/src/Http/Resources/Drive/NodeResource.php:138-148
private function abilities(Request $request, Node $node): array
{
    $user = $request->user();
    $actor = $user instanceof Authorizable ? $user : null;
    return NodeAbilities::for(actor: $actor, node: $node, resolver: app(AccessResolver::class))->toArray();
}
```
Repro (окружение сломано, см. §3): `plans/AUDIT-VLT/artifacts/repro/P4.2/NPlusOneReproTest.php` тест `C4: resolving abilities for N sibling nodes issues O(N) queries, not O(1)` — не запущен, вердикт по чтению кода: `storageOf()` не кеширует между вызовами в рамках запроса (нет memo/статик-кеша на инстансе `AccessResolver` или `StorageReadRepository`), поэтому N узлов на одной странице ⇒ N вызовов `StorageReadRepository::find()`, N вызовов `ancestorChain()`, N вызовов `forSubjectsOnNodes()`.
**Норма, которая нарушена:** Code Guidance item'а: «Число запросов доказывается `getQueryLog()`/`DB::listen` или чтением `with([…])`; отсутствие eager-load в листинге + resolver-per-node = Major».
**Сверка с ADR:** не затрагивается ADR-0005 (перф листинга — вне предмета ADR о структуре дерева).
**Рекомендация:** минимум — замемоизировать `storage` per-request (напр. кеш в `AccessResolver`/`StorageReadRepository` по `storage_id`, раз все узлы страницы принадлежат одному storage); дальше — рассмотреть батч-резолюцию abilities для страницы разом (один проход по грантам всех узлов страницы + их общих предков вместо N независимых обходов).

### F-P4.2-04 — `NodeController::shared()` — offset-пагинация на растущей кросс-storage ленте · Severity: Minor · Уверенность: high

**Где:** `packages/drive/src/Http/Controllers/NodeController.php:109-137`
**Что:** `shared()` — лента «расшарено со мной», по своей природе неограниченно растущая (§2.6) — построена на `LengthAwarePaginator` (offset: `page`/`total`), а не `cursorPaginate()`.
**Почему опасно:** offset-пагинация на растущей ленте даёт классический drift (дубли/пропуски при конкурентных вставках грантов между запросами страниц) и деградирует на глубоких страницах (норма keyset-пагинации фидов, скилл `php:cursor-pagination-design`), которую P4.2 C6 прямо называет находкой для «узлы, shared».
**Доказательство:**
```php
// packages/drive/src/Http/Controllers/NodeController.php:121-136
$shared = $this->nodes->sharedWith($actor);
...
$paginated = new LengthAwarePaginator(
    items: $shared->forPage(page: $page, perPage: $perPage)->values(),
    total: $shared->count(),
    ...
);
```
**Норма, которая нарушена:** C6 item'а: «для бесконечных лент (activity, узлы, shared) offset даёт drift… offset на растущей ленте = находка Minor».
**Сверка с ADR:** не покрыто ADR; докблок метода (`:103-108`) объясняет ОСОЗНАННЫЙ компромисс (эксакт-резолюция кросс-storage набора не может честно бэкать cursor), но это компромисс архитектуры/реализации, не зафиксированное ADR-решение — остаётся находкой, severity понижена до Minor именно из-за документированной, обоснованной причины (эксакт re-resolve через `AccessResolver::filterSharedWith`, `packages/core/src/Access/AccessResolver.php:162-173`, не может отдавать честный курсор).
**Рекомендация:** зафиксировать offset-природу этой ленты явно в API-контракте (не как «cursor-совместимый» эндпоинт), либо исследовать материализованный candidate-индекс, который позволил бы курсорную пагинацию без потери эксакт-резолюции (вне минимального фикса).

### F-P4.2-05 — Нестабильные (неуникальные) ключи курсорной пагинации в трёх фидах · Severity: Minor · Уверенность: high

**Где:** `packages/core/src/Repositories/Drive/NodeReadRepository.php:171-177` (`search()`), `:186-191` (`trashed()`); `packages/core/src/Repositories/Access/GrantReadRepository.php:59-65` (`forNode()`)
**Что:** три `Builder`, отданных под `->cursorPaginate()` в контроллерах (`NodeController::search/trashed`, `GrantController::index`), сортируют по единственной НЕуникальной колонке без тай-брейкера: `search()` — `orderBy('name')` (уникальность `name` гарантирована только per-parent, `search()` не скоупит по `parent_id`, значит совпадения между узлами разных папок обычны); `trashed()` — `orderByDesc('trashed_at')` (несколько узлов, оттрешенных одной операцией/запросом, получают идентичный timestamp); `forNode()` — `orderByDesc('created_at')` (гранты, созданные в одной транзакции/бате, коллизируют).
**Почему опасно:** норма keyset/cursor-пагинации (скилл `php:cursor-pagination-design`): курсор-ключ обязан быть стабильным И уникальным — иначе Laravel `cursorPaginate()` на границе страницы с повторяющимся значением ключа не гарантирует, какие из "равных" строк попали на текущую страницу, а какие — на следующую: возможны пропуски и дубли на границе страницы.
**Доказательство:**
```php
// packages/core/src/Repositories/Drive/NodeReadRepository.php:171-177
public function search(Storage $storage, string $term): Builder
{
    return $this->query()->treeOf($storage->id)->whereNull('trashed_at')
        ->whereRaw('lower(name) like ?', ['%'.mb_strtolower($term).'%'])
        ->orderBy('name');               // ← нет тай-брейкера, не уникален глобально
}
```
Контрпример из того же кодового пути, показывающий, что паттерн «уникальный тай-брейкер» пакету известен и применяется:
```php
// packages/core/src/Models/Activity/Activity.php:71-73
public function scopeNewestFirst(Builder $query): Builder
{
    return $query->orderByDesc('created_at')->orderByDesc('id');   // ← id как тай-брейкер
}
```
**Норма, которая нарушена:** C7 item'а: «курсор-ключ сортировки — не-nullable уникальная колонка (иначе пропуски/дубли при ties); …неуникальный курсор-ключ = находка Minor».
**Сверка с ADR:** не покрыто ADR-0005 (пагинация вне предмета ADR).
**Рекомендация:** добавить вторичный `orderBy` по первичному ключу (`->orderBy('name')->orderBy('id')` в `search()`; `->orderByDesc('trashed_at')->orderByDesc('id')` в `trashed()`; `->orderByDesc('created_at')->orderByDesc('id')` в `GrantReadRepository::forNode()`) — тот же паттерн, что уже применён в `Activity::scopeNewestFirst()`.

- **Фактическое число SQL-запросов на странице листинга (F-P4.2-03) не измерено `getQueryLog()`** — вывод сделан из чтения кода (`storageOf()`, `ancestorChain()`, `GrantReadRepository::forSubjectsOnNodes()` — ни одна не кеширует между вызовами в рамках запроса, значит N узлов ⇒ ≥3N запросов), уверенность `high`, но без фактического числа из прогона.
- **`NodeResource::handler()` (`packages/core/src/Http/Resources/Drive/NodeResource.php:122-129`)** резолвит `NodeHandlerResolver::describe($node)` для каждого leaf-узла на листинге — потенциальный дополнительный источник N+1 (доступ к `file`/`currentVersion` relations внутри `documents`-пакета). Вне Scope Included этого item'а (`NodeHandlerResolver` не в списке Required Reads/Scope) — не проверено, флагуется как вход для будущего аудита `packages/documents`.
- **Постгрес-специфичный порог `max_stack_depth`/`statement_timeout` для F-P4.2-01/02 не измерен** — норма из T4 (RAG), не воспроизведена локальным прогоном (SQLite тестовое окружение и так недоступно, см. выше).
