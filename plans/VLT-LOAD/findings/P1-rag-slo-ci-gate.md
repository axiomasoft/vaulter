## RAG-6 — Можно ли делать абсолютный latency-порог CI-гейтом на shared-раннерах?

**Вопрос:** SLO решено делать машинно-проверяемыми (CI-гейт на PR). В репо vaulter — только
GitHub-hosted `ubuntu-latest` (26 вхождений `runs-on` в `.github/workflows/`, self-hosted нет).
Выдержит ли абсолютный порог `p95 < X ms` на таком раннере?

**Вывод (прямо меняет дизайн):** **нет — абсолютные латентные пороги на шумных shared-раннерах
гейтом не делают.** Дословно из выдачи: «You generally should not gate on absolute latencies from
noisy shared GitHub Actions runners; instead, gate on relative-to-baseline metrics computed in a
controlled environment». Рекомендованная в 2026 практика — расслоение:

| Что гейтим | Как | Почему |
|:--|:--|:--|
| error-rate, checks-rate, throughput при фикс. конкуренции | абсолютный порог, блокирующий | шумоустойчиво: не зависит от такта CPU раннера |
| p95/p99 латентности | **относительная регрессия к baseline** (`p95(current) ≤ p95(baseline)·1.15`), baseline — версионированный артефакт | единственный способ поймать регрессию на шумном железе |
| p95/p99 — абсолютный «широкий guardrail» | порог **120–150 %** от целевого, не «в притык» | ловит катастрофу, не флапает на шуме |

Дополнительно:
- **Baseline — версионированный артефакт**, привязанный к `commit SHA` / `profile name` /
  **environment fingerprint** (cpu/mem-лимиты, датасет, версии) / набору метрик. Сравнение PR-прогона
  с baseline — шаг вне k6 (PromQL/скрипт по `summary.json`).
- **Шум**: считать **coefficient of variation** CV = σ/μ по ключевой метрике. При высоком CV
  одиночный прогон p95 недостоверен. Практика — **медиана из N=3** прогонов (компромисс между
  устойчивостью и временем CI); при CV < 5–10 % по дням достаточно одного прогона.
- **SUT vs генератор.** Главный источник дисперсии — не k6-процесс, а **где крутится система под
  тестом**. Если SUT в контролируемом окружении, а раннер лишь генерирует нагрузку — шум раннера
  бьёт по ровности offered load, а не по планировщику SUT. **У vaulter SUT и генератор — на одном
  GH-раннере** (docker-стенд), т.е. эта смягчающая развилка НЕ работает: значит либо dedicated/
  self-hosted раннер, либо latency-гейт остаётся relative/advisory.
- **PR vs nightly:** на PR — короткий smoke-perf (1–3 мин, широкие пороги, «драматически плохое»);
  nightly/cron — длинный regression-профиль с относительным сравнением и трендом.

**Механика k6 (для P1.4 и P2):**
- Threshold-брейч → **exit code 99** → шаг Actions падает сам, glue-код не нужен.
- `checks` сами по себе НИКОГДА не меняют exit-code — чтобы провал проверки валил CI, нужен
  порог `checks: ['rate>0.99']`.
- Ранний обрыв: `abortOnFail: true` + **`delayAbortEval: '30s'`** — без задержки rate-пороги убивают
  прогон на разгоне (ramp-up blip), до выхода на steady state.
- Пер-сценарные/пер-эндпоинтные пороги — через теги:
  `'http_req_duration{scenario:tus_patch}': ['p(95)<300']`, `'http_req_failed{name:search}': ['rate<0.02']`.
- Экспорт: `--summary-export summary.json` (вход для baseline-логики), либо remote-write в Prometheus.

## RAG-7 — Даёт ли docker-стенд с cpu/mem-лимитами воспроизводимую латентность?

**Вопрос:** решено закрепить эталонный «железный конверт» как docker-стенд в `load/`. Даёт ли
`--cpus`/`mem_limit` стабильные, сравнимые между прогонами числа?

**Вывод (прямо меняет дизайн):** лимиты годятся, чтобы **задать форму** окружения («машина на 2 ядра
и 4 ГиБ»), но **`--cpus`-квота — плохой выбор для замера латентности**:

- `--cpus` транслируется в **CFS-квоту** (`cpu.cfs_quota_us`/`cpu.cfs_period_us`). Исчерпав бюджет
  внутри периода, контейнер **принудительно паркуется до конца периода** → «пилообразный» профиль
  (работа → сон), который на CPU-тяжёлых PG-бэкендах виден как ступенчатые всплески латентности.
  Детерминировано на уровне ядра, но **не повторяемо** по перцентилям.
- **`cpuset` (пиннинг на конкретные ядра) без квоты** — то, что реально нужно: планировщик крутит
  PG на выделенных ядрах до 100 % без квотных засыпаний, распределение латентности гладкое (при
  тихом хосте). Это ближе к «что будет на N-ядерной машине», а не «что будет, если ядро отбирает
  у PG половину каждого периода».
- Память: `mem_limit` == `memswap_limit` → **swap внутри контейнера выключен** (иначе шум от
  swap-трэшинга). `shared_buffers`/`work_mem` PG задавать **от cgroup-лимита, а не от RAM хоста**.
- Остаточный шум, который cgroups НЕ убирают: соседи по хосту, IRQ/IO-подсистема, **turbo/SMT и
  частотный governor** (меняют эффективную производительность ядра от прогона к прогону).
  Лабораторный рецепт: governor=`performance`, резерв ядер под хост (не входят ни в один cpuset),
  непересекающиеся cpuset'ы app/PG/генератора, отдельный диск или tmpfs под PG-данные.
- **Compose-нюанс:** `deploy.resources.limits` в v3 читается только Swarm'ом (или `--compatibility`);
  в обычном `docker compose up` работают `cpuset` / `mem_limit` / `memswap_limit` / `cpus`.

**Следствие для VLT-LOAD:** «эталонный конверт» = **cpuset-раскладка ядер + mem_limit(=memswap)**,
а не `--cpus`. На GitHub-hosted раннере (общий хост, нет контроля governor/SMT, 4 vCPU) такой конверт
воспроизводит **форму**, но не абсолютную латентность — что смыкается с RAG-6: авторитетные
латентные числа снимаются на контролируемом lab-box, CI держит шумоустойчивый класс гейтов.
