# P2 — W2: Авторизация и изоляция

## Phase Context

Волна W2 бэклога (`plans/AUDIT-VLT/findings/P5.2-remediation-backlog.md` §5): инвариантные дефекты
авторизации и изоляции (ранги top-6/7/8 P5.1). В отличие от дешёвых фиксов W1, эти находки требуют
осторожного редизайна шва и регрессионного покрытия — поэтому идут после W1. Общий корень волны: **авторизация

листинг), листинги Filament обязаны скоупиться (а не полагаться на allow-по-умолчанию), а объявленные инварианты
ядра ACL/дедупа обязаны совпадать с кодом и ADR.

**Мягкое ребро B12 → (B9, B10)** (D2): корректность ядра ACL (инвариант H.2) — фундамент, на который опираются
remanence- (P2.2) и scope-фиксы (P2.3): обе используют `AccessResolver::can()` как барьер. Нарушение ребра не
блокирует, но удваивает риск переделки — поэтому **P2.1 (B12) исполняется первым** (opus/high, Routing).
P2.1 при этом НЕ меняет поведение `can()` на дефолтном `database`-лейне (только докблок/ADR-выравнивание +
диагностический `explain` + fail-loud для role/group-грантов под gate/azgard), поэтому не конфликтует с
issuer-re-check, добавленным в P1.2.

Три несущих ADR-инварианта, которые фаза НЕ ломает, а приводит код/докблоки/тесты в соответствие с ними:
ADR-0007 (nearer-allow-beats-farther-inherited-deny — код верен, докблок «un-overridable wall» врёт, D17),
ADR-0003 (пакет сознательно НЕ скоупит по тенанту — хост владеет tenancy; фиксы НЕ вводят global-scope, D-ось),
ADR-0012 (dedup-unique = `unique(tenant_id, sha256)` — NULL-tenant семантика UNIQUE не покрыта, backbone держит
`storage_key_uniq`, D18). Любое расхождение с ADR при исполнении → эскалация (`rule conflict`), а не импровизация.

### P2.1 — B12 — Корректность ядра ACL (инвариант H.2)

**Status:** 🟠 Done with deviations
**Intent:** Привести три расхождения ядра авторизации в порядок, НЕ меняя вердикт `can()` на дефолтном `database`-лейне: (1) выровнять докблок/комментарии `AccessResolver` к фактическому коду и ADR-0007 (удалить ложную гарантию «un-overridable wall / nearer allow can never pierce», D17); (2) добавить диагностический путь «explain access» (какой ACE дал вердикт), не трогая горячий `can()`; (3) сделать fail-loud молчаливое неисполнение грантов, адресованных ролям/группам, под драйверами `gate`/`azgard`, чей `subjectsFor()` их не энумерит.
**Why:** F-P1.1-01 (Major, top-6): класс-докблок `AccessResolver.php:41` и комментарии `:205-210`/`:273-276` заявляют, что deny на `inherit_grants=false`-стене — «un-overridable wall», которую «no farther/**nearer** allow can ever pierce»; фактический fold `:291-301` вычитает из deny-маски биты allow со строго меньшей глубины (`$allowDepth < $depth`) — более близкий allow между целью и стеной ПРОБИВАЕТ deny. Код соответствует ADR-0007 («a nearer explicit allow beats a farther inherited deny»); неверен именно докблок (заявляет гарантию, которой ADR не давал). Администратор, полагающийся на «глухую стену» по докблоку, получает тихую over-permission. RAG:✅ 2026-07-11 (ADR-0007 прочитан: «nearer explicit allow beats a farther inherited deny», без исключения для стены). F-P1.1-02 (Minor): `effectiveGrants()`/`abilitiesFor()` возвращают только маски/флаги без провенанса — «почему у актора такой вердикт» неотлаживаемо (S1.7). F-P1.2-01 (Minor): под `gate`/`azgard` `subjectsFor()` возвращает только `[actor]`, поэтому строка `v_node_grants`, адресованная роли/группе/команде, молча не даёт эффекта — fail-closed (безопасно), но оператор не узнаёт о неисполнении, и один ACL даёт разный результат на разных драйверах (расхождение с ADR-0007 «actor → users + roles + teams»).
**Scope Included:** F-P1.1-01, F-P1.1-02, F-P1.2-01. (1) Выравнивание докблоков/комментариев `AccessResolver` (класс + `resolveAcl` phase-1/phase-2 + `resolveRole`) к коду и ADR-0007; характеризационный тест, пиннящий ADR-0007-семантику (nearer-allow пробивает inherited deny, включая на стене). (2) Публичный диагностический метод `explain(actor, ability, node): AccessExplanation` (цепочка решающих ACE + глубина + итог), НЕ на горячем пути `can()`; VO `AccessExplanation`. (3) Fail-loud при выдаче гранта на `subject_type` роль/группа/команда под драйвером, чей `subjectsFor()` их не покрывает: warning в лог всегда + бросок в non-production; оговорка в ADR-0007.

### P2.3 — B10 — Tenant/scope-изоляция

**Status:** ⬜ Not started
**Intent:** Закрыть пять fail-open точек изоляции, НЕ вводя global-scope (ADR-0003 сознательно делегирует tenancy хосту): (1) скоупить листинги 4 из 5 Filament-ресурсов к доступному актору набору (сейчас любой пользователь панели читает ACL/share/activity/storage всех тенантов); (2) резолвить актора панели по её guard'у, а не глобальному дефолтному; (3) сделать fail-loud footgun `tenant.enabled=true` при дефолтной (не-скоупящей) модели узла; (4) зафиксировать контракт делегированной tenancy исполняемым тестом; (5) выровнять инвариант дедупа для NULL-tenant (`storage_key_uniq` — истинный backbone, D18).
**Why:** F-P1.10-01 (Major, top-8): из пяти ресурсов панели только `NodeResource` скоупит `getEloquentQuery()`; `StorageResource`/`NodeGrantResource`/`NodeShareResource`/`ActivityResource` не переопределяют его, не определяют `canViewAny`, их модели без политики → в Filament-5 (нет политики + strict off) `canViewAny()`=allow, листинг отдаёт ВСЕ строки.
