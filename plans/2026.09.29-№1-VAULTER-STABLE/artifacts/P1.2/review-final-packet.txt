## Lock matrix (design under review)
# P1.2 — Lock matrix (tree operations × drivers)

Status: final design after review rounds 1–3. It replaces the per-action lock table of the item
spec (Scope п.4), which did not guarantee freedom from cycles (see «Why the spec table was not enough»).

## Primitives

| Symbol | Meaning | PostgreSQL | MySQL/MariaDB | SQLite |
|:--|:--|:--|:--|:--|
| `TX` | `VaulterDatabase::lockTree($storage)` — exclusive tree lock | `pg_advisory_xact_lock(hashtext('vaulter:tree:{id}'))` | `SELECT … FOR UPDATE` on the `v_storages` row | storage row select (database-level writer lock serialises) |
| `TS` | `VaulterDatabase::lockTreeShared($storage)` — shared tree lock | `pg_advisory_xact_lock_shared(…)` on the same key | = `TX` (the row is updated/referenced anyway) | = `TX` |
| `N(ids)` | `NodeStoreRepository::lockForUpdate` — node rows, ascending id | `FOR UPDATE` | `FOR UPDATE` | no-op |
| `N↑` | lock of the node's current parent after the node (upward only) | `FOR UPDATE` | `FOR UPDATE` | no-op |
| `SUB` | bulk subtree `UPDATE` (trash / restore / soft-delete) — many node rows, unordered | row X | row X | — |
| `INS` | node/file/version `INSERT`; FK check on `storage_id`, `parent_id` | `FOR KEY SHARE` on referenced rows | S on referenced rows | — |
| `Q` | `UPDATE v_storages SET used_bytes` | `FOR NO KEY UPDATE` on the storage row | X on the storage row | — |
| `CAS` | `BlobLock` per (scope, sha256) | advisory xact | row lock (MySQL path in `BlobLock`) | — |

D21 order: tree lock → node rows → aggregates → `Q` → `CAS`. Pre-existing exception owned by
PLAN2.P1.6: Upload takes `CAS` before `Q`.

## Acquisition order per operation (first statement first)

| Operation | Tree lock | Node locks | Then |
|:--|:--|:--|:--|
| Create folder | `TS` | `N(parent)` | `INS` |
| Create document | `TS` | `N(parent)` | `INS` (node, version) |
| Upload — new file | `TS` | `N(parent)` | `CAS` → `INS` → `Q` |
| Upload — new version | `TS` | — (`UPDATE` of the target node row) | `CAS` → `INS` → `Q` |
| Copy | `TS` | `N(destination)` | `INS` (copies; parents are the new rows) → `Q` |
| Rename | `TS` | `N(node)` → `N↑(parent)` | `UPDATE name` |
| Move | `TX` | `N(node, into)` | `UPDATE parent_id` |
| Restore | `TX` | `N(node, root)` → `N(original parent)` | `UPDATE parent_id` → `SUB` |
| Trash | `TX` | `N(node)` | `SUB` |
| ForceDelete | `TX` | `N(node)` | blob-edge deletes → `SUB` → `Q` |

## Pairwise argument (no wait-for cycle within one storage)

1. **`TX` holder vs anything in the same storage.** `TX` conflicts with `TS` and `TX`; every tree
   operation takes one of them as its first statement. A `TX` holder therefore never overlaps
   another tree operation of its storage, so the unordered `SUB` and the second `N` of Restore
   cannot meet a competing node lock. (Before the fix, Trash had no tree lock: Trash P ‖ Restore C
   and Trash P ‖ Move N→P deadlocked on PG/MySQL — recheck 2.)
2. **`TS` holders among themselves (PostgreSQL).** Each holds at most one node row before its
   writes (Rename: the node, then only upward to its parent). Their later waits are on `CAS`, `Q`
   and FK `KEY SHARE` — none of which is held while waiting for a node row: `Q` is the last
   statement of every holder, `KEY SHARE` conflicts only with `FOR UPDATE`/key updates of
   `v_storages`, which no `TS` holder takes on PG, and `CAS` holders do not wait for node rows.
   Rename's upward wait follows parent links, which are acyclic and cannot change while `TS` is
   held. Hence the wait-for graph is acyclic.
3. **`TS` holders on MySQL/MariaDB and SQLite.** `TS` = `TX` = the storage row X, so all tree
   writes of one storage are serialised; the later `Q` and FK S lock hit a row already held
   (recheck 1: before, Create's FK S lock and Upload's `Q` took the row after a node lock).
4. **Across storages.** Locks of different storages are disjoint, except a node of another
   storage passed as a destination: it is locked (ascending, after the own tree lock) and the
   operation then throws `CrossStorageMoveException`/`InvalidDestinationException`; the foreign
   storage's operations never wait for a row of this storage, so no cycle closes.
5. **Copy reads, never locks, the source subtree** (`TS` excludes concurrent structural changes;
   rename of a source row can still happen and only changes the copied name).

## Lost-update / invariant races closed by the same rule

- Move cycle A→B1 ‖ B→A1 (V19): `TX` serialises the cycle checks.
- Trash ancestor ‖ create under a descendant: without `TS` a child committed after Trash read the
  subtree stays live under a trashed folder — reproduced 2/10 on PG without `TS`
  (`TreeLockRaceTest`), 0/5 with it.
- Rename ‖ create of the same name in the parent: the parent row lock makes the sibling check and
  the write atomic (the sibling-unique index remains the backstop).

## Cost

- PostgreSQL: tree writes under one parent stay concurrent with each other; a structural operation
  (`TX`) waits for in-flight creates/uploads of its storage, including an upload's blob commit, and
  new tree writes queue behind a waiting `TX`.
- MySQL/MariaDB/SQLite: all tree writes of one storage are serialised (they already serialised on
  the `Q` UPDATE of the same row).

## Why the spec table was not enough

The spec listed locks per action without a global order: Trash, Create, Upload, Copy and Rename had
no tree lock; it did not account for MySQL's `lockTree` being the very row that `Q` updates and that
node `INSERT`s FK-check; and the V19 two-node shape is already serialised by row locks, so its
negative control could not fail. Review found one cycle per round because each fix was local.

## BlobLock (CAS)
final class BlobLock
{
    public function __construct(private readonly VaulterDatabase $database) {}

    /**
     * Take the per-(scope, sha256) advisory lock for the current transaction.
     * Must be called as the first statement inside $this->database->transaction().
     */
    public function acquire(string $scope, string $sha256): void
    {
        $this->database->advisoryLock($scope.'|'.$sha256);
    }

    /**
     * Whether the active connection uses pessimistic row locks (FOR UPDATE) as the
     * lock mechanism — i.e. MySQL/MariaDB. PG uses the advisory lock above; SQLite
     * uses single-writer and ignores FOR UPDATE.
     */
    public function usesRowLock(): bool
    {
        return in_array($this->driver(), ['mysql', 'mariadb'], strict: true);
    }

    /**
     * Whether a critical section that takes this lock but performs NO database WRITE
     * is still serialised against a concurrent transaction by THIS driver.
     *
     * The orphan prune is exactly such a section (it re-reads under the lock, then
     * deletes BYTES off disk — no row write). It is safe only when the lock alone
     * orders it against a concurrent BlobStore::commit of the same content:
     *
     *  - pgsql : pg_advisory_xact_lock() is a real mutex held for the whole tx — a
     *            commit of the same (scope,sha256) blocks on it ⇒ serialised.
     *  - mysql : findByStorageKey(lock: true) issues SELECT … FOR UPDATE, so the
     *            recheck contends with the concurrent INSERT ⇒ serialised.
     *  - sqlite: acquire() is a no-op AND FOR UPDATE is ignored, so a read-only
     *            critical section never engages SQLite's single-writer lock — a
     *            concurrent commit can INSERT the owning row between the recheck and
     *            the byte delete. NOT serialised; the prune must be refused (the GC
     *            is unaffected — it does a real markDeleting() write that forces the
     *            write lock).
     */
    public function serializesCriticalSection(): bool
    {
        return $this->isPostgres() || $this->usesRowLock();
    }

    public function isPostgres(): bool
    {
        return $this->driver() === 'pgsql';
    }

    private function driver(): string
    {
        return $this->database->driver();
    }
}
