### P1.6 — Атомарная квота и счётчик ревизий

**Intent:** Квота storage не превышается при параллельных загрузках и копиях, номера ревизий файла идут без дублей и
дыр, дельта квоты считается от фактически перечитанной головы, а все операции берут блокировки в каноническом порядке D21
(drive → узлы по id → агрегат → квота → CAS) с ретраем транзакции при deadlock/serialization (E2, AD21, I7; V02, V03, V20, V21).

**Why:** OPUS 13 P1.6, 02 D21, 08 §1 (I7), §5. Сегодня квота проверяется до транзакции по модели в памяти
(`packages/drive/src/Actions/UploadFileAction.php:78, 245–261`), а `adjustUsedBytes` (`packages/core/src/Repositories/Drive/StorageStoreRepository.php:59–74`)
прибавляет без условия; номер ревизии — `max(version_no) + 1` без блокировки (`packages/core/src/Repositories/Drive/FileVersionStoreRepository.php:40–49`);
`previousHeadSize` читается до транзакции; `version_count` увеличивается от значения в памяти (`FileStoreRepository.php:46`).

**Scope Included:**
1. `StorageStoreRepository::reserveBytes(Storage $storage, int $delta): void` (new) — при `$delta > 0` внутри транзакции
   вызывающего: `UPDATE <storages> SET used_bytes = used_bytes + ? WHERE id = ? AND (quota_bytes IS NULL OR used_bytes + ? <= quota_bytes)`
   на `VaulterDatabase::connection()`; 0 строк → перечитать `quota_bytes`/`used_bytes` и бросить
   `QuotaExceededException::forStorage(...)` (транзакция откатывается); при `$delta <= 0` — существующий `adjustUsedBytes`
   (освобождение с ограничением снизу 0). Предпроверка `assertWithinQuota()` остаётся только как быстрый отказ.
2. CAS-коммит готовых байтов (уровень 5 после уровня 4): `Contracts\Cas\BlobStore::commitStaged(StagedObject $staged, BlobScope $scope, ?string $disk = null): Blob` (new);
   `media BlobStore::commit()` = `stage()` + `commitStaged()` + `discard()` в `finally`; `commitStaged` не вызывает `discard()`.
3. `UploadFileAction::executeUpload()` — порядок:
   1) до транзакции: `$staged = ContentStore::stage($data->stream)` (размер и sha известны), `try { … } finally { $staged->discard(); }`;
   2) `VaulterDatabase::transaction()`: `lockForUpdate([parent])` (уровень 2, P1.2; для новой ревизии — `[node]`) → для новой
      ревизии `FileStoreRepository::lockForUpdate(File)` (new, `SELECT … FOR UPDATE` строки `files`, уровень 3) и перечитанная
      голова (`current_version_id` → её `size_bytes`; нет головы → 0) → `delta = $staged->sizeBytes() - $headSize` →
      `reserveBytes` при `delta > 0`, иначе `adjustUsedBytes(delta)` при `delta < 0` (уровень 4) →
      `commitStaged($staged, BlobScope::forUpload(...), $disk)` (уровень 5) → строки node/file/version/edge → голова;
   3) номер ревизии = `$lockedFile->version_count + 1` (новый файл — 1); `FileStoreRepository::repointHead` пишет
      `version_count` = этот номер (не `+1` от модели в памяти); `FileVersionStoreRepository::nextVersionNo()` удаляется (документы
      используют свой `NodeDocumentVersionStoreRepository::nextVersionNo` — без изменений, R8).
4. `CopyNodeAction`: `adjustUsedBytes($addedBytes)` → `reserveBytes($addedBytes)` в той же транзакции (одна операция на сумму
   поддерева; превышение откатывает копию целиком).
5. Порядок блокировок: в `UploadFileAction`, `CopyNodeAction`, `MoveNodeAction`, `RestoreNodeAction`, `ForceDeleteNodeAction`
   уровень блокировки не убывает (D21); над последовательностью в `UploadFileAction` — однострочный комментарий
   `// Lock order: drive → nodes → file → quota → CAS, so concurrent writers never deadlock.`
6. Ретраи: `VaulterDatabase::transaction($callback, 3)` (P1.1, R4) — замыкания `UploadFileAction`/`CopyNodeAction` не имеют
   побочных эффектов вне БД до коммита, кроме promote объекта (сага: при откате — сирота для reconcile).
7. Тесты (PG, `ForkRace`, `DatabaseMigrations`, каталог `packages/drive/tests/Concurrency/`):
   - V02 — `QuotaRaceTest.php`: квота 10 МБ, свободно 10 МБ; две задачи загружают разные файлы по 8 МБ на разных соединениях →
     ровно одна успешна, другая `failedWith(QuotaExceededException::class)`; `used_bytes` = сумма `size_bytes` голов всех файлов
     storage; строки blob проигравшей нет; `vaulter:reconcile-blobs` после grace не удаляет байты победителя.
     Негативный контроль: временно заменить `reserveBytes` на безусловный `adjustUsedBytes` → обе успешны (`used_bytes` 16 МБ) — красный.
   - V03 — `RevisionNumberRaceTest.php`: файл с ревизией 1; две параллельные новые ревизии → номера `{2, 3}` без дублей и дыр;
     `files.version_count = 3`; голова — ревизия с номером 3; `used_bytes` = размер головы (дельты от реальных предыдущих голов).
     Негативный контроль: убрать `FileStoreRepository::lockForUpdate` → дубль номера/нарушение уникальности хотя бы в одном из 5 прогонов.
   - V20 (часть P1, R9) — `SameNameUploadRaceTest.php`: два upload `x.pdf` в одну папку → ровно один узел `x.pdf`, вторая задача
     `failedWith(NodeNameConflictException::class)`; нет 500 и нет второго узла.
   - V21 — `LockOrderRaceTest.php`: 10 итераций `move(A → F)` ‖ `upload(в F)` → обе успешны в каждой итерации (deadlock не выходит
     наружу — максимум внутренний ретрай), дерево ацикличное, `used_bytes` = сумма голов.
   - SQLite: `packages/drive/tests/Feature/QuotaReserveTest.php` — `reserveBytes` при `quota_bytes = NULL` (без ограничения),
     ровно на границе (успех), +1 байт (исключение, `used_bytes` не изменился); копия поддерева сверх квоты → `QuotaExceededException`,
     строк копии нет.
