# D09 — Закрытие B0-A: фикстура 0.2 только PostgreSQL, ревью B0-A, бюджет прогонов (accepted)

**Actor:** repository owner делегировал решения исполнителю; фиксирует claude-opus-5-5/high.
**Evidence:** сообщение владельца 2026-10-01: «Я, в принципе, со всем согласен, только лишь бы не было вот этих
вот гигантских часовых прогонов … я за любые компромиссы. Мне важен современный стек, … чистая архитектура и чтобы
мы сейчас вот хвосты не плодили … ты, в принципе, рулишь этим проектом. Я утверждаю только начальный план, ну и ты
можешь решения уже принимать сам»; `artifacts/P0.3/completion.md` (MySQL 1215); `artifacts/P0.2/completion.md`.

## Solution

1. **Фикстура 0.2 — только PostgreSQL.** Тег `v0.2.0` не устанавливается на MySQL 8: `PanelTablesBuilder` добавляет
   STORED-генерируемую колонку `v_nodes.sibling_active` над `parent_id` с FK `ON DELETE CASCADE` → `SQLSTATE 1215`;
   CI тега MySQL не проверял. Данных 0.2 на MySQL существовать не может. Отказ от MySQL-части единицы OPUS
   `13:76f51728` («дамп для PG и MySQL»): `plan:D09`. P0.3 поставляет `pgsql-bigint`, `pgsql-ulid`,
   `pgsql-bigint-preflight-red`; `mysql-*` удалены из Scope/Files/Validation P0.3.
2. **Следствие для upgrade (P2.1, P4.1, V15):** путь 0.2 → 0.3 проверяется на PostgreSQL-фикстуре; MySQL-ветки
   upgrade-миграций не нужны для данных 0.2 (их нет). MySQL-поддержка 0.3 доказывается свежей установкой 0.3 на MySQL
   в тестах соответствующих фаз; UPGRADE.md указывает, что 0.2 на MySQL не поддерживался.
3. **Независимое ревью B0-A** (`Review full`, execution-sheet строка 2) выполняет read-only ревьюер Claude Code
   со свежим контекстом на модели, отличной от исполнителя (`claude-sonnet-5-5`), вместо `cursor/grok-4.7/high`.
   Ревью — отдельный read-only результат после локальной Validation P0.2 и P0.3 (не шаг items); вердикт и находки —
   `findings/B0-A-review.md`. GREEN даёт receipt Validation-строки «Independent review» обоих items; находки
   Major+ исправляются исполнителем B0-A (≤2 раунда, D05).
4. **Бюджет прогонов.** Без многочасовых прогонов: item — только затронутые проверки; широкие suites — один раз
   в последнем item/фазовой проверке; mutation-прогоны не запускаются без отдельного запроса владельца (как P0.1).
5. Owner gate O-3-CI (push кандидата и hosted run) не меняется: внешнее действие, только по явной команде владельца.

## Why

Требование MySQL-дампа 0.2 невыполнимо без изменения исходной схемы, а изменённая схема — уже не данные 0.2
(правило P0.3 запрещает). Отказ убирает хвост, а не прячет его: upgrade-путь, которого не существует, не нужно
тестировать. Ревьюер другого провайдера требует отдельного ручного запуска владельцем; владелец делегировал
маршрутизацию исполнителю, а независимость (другая модель, свежий контекст, read-only) сохраняется.

## Consequences

- P0.3 Validation проверяет три PG-дампа; `--verify` по умолчанию собирает только их.
- P2.1/P4.1 при дизайне берут D09 п.2 как вход; MySQL-фикстура 0.2 не появится.
- Независимость ревью B0-A — модель/контекст, не провайдер; журнал и findings это указывают.
