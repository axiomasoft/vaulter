# D03 — Порядок фаз и жизненный цикл «дизайн → исполнение → аудит» (accepted)

**Actor:** author-choice (claude-opus-5-5/high) по B2, B3, B5.
**Evidence:** RAG:— OPUS `13-workstreams.md` §«Граф фаз»; `corex:PLAN3.D21`, `corex:PLAN3.D24` (катящийся дизайн);
OPUS `08-data-model-and-migration.md` §3 (порядок миграций), §6 (`sequence` в событиях); AD23; D02 п.1.

## Решение

1. **Порядок — строго последовательный:** P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7 → P8.
   - **P1 до P2** (как в OPUS), хотя 0.2.1 не выпускается (D02): исправления T0 делаются на знакомом коде, а их
     сценарии V17–V26 и V01–V03/V09/V13/V14 становятся страховочной сеткой массового переименования P2. Обратный
     порядок (сначала механика, как corex P02/P03) отвергнут: переименование без сетки на коде с известными дефектами
     атомарности (N01) и видимости (N08) переносит дефекты в новые имена без доказательств.
   - **P4 до P5** (OPUS допускает параллель): P5.1 кладёт `sequence` узла в событие, а `v_nodes.sequence` вводит P4.7;
     один исполнитель ведёт фазы по очереди — параллель не даёт выигрыша, но создаёт конфликт миграций.
   - P6 стартует после закрытия P5 (контракты P3–P5 заморожены), P7 после P6, P8 после P7.
2. **Катящийся дизайн.** Детализирована только текущая фаза (`phases/Pn/`); остальные — skeleton в `backlog/Pn.md` и
   детализируются `task:plan-design <ID> Pn` по фактическому коду после закрытия предыдущей. Дизайн вперёд не делается.
3. **Цикл на фазу (B3):** `task:plan-design <ID> Pn` → `task:plan-design <ID> finish` → независимый
   `task:plan-audit <ID> design` (не автор дизайна) → исполнение строк `execution-sheet/v1` (`task:plan-run`, review по
   строке) → **фазовый аудит** `task:plan-audit <ID> Pn` (B5: требование владельца для каждой фазы; consent —
   `audit-admission/v2` по протоколу, ссылка на `brief/00-brief.md#repository-owner-message-дословно-2026-09-29`) →
   `task:plan-close <ID> Pn` → дизайн Pn+1.
4. Носители плана (plan.md, roadmap, handoff, phase index) сводит только автор плана; исполнитель пишет item state и
   Completion Notes через Task tooling.

## Почему

Владелец просит «сформировать фазу → реализовать → аудит» и выбирать порядок самому; процесс corex PLAN3 уже доказал
этот цикл. Последовательность снимает конфликты миграций и публичных контрактов между соседними фазами.

## Последствия

`roadmap.md` держит карту фаз P0–P8 и `execution-sheet/v1` только для детализированных фаз. Фазовый аудит — обязательный
шаг каждой фазы; его отсутствие блокирует дизайн следующей.
