## 1. Рекомендуемая первая схема

**Оставить родное авторитетное состояние каждого редактора и добавить в PostgreSQL перестраиваемые проекции блоков и ячеек.**

Для одиночного текста источником остаётся принятый ProseMirror JSON с существующей проверкой ожидаемой версии. Для совместного текста — долговечные двоичные обновления Yjs и контрольные снимки. Для книги — нативное состояние и подтверждённые операции выбранного движка.

SDK применяет команды через владельца соответствующего документа. Проекции обслуживают адресное чтение; их можно удалить и восстановить из источника.

Это позволяет удешевить обычные чтения агента, сохранив нынешние границы Vaulter. **Стоимость сохранения и разбора целого источника при этом остаётся отдельной статьёй расходов.** Маленькая команда SDK ещё не означает маленькую работу сервера при записи.

### Матрица вариантов

| Критерий | Целое содержимое, извлечение при запросе | Источник плюс перестраиваемые проекции | Адресуемые авторитетные части плюс снимки |
|---|---|---|---|
| Начальная сложность | Минимальная | Умеренная: строки, версии, обработчик событий | Высокая: протокол частей, структурных операций и сборки |
| Небольшое чтение | Может потребовать загрузить и разобрать весь источник | Читаются нужные строки и небольшой контекст | Читаются нужные части, если формат допускает это |
| Свежесть | Определяется загруженной версией источника | Требует явной позиции проекции | Требует согласованного состояния нескольких частей |
| Простая запись | Часто новая сериализация большого значения | Цена источника плюс обслуживание проекции | Потенциально локальная запись |
| Структурные изменения | Обрабатываются нативным редактором | Могут затрагивать много производных строк | Требуют корректной семантики адресов, ссылок и порядка |
| Восстановление | Снимок и, при необходимости, журнал | Восстановить источник, затем проекцию | Восстановить согласованный граф частей |
| Выбор для первого выпуска | Допустим для простой CMS и резервного чтения | **Основная рекомендация для SDK** | Только через проверенный контракт движка либо после доказанного ограничения |

Различия по типам документа существенны:

- **Одиночный текст.** Проекцию небольшого документа можно публиковать синхронно с сохранением. Для большого — асинхронно, сохраняя тот же контракт версий.
- **Совместный текст.** Подтверждение журнала и готовность проекции разделяются. JSON является производным представлением. Hocuspocus прямо рекомендует сохранять Yjs в бинарном формате; восстановление сотрудничества из одного JSON может нарушить объединение обновлений. [Hocuspocus Docs](https://tiptap.dev/docs/hocuspocus/guides/persistence?utm_source=chatgpt.com)
- **Разреженная книга.** Проекция должна хранить входы, формулы и вычисленные значения с отдельным признаком актуальности. Запись ячейки через SQL-проекцию не должна обходить движок формул и структурных операций.

## 2. Почему маленький JSON-ответ не доказывает дешёвого чтения

Нужно измерять несколько разных величин: ответ агенту, трафик между приложением и БД, обращения к буферам PostgreSQL, чтение объектов, распакованные данные и работу редактора.

TOAST физически разбивает большие значения, но это не создаёт адресацию абзацев. Возможность частичного извлечения зависит от типа и функции. Нельзя предполагать, что выбор нескольких ветвей большого JSONB прочитает только соответствующие байты. В отчёте отдельно разобран опубликованный путь detoast; для производственной версии его необходимо подтвердить исходниками и планом запроса. [postgresql.org](https://www.postgresql.org/docs/18/storage-toast.html?utm_source=chatgpt.com)

GIN помогает находить строки документов по содержимому. Он не превращает вложенные абзацы в отдельные возвращаемые записи и не поддерживает index-only scan. Большой JSONB в `INCLUDE` также увеличивает индекс и может превысить допустимый размер индексной записи. [postgresql.org](https://www.postgresql.org/docs/18/datatype-json.html?utm_source=chatgpt.com)

Для книги есть дополнительная ловушка: индекс

```text
(tenant, document, generation, sheet, row, col)
```

не гарантирует чтение ровно двадцати ячеек при двух условиях `BETWEEN`. Для небольшого прямоугольника разумно сравнить двадцать полных адресов одним SQL и несколько поисков с равенством по строке. PostgreSQL 18 допускает skip scan, поэтому окончательное решение принимается по фактическому плану. [postgresql.org](https://www.postgresql.org/docs/18/indexes-multicolumn.html?utm_source=chatgpt.com)

## 3. Минимальные дополнительные сущности

Дерево документов, ACL, хранилище объектов, историю и существующий outbox повторно создавать не требуется.

| Дополнение | Основной ключ | Что хранит |
|---|---|---|
| `office_projection_head` | `(tenant_id, document_id)` | Поколение, позицию источника, версию представления, готовность, формат, происхождение; для книги — состояние расчёта |
| `office_block_read` | `(tenant_id, document_id, generation, block_id)` | Порядок, родителя, тип, attrs, inline-разметку, текст для поиска, связи с заголовками |
| `office_cell_read` | `(tenant_id, document_id, generation, sheet_id, row, col)` | Вход, формулу, нативные данные ячейки, вычисленный кэш и его происхождение |
| `office_command_receipt` | UNIQUE `(tenant_id, document_id, command_id)` | Пользователя, hash команды, поколение и позицию записи, сохранённый исход и ссылку для проверки |

К существующему состоянию документа добавляются или отображаются на имеющиеся поля поколение, позиция долговечной записи и позиция контрольного снимка.

Для строгого отзыва прав нужен общий механизм сериализации изменений доступа. Если эквивалентного механизма в Vaulter нет, минимальный вариант — небольшая строка состояния авторизации организации с `authz_epoch`.

### Индексы и содержимое проекции

Для текста нужны поиск по ID и B-tree по порядку. Оглавление читается из строк заголовков, при необходимости через частичный индекс. Полнотекстовый GIN добавляется только для действительно включённого поиска по содержимому.

Проекция сохраняет разметку, а не только текст. Для абзаца в списке возвращаются сведения о контейнерах. Связь с разделом хранится отдельно: заголовок и следующий абзац могут быть соседями дерева.

Для книги первичный ключ обслуживает точечные чтения. Пустая ячейка, формула с пустым результатом, форматированная ячейка и отсутствующий лист должны различаться. Отсутствие строки можно трактовать как пустоту только после проверки готовности проекции, существования листа и допустимости координат.

### Цена обслуживания

| Изменение | Возможная работа в первой схеме |
|---|---|
| Изменить текст абзаца | Обновить одну строку и поисковый текст; обнаружение изменения может потребовать разбора всего JSON |
| Вставить абзац | При плотных порядковых номерах обновить хвост |
| Перенести раздел | Обновить порядок и контекст перемещённых узлов, иногда большой хвост |
| Изменить входную ячейку | Обновить вход и результаты затронутых формул |
| Вставить строку | Сдвинуть адреса, учесть ссылки и диапазоны; первоначально допустим полный rebuild |
| Пересчитать формулы | Обработать замыкание зависимостей, которое может быть гораздо больше ответа агенту |

Разреженные ключи порядка, стабильные ID строк и инкрементальные изменения — следующие возможные оптимизации. Они не отменяют семантику ссылок и формул.

## 4. Какие версии обязательно разделить

Один универсальный `version` здесь создаёт неоднозначность.

| Координата | Смысл |
|---|---|
| `G` — поколение | Новая линия рабочего состояния после восстановления |
| `H` — долговечная позиция | Подтверждённый префикс журнала данного поколения |
| `S` — позиция снимка | До какой позиции сохранён checkpoint |
| `P` — позиция проекции | Какой источник полностью отражён во входах, структуре и формулах проекции |
| `V` — версия представления | Версия опубликованного набора данных; может меняться при том же `P` |
| `C`, `calc_run_id`, контекст | Для какого входного состояния завершён расчёт |
| `revision_id` | Именованная историческая ревизия Vaulter |

**Все позиции сравниваются внутри одного поколения одного документа.**

`ready=true` означает готовность входной проекции. Кэш формул может оставаться устаревшим. Для свежего вычисленного ответа нужны совпадение `C=P`, завершённость расчёта и требуемый контекст.

Даже тогда ответ является рассчитанным **для P**. Если источник уже дошёл до `H>P`, его нельзя безусловно называть последним состоянием.

### Правило публикации

Обработчик готовит результат вне короткой транзакции. При публикации он блокирует состояние документа и заголовок проекции, затем проверяет:

```text
current.generation == job.generation
head.projection_version == job.baseV
job.source_position <= current.durable_position
head.source_position IS NULL
    OR job.source_position >= head.source_position
```

Для инкрементального изменения дополнительно требуется совпадение родительской позиции и полный переход к целевой версии. Все вставки, изменения, удаления, поисковые данные и продвижение заголовка фиксируются одной транзакцией.

Проверка `baseV` принципиальна. Обработчик может вычислить diff по старой проекции, пока другой уже опубликовал промежуточное состояние. Применение старого diff к новой базе способно дать неверный результат даже при полностью атомарной записи.

Отдельно защищается расчёт: старый запуск не должен перезаписать более новый при том же `P`. Для этого проверяется актуальный `requested_calc_run_id`.

## 5. Что означает «прочти после моей команды»

SDK должен предоставлять разные режимы:

- `eventual` — завершённая проекция с явными `P` и наблюдавшимся `H`;
- `at_least(token)` — состояние того же поколения не раньше позиции команды;
- `current` — состояние не раньше `H`, захваченного при начале запроса;
- `exact(source)` — точно указанная историческая позиция;
- `require_calculated` — дополнительно завершённый расчёт для возвращаемого источника.

**Чтение не раньше команды и чтение точного результата команды — разные гарантии.** После вашей записи другой пользователь мог изменить тот же абзац.

Проверяемая цепочка выглядит так:

```text
command_id
→ сохранённая квитанция
→ конкретные поколение и позиция
→ повторно прочитанное сохранённое состояние
→ фактический фрагмент и его версия
```

Возврат исходного текста команды из памяти эту цепочку не заменяет. Если нужна проверка точного результата спустя время, соответствующий исторический источник должен сохраняться.

### Два ключевых запроса

В полном документе приведены также SQL-фрагменты. Ниже — логика, связывающая индексный доступ с правами и свежестью.

**Блок с соседями после команды:**

```text
readBlockAfter(actor, document, blockId, token):
  repeat within deadline:
    BEGIN READ COMMITTED on primary
      lock organization_authorization_guard FOR SHARE
      check current read permission

      r = one SQL snapshot:
          document head + projection head
          target by block ID
          previous and next blocks by order, LIMIT 1 each
          required markup and structural context
    COMMIT

    if generation differs:
      return generation_changed

    if projection is ready and P >= token.position:
      return fragment with actual source token

    wait for notification or short timeout outside transaction

  if authoritative fallback fits budget:
    reconstruct a confirmed source
    extract fragment
    recheck current permission and generation
    return fragment with authoritative origin

  perform final authorized read:
    return ready result, generation_changed, or projection_pending
```

**Небольшой диапазон с актуальностью расчёта:**

```text
readCellsAfter(actor, document, sheet, addresses, token, needCalc):
  repeat within deadline:
    BEGIN READ COMMITTED on primary
      lock organization_authorization_guard FOR SHARE
      check current read permission

      r = one SQL snapshot:
          document and projection heads
          sheet manifest
          requested addresses joined to cell rows
          formula inputs, caches and calculation markers
    COMMIT

    if generation differs:
      return generation_changed
    if projection is behind token:
      wait or use an allowed authoritative fallback
    else if calculation is not required:
      return inputs, formulas, caches and explicit freshness
    else if calculation is complete for returned source and context:
      return calculated result

    wait outside transaction

  perform one final authorized read:
    distinguish ready result, projection_pending,
    calculation_pending and generation_changed
```

Финальная проверка нужна и после последнего ожидания: за это время доступ могли отозвать.

### Когда достаточно повторения

| Причина | Действие |
|---|---|
| Устарел локальный кэш | Обойти его и перечитать primary |
| Отстаёт replica | Перейти на primary либо дождаться проверяемого replay |
| Primary видит запись, проекция отстаёт | Дождаться обработки; простой повтор без прогресса не помогает |
| Обработка не укладывается в срок | Ограниченное чтение источника либо явный pending |
| Изменилось поколение | Вернуть конфликт поколения |
| Отстаёт расчёт | Вернуть его статус или дождаться нужного запуска |
| Отозваны права | Отказать независимо от готовности данных |

Поиск также проверяет текущие права. Начальная выдача содержит только разрешённые ID и метаданные; сниппеты и счётчики скрытых документов не раскрываются. При последующем открытии проверка выполняется заново. Отставший поисковый индекс может временно не находить новый текст — это ограничение полноты поиска.

## 6. Учебный пример с p17

Исходные условия:

```text
generation = 3
durable position = 42
projection position = 41
```

Команда заменила «Срок 15 дней» на «Срок 30 дней» и получила подтверждение `(3,42)`.

### Чтение после команды

Проекция 41 не удовлетворяет запросу. SDK может ограниченно ждать либо прочитать подтверждённый источник. Если обработка не завершилась в отведённое время, допустим ответ:

```json
{
  "status": "projection_pending",
  "required": {"generation": 3, "position": 42},
  "available": {"generation": 3, "position": 41}
}
```

После восстановления сохранённого состояния до 42 SDK возвращает p17 с текстом «Срок 30 дней», разметкой, соседями и фактическим токеном `(3,42)`.

Если на 43 человек изменил срок на 45 дней, `at_least(3,42)` вправе вернуть 45 с позицией 43. Для проверки именно состояния после вашей команды требуется `exact(3,42)`, который при сохранённой истории вернёт 30.

### Восстановление ревизии

Для демонстрации в отчёте явно принято допущение: восстановленная ревизия содержит исходный p17 со сроком 15 дней.

Restore создаёт поколение 4. В одной транзакции:

```text
document.generation = 4
document.durable_pos = 0
document.checkpoint_pos = 0

projection.generation = 4
projection.source_pos = NULL
projection.ready = false
projection.version = nextV

calculation markers = reset
```

Старое `P=42` нужно очистить: иначе проверка монотонности помешает опубликовать начальную позицию нового поколения.

Позднее событие `(3,42)` отсекается под общей с restore блокировкой:

```text
current.generation == job.generation
4 == 3 → false
```

Ни одна строка его результата не публикуется.

Последующее поведение различается:

| Запрос | Результат |
|---|---|
| Прежний `at_least(3,42)` | `generation_changed` |
| Явное чтение текущего поколения 4 | После готовности — 15 дней |
| Явное историческое `(3,42)` | 30 дней при наличии истории и текущих прав |
| Повтор старой команды с тем же ID | Исходная квитанция в пределах прав; команда повторно не применяется |

## 7. Учебный пример с формулой

Вымышленное состояние книги:

```text
B2 = 12
B3 = 8
D2.formula = "=SUM(B2:B3)"
D2.cached_value = 20
```

После сохранения `B2=15` входная проекция может уже соответствовать новой позиции, а расчёт оставаться старым.

Корректный ответ сохраняет различия:

```json
{
  "cell": "D2",
  "formula": "=SUM(B2:B3)",
  "cached_value": 20,
  "calculation_status": "stale"
}
```

Если агент потребовал актуальное вычисленное значение, SDK ждёт либо возвращает `calculation_pending`. После завершения и согласованной публикации расчёта результат равен **23**.

У Univer есть отдельный барьер применения результатов `onCalculationResultApplied(timeout)`. При работе с изменяемой книгой ожидание дополнительно нужно связать с нужной версией входов; сам факт завершения некоторого расчёта этого не доказывает. [Univer Office SDK](https://docs.univer.ai/reference/facade/formula?utm_source=chatgpt.com)

Вторая существенная гонка: повторный rebuild может принести из нативного снимка старое `v=20`. Он не должен затереть уже опубликованное 23, сохранив признак свежего расчёта. Входной обработчик и обработчик расчёта должны иметь явные правила владения колонками либо атомарно сбрасывать расчётный статус.

Если между чтениями пользователю отозвали доступ ко всей книге, следующий запрос получает отказ. Нельзя вернуть ни новую величину 23, ни старый кэш 20, ни формулу на основании предыдущего разрешения.

## 8. Сбои, права и внешние компоненты

### Фиксация состоялась, ответ потерян

Квитанция хранится вместе с источником и outbox. Повтор использует прежний `command_id`.

После актуального допуска к результату сервер сначала ищет сохранённую квитанцию и проверяет hash команды. Только для действительно новой команды применяются expected version и смысловые предусловия. Иначе повтор после потерянного ответа ошибочно упрётся в уже изменённую версию документа.

Идемпотентность обновлений Yjs относится к повторной доставке тех же бинарных данных. Повторное исполнение бизнес-команды может сформировать другое обновление. [docs.yjs.dev](https://docs.yjs.dev/api/document-updates?utm_source=chatgpt.com)

### Повтор или нарушение порядка событий

Повтор уже покрытой позиции — безопасный no-op. Инкрементальное событие 43 при проекции 41 требует недостающего перехода. Полный подтверждённый снимок 43 может заменить 41 непосредственно.

Отметка обработки события выполняется после публикации. Сбой между публикацией и отметкой создаёт повтор, который проходит те же проверки.

### Отзыв прав

Минимальный строгий протокол использует короткий `READ COMMITTED`:

1. Захватить `FOR SHARE` на строке состояния авторизации.
2. После захвата проверить текущую ACL.
3. Одним SQL прочитать заголовок и содержимое.
4. Завершить транзакцию.

Все изменения эффективных прав получают конфликтующую блокировку: прямые разрешения, роли, членство, наследование и перемещения между папками.

В PostgreSQL отдельные запросы `READ COMMITTED` могут видеть разные снимки. Поэтому проверка прав должна идти после возможного ожидания блокировки. `FOR KEY SHARE` не заменяет `FOR SHARE` для защиты от любого обновления такой строки. [postgresql.org](https://www.postgresql.org/docs/18/transaction-iso.html?utm_source=chatgpt.com)

Гарантия относится к точке допуска финального чтения. Уже переданные пользователю байты отозвать невозможно.

### Кэши и организации

Ключ кэша включает организацию, документ, поколение, версию представления и параметры выборки. Публикация расчёта увеличивает версию представления даже при прежнем `P`.

TTL и доставка invalidation ускоряют работу, но не заменяют проверку свежести. ACL проверяется также для ответа из кэша и `304`.

Организация берётся из доверенного серверного контекста. Составные ключи и внешние ключи препятствуют межорганизационным ссылкам. RLS может служить дополнительной защитой; документация отдельно предупреждает о гонках, когда политика читает другие таблицы. [postgresql.org](https://www.postgresql.org/docs/18/ddl-rowsecurity.html?utm_source=chatgpt.com)

### Объектное хранилище

Порядок публикации следующий: полностью загрузить неизменяемый объект, проверить hash и доступность по принятому контракту, затем одной SQL-транзакцией опубликовать ссылку, квитанцию и событие.

Сбой до SQL commit оставляет удаляемый orphan. Обратный порядок способен оставить видимую ссылку на отсутствующий объект.

Хеш содержимого подтверждает идентичность байтов. Он не является разрешением на чтение. Сборщик мусора должен учитывать ссылки, историю и незавершённые операции.

### Внешний движок таблиц

Univer рассмотрен как проверяемый открытый аналог, а не как окончательный выбор движка.

Его публичный persistence contract описывает snapshots, Sheet blocks, changesets и CAS. Это позволяет проектировать адаптер, не предполагая устройство внутренних таблиц коммерческого облака. [Univer Office SDK](https://docs.univer.ai/server/collaboration/database-adapters?utm_source=chatgpt.com)

Если движок управляет отдельной транзакцией, общая атомарность с локальным receipt и outbox автоматически не возникает. Стабильная submission identity позволяет повторять запрос и сверять исход; при недостаточном контракте остаётся `outcome_unknown`.

У Univer `changesetCommitted` — событие процесса после commit, доставка которого внешнему потребителю не гарантирована. Запись outbox в его обработчике не эквивалентна записи outbox в транзакции изменения. [Univer Office SDK](https://docs.univer.ai/server/collaboration/middleware-and-events?utm_source=chatgpt.com)

## 9. Что измерено и как проверять производительность

В архиве зафиксированы следующие **размеры файлов**:

| Объект | Проверенный размер |
|---|---:|
| JSON договора: 100 заголовков и 1 000 абзацев | 1 118 863 байта |
| JSON книги: 100 000 непустых ячеек | 3 097 200 байт |
| Эталон ответа p16/p17/p18 с разметкой | 2 415 байт |
| Эталон ответа на 20 адресов B2:E6 | 935 байт |
| PDF того же договора, 100 физических страниц | 506 711 байт |

Источник — manifests и генератор в приложении: Python 3.12.14, seed `20261120`, компактный UTF-8 JSON с зафиксированными правилами сериализации. PDF имеет фиксированные формат A4, шрифт и разрывы страниц.

Эти числа не являются размерами TOAST, фактическим I/O или сетевым ответом. Книга использует упрощённый тестовый формат; кэш D2 задан в данных, вычислитель его не рассчитывал.

### Протокол испытания

Сначала фиксируются точная версия PostgreSQL, образ, CPU, RAM, диск, RTT, ограничения процессов, настройки компрессии, WAL, checkpoint, JIT и autovacuum.

Для каждого варианта сравниваются одинаковые полезные ответы:

- три соседних абзаца из договора;
- двадцать адресов из книги;
- затем те же ответы при десятикратном увеличении общего размера.

Предлагаемый прогретый прогон: **100 прогревов и 1 000 измерений для каждого из восьми случаев, пять серий**. Получается 40 000 измеряемых чтений и 4 000 прогревочных. Это параметры будущего испытания.

Холодный режим требует отдельной подготовки перед каждым измерением. Один холодный запрос среди тысячи прогретых не даёт холодный p95. Нужно различать холодность PostgreSQL, ОС, объектного кэша и загруженного runtime редактора.

### Обязательные метрики

| Метрика | Как получать |
|---|---|
| Число обращений | Трассировка SQL, SDK и GET/HEAD/PUT, включая retries |
| Байты ответа | Реальная сериализация, отдельно сжатие и протокольные расходы |
| Работа БД | План, buffers, heap/index/TOAST, статистика I/O |
| Физическое чтение | Дополнительные метрики ОС, устройства или провайдера |
| p95 | Сырые времена обычных запросов и отдельно полный SDK-вызов |
| Память | Процессы PHP, Node и PostgreSQL; peak и ограничения sampling |
| Запись | Время commit, WAL/FPI, изменённые строки, блокировки, объекты |
| Перестроение | Прочитанные байты, CPU, память, WAL, задержка публикации и уборка |

Для диагностического плана PostgreSQL 18 используется `EXPLAIN` с `ANALYZE`, `BUFFERS`, `WAL` и `SERIALIZE TEXT`. Сериализация помогает учесть работу, которую обычный EXPLAIN может не выполнить, но сеть всё равно не измеряет. Параметр `MEMORY` относится к планированию, а не к полному пику памяти выполнения. [postgresql.org](https://www.postgresql.org/docs/18/sql-explain.html?utm_source=chatgpt.com)

Счётчик чтений PostgreSQL также не доказывает обращение к физическому носителю: данные могла предоставить ОС. Поэтому нужны оба уровня наблюдения. [postgresql.org](https://www.postgresql.org/docs/18/monitoring-stats.html?utm_source=chatgpt.com)

В микротесте один случай — один SQL на существующем соединении. В полном SDK дополнительно учитываются проверка прав, чтение квитанции, ожидания и резервная загрузка источника.

### Как обнаружить скрытую полную загрузку

Сохраняем размер полезного ответа и увеличиваем общий документ или книгу в десять раз.

Если вслед за источником растут распакованные байты, CPU, память или чтение объектов, короткий ответ получен ценой большой внутренней обработки. Для адресной проекции ожидается существенно меньшая зависимость от остальных частей документа. **Это проверяемая гипотеза, а не уже полученный коэффициент ускорения.**

Отдельно измеряются три задержки: до подтверждения записи, до чтения нужной версии через SDK и до свежего результата формул.

## 10. Наблюдаемый сигнал для усложнения

Команда заранее устанавливает бюджеты p95 чтения, проверки команды, памяти worker-а и допустимого отставания проекции.

Первое усложнение выбирается по причине: разреженные ключи порядка при дорогом сдвиге абзацев; инкрементальная обработка при дорогом diff; подготовленная сборка с атомарной сменой указателя при долгой публикации rebuild; более частые checkpoints при дорогом replay.

**Переход к адресуемым авторитетным частям оправдан, когда на целевой нагрузке основную стоимость подтверждённой правки или её проверки всё ещё составляет загрузка, распаковка, сериализация либо replay всего источника; эта работа растёт с размером документа, нарушает бюджет времени или памяти, а прототип частичного хранения устраняет именно её, сохраняя гарантии поколений, истории, расчёта и ACL.**

Практический сигнал в эксплуатации: очередь проекции устойчиво растёт, проверки после команды всё чаще загружают целый источник, а p95 свежего ответа выходит за согласованный предел даже после устранения лишних загрузок и объединения событий. Именно такой профиль затрат обосновывает следующую схему хранения.
